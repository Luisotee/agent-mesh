# daemon

The Go daemon that replaces herdr and the old `bin/mesh` script, the mesh every agent on this machine runs on (`docs/apps.md`, "Order of work"). `./install.sh` builds and installs it (see "Installing" below). The `bin/mesh` era is recorded in `docs/design.md`; its design decisions still hold where `docs/apps.md` doesn't say otherwise.

## Layout

- `../proto/`: the API as protobuf. `agentmesh/v1` is the action registry (`MeshService`, each RPC with its allowed actor classes in the `action` option), `agentmesh/term/v1` the terminal host's API and WebSocket frames, `agentmesh/adapter/v1` the CLI-adapter plugin interface. `buf.yaml` and `buf.gen.yaml` live there.
- `gen/`: the generated Go code (committed; regenerate with `cd proto && buf generate`). Reviewers can skip it.
- `cmd/meshd`: the daemon (including optional `--listen` TLS, `--relay-url` outbound relay connector and `--tailscale` built-in tailnet node).
- `cmd/protoc-gen-flagdocs`: a `buf generate` plugin that writes the schema's field comments into `gen/` (`FieldDocs`) for `mesh help`; not shipped.
- `cmd/mesh-relay`: the self-hosted stream relay (`docs/relay.md`), static binary for VPS deployment (`packaging/relay/`, `packaging/systemd/agent-mesh-relay.service`).
- `internal/tlsutil`, `internal/pairing`, `internal/relay`: persistent ECDSA P-256 cert & SHA-256 fingerprint pinning, `agentmesh://pair` URI codec, and zero-trust relay server/connector/client (per-device client tokens, `docs/relay.md`).
- `internal/tailnet`: the built-in Tailscale node over tsnet (`meshd --tailscale`, `docs/relay.md` "Built-in Tailscale"); only it and `cmd/meshd` import tsnet, so the daemon's tests never compile it, and its own test runs Tailscale's test control server on 127.0.0.1.
- `internal/registry`: the action registry read from the descriptors; `testdata/actors.golden` pins what each actor class may call.
- `internal/auth`: tokens (stored as SHA-256), the interceptor that takes the actor from the token, and the browser refusal.
- `internal/store`: SQLite (pure Go, WAL), embedded numbered migrations, backed up before migrating.
- `internal/settings`: the host's settings table (`schema.go`): each leaf's key, type, default, summary and choices, and the check a value must pass.
- `internal/repoarg`: what a `--repo` argument is (a path, or a bare name looked up in `repos.dir`), shared by the CLI and the daemon.
- `internal/events`: the resumable event stream.
- `internal/notice`: what a notification is made of (kinds, tabs, plain-text bodies); `internal/daemon/notify.go` decides what deserves one ("Notifications"); `internal/webpush`: WebPush encryption (RFC 8291) and the POST to a push endpoint. See "Push".
- `internal/daemon`: the server and its handlers (`agents.go`: spawning, hooks, adoption, the terminal proxy; `delivery.go`: doorbells, "Doorbell delivery"; `chat.go`: the chat view's `ReadTranscript` and `PromptAgent`, "Chat view"; `commands.go`: the composer's `ListAgentCommands` and `GetPromptSuggestion`; `prompts.go`: the chat's prompt queue and `InterruptAgent`; `rewind.go`: `RewindAgent` and `AddAttachment`; `cost.go`, `models.go`, `conflicts.go`: reporting); `internal/client`: how local callers dial it; `internal/statedir`: the state dir's files.
- `cmd/mesh-term`, `internal/termhost`: the terminal host. `internal/termclient`: the daemon's side of it (its API, terminal streams, starting it).
- `internal/adapter`: the CLI-adapter registry; `internal/adapter/claude`: Claude Code's adapter (`transcript.go` reads its session record for the chat view); `internal/adapter/agy`: Antigravity CLI's (`agy`) adapter; `internal/adapter/opencode` and `internal/adapter/copilot`: OpenCode's and GitHub Copilot CLI's (each has a `transcript.go` for the chat view, Copilot a `usage.go` for `mesh cost`); `internal/transcript`: what the adapters share for it (the JSONL pager, the cuts). `internal/inputbox`: reads an agent's input box and a doorbell's `ref` from a terminal repaint (a draft, a placeholder, a gutter box); `internal/shellmatch`: publish-command matcher for `PreToolUse`. `internal/reducer`: the pure state reducer. `internal/hook` and `cmd/mesh`: the hook command and its spool. `internal/proc`: pids checked by start time.
- `internal/probe`: runs a CLI the daemon asks a question of (`agy -p /usage`, `agy models`, `opencode models`) so that it can never open a login: a session of its own with no terminal, stdin from `/dev/null`, no `DISPLAY`/`WAYLAND_DISPLAY`/`WSL_*`/`BROWSER`, a PATH that starts with stub openers (made under `<state>/probe`, not `/tmp`, which can be mounted noexec; a stub that can't be run stops the probe) (`xdg-open`, `wslview`, `cmd.exe`, `explorer.exe`, …) and has no `/mnt/*` entry (a WSL host's Windows programs); a stub records the attempt (only a PATH or `BROWSER` lookup is caught: an opener started by an absolute path is not), the probe kills the CLI's process group at once and returns `ErrLoginNeeded` (the URL is never kept).
- `internal/daemon/compact.go`, `reset.go`, `brief.go`, `reminder.go`: context management; `internal/adapter/*/context.go`: measuring a conversation and planning a headless compaction; `internal/cli/protocol.go`: `mesh protocol`.
- `internal/testutil/fakeclaude`, `internal/testutil/fakeagy`, `internal/testutil/fakeopencode`, `internal/testutil/fakecopilot`: the fake CLIs the tests run (turns and hooks, no network). `internal/testutil/screendump`: prints what a terminal of a host shows (its repaint, the raw output with `--replay`) and what an input-box profile reads from it, and can type into it (`--write`) or attach at another size; a debugging aid for the live checks ("Live checks"), built by hand: `go build -o bin/ ./internal/testutil/screendump`.
- `packaging/systemd/`: the two user units for production (`install.sh` installs them).
- `share/`: the protocol and skills daemon agents follow (`protocol/`: `PROTOCOL.md` for every agent, `ORCHESTRATE.md`, `ROOT_CARD.md`, `PLAN_TEMPLATE.md`, `SETUP.md`; `skills/`; `.claude-plugin/plugin.json`), see "Protocol and skills".
- `cmd/mesh`, `internal/cli`: the CLI (`mesh`), generated from the registry at run time.
- `e2e/`: the end-to-end test of the real binaries (`TestEndToEnd`).

## Toolchain

Go (see `go.mod`), [buf](https://buf.build) for the protos, and for `go test -race` a C compiler. The code generators are pinned as `tool` directives in `go.mod`, so `buf generate` installs nothing. On the dev machine they are user-local, off PATH: Go in `~/.local/go`, buf in `~/.local/opt/buf/bin`, and `~/.local/opt/zigcc/cc` (a `zig cc` wrapper) as the C compiler. `scripts/check.sh` finds them there.

## Commands

```bash
daemon/scripts/check.sh                      # the CI equivalent: buf lint and breaking, gen current, vet, test -race, pytest (its scratch dirs are removed when it ends, however it ends but SIGKILL; clears AGENT_MESH_*: an agent's own token would be refused by the tests' daemons)
cd daemon && go test ./...                   # the Go tests only
cd proto && buf generate                     # after changing a .proto
cd daemon && go test ./internal/registry -update   # accept a reviewed change of who may call what
cd daemon && go build -o bin/ ./cmd/...      # binaries into daemon/bin/ (gitignored)
cd daemon && go build -tags ts_omit_logtail,ts_omit_peerapiserver -o bin/ ./cmd/...   # as install.sh builds: --tailscale needs the tags
```

## Installing

`./install.sh` (safe to re-run; `--daemon` is accepted as an alias) installs the daemon from this checkout's branch:

- It builds `cmd/meshd`, `cmd/mesh-term` and `cmd/mesh` (with `-tags ts_omit_logtail,ts_omit_peerapiserver`, which `meshd --tailscale` requires: no tsnet log upload, no Tailscale peerapi) into a temp folder first (a failed build changes nothing, links included), then moves each binary into `~/.local/lib/agent-mesh/bin/` with one rename, so a running meshd or mesh-term is never broken by an upgrade. `daemon/share/` (the protocol and skills) is copied to `~/.local/lib/agent-mesh/share/`. The installed daemon is versioned by install, not by the checked-out branch: a branch switch here changes no agent until the next install.
- It copies `packaging/systemd/agent-mesh.service` and `agent-mesh-term.service` into `~/.config/systemd/user/` (or `$XDG_CONFIG_HOME`), each with a drop-in `<unit>.d/path.conf` holding the `PATH` of the shell that ran the installer: a user unit's own `PATH` is short, and the agents' CLIs (`claude`, `agy`) must be found. Re-run it to refresh that `PATH` or to upgrade. Independently of that drop-in, `meshd` resolves the login shell's `PATH` once at startup (`$SHELL -lc`, bounded at 3 s, process group killed, read between NUL sentinels so profile noise can't leak in) and merges it ahead of its own `PATH` and the usual `~/.local/bin` and `~/bin` fallbacks, so `nvm` and other user-installed CLIs are found under systemd; a failing, slow or empty shell is logged and the inherited `PATH` stays (`--no-login-path` skips it).
- It runs `systemctl --user daemon-reload`, `enable agent-mesh.service` and `restart agent-mesh.service` (meshd Wants the terminal host, which stays up across a meshd restart, with its terminals). Without a user session or `systemctl` the files are installed and it says how to start meshd.
- It links `~/.local/bin/mesh` to the installed `mesh`, `~/.config/agent-mesh` to the installed `share/protocol` (the snippet's fallback path), and each skill of `share/skills` into `~/.claude/skills` and `~/.gemini/config/skills` (the installed copy's, so agy gets them globally; Claude's come from the marketplace plugin instead when it is installed at user scope, or with `--plugin`). A real file where a link goes is left alone.
- It writes the rules block (`rules/global-snippet.md`) into `~/.claude/CLAUDE.md` and `~/.gemini/AGENTS.md` between markers, when the CLI is on PATH.
- It cleans up an install of the old `bin/mesh`: links into the checkout (dangling once it is pulled) are re-pointed, the retired `delegate-claude` and `delegate-agy` links, the `meshctl` link and the herdr plugin (`local.mesh-notify`) are removed, and the Copilot and OpenCode rules blocks, which name the herdr mesh, are taken out (a daemon OpenCode or Copilot agent learns the protocol from its first doorbell). `~/.local/state/agent-mesh` is left untouched and unread; `~/.config/agent-mesh.json` is left in place and imported once by meshd on its first start (`--policy-file`, read-only; "Settings").
- State is `~/.local/state/agent-mesh-daemon`.

`./install.sh --uninstall` reverses all of it (units, drop-ins, binaries, `share/`, links, blocks) and keeps both state dirs. `tests/test_install.py` runs all of it in a temp HOME with `go`, `systemctl` and `herdr` stubbed, an upgrade from the old links included.

## Running a dev instance

Always give it a state dir of its own: meshd has no default, so it can't land in a real one by accident. A unix socket path holds about 107 bytes, so keep the state dir path short: meshd refuses to start with a longer one.

```bash
state=$(mktemp -d)
daemon/bin/meshd --state "$state"            # socket at $state/meshd.sock, device token at $state/device.token
```

Every call needs a token. The host's own CLI uses the device token meshd writes on first start (`device.token`, mode 0600); each agent gets its own at spawn, in `AGENT_MESH_TOKEN`. The actor of every action comes from the token, never from the request. Requests that carry a browser's `Origin` or `Sec-Fetch-Site` header are refused, and `--tcp` binds loopback only. A worker, asker, or reviewer token reads only its own run; a root may list earlier runs (`ListRuns`, `ListAgents`, `GetAgent`, `ListMessages`) and resume stopped non-root workers from them into its own open run. A token without a run is not stored.

A run is one trust domain for events, with one exception: an asker or a reviewer (read-only, short-lived, and possibly on a third-party model) reads, in `SubscribeEvents` and `StreamLog` (`mesh events`, `mesh log`), only the text-bearing events that are its own: a `MessageSent` to or from it, its own `PromptQueued`, `DoorbellHeld`, `RootResetRequested`/`RootResetFinished`, `AgentReopenRequested`, `AgentReopened` and `AgentReopenDropped` (`events.VisibleTo`, `restrictedViewer`). The agent rows (`GetAgent`, `ListAgents`, the snapshot) still carry a root's `pending_reset`/`last_reset` notes and a reopen's reason to them: a TODO line tracks stripping those. Every other event (states, spawns, PRs, the run) is run-wide metadata and reaches them; `ListMessages` already withholds the bodies from every agent but the root. A worker, a root and the devices read the run's events whole; `TODO.md` tracks whether a worker on a free or third-party model should be filtered too.

## mesh (the CLI)

Every action of the registry is a `mesh` command, built at run time from the compiled schemas: the command is the action's `cli` name, each request field is a flag (`snake_case` → `--kebab-case`; a bool is a switch, `--peek`; enums by short name, `--role worker`; message fields as JSON; `@file` or `@-` for text, `@@` for a literal leading `@`), `--json` gives the whole request (also before the command: `mesh --json '{…}' set`) and the other flags override it (a repeated field's first flag replaces the list the JSON gave, the next ones add to it), a `google.protobuf.Value` field takes any JSON or, when the text isn't JSON, the string it spells (`--value sonnet`, `--value 75`, `--value '["haiku","sonnet"]'`), and the response prints as JSON (a stream as one object per line), except `mesh inbox`, `mesh settings`, `mesh cost`, `mesh models`, `mesh model`, `mesh import-settings`, `mesh conflicts`, `mesh log`, `mesh ring`, `mesh ask` and `mesh asks`, which print short text by default (an inbox as a header line and the body of each message, settings as `key = value`, with the default after an override, formatted tables/summaries for reporting, date-grouped timeline lines for `log`, one-line delivery status for `ring`, an ask as its members and the file the answers go to, and `asks` as one line each with who answered and the verdicts) and give the whole response with `--format json`, while `mesh open` attaches to a live agent's `mesh-term` PTY (`Ctrl-]` to detach) or reopens a stopped agent directly in the caller's terminal (`--format json` prints the plan instead): the CLI's own view, the API is the same. Writes get a fresh mutation id unless `--mutation-id` is given. `--state` goes before or after the command; without it (and without `$AGENT_MESH_STATE`) the CLI uses `$XDG_STATE_HOME/agent-mesh-daemon` (else `~/.local/state/agent-mesh-daemon`), where the installed units keep the state, but only when `meshd.sock` is there (`meshd` itself has no default). `mesh help` lists the commands, `mesh help <command>` its flags, each with the schema's own comment on the field (generated into `gen/` by `cmd/protoc-gen-flagdocs`, a `buf generate` plugin). A command whose request has a string field `to` or `agent` takes it as its one bare argument, wherever it stands among the flags (`mesh send parent --type done --body @report.md`, `mesh approve <agent> --tier mid`), and an `extra_args` list takes arguments after `--` (`mesh open <agent> -- --verbose`); it is a convention of the schema, so an action added with such a field gets it, and giving the positional one twice (argument and flag) is an error. Only `hook`, `statusline`, `version`, `whoami` and `dir` are written by hand: `mesh whoami` prints the caller's role, name, id, run, run folder and parent as JSON, and `mesh dir` the run's folder (`$AGENT_MESH_RUN_DIR`, or `--run <id>` for a device).

```bash
export AGENT_MESH_STATE=$state
daemon/bin/mesh start-run --title demo
daemon/bin/mesh spawn --run-id <run> --repo ~/projects/shop-api --slug fix-typo --task @task.md
daemon/bin/mesh agents --run-id <run>
daemon/bin/mesh send --to shop-api-fix-typo --type task --body "…"
daemon/bin/mesh events --run-id <run>                 # follow; resume with --cursor '{"generation":…,"seq":…}'
```

An agent's own shell has `AGENT_MESH_TOKEN` and `AGENT_MESH_STATE`, so the same commands act as the agent (`mesh inbox`, `mesh send parent …`). Its environment also holds `AGENT_MESH_RUN_DIR` (the run's folder, `<state>/runs/<run>/`, made when the run starts, with `plans/`, `reports/` and `tasks/` in it: where the protocol's files go), and the folder of `meshd --mesh` is first on its `PATH` (whatever `--agent-env PATH=…` says), so a bare `mesh` in an agent is this CLI.

## Settings

The policy (design §21) is host data, the same from every device and readable by the agents that run under it. `internal/settings/schema.go` is the one table: a leaf's key, type, default, summary, choices (a string leaf with choices takes one of them) and whether it is read only at start. The settings screen is generated from it, and an app adds its own rows there (the desktop's `app.*`, such as `app.theme`: the name of one of the six themes in `shared/themes/`, which the desktop follows and the Android app follows unless the phone chose its own); it needs no action or event of its own. Only overrides are stored (the `settings` table, migration `0002`); a leaf nobody set is its default, so a new default reaches every host that never overrode it.

- `ListSettings {prefix}` returns `Setting`s: `key`, `value` (effective), `default`, `is_set`, `schema {type, summary, choices, restart}`, and who set it and when. Any actor class may call it. `mesh settings --prefix tiers.claude.`.
- `SetSetting {meta, key, value}` and `ResetSetting {meta, key}` write: only a device or a root, idempotent like every write, and each emits a global `SettingChanged {key, value, previous, to_default}` with the actor and the mutation id. The event has no run, so every subscriber gets it, a run's agents included. A `Snapshot` doesn't carry settings: a client lists them after one, then follows the events. `mesh set --key quota_stop --value 75`, `mesh unset --key quota_stop`.
- A value is checked against its type: `string` (one of the leaf's choices when it has them: `claude.mcp`, `limits.auto`, `app.dock.new_agents`; a string with choices was not enforced before PR #172, so a host that stored another value reads the leaf's default with a warning in the log, except `limits.auto`, where an off-list value still reads as `off`), `strings`, `int`, `percent`, `bool`, `seconds`, `effort`, `chain`, `slots`, `kinds`, `mb_or_auto`, `shortcut` (a key chord such as `Mod+Shift+P`, or `""` for none: modifiers `Mod` (Ctrl, or Cmd on macOS), `Ctrl`, `Alt`, `Shift`, `Meta` then one key; a modifier besides Shift is required unless the key is F1 to F24; `ValidShortcut`), `json`. A failure is `InvalidArgument` naming the rule (`quota_stop must be a whole number 0 to 100`); a key no leaf has is `NotFound`.
- The daemon reads a leaf with `Daemon.Setting(reader, key)` (the override, else the default; a stored value the leaf's rule no longer takes is logged and the default used; a failed read is an error), so a change applies to the next read. A write that changes nothing (the same value again, a reset of a setting nobody set) emits no event. `seconds` is capped at 1e9 so a `time.Duration` can't overflow. `compact.*` and `root_reset.*` are the context leaves ("Context management").

**The policy file** (`bin/mesh`'s `~/.config/agent-mesh.json`, `internal/settings/policyfile.go`, `internal/daemon/settings_import.go`) is imported once, not read as a layer: the store stays the one source of truth that `mesh set`, the apps and every agent read and write, so there is no third source, no `source` on a setting and no `unset` that falls back to a file the app can't show.
- `meshd --policy-file <file>` (no default, so a dev or test meshd reads no real home; the systemd unit passes `%h/.config/agent-mesh.json`) imports the file at its first start with that path and records it (`meta` key `policy_import`: path, sha256, counts). Later starts import nothing; if the file changed since, meshd logs one line saying `mesh import-settings` applies it. A missing, unreadable or non-JSON file is logged and never stops meshd (nothing is recorded, so the next start tries again).
- `mesh import-settings [--from <file>] [--overwrite] [--dry-run]` (device only) does it on demand, for the file meshd was started with or another. It prints what was stored and what was left alone, each skip with its reason. Importing writes each leaf as a stored override (the owner's explicit choice stays pinned, as it was in the file), through the same path as `mesh set` (one `SettingChanged` event per leaf that changed, in one transaction), and never replaces a setting that is already set (a `mesh set` or the app's) unless `--overwrite`. Importing again is idempotent. `unset` goes to the built-in default, never back to the file.
- Mapping: the same key by default (the tiers, `review.*`, `compact.*`, `root_reset.*`, `claude.*`, `quota_stop`, `idle_retire`, the guards, `skip_permissions` are all leaves here); `peers_dir` is `peers.dir`; `repos_dir` is `repos.dir`; `copilot_model`, when set, becomes the `tiers.copilot.<tier>.model` of every Copilot tier the file doesn't name itself (`bin/mesh`'s rule, applied once at import, so there is no leaf for it). `hang_after`, `held_wait`, `side_panes`, `watch.timeout` and `models.<kind>.<size>.view` belong to herdr's panes, `mesh watch` and `--bg` views, which the daemon has none of: they are skipped with "not used by the daemon", as are the keys no leaf has ("no such setting") and values that fail their leaf's rule (named in the skip); the rest of the file still imports (`bin/mesh` refused the whole file; for a one-time carry-over that would lose the good keys). `_`-prefixed keys are comments. The `MESH_*` environment layer is not carried over: meshd has none.
- **`repos.no_free_models`** (strings, default none) lists the top folders of repos whose code must not go to OpenCode's free models, some of whose providers keep prompts or train on them (OpenCode's Zen docs); every repo may until it is listed (the user's choice, 2026-11-25). `internal/daemon/freemodels.go` enforces it wherever a model is picked for work in a repo: `pickIn` (a spawn, an ask or review member, a reopen, switch or approve, a peer), the reviewer round (`pickReviewers`: OpenCode drops out of a slot with a note, unless its tier has a paid model) and the auto switch on a usage limit (`nextOnChain`). Only the zero-cost models are held back, and "zero-cost" is what OpenCode itself lists: a model whose input and output `cost` in `opencode models --verbose` are both 0 counts, whatever its provider, status or tool support (wider than the `free` family, which is only the active, tool-calling `opencode/*` ones), as does `free`; a model listed with a price still runs, named or in a tier's chain. A model with no listed cost, or one not listed, and any model when the listing could not be read, can't be told from a free one and is refused (a chain loses such models too) rather than guessed, naming the setting. A model that is kept, not picked, is checked too: a resume, a task sent to a stopped agent (it stays stopped, with the reason), an approve that keeps the model, and a reopen after a limit's reset (the agent stays at its limit, and its parent is told once), a direct task that would lift a running planner's deny list, and a switch of effort alone; the checks run before anything is written, so a refusal changes nothing; a round's earlier OpenCode reviewer on such a model is not reused (a fresh one starts on a model the tier allows). An OpenCode root in a listed repo has to name a tier or a model: its default model may be a free one. The repo is matched as the same folder (symlinks resolved, a leading `~` is the home), and a linked worktree of a listed repo counts as it (the parent of its common git dir is compared too). An agent that is running keeps its model, `mesh model` (no repo) ignores the setting, and the desktop's settings screen has a switch per repo.
- **`tier_lean`** (`quality` | `balanced` | `thrifty`, default `balanced`) is how strongly the root favours saving tokens over quality when a task could go either way: guidance, never enforced. `mesh brief` prints one line for the root saying what the value means for its tier and effort picks, and ORCHESTRATE "Tiers" is written around it (judge each task, no default lean; the size rules and the risky areas stay as written). The user's words, 2026-11-25: "be mindful, be smart, be dynamic, think if that task needs a big model or a small is fine". An app setting for it comes with the settings screens.
- **`repos.dir`** (strings, `~` is the daemon's home) is where a bare `--repo <name>` is looked up, in order, for a folder that is a repo's own top (`repoTop` in `internal/daemon/repo.go`, used by `SpawnAgent`, `Ask` and `ListMCPServers`; the bare-name rule is `internal/repoarg`, shared with the CLI). The CLI sends a bare name as it is only when no repo of that name is in its working directory (a folder with its own `.git`: a plain subfolder of the repo the caller is in is not one; the `(agentmesh.v1.repo_name)` option on those three `repo` fields), so a repo in the caller's directory works with no setting and wins over `repos.dir`: `bin/mesh` refused a name that was both, which the CLI cannot see without asking the daemon. A path (a slash, `.`, `..`, `~`) is taken as before.

## Chat view

The desktop's chat tab shows an agent's conversation and lets the user write to it, without a second process on it: the agent stays the real CLI in its terminal (`chat.go`, `internal/adapter/claude/transcript.go`).

- **`ReadTranscript {agent, offset, backward, max_bytes}`** (`mesh transcript`; root, device and read-only device, as `OpenTerminal`) returns `TranscriptEntry`s read from the CLI's own record through the adapter's `ReadTranscript` (capability `transcript`, which all four built-ins have): Claude Code's session JSONL (the file `MeasureContext` sizes), Copilot's `session-state/<id>/events.jsonl` (`user.message`, `assistant.message` with its tool requests, `tool.execution_complete`; a subagent's lines, which carry a `parentToolCallId` or a `source` naming an agent, and its reasoning are left out), agy's `<session>.db` (the `steps` table's protobuf blobs: type 14 the user's text, 15 the model's reply without its thinking, 132 a tool run with its JSON arguments and output; types 17, 23 and 101, the compaction and system notices, are left out) and OpenCode's `opencode.db` (`message` and `part` rows; not its HTTP API, which needs a `--port` and answers only for a running TUI). The three non-JSONL records page by position, not by byte: agy's `offset` is a step's `idx`, OpenCode's a message's rowid, and a step or message still being written (agy: any step among the last 30 whose status is not 3, 4, 6 or 7, such as 1, 2 and the model's 8, the earliest of them, because parallel tool calls finish out of order; OpenCode: an assistant message with no `time.completed` last in its session; their content changes in place) is left for a later read, so `end_offset` stops before it, until its record has been quiet for 10 minutes (agy: `<session>.db` and its `-wal`, where a live conversation writes; OpenCode: the message row and its parts; an interrupted or aborted turn leaves it so for good: it is shown then); agy's failed and refused tool calls (statuses 4, 6, 7) show their error (field 31) as the result; `offset: start_offset, backward` keeps reading back until it has a few entries, as for JSONL. Shown: what the user typed, the model's text, tool calls (with a one-line summary of their input) and results (cut at 8 KB, `truncated`), and mesh doorbells (`MESH`, even though Claude marks them as injected context). Left out: thinking, subagents' own turns, other injected context (`<system-reminder>` is stripped from what the user typed, and the `<pasted_content id="…">` / `</pasted_content id="…">` tags Claude Code writes around a paste are unwrapped: the pasted text stays), what the CLI writes for itself (the summary a compaction leaves, `isCompactSummary` and `isVisibleInTranscriptOnly` lines; a slash command's `<local-command-caveat>`) and bookkeeping lines; what a slash command printed (`<local-command-stdout>` and `-stderr`, colour codes taken out, an empty one dropped) is kept as a `COMMAND_OUTPUT` entry, so `/context` and `/usage` answer in the chat (Claude only); a slash command the user typed shows as the command and its arguments, not its tags, bash mode (`<bash-input>`) as `! cmd` with its `<bash-stdout>`/`<bash-stderr>` dropped; a line that doesn't parse is skipped. Paging is by byte offsets of line starts: `offset -1, backward` is the tail, `offset: start_offset, backward` the earlier part (it keeps reading back until it has a few entries, and goes past a line of any size up to the 16 MB cap, so every page moves back), `offset: end_offset` the entries written since. A line still being written (no newline yet) is left for the next read; an `end_offset` smaller than the reader's means the record was rewritten, and a `session_id` that changed means a new conversation (a reopen, `/clear`): the reader starts over. A page is about 256 KB (at most 2 MB); a line over 16 MB is skipped. A CLI whose adapter lacks the capability (a plugin's) answers `supported: false`. The record layouts of agy and OpenCode are those of the files found on this machine (agy 1.5.17, OpenCode 1.19.6; the tests build the same shapes with invented text) so a CLI update that moves a field shows as missing entries (a table that is gone, as an error).
- **`PromptAgent {meta, agent, text}`** (`mesh prompt`; a device with the `terminal.input` right, so never an agent or a read-only device) sends the user's prompt to the agent's running CLI, the composer of the chat tab. It is never refused for what the agent is doing: it types the text into the terminal at once, then Enter, only when the agent is at its prompt, nothing is queued before it, nobody is typing and the screen reads an empty input box. Otherwise (the agent works, starts, waits at a prompt whose answer a typed line would be, is at a usage limit, has a draft in its box, or shows a dialog) it **queues** the prompt and answers with it (`queued`, saying what it waits for in `held`). It refuses only an agent with no terminal, exited or retired (`FailedPrecondition`). Typing can't be undone, so its `meta` is honoured as a write's is: a retry with a mutation id already used gets the first answer (typed, or the same queued prompt) and sends nothing again, and a request past `expires_at` sends nothing. It is not a mesh message (it carries no authority a peer's would) and it doesn't use Claude's inbox socket, whose frames Claude presents as another session's message, not the user's. It takes the agent lock (no interleaving with a doorbell or a reopen) and reads the agent again under it. Control characters other than newline and tab are dropped (`CleanPrompt`), so a prompt can't carry keystrokes, an Escape that would end a paste included. Several lines, or a tab (a typed Tab is a keypress, not text), are one bracketed paste where the adapter has the `bracketed-paste` capability (Claude), else newlines and tabs become spaces; a paste whose Enter never went in is taken back out with Ctrl-U, repeated while the box still reads typed (Ctrl-U clears one line), and the error says part of it may remain when the box can't be shown empty. Not checked against the real CLI: the fake takes a paste as one prompt.
- **`ListAgentCommands {agent}`** (`mesh commands`; root, device and read-only device) lists what the agent's CLI accepts when it is typed at its prompt, for the composer's `/` popup (`internal/daemon/commands.go`, the adapter's `ListCommands`): name, aliases, description, argument hint, where it comes from (`builtin`, `project`, `user`, `plugin`, `skill`, `custom`), whether typing it opens a dialog or picker in the terminal that the chat can't show (`dialog`: `BARE` when typed without an argument, `ALWAYS`) and whether it ends or signs out the session (`danger`: `/exit`, `/logout`). Claude Code's list is its own answer to the SDK's `initialize` control request (`claude -p --input-format stream-json --output-format stream-json --verbose` with one request on stdin; no model call, about 2 s), run in the agent's worktree through `internal/probe` and kept 30 s per worktree (one probe at a time, a failed one retried after 5 s): the commands and skills it loads there (the repo's and the user's `.claude/commands` and skills, enabled plugins, the share plugin), with descriptions. The probe leaves no trace: `--no-session-persistence` (no session file; checked that even without it an `initialize` alone writes none), `--settings '{"disableAllHooks":true}'` (the user's `SessionStart` hook ran in a first try), `--strict-mcp-config` with no config (a repo's `.mcp.json` can't start a program from a probe; MCP prompts are not listed), `--setting-sources user` for an asker or a reviewer (as their launch), no `AGENT_MESH_*` identity and no session variables in its environment; the agent's lean launch applies (`ListCommandsRequest.lean`: the plugins turned off and the claude.ai skills, as `--settings`; a skill only hidden from the model can still be typed, so it stays listed), the share plugin's copies in the user's own plugins are shadowed as at launch, and the settings are part of the cache key. OpenCode's `debug config` runs with no `AGENT_MESH_*` and, for an asker or a reviewer, `OPENCODE_DISABLE_PROJECT_CONFIG=1` (a PR head's `.opencode/` plugin ran when the config was read: checked live). The commands only the terminal UI has (`/resume`, `/permissions`, `/help`, `/exit`, …, read from the popup of Claude Code 2.1.332) are a table (`claude/commands.go`), as is which of the probe's commands open a picker (`/model`, `/config`, `/usage`). agy, OpenCode and Copilot list nothing without a terminal: their built-ins are tables read from their `/` popups (agy 1.5.18, OpenCode 1.19.6, Copilot 1.0.116; a table's version is its `CommandsVersion`), plus what is on disk: agy's skills in `~/.gemini/config/skills` and its plugins' (`/plugin:skill`), Copilot's in `~/.copilot/skills` and the worktree's `.github/skills`, `.claude/skills` and `.agents/skills`, and OpenCode's custom commands from `opencode debug config`. A command a newer CLI has and a table lacks is not offered (typing it still works). `dialog` is judged from each command's description; the ones not run live are `BARE`, whose only cost is the app opening the terminal tab. The list is not a security boundary: nothing here types anything.
- **`GetPromptSuggestion {agent}`** (`mesh suggestion`; same actors) is the grey text Claude Code shows in its empty box after a turn (a predicted next prompt: `promptSuggestionEnabled`, on by default), read from the agent's screen through the adapter's `ReadInputBox` (`ghost`: `inputbox.Reading.Ghost`, the ghost cells of an empty rules box, the cursor character included, since with the terminal focused Claude inverts the first character; its own fixed hints `Try "…"`, the one about queued messages and `Message @…` are not suggestions, `Profile.Hint`; a wrapped one is one text): it exists only on the screen in an interactive session (no hook, no line in the session file; the `prompt_suggestion` message is print/SDK mode's). Empty unless the agent is at its prompt with an empty box. Only Claude's adapter says it; agy's `Auto mode: …`, OpenCode's `Ask anything…` and Copilot's hint are fixed texts, not predictions.
- **The prompt queue** (`internal/daemon/prompts.go`, the `prompts` table of migration 0013, so it survives a restart): the delivery (`deliver`, the same pass and lock as the doorbells) types an agent's oldest queued prompt when it is at its prompt (`takesDoorbell`) with no doorbell in flight and its box reads empty with nobody typing, one per idle, **before** its doorbells (the user is watching; a doorbell only says to read the inbox, which the next turn does as well). A draft, someone typing or a dialog holds it, and `ListPrompts` says which (`held`: `working`, `starting`, `at_prompt`, `limited`, `stopped`, `draft`, `typing`, `no_box`). The delivery **claims** a prompt (a compare-and-set from `queued` to `typed`, with a `PromptTyped` event) before it types; a write that certainly never reached the terminal puts it back (`PromptQueued` again). **`WithdrawPrompt {meta, agent, prompt_id}`** (`mesh withdraw-prompt`; a device; the chat's Up arrow, the newest when `prompt_id` is empty) takes it back by the opposite compare-and-set and returns it, `FailedPrecondition` once it was claimed: a prompt is typed or withdrawn, never both (tested by racing the two). **`ListPrompts {agent}`** (`mesh prompts`; any device) lists the queue, oldest first. Events: `PromptQueued`, `PromptTyped`, `PromptWithdrawn`. Rows that left the queue are pruned after 14 days. **`SendPromptAnyway {meta, agent, prompt_id, draft}`** (`mesh send-prompt-anyway`; a device; the chat's "Send anyway") types a prompt held for a draft over it: `ListPrompts` and the answer that queued the prompt carry the draft the daemon read as `held_text` (squeezed, cut at 300 characters), the app names it in a confirmation, and the call clears the box (Ctrl-U, read after each, as when a paste never got its Enter) and types the prompt. Refused with `FailedPrecondition`, and the draft left alone, unless all of these hold under the agent's lock: the prompt still waits; the agent is at its prompt with no doorbell, prompt, reopen, compaction or reset in flight; nobody with the terminal open typed within `TypingQuiet`; and the box reads exactly the draft that was confirmed (whitespace aside; one that changed since is quoted in the error). It answers with the `discarded` draft, and a retry with the same mutation id gets that answer. A person who typed a draft and left loses it, as the confirmation says; one typing at that moment is refused, and a keystroke in the instant between the check and the Ctrl-U is the one loss left.
- **`InterruptAgent {meta, agent}`** (`mesh interrupt`; a device with `terminal.input`, or the root of the agent's run) sends the CLI's interrupt key, as Esc in its terminal, to an agent that works or waits at a prompt, and watches for a moment (4 s) for its box to read empty on a screen that stopped drawing: `stopped`. Claude Code fires no `Stop` hook for an interrupted turn, so the daemon then records the turn's end itself (a `TurnEnded` through the reducer) and the agent's queued prompts and doorbells go next. Only an adapter with the `interrupt-esc` capability (Claude) takes it; the other CLIs' keys are not verified yet (`TODO.md`). An agent at its prompt gets no key (a second Esc at an empty box opens Claude's rewind menu), and the mutation id is honoured so a retry sends no second Esc. The fake's `FAKECLAUDE_ESC` takes a lone Esc as a key, ending a `/hold` turn with no Stop hook.
- **`RewindAgent {meta, agent, entry_id}`** (`mesh rewind`; a device) takes an agent's conversation back to before one of its prompts, a USER entry of `ReadTranscript`: the Claude adapter's `claude.CutSession` writes a copy of the session cut before that prompt's line, under a new session id with every line's `sessionId` set to it, beside the original (which is kept), and the agent's session becomes the copy. A live agent at its prompt then gets a reopen (`rewound`, the usual reopen: same model, effort and worktree, `--resume <copy>`); a stopped one is revived on it. It answers with the prompt's text as the chat shows it (injected reminders and a command's tags dropped), for the app to put back in the composer. Files, commits and the mesh messages sent since are left as they are. It is refused while the agent works or waits at a dialog (interrupt it first), for an adopted session, for an entry that is not a prompt (a line holding a tool result isn't one), for a prompt with no assistant reply before it (the first, or one after only a root's `/clear`: a copy with no messages can't be resumed, "No conversation found", checked live), while a compaction or reset waits, and for a CLI without the `rewind` capability (Claude only); a stopped agent is revived on the copy without compacting it. Claude Code resuming a copy cut this way was checked live (2.1.332): the copy resumes without what was cut.
- **`AddAttachment {meta, agent, name, data}`** (`mesh attach`; a device) stores an image for a prompt in the agent's run folder, `attachments/<agent>/<id>.<ext>`, and answers with its path, which the prompt names (`[image: <path>]`) for the CLI's file tool; the host may be another machine than the app's. PNG, JPEG, GIF or WebP by extension, the bytes sniffed to match, at most 10 MB.
- **Typing, as the daemon counts it:** the terminal host stamps a terminal's last client input (`last_client_input`, what "someone is typing" reads) only for input that is a key a person pressed: a client's terminal replies alone (focus in/out `ESC[I`/`ESC[O`, a cursor position, device attributes, a status or colour report: `termhost.OnlyReports`) pass through to the program without it. xterm.js sends focus reports whenever the app's window or tab gains or loses focus once the CLI turned them on (Claude does), which before this read as someone typing and held every prompt and doorbell for `TypingQuiet`.
- The fake claude writes a transcript for each plain prompt when `FAKECLAUDE_TRANSCRIPT` is set; the e2e harness sets it through a wrapper script (`fakeClaudeEnv`).

## Terminals

`mesh-term` owns the agents' PTYs, in a process of its own so a daemon restart leaves them running; at boot the daemon adopts what it finds (`AgentAdopted`), records exits that happened while it was down, marks an agent whose terminal is gone as `lost`, and never kills a terminal no agent claims.

- **Supervision.** In production both run as systemd user units (`packaging/systemd/`): `agent-mesh-term.service` holds the PTYs in its own cgroup, and `meshd --term-launch systemd` starts it when no host answers. Without systemd (and in dev and tests), `--term-launch detached` starts `mesh-term` in its own session; tests pass `--max-lifetime` so a killed test leaves nothing behind. One host per dir (a held lock), a token in `term/term.token`, and no pid is ever signalled without its start time matching (but for `SignalSession`, which a closed shell's background jobs are reached by: it matches the session id and the PTY, and a live session's pid is not reused while the host holds the PTY, and a session whose leader is gone has no terminal left to match, so a shell that exited on its own leaves its jobs running, as a shell does; it also hangs up a job the user `disown`ed, which the shell would not).
- **Project shells.** `OpenShell` (a device with the `terminal.input` right; a project the host knows: a folder of `repos.dir` or a repo an agent worked in) starts a login shell (`$SHELL -l`, else `/bin/bash -l`) in the project's folder on the host, labelled `kind=shell` and `repo`; `ListShells` and `CloseShell` (SIGHUP, as closing a terminal window does: the terminal host sends it to the shell's background jobs too, which have process groups of their own, before the shell, because a bash that gets it just after running a command can exit without passing it on, and a session without its shell has no terminal left to find the jobs by; SIGTERM then SIGKILL after 3 s if it is still there) go with it, and `OpenTerminal` takes `shell` beside `agent` for a ticket at `/v1/shell/<id>` (devices only: an agent gets none; a read-only device views). A shell is not an agent: no run, no row, no events, no confinement, and a clean environment (HOME, USER, LOGNAME, SHELL, PATH, LANG, LC_*, TZ, TMPDIR, TERM, COLORTERM and the user's session: XDG_RUNTIME_DIR, DBUS_SESSION_BUS_ADDRESS, SSH_AUTH_SOCK, DISPLAY, WAYLAND_DISPLAY; no `AGENT_MESH_*`, token or API key). Nothing is stored: the host's terminals carry the labels, so shells survive an app and a daemon restart; at boot the daemon adopts them, and a shell that died meanwhile (or exits later) is acknowledged and forgotten. At most 20 live shells. A shell opening or ending is told to the apps as a `ShellChange` frame (`shell`, and `closed` for an end: a shell's own exit, `CloseShell`, or one found dead at boot), ephemeral like `view` and `activity` frames (a shell has no run, so there is no stored event): sent to the live `SubscribeEvents` streams of devices that asked for activity, never replayed, so an app lists the shells (`ListShells`) when it connects and follows the frames after.
- **Streams.** `OpenTerminal` gives a one-time ticket; the client opens `/v1/term/<agent>?ticket=…` on the daemon, which splices it to the host. Frames are `agentmesh.term.v1.TermFrame` (binary). The first client frame is `Attach`: `EXACT` (from an epoch and offset, falling back to a repaint marked `reanchored`), `TAIL` (mode preamble, then live) or `REPAINT` (preamble and the screen from the host's emulator, then live). The replay ends with `ReplayDone`; input sent before the client's `Ready` is dropped, so replayed queries draw no answers. While no client that can type is attached, the host's emulator answers terminal queries itself. The size is the smallest client's, clamped to 20-500 columns by 5-300 rows; only a client with input rights may resize after attaching; a resize moves the epoch and every attached client but the one that attached is told in a `Resized` frame (epoch, the offset the new epoch starts at, cols, rows), in order with the output (an exact attach's own size counts after its `ReplayDone`, so it continues at another size and is told by a `Resized` after it; a repaint is drawn at the size that counts the client); a `Resize` that moves nothing is answered to its sender with the current epoch and size. A client that falls behind is closed with code 4001 and reattaches by offset; the PTY is never paused.

## Agents and hooks

An agent starts with an allowlist of meshd's environment, not all of it: the shell basics (`HOME`, `PATH`, `LANG`, `TMPDIR`, `XDG_*`, `SSH_AUTH_SOCK`), what Claude Code needs to reach its model (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_*`, the proxy variables, the Bedrock and Vertex settings and credentials), Copilot's state folder and tokens (`COPILOT_HOME`, `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, inherited only by `copilot` agents), OpenCode/OpenRouter provider keys (`OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `OPENCODE_API_KEY`, inherited only by `opencode` agents whose model is not `opencode/*`, and never written into `OPENCODE_CONFIG_CONTENT` or logs), a terminal, and its own identity. `meshd --agent-env KEY=VALUE` adds more, and `--cli claude=<path>` pins the binary; without it a bare `claude` is looked up on the agent's `PATH` by meshd, not on `mesh-term`'s. A meshd run by a systemd user unit has only what the unit sets, so put the login variables there (or in `--agent-env`).

`SpawnAgent` makes a worktree on `mesh/<run>/<slug>`, started from `base` (default: the repo's `origin/HEAD`, such as `origin/main` as last fetched, so a worker never branches off the branch the user's checkout is on; a repo with none starts from its `HEAD`), mints the agent's token (in `AGENT_MESH_TOKEN`, and in `<state>/agents/<id>/token` for its hooks), and starts its CLI through the adapter. Claude Code gets a `--session-id` and per-launch `--settings` hooks that run `mesh hook claude --state <dir> --agent <id> <Event>`. Before the launch the worktree is trusted in Claude's global config (`projects[<worktree>].hasTrustDialogAccepted` in `$CLAUDE_CONFIG_DIR/.claude.json` or `~/.claude.json` of the agent's environment, written under the lock Claude takes, every other key kept; nothing when the worktree, its main checkout or a parent is trusted already, or the file doesn't exist): Claude shows its folder-trust dialog even under `--dangerously-skip-permissions`, fires no hook before it is answered, and its default answer is "No, exit". The launch also hooks `StopFailure`, which Claude fires on an API error instead of `Stop`: a `rate_limit` or `billing_error` whose message is a usage limit (`You've hit your session limit · resets 3pm (America/Sao_Paulo)`, `You're out of extra usage`) is `AGENT_STATE_LIMITED`, with the reset it names and whether it is the account's (session, weekly, usage, monthly spend: every model) or one model family's (`Opus limit`, `Sonnet limit`); any other failure (a capacity 429, a login error) is `AGENT_STATE_ERROR`. Antigravity (`agy`) resolves model+effort via `agy models` (never passing `--effort`), skips the folder-trust dialog with `--settings '{"trustedWorkspaces":[…]}'`, resolves an exact id named without an effort at its own effort (`DescribeModel`: `gemini-4-neon-low` runs as named), writes `.agents/hooks.json` into the worktree (a worker's repo's own committed hooks deep-merged beside the mesh's when that version is on one of the repo's own refs, a local non-mesh branch or an origin branch, with the mesh's own `"agent-mesh"` key replaced wholesale; an asker's, a reviewer's or one from a fork's head replaced; kept out of git by `--skip-worktree` on a tracked file, else by a self-ignoring `.agents/.gitignore` in that worktree alone), enforces read-only and planning rules locally in `PreToolUse` (fail-closed across every tool with `HookTimeout`, overriding `--dangerously-skip-permissions`: a payload it can't read whole is denied, and a session that isn't the agent's, its `$AGENT_MESH_AGENT` unset or another's, still has the rules checked but reports nothing; agents without deny rules wrap `PreToolUse` to exit 0 silently so hook failures never block tools), reports `PreToolUse` within a second without waiting on the spool lock (agy denies a tool whose hook outlives its timeout), becomes `IDLE` once its terminal has drawn and been quiet for `ReadySettle` (or 30 of them after its first output, for one that never stops drawing), records its `conversationId` from its first prompt's hooks (with `LookupSession` falling back to the newest top-level conversation of its worktree in `conversation_summaries.db` or `history.jsonl` that isn't older than the agent, looked up only for an action that uses the id (a resume or a reopen) by an actor allowed to act on the agent, before that action's write, never inside it), reads a `Stop` with `continuationActive` as activity, not the turn's end, and maps `Stop` `ERROR` with `RESOURCE_EXHAUSTED` / 429 to `AGENT_STATE_LIMITED` (ready for `SwitchAgent --next` on `--conversation`) and any other to `AGENT_STATE_ERROR`; an agent at either is at its input box and takes reopens and idle retire as an idle one does, and at `ERROR` doorbells too (at `LIMITED` a doorbell's turn would fail on the same quota: its messages wait for the switch). OpenCode (`opencode`) has no hooks: `installed("opencode")` checks the configured or `PATH` binary, expands `free` in tier chains to active zero-cost `opencode/*` models (`opencode models --verbose`), launches `--agent mesh-<hash> [-m <model>] [-s <session>] [--auto]` (omitting `-m` and `model` when no model is picked, e.g. a default root) with per-launch `OPENCODE_CONFIG_CONTENT` (the agent, and `permission.external_directory`, ordered because OpenCode takes the last match: every external directory is denied (`*` first), so the agent is refused and carries on instead of hanging at OpenCode's "Access external directory" dialog, which nobody answers in a mesh (`review-187-opencode` stopped on `/etc/profile.d`, three reviewers timed out at 30 minutes), then allowed after it: the daemon's share folder (`$AGENT_MESH_SHARE`, with `edit` denied there: the protocol and skills sit outside the worktree), the run's folder (`$AGENT_MESH_RUN_DIR`: plans and reports), the toolchain (`~/.local/go`, `~/go`, `~/.cache/go-build`, `~/.local/opt`, `/usr/local/go`, `/usr/lib/go`, `/tmp`, `/var/tmp`; `toolchainDirs`), with `edit` denied in the share and the toolchain (as paths relative to the worktree, which is how OpenCode matches an edit) but not the scratch dirs; also a `TMPDIR` that is not `/tmp`, and each directory itself, not only what is under it; not the repo's main checkout, whose untracked files are the user's; the deny is there even without an absolute share path), `OPENCODE_DISABLE_AUTOUPDATE=1`, and ordered `OPENCODE_PERMISSION` when read-only or planning (lifted on `approve` or direct task in the same `-s` conversation, with a distinct `--agent` on each reopen): `edit` denied but the run folder's `reports/` (and `plans/` for a planner), and `bash` denied but a read-only list (`readOnlyBash`: git status, diff, show, log and the like, `gh pr view|diff|checks|list`, ls, cat, grep, rg, find without `-exec` or `-delete`, jq, awk without `system`, `go test|vet`, `go build -o /tmp/…`, `gofmt -l`, `buf lint`, `pnpm typecheck|test`, `uvx pytest`, `mesh`), then the publish commands and the dangerous forms of the allowed ones denied (any `>`: a redirect or an awk print to a file, `-exec`, `--output`, `go test -o` and the profiles). OpenCode 1.19.6 asks for each simple command of a line alone (`;`, `&&`, `|`, `$( )`, backticks, `<( )`), so `ls; rm x` is refused at `rm x`, and a command that starts with `VAR=value` matches no allow. A bare redirect with no command (`> file`, `>> file`, `2> file`) is not asked for at all by OpenCode 1.19.6, so no pattern sees it: the launch of a read-only or planning agent also loads a plugin (`share/opencode/readonly-guard.js`, in `OPENCODE_CONFIG_CONTENT`'s `plugin`) whose `tool.execute.before` hook refuses a bash command with a `>` in it before it runs (the model gets the refusal as the tool's result and carries on; `scripts/check-opencode-redirect-guard.sh` runs the real OpenCode against a fake local model to show it, by hand), appends `--body @"<path>"` guidance to its tasks so backticks never expand in bash, tracks session IDs, turns (`MessageAbortedError` treated as an idle turn end), and limits (`FreeUsageLimitError`, `GoUsageLimitError`, `429`, `"Upstream request failed: Model is unavailable."` / status 400, and `[retrying ... attempt #3+]` banners after a model reply, drawn in a `┃` callout or, as OpenCode 1.19.6 does, in the footer under the input box after its `■⬝` spinner (a free-usage line there is attempt #1 and counts)) by polling read-only `opencode.db` and `REPAINT` screen lines asynchronously when `LastOutput` advances, and rotates held models cleanly (`model_limits`, `limits.auto=switch`, `SwitchAgent --next`). GitHub Copilot (`copilot`, `internal/adapter/copilot`, `copilot.go`; design §22) has no hooks and chooses its session id at launch like Claude (`--session-id <uuid>`, new or reopened, so a switch, an approve and a resume keep the conversation; no `LookupSession`). It launches `--session-id <id> --model auto --auto-tier intelligence` (a named model takes `--reasoning-effort <effort>`; `tiers.copilot.*` default to `auto`), `--yolo` under `--skip-permissions`, and, for an asker, a reviewer or a planner not yet approved, one `--deny-tool=<rule>` per rule (`write`, and `shell(<publish command>:*)`; the `=` form so no rule swallows the next flag; a deny rule wins over `--yolo`), lifted on approve like the other CLIs. `installed("copilot")` checks the configured or `PATH` binary. A background pass reads each live Copilot agent's `$COPILOT_HOME/session-state/<id>/events.jsonl` (the last 256 KiB): a `user.message` or an `assistant.turn_start` starts a turn (a turn whose `user.message` is out of that tail is still followed) and an `assistant.turn_end` after a final answer (an `assistant.message` with no tool requests; a tool call's turn end is not idle) ends it, and its screen: a rate limit line (`You've hit your … rate limit`, anchored at the line start so a quote doesn't count, with its `resets in …` if it names one, else 5 h, `bin/mesh`'s `LIMIT_UNKNOWN_RESET`; a line about "this model" holds the agent's model only, the session and weekly ones every Copilot model; a line already reported counts as new again once it has left the screen) or `Failed to load models: access denied by Copilot policy` while a prompt is unanswered. A `session.error` that is a 402 (`errorType` `quota`, `statusCode` 402 or `errorCode` `quota_exceeded`: the monthly quota, held a day, Copilot names no reset) or a 403 policy refusal (held an hour: an admin has to change a setting) is `AGENT_STATE_LIMITED` with a kind-wide `*` hold in `model_limits`, so `--reviewers auto` leaves Copilot out (and says so, also for a tier it has none of) until it answers again: an answer to a prompt typed after the hold was set deletes it (`DeleteModelLimit`; the answer of a turn already running when the quota ran out says nothing), and the agent's next turn moves it on. Copilot shows a folder-trust dialog that neither `--yolo` nor `--add-dir` skips (1.0.115, checked with the real binary in an empty folder): while an agent is starting the daemon answers it from the screen (Enter on `❯ 1. Yes`, which trusts the folder for the session only and writes nothing to `~/.copilot`) before marking it idle, so no doorbell lands in the dialog (five presses; one that does not answer it leaves the agent `needs_input` with "folder trust dialog not answered", and it goes on to idle once someone answers by hand). A Copilot hold is lifted by an answer to a prompt typed after it, on the held model or for a hold on every model (a quota or policy hold), never by an answer on another model; a screen limit line counts once while it stays on the screen, whatever its countdown says. Its `ReadInputBox` reads the `┃` gutter box between `╻▄▄` and `╹▀▀` (`inputbox.Copilot`: every `┃` row is typed text, the dim placeholder `Type @ to mention files, / for commands` is empty), so the draft guard of "Doorbell delivery" holds a doorbell for a human's draft and the placeholder never does (tested on the fake's box and on drawn screens; the box shape is `bin/mesh`'s, not seen on a live Copilot). The hook reads the daemon's address at call time and, when the daemon is down, spools to `<state>/spool/<agent>/`; the daemon drains the spool every few seconds. Hooks always exit 0 and print nothing (except an agy `PreToolUse` deny JSON, and the Claude `SessionStart` reminder of "Context management"; failures go to `<state>/hook.log`). The adapter turns each hook into neutral events and `reducer.Reduce` derives the state; a working agent, or one waiting on a prompt, that nothing was heard from for 10 minutes shows as unknown (Claude may fire no hook when a prompt is dismissed). A compaction remembers the state it interrupted and restores it when the compacted session starts (idle stays idle, mid-turn stays working); a resume's `SessionStart` does not make an agent idle. A spooled hook the daemon's drain gets an error for (not "unreachable") at least ten times over at least five minutes is dropped (kept as `.bad`, with a `HookDecodeFailed` event); the hook process's own drain never drops one; idempotency records of hooks are pruned after a day, others after two weeks. Messages are stored and announced by a one-line doorbell once the agent is idle ("Doorbell delivery" below: written into a Claude agent's inbox socket, else typed into its terminal, retried until the agent has taken it, never into a human's draft); the agent reads them with `mesh inbox`. An asker or reviewer (and a planner) launches with a `--disallowedTools` list (Claude: `Edit` rules, which Claude applies to every tool that edits files, `NotebookEdit` included, and prefix rules for `git push` and the gh writes) and `PreToolUse` deny flags (agy: paths and publish commands; Claude: publish commands only), which hold under `--dangerously-skip-permissions`. Claude's prefix rules miss `git -C . push` and the like, so its `PreToolUse` hook (`--deny-publish`) also checks every Bash command with the shared `shellmatch` matcher, and a hook's denial is final in every permission mode (a hook that fails to run lets the tool through: the prefix rules stay as the backstop). The command check, for both CLIs, also unwraps `env`, `sudo`, `timeout`, `xargs` and the like, `sh -c` and `eval` strings, skips gh flag values (`gh pr --repo o/r merge`), and blocks `gh api` writes (a method other than GET, fields without one, a GraphQL mutation), and every gh command but an allowlist of reads (`pr list/view/diff/checks/status`, `issue list/view/status`, `release list/view/download`, `run view`, `search`, …: a gh command added later is denied until listed); it guards against an agent's mistake, not a determined one (a script it writes, a git alias).

**No kill by pattern.** Every agent shares the host with the others, and `pkill -f "sleep 30"` once killed another session's watcher. The protocol tells an agent to kill only a PID it started and kept; the mesh also refuses the commands (`internal/shellmatch`, `MatchPatternKill`: `pkill`, `killall`, `killall5`, a `kill` fed by `pgrep`/`pidof`/`ps … | grep`, wrapped in `sudo`, `env`, `timeout`, `sh -c` and the like; a `pgrep -P`, `-s` or `-g` lookup, which walks one's own children, and a kill of a held PID pass). A Claude or agy agent's PreToolUse hook (`mesh hook`, which runs for every agent, a read-only one or not, not for a person's own agy session in the agent's worktree) prints a denial that holds in every permission mode, saying what to do instead; it fails open (a payload it can't read passes), where the read-only rules fail closed. An OpenCode launch loads `share/opencode/kill-guard.js` (the same check by regular expression), and a Copilot launch, which has no hooks, `--deny-tool=shell(pkill:*)` and its kin (a prefix rule: no `kill $(pgrep …)`). A script an agent writes and runs gets past all of it: the guard is against a mistake.

**Lean Claude sessions** (`internal/daemon/lean.go`, `adapter/claude/lean.go`, design §11; `claude.lean`, on by default). A Claude agent starts without what a mesh doesn't use, about 39k tokens of its first call, re-read on every call: its launch gets one `--disallowedTools` (the read-only rules, then `claude.deny_tools`, or `claude.root_deny_tools` for a root, which keeps `AskUserQuestion`), `--settings` keys `skillOverrides` (`claude.skills_hidden`, and `claude.worker_skills_hidden` for a non-root: only a root starts a mesh), `syncClaudeAiSkills: false`, and `enabledPlugins: false` for the plugins of `claude.plugins_off` the user's settings enable, and `--strict-mcp-config --mcp-config <state>/agents/<id>/mcp.json` (mode 0600: a server's config may carry secrets) with the user's servers it loads: with `claude.mcp` `repo` the repo's own (its project entry in `~/.claude.json` and its approved `.mcp.json`), `claude.mcp_keep` (`context7`) and the spawn's `--mcp` names (`Agent.mcp`, kept by every reopen); claude.ai's connectors are off (`ENABLE_CLAUDEAI_MCP_SERVERS`). `claude.mcp` `inherit` loads whatever the user's config has, `claude.lean` false launches as before. `--mcp` is refused for a name the user's config lacks, a non-Claude agent, or when lean is off. **`mesh tools`** lists what the agent runs without (tools, skills, plugins, MCP servers cut and loaded, `claude.ai` connectors); **`mesh tools servers`** the user's MCP servers (name, one line from `claude.mcp_about` or the config, `always loaded`, `exclusive`, holder); **`mesh tools add <name>… [--agent <name>] [--next "…"]`** (`ListTools`, `ListMCPServers`, `AddTools` in `proto/agentmesh/v1/tools.proto`, `internal/daemon/tools.go`) reopens the agent's own conversation with one more tool, skill, plugin, MCP server, or `claude.ai` (its connectors, and with them every MCP server of the user's config: `Agent.mcp_all`, no `--strict-mcp-config`). The names go in `Agent.added_tools` / `Agent.mcp`, the reopen is deferred to the agent's next idle (`PendingReopen`, before any doorbell, and the accountability nudge skips an agent with a `tools added` one pending, for `accountability.wait_max` at most; a worker's own add also sends its parent a `wait`), and once anything is added back the launch passes `--system-prompt-snapshot off` (`LeanLaunch.disable_prompt_snapshot`). An agent adds to itself; a root or a run's other callers may name a child with `--agent`. **The shared-browser lease** (`claude.mcp_exclusive`, default `playwright`): at most one live agent on the host holds an exclusive server, whether it was named (`--mcp`, `tools add`) or its launch loads it unnamed (the repo's own servers under `repo`, every server under `inherit` or `mcp_all`). `SpawnAgent`, `Ask --mcp`, an explicit `ResumeAgent --mcp` and `AddTools` (also `claude.ai`, which brings every server) refuse a second claimant, naming the holder within the asker's run (an agent of another run is "another run", here and in `tools servers`; the user's own CLI sees all) (checked again inside the one store writer, so two concurrent claimants cannot both win); retire and stop release it and delete the agent's `mcp.json`; an implicit carry-over (`resume`, a `send` that revives a retired agent) drops a server now held by another agent and says so in `notes` (also a dropped `mcp_all`: `mesh tools add claude.ai` brings the connectors back). A server a launch would load unnamed that another agent holds stays out of its `mcp.json`, and the agent is told in an `info`; `mesh tools add <name>` takes it once the holder is retired. `mesh tools add` has the group form `tools add` / `tools servers` in `mesh help`; a short plain word after `tools` that is no subcommand is refused, not taken for an agent.

## Same conversation: tiers, approve, switch, resume

A model change reopens the agent's own conversation (`claude --resume <session> --model … --effort …`), never a fresh agent briefed again, so it keeps its research (design §9, `bin/mesh`'s `swap_model`).

- **`mesh model`** (`ResolveModel`, every actor class may read it: `mesh model [--kind agy] --tier strong [--effort high]`, or `--model <name>`) prints what a spawn of that kind and tier would run now: the model and effort, then the tier's chain (OpenCode's `free` expanded) with each model's standing (`held until 17:40`, `at the reserve (6% left)`). It runs the spawn's own `pick` after the spawn's own warming (`warmUsage`, `warmOpenCodeModels`, outside the snapshot, so agy's reserve and OpenCode's `free` count on a daemon that hasn't spawned anything yet), so the two cannot disagree, and starts nothing; neither tier nor model is `InvalidArgument`, as for a spawn. `--format json` gives the response.
- **Tiers.** `SpawnAgent` takes a `tier` (`tiers.<kind>.<tier>` in the settings: the chain's first model at its effort) or a `model` the user named (at `effort`, else high). Neither is `InvalidArgument`: there is no default model, except for a root, whose model is the user's (it launches on the CLI's default unless one is named). A tier is checked whenever it is given. A named model leaves the agent no tier (the tier only gives the effort), so `next` is refused from it. A named model or effort with no plan phase is `pinned`.
- **Plan phase.** `plan` starts the agent `PLANNING`, a Claude agent under the same `--disallowedTools` list as a read-only one (`deny_edits`), optionally with a preset `exec_tier`. A `plan` sent by an agent with no phase that isn't pinned enters one, without a reopen (it plans on the model it is on, with no deny list).
- **`ApproveAgent`** (its parent or a device, only when its newest report since its last task or answer is a `plan`, or when it is a planner that has sent none: that is the parent skipping its plan, and the answer says so) stores the `approved` answer, sets `EXECUTING`, and reopens it on the execution tier (given, else the preset; or a named model) without the deny list. `keep_model` executes on the planning model; only the deny list goes, which is still a reopen. An agent with no plan phase is approved as it is. A task marked direct (it begins `Direct task`, as bin/mesh's does) sent with `SendMessage`, by the agent's parent or a device, ends a plan phase (the tier it runs on becomes the one `next` walks) and lifts a planner's deny list by a reopen on the same model, unless the role is read-only; any other task leaves a planner planning, under its list and with its preset execution tier; a `plan` from an agent that is executing, or has no phase and isn't pinned, enters the plan phase again, so its approval can name a tier.
- **Change tasks for askers and reviewers.** An asker or reviewer given a task that doesn't begin `Question (read-only)` or `Review (read-only)` (by `SendMessage` or `resume --task`, from its parent or a device) becomes a worker in the same conversation (`takeChange`): its role, its live tokens' class (read from the row on every call, so a running process follows) and an `AgentRoleChanged` event change, and a planned task (not direct, or `resume --plan`) puts it in the plan phase under the list it already has; the paths above then lift the list as for any worker (a direct task by a reopen, or at launch when it is stopped; approve by a reopen on the execution tier). An agent a worker started never changes role (a worker never gets a change worker): to it every task is a read-only follow-up. A refused resume of a stopped agent keeps the conversion with the stored task; a direct task that made an asker or reviewer a worker also lifts its list, so the next resume brings it back able to edit.
- **Asks and review rounds** (`mesh ask`; `internal/daemon/ask.go`, `review.go`, `collect.go`, `pr.go`). `Ask` (root or worker) starts a read-only agent or asks one the caller started: `ask --repo R --tier T --body …` a fresh asker (slug `ask-<words>`, task `Question (read-only): …`); `ask <agent> --body …` a task to an existing one (resumed if retired; a busy one is told the task waits); `ask --repo R --review <PR> --size S --tier T [--kind K]` one fresh reviewer at the PR's head; with `--reviewers auto|all|<kinds>` a **round**. The PR is read with `gh pr view <PR> --json number,url,headRefOid,headRefName,baseRefName` in the repo (the daemon only ever runs that: `Binaries["gh"]` is the fake in tests), its head is fetched (by id, else `pull/<n>/head`) so each reviewer's worktree starts on it, and the task names the diff command instead of embedding it. A reviewer's task is `bin/mesh`'s text (CI first, tests the change touches, findings with file:line and blocking or advisory), with `/code-review <review.level.size> <PR>` for a Claude one. `auto` fills `review.reviewers.<size>`'s slots with the first adapter registered and not picked, the PR author's CLI (the newest agent whose branch is the PR's head ref) after the others of the slot (`authorLast`: removed, then reinserted right after the slot's last non-OpenCode kind, so OpenCode keeps its place). The default is one slot each: `small` is `opencode, agy, claude` (OpenCode's DeepSeek first: free and another family than either author; then the CLI that isn't the author's; then the author's in a fresh session) and `large` is `agy, claude, opencode` (Copilot is left out until verified live; a user can add it), and OpenCode's tiers default to `opencode/deepseek-v4.1-flash-free` alone, with no `free` fallback (docs/cost-research/roles-and-reviews.md). A re-review asks the last round's kinds minus `review.re_review.skip` (plus `keep.<size>`); a kind with no adapter is left out with a note. The record is an `Ask` (table `asks`, `ask.proto`), stored before its members start (`starting`: it can't finish until all are started, so a fast report is collected) with an id derived from the caller and the request's mutation id, and with derived mutation ids on each spawn, so a retried ask finds the ask it left, keeps its started members and starts nobody twice. A re-review asks again only a reviewer that answered the last round; one that didn't (a question, a crash, the timeout) starts fresh on the whole PR. **Collecting:** a round's members' `done` and `failed` to the caller are stored delivered and read (no doorbell) and settle the member; a `plan` or `question` rings as usual and settles it; an exit or silence alert settles it with the alert's first line (`alertParentTx`); the accountability pass settles a member whose agent was stopped without reporting, and every member still pending after `ask.timeout`. When none is pending (same transaction) `reports/review-<pr>-<stamp>.md` is written (bin/mesh's format; a file that can't be written is said in the message, and the answers stay in the ask) and the caller gets one `info` `[mesh answers <id>]` with who answered, the path and the rounds hint (`review.rounds.<size>`, a ceiling counted across runs: finished rounds of the PR with an answer). A re-review in the same run asks the earlier round's own reviewers again (resumed if retired; a clean worktree at the head they reviewed moves to the new one, else it stays and the task says why) and reads only what changed since; in another run (an agent reads only its own run) fresh reviewers of the same kinds read only the fix commits. Every launch asks `ReserveGuard` first (a retry whose spawn already went through skips it: the spawn replays). `RecordVerdict` (`mesh verdict`, root, a worker or a device) stores a reviewer's verdict (counts, kind, model, tier, and `judge`: `author`, `root` or `user`) on the PR's newest round; `ListAsks` (`mesh asks`) lists them. **A worker runs its own PR's rounds** (`worker_review.go`): the default (`review.by` = `worker`; `mesh spawn --reviews` / `mesh approve --reviews` set `Agent.review_by` per worker, `root` for a risky PR's relay, which the root runs) is that, after its self-review, a worker asks the round itself and the answers file and the `[mesh answers]` info come to it. For a worker's review the daemon fills in what the root would give (a root must name `--repo`; a PR given by URL must be of the repo's own GitHub origin): no `--repo` (or its own worktree) is its repo (`reviewTop`: reviewers are named after the repo, their worktrees come from it, and the author's CLI is found), no `--tier` is `review.tier.<size>` (from any caller). It refuses a PR of another repo (before fetching it) or whose head branch is neither the worker's registered branch nor the branch checked out in its own worktree with commits of its own past its base nor another branch of its own series (`mesh/<run>/<slug>`, `<slug>-2`, `<slug>-3`: a worker that stacks PRs opens the next one from a branch it is not registered on; `inSeriesOf`), when it is not the repo's default branch, no other agent of the repo is registered on it or has it checked out, and no other worker owns the PR (`AgentPRs`) or asked a round on it (a worker that moved to another branch can still review its PR, but switching onto another worker's branch doesn't make that PR its own; the author's CLI is found by the same branch rule, `prAuthorKind`; slugs are unique per repo, so two repos' workers can share a branch name), any review while `review.by` is `root` (the refusal says to report `done`: the hook for a relay), a round while another round of the PR is open (`wait for its answers`: two asked together would both pass the count), a round past `review.rounds.<size>` (both checked again in the write that stores the ask) (its answered rounds and its single reviewers count; the root may still run one) and `ask <reviewer> --review` (a re-review is a round, which asks the earlier reviewers again). The round's hint speaks to the author (judge, record verdicts, fix, re-run for a re-review of the fix commits, or report `done`). A worker with its own collected ask open (a round or peers), or a single reviewer it asked that has not reported, is not nudged (`openOwnAsk`, before its `deadline`). The footer's "asked no review round" (only for a worker with commits on its branch: one without names somebody else's PR) reads every ask of the PR (by its normalized URL) and names who asked the rounds that exist; a single reviewer shows as "asked alone" (its `done` goes to the worker, so the ask never learns it answered) with its missing verdict flagged. A worker may record a verdict only on the rounds it asked and never over a root's or a user's (a root's replaces its own); `GetCost`'s verdict rows count `by_author`. Its `done` to its parent ends with one `[mesh reviews]` outcome line per PR, from the store alone (`reviewFooter`, `reviewOutcome`): **SETTLED** (rounds and reviewers, findings agreed and declined, checks) or **NEEDS YOU** with why (the parent reads findings only then, the file named). Settled needs every reviewer of the last round answered, a verdict recorded for each (`mesh verdict`; its `--declined-blocking` count is the blocking findings the author declined, and any makes it NEEDS YOU until a root's verdict replaces the author's), no round open, checks not failing or pending and the PR's GitHub state read (`checks none` is shown, not blocking), a relay run to its end for a worker on `--reviews relay` (3 steps, or a step the author agreed nothing in), and no other open PR of the worker's own without a round (named in the done or not: an unknown is not a pass). The PRs are the worker's own by a recorded head that is its branch or one of its series (`mesh/<run>/<slug>`, `-N`), a branch-lookup PR, the first link no recorded head rules out, or any PR it asked a round on, except one that merged or closed and that the `done` does not name (it is over: by its row, or by what GitHub says of it when no row remembers it, read before the write like the head). `mesh brief` shows `reviews: settled|needs you|running` per worker, and `mesh prs` the same word as `reviews` on the worker's row (both only once its `done` is in). A SETTLED line also says `N commit(s) after the last reviewed head` when the PR's head is past the head its newest round reviewed (`PullRequest.head`, GitHub's `headRefOid`, recorded with each read; before the write `done` asks GitHub for the head once, under the brief's 8 s wait, and falls back to the row's when it cannot, and counts with `git rev-list` in the worker's worktree, since a store write runs no git): a head that is not past the reviewed one (a rewritten branch) says `the PR's head is not the last reviewed head (commits after it, count unknown)`, never nothing. It is a note on SETTLED, not NEEDS YOU: the lead samples it. No footer for a worker whose reviews are the root's (`--reviews root`). `--reviews relay` (spawn, approve) refuses the worker's plain rounds and single reviewers and leaves `--relay` to it. **A relay** (`--relay`, `review_relay.go`) is one reviewer at a time on a risky PR: each call runs the next step (A, a CLI that isn't the author's, on the whole PR; B, the other family, fresh, on the whole PR at the new head with the note that commits X..Y fixed an earlier review; A's own agent again on the fix commits, `--since` the head it saw), and `size` defaults to `large`, `tier` to `strong`. A step is a collected one-reviewer round whose ask records `relay_step` and `relay_of`; the call is refused while a step collects, with no commit since the last step, or past the third; `roundsOf` leaves relay steps out, so they are no round of the PR's, and their hint (`relayHint`) says what to run next.
- **Standing peers** (`mesh peers`, `add-peer`, `edit-peer`, `remove-peer`, `import-peers`, `ask --peers`; `internal/daemon/peers.go`, tables `peers` and `peer_groups`, migration 0007). A peer is a cloned project kept as a standing read-only asker: the registry holds its clone, group, `about` (at most 400 characters), kind, upstream, a detached **worktree of its own** (`<worktrees>/peers/<name>`), the commit it last saw (`seen`) and its conversation id. `AddPeer` (root or device) clones a URL (https, ssh, git, file or `user@host:path`, never `ext::`; `GIT_ALLOW_PROTOCOL` pinned) into `peers.dir`/`<group>`/`<repo>` or uses the clone at a path, and names it `<repo cut to 20>-research`. `ImportPeers` reads bin/mesh's `peers.json` and never writes it: peers and group `about`s not registered yet are, **with their conversations**: the session id comes from the `run.json` of the run `peers.json` names (`run`, `as`; in `<state>/<run>/` or `<state>/archive/<run>/`, else the newest run whose agent of that name, or marked `peer`, ran on that clone), the worktree path in `cwd` is kept as the peer's worktree (Claude keys a conversation by its folder; made again there when it is gone, detached at `seen`), and `asked`, the last run and agent and the `answers` file come across, so the next round resumes it and `harvest-peers` follows up instead of briefing again. A peer `in_clone` (it ran in the clone's own checkout, or its `cwd` is the clone) is marked `Peer.in_clone`: the daemon never checks out in it, moves it or removes it on `remove-peer`, and tells the peer with `git show <head>:<path>` that upstream moved. A conversation whose bin/mesh agent may still be running (`starting` or `running` in a run that isn't archived), or whose folder can't be used, comes across without it and says so in `skipped` (one process per conversation: retire it there and import again); `unbriefed` skips every conversation. A registered peer that was never asked is upgraded the same way (its own worktree is dropped when clean, and the commit bin/mesh last showed it, `seen`, comes with it); one already asked, one registered on another clone than peers.json names, or one an ask is starting (the upgrade takes the lock an ask of that peer takes) is left alone. A folder that exists is adopted only when it is a worktree of the peer's clone (same git common dir), wherever it is; one that is gone only when it is where the daemon keeps that peer's worktree or outside the daemon's worktrees; else the peer comes across without its conversation, with a note (an agy peer from the clone's own checkout too: its hooks are written into its worktree, so it gets one of the daemon's). A peer already registered that is not upgraded gets a `not upgraded` note. The import holds the lock of only those registered peers that may be upgraded, until its write. `remove-peer` removes only a worktree of the daemon's own: a folder outside its worktrees (bin/mesh's), the clone's checkout and one another peer still uses stay. An ask of a peer whose in-clone checkout is gone says so. An agent belongs to one run and reaches only its parent, so a peer is not one agent: each run that asks it gets an agent record of its own (role asker, `Agent.peer`, named as the peer) in the peer's worktree that **resumes the peer's conversation** (`--resume <session>`; a fresh one with a tier for an unbriefed peer), refused for a peer whose agent runs in another run (one process per conversation). `Ask` with `peers` (`all`, a group, or names) prepares each peer first (a 60 s fetch of its upstream, the checkout moved to the new head when clean, and the note "Upstream moved since you last looked: N commit(s) … `git log --stat`" or "hasn't changed" at the top of its task; `no_refresh` skips it), then collects like a round (`ASK_KIND_PEERS`) into `reports/peers-<stamp>.md` (question, then a section per peer: its repo at the head, upstream commits since last asked, `about`, answer). The registry records `seen`, the asking run and agent, the conversation id and the answers file. A peer's agent is never given a change task (`takeChange` skips it) and `StopRun` keeps its worktree. `remove-peer --delete-clone` deletes the clone only when the daemon made it (a URL's) and no other peer uses it. A peer's conversation has one process: a peer agent with a process (running, starting or a reopen asked for) in another run refuses an ask, a resume and a `send` from this one, and an ask of a peer is serialised per peer (the fetch, the checkout and the launch run under one lock, the check repeated inside the launch's transaction); a task stored for a peer agent that could not be resumed is marked read. A peer's agent in a run is the child of whoever asked it last (it reports to its parent only): a second caller of the run asking it moves it to itself under the peer's lock, in the write that stores the task (a refused ask leaves it where it was), unless it is the first caller's still: it is working, it owes it an answer or a report on a task it read (a `plain` task sent straight to it), has a task or answer of it unread (while it is running), or sent it a `question` or `plan` and waits for the answer (a stopped peer, or one whose caller is stopped, is let go; the check, its state included, is repeated in the write that moves it, and an ask refused after the peer's checkout was brought up to its upstream puts the checkout back; then the peer is not asked: "still answering an earlier question of <caller>", "has not yet read a message of <caller>" or "waiting for the answer of <caller> to its question"). An imported peer's group, upstream remote and branch are checked (an option-like one is left out) and its `about` capped.
- **`SwitchAgent`** moves it to a tier, a model, an effort alone, or `next`: the next model of its phase's tier chain (the quota move; never back to one before, and `FailedPrecondition` at the chain's end). It stores an `info` telling the agent where it is now (not a task: a planner switched before approval is still approved on its plan). A switch to a named model leaves the phase no tier, so `next` is refused from it rather than going back to the chain's first model. A model at a usage limit is persisted in SQLite (`model_limits`, migration `0005`: until the reset the CLI named, else `limits.hold` seconds; an account-wide limit holds every model of the CLI), and the chain is walked past held models (and agy models at `quota_stop`): a new agent, an approve and a switch to a tier take the first model with quota left (all held: the one freed first), and `next` the first free one after the agent's own (or for OpenCode when the chain changed, the first unheld one, refusing with the soonest reset when every candidate is held; other kinds fall back to `chain[0]` or `chain[i+1]`).
- **`ApproveAgent` on a stopped agent** is refused: approving never undoes a stop; resume it (it comes back planning), then approve.
- **Usage limits and quota reserve** (`limits.auto`, default `switch`; `limits.hold`; `quota_stop`, default 90%): a pass every few seconds looks at each agent at `LIMITED` that isn't a root (its model is the user's) and has no reopen pending, moving it to the next free model (`switch`) or continuing once the hold expires (`switch` / `continue`). A limited member of a round whose limit outlasts the ask's deadline and that isn't moved off is settled at once, and with `limits.auto=off` (nothing moves or continues it) whatever the limit's end (the line says why: `limits.auto is off`, `limits.auto is continue`, the account or CLI at its limit on every model, or no other model to move to), so the round isn't held for a reviewer that can't answer. Claude usage comes from Claude Code's `statusLine` command (`mesh statusline --state <dir>` recording `rate_limits`, chaining read-only to any user `statusLine` command) with OAuth endpoint and `.claude.json` `cachedUsageUtilization` fallbacks; agy usage comes from `agy -p /usage`. `ReserveGuard` blocks new tasks (`SpawnAgent`, `ApproveAgent`, `ResumeAgent --task`, `SendMessage` of a `TASK`) when a vendor window or model reaches `quota_stop` (while answers still deliver), until reset or `mesh reserve off` (`Run.over_reserve`). `GetUsage` (`mesh usage`) reports current windows and tier picks, `SetReserve` (`mesh reserve on|off`) toggles `over_reserve`, and periodic `reserveAlertPass` posts deduped `[mesh alert reserve …]` info messages to open runs' leads.
- **`ResumeAgent`** reopens a stopped agent (with a task it plans, a direct task, or as it was): it recreates clean removed worktrees, moves a change worker off an already merged or closed GitHub PR (when none is open) onto a fresh `mesh/<run>/<slug>` branch (`LeftPr`/`Notes` and task note), and lets a `ROOT` (or `DEVICE` naming `run_id`) resume a stopped non-root worker from a closed earlier run as a new follow-up `Agent` in the open run keeping the same conversation and worktree (`ResumedFromRunId`/`ResumedFromAgentId`), enforcing one live process per conversation/worktree across all runs (`StopRun` leaves worktrees held by live agents or active open runs untouched).
- **Reporting** (`internal/daemon/cost.go`, `models.go`, `conflicts.go`, `proto/agentmesh/v1/report.proto`):
  - `GetCost` (`mesh cost`) measures in tokens: per run, agent, kind, model and phase, one set of rows for Claude, agy, OpenCode and Copilot alike (input, cache write, cache read, output). The headline `total` is input + cache writes + output; cache reads are listed apart (most of a Claude session, far cheaper on a plan), and `clis` says per CLI how exact the counts are (Claude: the API's usage per call; OpenCode: the provider's own, reasoning in output; agy: as it records each step, with no cache-write split, so an estimate; Copilot: its `session.usage_record` events, with `inputTokens` less the cache reads and writes it contains, and no dollars: Copilot bills premium requests per call, so its call count is its cost). Rows sort by tokens; an agent's tokens include its Claude subagents' (their dollars are its `sub $`), so the agent rows add up to the total. Dollars are secondary and Claude's: its API-equivalent price (`usd`, `≈ $` in the CLI) is the headline and in every row; what an OpenCode provider billed shows once, on its own CLI row (`clis[].usd`), in no other figure. It sums Claude JSONL token/USD spend (folded by `message.id`, attributed across phases and cold resumes by `Event_AgentSpawned`/`Event_AgentPhaseChanged`, a run's window running from its creation to its stop, or for an unstopped run to its last event plus the cache TTL, and a root counting only inside it), agy conversation DB calls (`protowire`; each call's model is read from the file's `gen_metadata`, so an agy agent with no model on record still shows the one that ran (`gemini-4-neon` and `gemini-3.8-flash-n` count as the families `neon` and `flash`), and the agent's recorded model is used only where the file names none), Copilot `session.usage_record` events, OpenCode `opencode.db` token usage (with paid `cost` kept in its own `usd` column on token rows, separate from Claude's API-equivalent total), `--since`/`--until` global windows, and `mesh verdict` totals.
  - `CheckModels` (`mesh models [--check] [--ack <kind>:<family>]`) compares listed families against `tiers.<kind>.*` settings (caching checks for 24h in SQLite `meta`, populating `StartRunResponse.model_notice`, and exporting `Daemon.ModelNotice(ctx)` for `mesh brief`).
  - `CheckConflicts` (`mesh conflicts`) runs `git merge-tree --write-tree -z` pairwise across the branches of the run's agents that share a repo (skipping stacked ones, caching only the ancestry of each commit pair) and compares what each worker has changed, committed or not, for overlaps; every git call runs with `GIT_OPTIONAL_LOCKS=0`. A root may read any run and a `--since` window with `mesh cost` (bin/mesh parity); other agents only their own run.
  - **Operator parity commands** (`worktree.go`, `log.go`, `ring.go`, `open.go`, `cli/open.go`): `CreateWorktree` (`mesh worktree`, root or device) creates an integration worktree on `mesh/<run>/<slug>`, persists it in `worktrees` (migration `0008`), includes it in `CheckConflicts`, and cleans it up in `StopRun`; `StreamLog` (`mesh log`) streams run events and message/nudge/alert/review entries in `log` order with `--agent`, `--lines` and `--follow` (ending at `RunStopped`); `RingAgent` (`mesh ring`) re-rings unread mail for a live non-working agent through the per-agent lock, inbox socket and human-draft guard (`delivery.go`); `OpenAgent` (`mesh open`, device) returns either a one-time `mesh-term` attach ticket (`OPEN_MODE_ATTACH`, attached in raw mode by the CLI until `Ctrl-]`, refusing model/effort/extra args while live; a stream that ends without the host saying so, as when meshd restarts, keeps the terminal raw, prints one `[meshd went away, reconnecting…]` line and re-asks `OpenAgent` for a fresh ticket (it is single-use and meshd forgets tickets) with a wait of 250 ms doubling to 5 s for up to 2 minutes, re-attaching in REPAINT mode at the current size; `Ctrl-]` still detaches meanwhile, a refusal (the agent gone, a bad token) ends it at once, and the window running out is an error; `cli/open.go`, `e2e` `TestMeshOpenReattachesAfterMeshdRestarts`) or a standalone CLI invocation (`OPEN_MODE_EXEC`, `PlanLaunch` with `standalone=true` omitting hooks, deny lists, lean cuts and skip-permissions, clearing mesh `.agents/hooks.json` for `agy` and stripping `AGENT_MESH_*`/`MESH_*`/session vars before `exec`).
- **The reopen.** Each of these stores a `Reopen` on the agent (`pending_reopen`, event `AgentReopenRequested`); a newer request replaces one not done yet. It runs when the agent is idle or stopped and no client with input rights is typing, else at its next `IDLE`, before any doorbell: the old process is stopped (SIGTERM, then SIGKILL), its exit is not recorded as one, a new token is minted, and the conversation is relaunched in a new terminal labelled with the reopen's id (`AgentReopened`). The agent keeps its id, name, worktree and session; the message the action stored rings in the new process. A pending reopen survives a meshd restart; a terminal a reopen had started when meshd died is found by its label and recorded, never launched twice. `StopAgent` drops a pending reopen (`AgentReopenDropped`); a relaunch that fails leaves the agent `EXITED`, for `ResumeAgent` to try again.

## Context management (compaction, root reset, brief)

What keeps an agent's and the root's context small (design §12, §15). The daemon owns every terminal, so each step hangs off `deliver`, under the agent's lock, before the reopen and the doorbell, and goes through the same "safe to type" check a doorbell does (`quietToType`: at its prompt, nobody typing).

- **Measuring.** `MeasureContext` of an adapter reads the CLI's own record: Claude's `~/.claude/projects/<cwd with [^A-Za-z0-9] as ->/<session>.jsonl`, read backwards (the newest reply's input + cache-read + cache-creation tokens, a `compact_boundary`'s `compactMetadata.postTokens` (what the compaction kept; 0 when the line has none); the cache lifetime from the `cache_creation` `ephemeral_1h`/`5m` counts of a reply up to 50 back, else 1 h; cold once the file was last written longer ago than that), and agy's `conversations/<id>.db` (a finished type-23 `steps` row is a compaction, size 0; else field 9 of a step's `metadata`, fields 2 + 5). OpenCode has no `MeasureContext`: it compacts itself, and mesh never does. The capabilities `context` (both) and `compact-live` (Claude: a cache whose compaction can be typed live) say which.
- **Compaction** (`compact.go`). A request is an `Agent.pending_compaction` whose thresholds are fixed when it is asked for and compared with the size when it runs. A resume (`ResumeAgent`, a message to a stopped agent) asks when the conversation is over `compact.claude` (`compact.agy`), or over the lower of that and `compact.claude_cold` once its cache is cold, twice that for a read-only task except a peer's, and, for an agy conversation of unreadable size, when it comes back from another run and the task isn't read-only (`--compact auto|yes|no`, `--focus`; a switch never compacts). `approve` asks, before the reopen it requests, when a Claude planner is over `compact.approve` (`compact.approve_switch` when the execution model differs). A task or answer to a live Claude change worker whose newest report is `done` or `failed` (a follow-up round) asks over `compact.followup` (cold: `compact.followup_cold`). 0 turns a threshold off. A stopped conversation is compacted headless (`PlanCompact`: `claude -p --resume <id> --model <m> /compact <focus>`, or `agy --conversation <id> --model <resolved id> -p /compact <focus>` (agy takes only an id of `agy models`, so the tier's family and effort are resolved as at launch), its own lean tools and MCP servers, a 5-minute cache, no `AGENT_MESH_*` and no mesh hooks, off the agent's lock, at most 15 minutes); a live Claude agent by typing `/compact <focus>` at its quiet prompt, which its hooks confirm (`PreCompact`, then `SessionStart` of source `compact`) and its transcript shows: Claude fires that `SessionStart` before the compacted transcript is on disk, so the compaction is done once the transcript's size is below what it was (a `compact_boundary`), or after `CompactSettle` (20 s) with an outcome that says no smaller size showed (without this wait, a reopen right after the hook stopped the process before the write, and the agent resumed whole: the "approve left a worker at 215k" of `bin/mesh`). Every outcome but "not worth it" is an `AgentCompacted` event with the sizes; a failure, a timeout (`CompactQuietWait`, `CompactStartWait`, `CompactTimeout`) or a user typing for a minute leaves the agent as it was and never fails the action. The focus is `bin/mesh`'s (`COMPACT_FOCUS`, `PEER_FOCUS`, `APPROVE_FOCUS`).
- **Root reset** (`reset.go`). `mesh reset [--next "…"] [--compact [--focus "…"]]` stores an `Agent.pending_reset` (refused while a plan or question waits on the root, or one is pending), and `deliver` carries it out once the root is at its prompt with nobody typing (`root_reset.wait` seconds at most; an unread plan or question cancels it): a Claude root is relaunched lean in a fresh conversation (a reopen with `fresh`; `root_reset.relaunch`), else `/clear` is typed (agy: its conversation id is cleared once the `/clear` is typed, so the next turn's hooks record the new one; a failed `/clear` keeps it), or `/compact` for `--compact` (a Claude root); then the bootstrap line, which tells the root to run `mesh brief`, is typed. A fresh launch that fails, or is not at its prompt within a couple of minutes, is stopped and the old conversation resumed, so a reset never leaves the root without a process or with an unbriefed one; a `/clear` that never brings the prompt back, a process that ends, or a relaunch whose fresh reopen another reopen replaced (the root is back on its old conversation) fails the reset, a terminal host that keeps failing counts against the same wait, `--next` and `--focus` are typed as one line, and a bootstrap line a user's typing holds back is given up after `root_reset.wait` (the root is told in the hint to run `mesh brief` itself). Each outcome is a `RootResetFinished` event and the root's `last_reset`. The keeper (a pass every `ContextEvery`, 60 s between looks) asks by itself (`root_reset.auto`, labelled `via keeper`) for a root over `root_reset.at` in an open run that still has live non-root agents, idle, with no unread mail, quiet 5 minutes after a turn a mesh doorbell started and 30 after the user's or one it can't tell (agy's hooks carry no prompt; Claude's `UserPromptSubmit` does, `TurnStarted.by_mesh`), no more than once an hour. A **plain agent** (`SpawnAgent.plain`, `Agent.plain`: the desktop's "New agent") is the user's own conversation with a CLI, like running it in a terminal: a root, with no task and no plan (anything else is refused), in a worktree of its own with the daemon's launch flags (skip-permissions), and still hooked and lean so the chat view, queue and context meter work. The mesh never treats it as a run's root: the keeper skips it, `ResetRoot` refuses it (type `/clear` in its chat), it gets no `root_line` hint, no `reminderText` on `SessionStart`, a first doorbell that names `PROTOCOL.md` (the messaging rules) instead of the root card, and a resume never queues its compaction (`requestResumeCompaction`); it has no workers, so no accountability nudge either (`owesParent`). Every call of a root but hooks, `brief` and `reset` carries `root_line`'s hint (cold and big: reset now; about to wait after a spawn, approve, switch, resume or ask; very big: at a quiet point; a failed reset, once) in the response header `Agent-Mesh-Hint`, which the CLI prints on stderr as `mesh: …`.
- **Pull requests per agent** (`prs.go`; `mesh prs`, `ListPullRequests`; `bin/mesh`'s `pr_states`, `report_prs` and `work_evidence`). A change worker (not a root, asker, reviewer or peer) owns the PRs of its branches (`gh pr list --head <branch> --state all` in its repo's GitHub remote for each, those whose head is on the branch and past its base commit): the one recorded at its spawn and the rest of its stack (`prstack.go`: the local `<base>` and `<base>-<n>` branches, where base is the recorded branch with a trailing `-<n>` taken off, plus the one its worktree is on, minus any branch another agent of the run records, the newest 8; an agent recorded on `foo-2-2` looks from each name it was made after (`foo-2`, `foo`); an agent recorded on `foo-2` while another owns `foo` (records it, or owns a PR from it) looks at no other branch, as it can't tell `foo`'s `foo-3` from its own; the branch the worktree is on is never cut by the cap), because a worker that stacks PRs moves on to `-2`, `-3` … which the recorded branch alone never finds and the ones named in its newest `done` that names any since its last task (read with `gh pr view <url>`: another repo, a fork). Their last state (`open`, `merged`, `closed`; draft; the checks folded to `failing`, `pending` or `pass`, where a failed check run that finished within 5 s of its start ran no job (GitHub refusing to start Actions for billing) and counts for nothing) is kept in `agent_prs` (migration 9), so a restart, a failed `gh` or an app reading later still has it. There is no timer for the state itself: a reader (`mesh prs`, the brief, an alert's evidence) refreshes an agent's PRs when its last read is older than 120 s (60 s after a failed one; `mesh prs --refresh` ignores both), eight agents at once, each `gh` call under 15 s, and a clean read is the whole truth (a PR it no longer returns is forgotten, and a brief waits at most 8 s for GitHub, then shows the last state), while a read that fails keeps the last state with `stale` set (`mesh prs` says `read_failed`, also while the first read is still under way; the brief says `GitHub not read: last state seen`, and for a worker with no state ever `PR unknown`, never `no PR`). A change of state or checks (or a PR seen for the first time) is a `PullRequestChanged` event of the run (`mesh log` shows it as `pr`), never a message: the root reads it in the brief or `mesh prs`; waking the root on CI results is the deferred CI step of `docs/apps.md`. **Feedback to the worker** (`prfeedback.go`; `prs.feedback` `off|notify|resume`, default `notify`; `prs.watch_every`, default 300 s, 0 stops it): every `prs.watch_every` a pass refreshes the PRs of each change worker of an open run that has an open PR (or reported a `done` and has none recorded yet) and reads each open PR once (`gh pr view <url> --json headRefOid,statusCheckRollup,reviews,comments`, and `gh api repos/<o>/<r>/pulls/<n>/comments` for the inline ones). What is newer than the PR's cursor (`PullRequest.feedback_cursor`, kept across refreshes; the first look sets it to the newest time GitHub gave on the PR, so old comments tell nothing and the daemon's clock is never compared with GitHub's) is told to the worker that owns the PR, never relayed by the root: a live worker gets an `info` `[mesh pr-feedback #N] …` (each item with its author and `path:line`, text cut at 600 characters, at most 10 items and 4000 bytes, never cut inside a group of one time (a group of more than 40 is told whole, each item cut to 200 characters): the cursor stops at the last one told, so the rest come at the next look) that rings at its next idle and says to treat each as a claim (`PROTOCOL.md` rule 8); failing checks are told once per head commit (`failing_head`; a pass in between, or a new head, makes the next failure news again, and a PR already failing at its first look tells nothing). Only the repo's owner, members and collaborators are heard (`authorAssociation`; one GitHub did not give is skipped): a stranger's comment on a public PR is never a task, least of all an unattended one. Reviews with no body, pending and approving reviews, and comments from `[bot]` accounts (or `is_bot` authors) or ending with an agent's attribution (a last line with `Generated with [Claude Code]` or `Co-Authored-By:`, or a `[mesh` first line) are skipped, because every agent shares the user's GitHub account: this, the cursor and the resume cap keep a worker from answering its own comment in a loop. Only a PR the worker owns is watched (`source` branch, or its head branch is the worker's), not one its `done` names. Its `info` also lets the worker report again on the same task (`reportsSinceWork` starts over at it, so `--re` still works). A comment signed with a last line `[mesh <name>]` (PROTOCOL.md has workers sign their PR comments) is skipped. A retired or exited worker gets the same `info` in its own inbox (an info starts nothing; a resume delivers it) and its parent is told one `[mesh alert pr-feedback <id>]` line with no text (`notify`; `mesh resume <worker>` then brings it back to act on it); `resume` sends the worker a `Direct task (no plan)` with the text through `SendMessage`'s revive path (the same cap, memory, quota-reserve and closed-run guards; `PullRequest.feedback_resumes`, at most 3 per PR), and a refusal, or a worker with no conversation to resume, falls back to the parent's line (the text stays in its inbox). When no PR is open the watch looks again only after a newer `done` than its last full read (a failed read counts as none). A PR opened since the worker's current task is news from its creation, even at the first look (a failing CI too); an older one only from its newest existing item. Merged and closed PRs are not read. `resume` spends quota unattended on any comment, so it is not the default. `mesh prs` also gives a worker's work evidence (commits past its base, pushed, dirty) when it reported `done` or has no PR, and the reviewers of this run that still owe their answer on each PR (open review asks). Resume onto a finished PR (`leave_finished_pr`) is `finished_pr.go`'s own `gh` read and depends on none of this. **Hold merge** (`hold.go`; `mesh hold-pr --url <url> [--release]`, `HoldPullRequest`, a root or a device): the user's brake on one PR is kept by the PR's normalized URL in `pr_holds` (migration 0012; so it outlives every `agent_prs` record of the PR, and `PutAgentPR` sets the record's `held` flag from it), matched by `PRKey` (case, a trailing slash, `?` and `#` don't matter); a root may hold a PR of its own run but never release one (only a device does, even a hold with no record left), shown by `mesh prs` and the brief (`HELD by the user: do not merge`), and set or cleared with a `PullRequestChanged` event (state and checks unchanged; `mesh log` says `held` or `released`) so a client updates at once; a PR the host doesn't list is refused. ORCHESTRATE and the root card say nobody merges a held PR. `ListPullRequests` also says why GitHub can't be read (`github_problem`: `no_gh` when the `gh` CLI is missing, `not_logged_in` when `gh auth status` fails; asked once a minute, nothing when it can't be told), so an app can say why "ready to review" is empty. Each row records the PR's head branch (`head_ref`, GitHub's `headRefName`): the `[mesh reviews]` footer of a worker's `done` calls a PR the worker's own when its head is the worker's branch (one the branch lookup found counts as its own even with no head branch; with none of its own recorded the first link in the `done` that no recorded head branch rules out).
- **Projects** (`projects.go`; `mesh projects [--repo <path>]`, `ListProjects`, a root, a device or a read-only device): the git folders directly under the `repos.dir` folders (hidden ones skipped) and every repo an agent worked in, newest used first, each with its default branch (`origin/HEAD`) and its newest 40 branches as refs a worktree can start from (a local branch by its name, the remote's as `origin/<name>`), all from git with no network. With `--repo` it is that one repo (by the path the list gives it; a root or a device may name any repo on the host), fetched from its origin first (a failed fetch is ignored) and with its open pull requests from `gh pr list` (none when `gh` fails; `cross_repository` marks a fork's); a read-only device may name only a listed repo (a read action touches no other) and gets the refs last fetched and no pull requests, no fetch and no `gh`. The desktop's New workspace dialog starts a worktree from a PR with `base` = `origin/<head>`, and shows a fork's PR as unavailable (its head is no ref of origin).
- **Worktree extras** (`worktree_include.go`, `changes.go`, `progress.go`, `archive.go`, `editor.go`). **`.worktreeinclude`**: a file at the top of a repo, in `.gitignore` syntax, listing the git-ignored files (a `.env`, a local config) a new worktree gets a copy of when it is made (`SpawnAgent`, `CreateWorktree`, and a worktree made again on resume); only files that git ignores (a directory the list names whole but the repo ignores in part is looked at file by file), regular files only (a symlink is never copied and nothing whose real path leaves the repo), written through a handle on the worktree (`os.OpenRoot`) that refuses a path leaving it, and into directories made one component at a time that refuse a symlink (the handle follows one that points elsewhere inside the worktree), so a symlink in the checked-out branch can't redirect a write, never over an existing file, a cap of 0 copying nothing, at most 5000 files and `worktree.include_max_mb` (default 50) megabytes in all; a list that is a symlink or over 64 KB is ignored, and what was left out is logged. **`GetAgentChanges`** (`mesh changes`; a root, a device or a read-only device) reads the agent's worktree with git and no optional locks: the files that differ from the commit its branch started at (uncommitted ones and untracked ones included, at most 200, most changed first), how many are uncommitted, and the commits past its base and those no remote branch has (`rev-list <tip> --not <base> --remotes`); an archived agent's is read from its branch. With `with_ignored` (`mesh changes --with-ignored`; the Archive dialog asks once when it opens, the side panel's poll never, because it walks the worktree) it also lists what archiving would delete that git ignores (`ignored.go`): a file or a whole ignored folder (`node_modules/`) with its bytes (counted up to 20,000 files and 5 s: `partial`), largest first, at most 20 and `ignored_more` for the rest, counting only what a restore does not give back: a file `.worktreeinclude` names is left out only when the repo's own checkout holds the same bytes (a restore copies from there, up to its cap, never a symlink), so a worktree's own or edited `.env` is listed. The walk stops at the time budget, 20,000 files an entry or a folder it can't read (`partial`), and counts a symlink as itself. It informs and never refuses: nearly every worktree has build output, so a refusal would be ticked through blindly. **`GetAgentProgress`** (`mesh progress`) reads a Claude agent's session file from its end: the newest `TodoWrite` list of the main conversation (within the last 16 MB; its input shape is the tool's documented one, `todos[{content,status}]`, with no fixture from a real session yet) and the conversation's size, with a window guessed from the model's name (1,000,000 for a `1m` model, else 200,000); any other CLI answers `supported: false`. It also answers, for every CLI, what the agent **waits on** (`wait`, `wait.go`: a background command it started (Claude: the command line), a wait it declared (with its deadline), the answer to its newest question or plan, a `done` or `failed` it sent for its current task, else a message, from its parent or `user` for a root; first match wins, and it means something while the agent is idle) and, for a Claude agent, the **context marks** (`marks`: the points where the daemon acts on its conversation, below the window only: a lead's `root_reset.at` while `root_reset.auto` is on, a planner's `compact.approve`, a worker's `compact.followup` and `compact.claude`; none for a plain agent). **`ArchiveAgent`** (`mesh archive`, a device only) retires a worker (a root, asker or reviewer is refused: they are not made again when resumed) and removes its worktree with `git worktree remove` (never forced), keeping the branch: it refuses a worktree another agent shares while that agent is alive or its run is open, and while the worktree has uncommitted changes (always) or commits no remote branch has (unless `force`), checks again once the process is gone, under the worktree's lock (a resume or a message waits for the removal, and the agent being resumed or its worktree shared by then refuses the call), refuses a call past its expiry before it retires anything, removes only a worktree under the daemon's own folder (never the user's checkout), and, once the process and anything it left running are gone and the work is read again (a work git can't read refuses too), records the mutation, `archived` and an `AgentArchived` event in one write after the removal (a call that fails half way leaves the agent retired and a retry carries on; a retry of a finished call gets its first answer); a message to the agent or `ResumeAgent` makes the worktree again from the branch (and clears `archived`). **`OpenInEditor`** (`mesh open-in-editor`, the host's own device only) runs `editor.command` (default `code`, split on spaces, no shell, found on the login shell's PATH) with the path as its one argument, resolved through symlinks and required to be inside the agent's worktree; `editor.command` can be changed only from the host's own device (a root could otherwise pick what runs on the user's click). **`SetTailnet`** (`mesh set-tailnet`, the host's own device only; turning on first asks the binary's `tailnet.CheckBuild`, and turning off while `--tailscale` runs also clears a stale marker) writes or removes `<state>/tailnet-on`, which meshd reads at start like `--tailscale` (the flag wins and can't be turned off from the app); under a service manager (`INVOCATION_ID` set and systemd its parent process: a meshd started by hand from inside a unit inherits the variable but nothing would restart it) meshd then stops cleanly, a moment after the answer and never after a failed or replayed call, and exits 75 so its unit (`Restart=on-failure`) starts it again, with the terminal host and the agents' terminals untouched, and otherwise the answer says a restart is needed. **`CreatePairing`** refuses (`failed_precondition`, with the cause) when the link would carry no address: no relay, no `--listen` address a device could reach, no running tailnet node and no `direct_url` given.
- **Held tasks** (`held.go`; `mesh send <agent> --type task --after <task id>`, `mesh held`, `mesh cancel-held --id <id>`, `ListHeldTasks`, `CancelHeldTask`). A task sent with `after` (a run's lead or a device; a task of the same run, the id in its `mesh inbox` header) is stored in the `held_tasks` table (migration 0015), not as a message, and the response says `held` with its id. When a `done` for that task is stored (`Message.re`), the daemon sends the held task through the whole `SendMessage` path as its sender, in the background, with the mutation id `held:<id>`, so every rule applies at that moment (the reserve, `takeChange`, a stopped agent's resume) and a restart in between sends it once. A sweep every minute (and at start) sends or drops what a restart or a busy host left (an error that is no refusal of the task keeps it held), and drops a held task whose run closed or whose agent is gone. A task whose dependency was already done goes at once, one whose dependency already failed is refused, and so is `--after` a task for the run's root (it reports to nobody) or a held id; a report of the recipient that names a later task sent to it (a follow-up) answers the earlier one too. A task whose agent could not be resumed when it was due is stored for its next resume and the lead is told. Revoking a device drops what it held. A `failed` for the task drops the held one; a refusal when it is due (a closed run, a retired agent that can't resume, the reserve) drops it too: the run's lead gets a `[mesh held <id>]` info with the reason (nothing for a run that is over). The lead's `mesh brief` lists what it holds. A held task sits in no inbox, doorbell, event or report rule until it is sent.
- **Run rename, view requests and model history** (`mesh.go`, `view.go`, `history.go`). `RenameRun` (`mesh rename-run`, a device or a root for its own run) changes a run's title and writes a `RunRenamed` event (`mesh log`: `rename`). `OpenView` (`mesh open-view --view agent|terminal|messages|plan|pr|settings|run --target <name>`, a device or a root; a root only for its own run and agents) asks the user's apps to show a view: the host sends a `ViewRequest` frame (ephemeral, like `AgentActivity`: never stored or replayed) to the live `SubscribeEvents` streams of devices that asked for activity (an app) and answers how many it reached; an app shows it as a toast the user opens or dismisses, and switches by itself only when `app.open_views` is on (a setting only a device may change, never an agent) and the user isn't typing; an agent may ask once in 10 s (`resource_exhausted` otherwise), and a target is looked for inside `run_id` when one is given (an agent's own run always). The daemon resolves the target, so the frame names ids: `messages` an agent's messages (or a run's lead's), in its chat on the desktop and in the Messages tab on Android, `plan` its author's newest plan (`message_id`; refused with none sent), `pr` a stored pull request by URL or `#number` and the agent that owns it (`agent_id`; a number two repos share is refused). A view asked while no app is connected is lost, not queued: `delivered` says so and the agent writes to the user instead, and a queue would be per-device state (expiry, order, a repeat when two apps connect) for a request that is only worth "look at this now". A held, answered or failed permission prompt's `asked` event is written in the same transaction that tells its parent, and the prompt is listed only then. `GetAgent` also lists the models the agent ran on (`model_history`: its spawn, then each reopen that changed its model or effort, from the run's events).
- **Autonomy** (`autonomy.go`): `repos.user_merges`, `repos.user_approves_plans` (repos by path or folder name) and `autonomy.ask_before` (free lines) are policy leaves the root's brief prints, and only when set, as what the user keeps for themselves (a repo they merge, one whose plans they also approve, what to ask first); a repo in no list is handled as before, so with all three empty the brief is unchanged. A run can start with autonomy of its own (`StartRun`'s `autonomy`, `Run.autonomy`: `user_approves_plans`, `user_merges`, `ask_before`): the brief then prints that for every repo of the run in place of the repo lists, with `ask_before` added to the settings' list, and `keep_repo_lists` keeps the repo lists and only adds `ask_before` (a level and the lists are trimmed and cut to 20 lines of 200 characters). Nothing enforces them on the host: the root acts on its brief (ORCHESTRATE, "Rules for everyone").
- **The root's weight** (`docs/cost-research/roles-and-reviews.md`, "The root's weight"). `ReadInbox` for a **root** returns a `plan` or `done` longer than `inbox.summary_over` characters (default 2000, 0 off) as a summary (`inbox_summary.go`): a plan's title and header, its `##` sections with their sizes and its "Open questions / risks" whole, a report's first ~1,200 characters and the pull requests it names, then the file the sender keeps it in (`plans/<name>.md`, `reports/<name>.md`, when it holds the same text) and `mesh inbox --id <id>` for the whole message. The stored message is never changed; `--full` prints every body whole, `--id` one message of the caller's (marking it read unless `--peek`). Workers, askers and reviewers always get whole bodies. `CheckAgent` (`mesh check <worker>`, `check.go`) prints a change worker's commits past its base (its start commit, or the newest commit of the default branch it has merged in: what main brought is not counted, nor are merge commits), the diff stat, whether the tip is pushed and the worktree clean (and the dirty files), and its PRs with their checks, read from GitHub now (a read-only device gets the stored PRs, with no `gh` call): one call for the fetch, diff, status and PR reads a root chained by hand. A daemon-launched Claude root's launch denies its Read tool `ORCHESTRATE.md` (`claude.ProcedureReadRules`: the path as given and as a symlink resolves it); it reads the part for its step with `mesh protocol <part>` (`Questions and reviews` is split into `reviewing-a-pr` and `after-the-answer` so no part is 9 KB).
- **`mesh brief`** (`GetBrief`, `brief.go`): the run, the root card (a root's), the `NOW:` pointers (`mesh protocol root.6` before a plan, `root.8` before a done), the root's context, the model notice (`ModelNotice`: new or retired model families, a root's only), `notes.md` and `board.md` (4000 characters each), the agents and what waits on the root (a plan or question until answered, a `done` or `failed` until the root has read it), each worker's pull requests (`PR #12 merged, checks failing`; a worker that reported `done` with none says its commits, whether they are pushed, `no PR` and `worktree dirty`; `in review (<reviewers>)` while a review round still waits on a reviewer), for the root only, unread mail headers (marks nothing read) and the last reset with the old transcript as an untrusted reference. **`mesh protocol [name]`** (hand-written, `internal/cli/protocol.go`) prints one heading of `ORCHESTRATE.md` or `PROTOCOL.md` by its slug, `protocol`, `root-card` or `root.<n>`, from `$AGENT_MESH_SHARE/protocol`.
- **The SessionStart reminder** (`reminder.go`): a Claude `SessionStart` of source `compact`, `clear` or `resume` returns `ReportHookResponse.context`, which `mesh hook` prints and Claude adds to the session: a root is told to run `mesh brief` (silent while its reset is typing), a worker gets its identity, run folder, protocol, current task (the task text up to 2000 characters, and the newest answer: a worker can't read messages again), phase and "run `mesh inbox`", cut to Claude's 10,000-character cap from the middle (`hookText`). A hook that can't reach the daemon prints a short fallback.
- Tests: `compact_test.go`, `reset_test.go`, `brief_test.go` run the fakes (`fakeclaude` handles `/compact`, print mode and a `compact_boundary` in its transcript, and logs what is typed); `internal/adapter/*/context_test.go` read crafted transcripts and conversation databases.

## Retire, stop, caps

- **Retire** (design §18). `RetireAgent` (its parent or a device) stops an agent's process on purpose and keeps its conversation: state `RETIRED`, token revoked, worktree and branch kept, terminal acknowledged; no `AgentExited`. A pending reopen is dropped. Anything its dying process or its spool still says is ignored. `ResumeAgent`, or a message, brings it back.
- **A message to a stopped agent** (`RETIRED`, or `EXITED` with a session) stores the message and requests the reopen in the same write: a `task` marked direct (it begins `Direct task`) resumes it direct, as one sent to a live agent is (it ends a plan phase and drops the planning deny list; not when it is an addition: sent to an agent that still owes its answer to an earlier task, with no `plan`, `question`, `done` or `failed` since, a `Direct task` is delivered like any task and leaves a planner planning, with no reopen: the planner is told so by an `info`; to skip a plan the parent uses `approve`, which a planner with no plan yet accepts). A planner counts as at work on its plan while it is starting, in a turn, or idle with a task or answer unread, and has reported nothing since its last task, any other task brings it back as it was (a planner still planning); for a task it plans on a tier use `ResumeAgent` with `plan`, an `answer` or `question` brings it back as it was. An `info` is only stored; it is read when the agent is next resumed. The response's `resumed` is the reopen. The message is stored in any case: when the resume is refused (the cap, the memory floor, a closed run, no conversation to resume) the agent stays stopped and the response's `resume_error` says why, so a report to a retired parent is never lost to the cap. Nothing is queued: the launch is not retried.
- **Idle retire.** A pass every `RetireEvery` (10 s) retires an agent that is IDLE, whose newest report since its last task or answer is a `done` or `failed`, and that stayed idle `idle_retire` seconds (0 never) since the later of that report and its last activity. Not a root; not one with a reopen pending, unread mail (work is coming, or a doorbell was lost), a `plan` or `question` waiting on its parent, or a client with input rights attached to its terminal (someone is looking). The check is repeated under the agent's lock inside the retiring write, so a message that arrives meanwhile either keeps it open or finds it retired and resumes it.
- **`StopRun`** (a device) retires every agent of a run and closes it (`RunStopped`); nothing starts or resumes in a closed run. A clean worktree is then removed, and its branch with it unless the branch moved past the commit it started at (`Agent.base_commit`, so a branch another one stacks on still counts), or has a remote branch of its name (a branch started from `origin/main` has an upstream for free: that is not work); a worktree with uncommitted changes stays, with its branch. An agent spawned while it runs is retired too, a pending resume on a stopped agent is dropped, and the processes are stopped together (one `StopWait` at most, not one per agent). The response says what happened to each.
- **`caps.agents`** (default `auto`; 0 no cap) limits agent processes on the host: starting, running, or a stopped agent whose resume is pending. A spawn or a `ResumeAgent` past it is `ResourceExhausted` (a message that would resume one is stored with `resume_error`), checked inside the write that stores the agent or the reopen, where the one writer makes the count and the record one step, so a burst of spawns can't all pass. A review round counts as one agent: its first reviewer has to fit, and the reviewers after it (and the earlier reviewers a re-review resumes) share its place (`withCapShared`; a re-review counts the reviewers already running as part of the round before it starts any, so the order of the slots never decides who the cap refuses; one whose slot then fails leaves the round's place and counts again), so a host one place short never starts the first slot and drops the second; a host with no room for the first reviewer holds the round for `review.wait_room` (below) and then refuses the whole round, and a peers group counts each peer. A switch or approve replaces a process and is never refused, and neither is the reopen a `Direct task` to a running planner requests to lift its deny list: each swaps one process for one, though the old one counts alongside the new until it exits. A direct task to a stopped agent is a resume and is refused like any (it stays as it was, planning). `auto` is worked out by `capacity.go` from the host: the memory and half the swap above `min_free_mb`'s floor divided by what an agent measured holds (its process tree's resident memory, at least `AgentMB`, measured every 30 s, reading `/proc` outside the sampler's lock), but no more than two agents per working worker, between 4 and 64. **`caps.working`** (default `auto`; 0 no limit) is the number of workers the root keeps working at once: the cores promised twice over, divided by the CPU a WORKING agent measured uses (its tree's user and system time, with that of the children it has waited for, so short builds and test runs count) (0.75 cores until three passes have seen one, clamped to 0.25 to 4). It is advice to the root: the daemon refuses nothing over it. `mesh brief` prints a `host:` line with the live and working counts against both, how they were sized and how many more agents fit now (the cap and the free memory above the floor, less launches still reserving), and `SpawnAgentResponse.capacity` carries the same line. A number set by hand replaces an `auto`. **A review round on a full host waits** (`review.wait_room`, default 5 min; 0 refuses at once): when the host has no room for the round's first reviewer (the agent cap, or the memory floor and pressure; not a quota), `Ask` stays open and looks every 2 s (`waitForRoom`, `ask.go`), then starts the round, with a note on how long it waited, or, past the time, refuses as before naming the cap. The check reserves nothing, so two rounds waiting for one place can both see it free and the loser is refused as before; a caller that gives up (Canceled) or a stopping daemon (Unavailable) ends the wait. Nothing is stored while it waits, so nothing has to survive a restart (a persisted queue of rounds would: a stored round state with its PR, body, tiers and caller, a loop woken by every retire and a state for the apps; not built); a round whose every slot has a running reviewer to reuse needs no process and never waits. The CLI and the relay set no overall timeout on a request, and meshd's servers only a header timeout; behind nginx the relay needs the long `proxy_read_timeout` of `docs/relay.md`.
- **The memory guard** (design §17) runs in the same places (with an early non-reserving check in `SpawnAgent` before creating a worktree, refreshed at `reopen` launch, released on closed-run cancellation, and seeded from adopted live terminals within `ReserveFor`): refused (`ResourceExhausted`) while memory plus swap free is under `min_free_mb` (`auto`: 10% of RAM plus 10% of swap plus 1 GB, at least 2 GB; 0 off) or `/proc/pressure/memory`'s `full avg60` is over `memory_pressure_max` (0 off). A launch that passes counts 400 MB used for 2 minutes, under its agent's id (a launch that fails gives it back), so four spawns in a row don't read the same free memory. `MeminfoPath` and `PressurePath` of the agent config point it at other files (tests); without them it reads `/proc`, and where there's no `/proc` it refuses nothing.
- **Process sweep and resource scopes** (design §17). On retire (`RetireAgent`, idle retire, crash-recovery adopt) and `StopRun` (before removing worktrees), `sweepWorktrees` waits briefly for the worker's own agent to exit and then sends `SIGTERM` followed by `SIGKILL` (checked by `StartTicks`) to leftover process trees in its worktree that hold no terminal and no agent CLI and hang off `init`/`systemd`, never touching main checkouts or roots. Every non-root agent launch (`startTerminal`) pins the process and its descendants to the least-held `worker_cpus`% core window (default 25%; `0` or `100` off) and, when `worker_memory_high` > 0 (default 0), places them into a transient `systemd --user` scope (`mesh-<name>-<pid>.scope`) with `MemoryHigh`. Adopted live non-root terminals restore their CPU holders on daemon restart. Both are abstracted behind `AgentConfig.Sys` (`SystemOps`) so tests never invoke real `busctl` or touch unrelated host processes.

**Adopted roots** (`mesh adopt`, `adopt.go`, `internal/cli/adopt.go`; the delegate skills' opt-in). A user's own Claude Code session becomes a run's root in place. `AdoptSession` (a device's call; `mesh adopt --run-id <run>` fills `pid` and `pid_start_ticks` from the nearest process above it with a session record under the Claude config folder) refuses a process that is gone or no Claude Code session, a session with no inbox socket or whose `crossSessionInbound` doesn't resolve to `accept` (the message names the line to add to the user's own `~/.claude/settings.json`: mesh never edits it), a session that is one of the daemon's own agents, a closed run, and a run whose root is another live adopted session. With no root in the run it creates an agent row (`<repo>-lead`, role ROOT, `adopted_pid`/`adopted_pid_start`, no terminal, worktree or branch: `Repo` is the session's cwd's top level); with a spawned root it retires that root (its process stops, its conversation stays on disk) and gives the **same row** (id, name, mailbox, workers) to the session. A fresh root token is kept in `<state>/adopted/<pid>.json` (0600), and the CLI, with no `AGENT_MESH_TOKEN` in its environment, walks up its process tree to a process with a file there whose pid still started at the recorded time and takes its `AGENT_MESH_*` variables: that session's `mesh` calls act as the root (the user's own commands, `stop-run` or `pair`, run in another terminal). Doorbells go through `deliverAdopted`: one frame into the session's inbox socket for the messages not rung yet, marked delivered (`via: socket`) when written, with no ring to follow and no typed lane (the daemon can't see the session's box). That is the one exception to "delivered only once the agent took its doorbell" ("Doorbell delivery"): a frame the session drops is not rung again, and the root finds the message with `mesh inbox` or `mesh brief`. The policy is read under the session's own cwd (its record's, as `AdoptSession` checked it; the row's `Repo` is the git top), and `AdoptSession` refuses while `delivery.socket` is off, since the socket is the only lane. A frame that can't be written (the socket, or a `crossSessionInbound` that is not `accept` where the session runs) is logged at Warn, shown in the agent's `state_detail` (`doorbells not delivered: <why>`, cleared by the next frame written) and tried again by the retry pass. Taking over a spawned root is one write (the retire and the adoption; its terminal is stopped after the commit, and a repeated call with the same mutation id changes nothing, except that a replay whose identity file is missing, because the first call's file write failed after its commit, mints a new token and writes the file; the file is written atomically, and a run's adoptions are serialized from the scan of its agents to the file), and the session's introduction to the protocol is sent again on its first doorbell. `mesh adopt` itself runs as the user's device even from a session that is a root already. `adoptedPass` (with the accountability pass) follows the process and the session record: a record's `idle`, `busy` or `shell`, and `waiting` show as IDLE, WORKING and NEEDS_INPUT, and a process that is gone makes the agent EXITED, revokes its token and removes the file. The daemon never resets (`ResetRoot` refuses), opens, stops, signals or resumes it (a message to an ended session is stored with a `resume_error` naming `claude --resume <session>`), and `StopRun`/`RetireAgent` only mark it stopped and revoke the token.

## Worker accountability

What `bin/mesh watch` did with exit codes (design, "The watchdog"), done by the daemon. A parent hears of its children as an `info` from the daemon (actor `mesh`, a message like any other: stored, doorbell at the parent's next idle). Nothing here reopens, switches or retires an agent: acting on a limit is the limits pass's job, this only tells the parent.

- **Exit and lost:** an agent whose process ends (or whose terminal is gone, `lost`) with no report to its parent since its last task or answer tells the parent how (`[mesh alert exited <id>]`: exit code, signal, or lost), in the transaction that records the exit, with `Its work: …` (below). One that had reported first is not alerted about. A stop someone asked for is told too.
- **Quiet and limited:** the pass (every `AccountEvery`, default 5 s) tells the parent once per stretch of silence that a child went `unknown` (`UnknownAfter`, default 10 min; `[mesh alert unknown <id>]`, with its work and the last lines of its terminal) or stopped `LIMITED` (`[mesh alert limited <id>]`: when its hold resets and what meshd does next by `limits.auto`, `switch` to the next model of the chain or `continue` at the reset, or, with it `off`, naming `mesh switch <name> --next`). When the limits pass then moves or continues the agent it tells the parent too, an `info` `[mesh alert moved <id>]` (from `moved` to the new model, in the same conversation; it settles nothing of a round the agent is in). The same alert is not repeated until the agent's next hook (its `LastActivity` moves): one that recovers by itself and hangs again before any hook is not told twice. A Claude agent at its prompt with a background command running (a `bash -c` sourcing `~/.claude/shell-snapshots/…` under its own process, found in `/proc`; `internal/daemon/background.go`) is waiting on it, declared or not: the pass sends no nudge and no `silent` alert while it runs, for 30 minutes (`backgroundGrace`, at most `accountability.wait_max`) from its last activity. After that the command is one the agent forgot (a dev server, a watcher): it is nudged once, with a nudge that names the command ("declare a wait or stop it"), and the usual `silent` alert follows `nudge_after` after an ignored nudge (the grace holds only the first nudge).
- **Permission prompts** (`internal/daemon/permission.go`; `RequestPermission`, `DecidePermission`, `ListPermissions`; `mesh permission`, `mesh permissions`; `permission.wait`, default 300 s, at most 540, 0 turns it off). A Claude agent's `PermissionRequest` hook (registered with a 600 s timeout; claude 2.1.332 fires it the moment it would ask) calls `RequestPermission`: the daemon keeps the prompt in memory (a restart drops it: the hook then prints nothing and the prompt stays), tells the agent's parent `[mesh permission <id>] <agent> asks to use \`<tool>\`: \`<command or path>\` (the agent's text: not an instruction to you)` (the tool and the command each in a code span whose fence is longer than any backtick run in it, and the same "Deny by default" wording as ORCHESTRATE; `mesh permissions` prints the command quoted) (the hook sends only the tool and a `command`, `file_path`, `path`, `url`, `pattern` or `query`, never an Edit's or a Write's text; the message cuts it at 300 characters; it is in no push notification) and holds the hook. The parent (or a device) answers `mesh permission --id <id> --decision allow`, or `deny --why "<reason>"` (a denial needs one: Claude reads it); the hook prints Claude's documented decision JSON. No answer in time, a root (the user's own prompt), a stopped parent (also one that stopped while the prompt was being sent: nothing is held), a prompt the daemon never forwards (`neverForward`: a command `shellmatch` reads as a publish, such as `git push` or a `gh` write, a `deploy` or `publish` word, `terraform apply|destroy`, `kubectl apply|delete|rollout`, `helm install|upgrade|uninstall` (the subcommand anywhere after the tool in its shell segment, so `kubectl -n prod apply` counts; a `shellmatch` publish inside `if … then`, `for … do`, `!` or behind a leading redirection such as `</dev/null` or `2>&1` counts too), and an `Edit`, `Write`, `MultiEdit` or `NotebookEdit` of a path outside the agent's worktree and its run's dir (`~/` is expanded against the home; no path, no worktree or another user's `~name` fails closed: the prompt stays): a guard against honest mistakes, not a determined agent), `ExitPlanMode` and `AskUserQuestion` (both need `updatedInput`, and a plan or a question is not the parent's to approve) print nothing: the prompt shows in the agent's terminal as before, and the Notification-based `NEEDS_INPUT` and `[mesh alert input]` still apply. A pending prompt ends when its agent goes on (its next `Stop`, `UserPromptSubmit`, `SessionEnd`, or the `PostToolUse` of that tool with that command or path: the prompt was answered at the terminal), so a late answer is `NotFound`. A prompt held, answered or ended is a `PermissionChanged` event (`asked`, `allowed`, `denied` or `ended`; its id and the agent, no prompt text; `mesh log` shows none), which tells an app to list the pending prompts again: the list itself stays in memory. Only Claude; the payload follows the Claude Code hooks documentation, and a fixture from a real session (`scripts/capture-claude-hooks.sh`, by hand) is still to be added.
- **CLI probes never open a login** (`internal/probe`, `internal/daemon/agylogin.go`). meshd's `agy -p /usage` probe once opened the user's Google login when agy's token refresh failed in the headless run, and retried every two minutes. Every probe (`agy -p /usage`, `agy models`, `opencode models --verbose`) now runs through `probe.Run`; the Claude usage reading is an OAuth HTTP call and Copilot's is file reads, neither can open a browser. A probe that tries to open one is killed and recorded in `<state>/agy-login-needed` (the time and a signature of agy's token file's mtime and size, never its content): `mesh usage` then shows "agy needs `/login`" (`GetUsageResponse.notes`), the root of each open run with an agy agent is told once `[mesh alert login agy]` (the alert is keyed on the condition, not on the record, so the record's renewals every 30 minutes don't repeat it; again a day later while it still is, or after a login and a new logout), and agy is not probed again for 30 minutes unless its token file changes. A record whose token file changed since (the user logged in) is stale: no note, no alert and no hold follow it until a fresh probe fails. A successful `agy -p /usage` or `agy models` clears the record. **No token file, no run:** an agy found on PATH (`agyBinary()` falls back to `exec.LookPath("agy")` outside go tests, which is how a dev or test meshd with a temp HOME reaches the real CLI; a binary the config names, a test's fake, is not checked) is not run at all (`-p /usage` and `agy models` alike: the adapter's `Hold`, which also holds while a login record does) while `~/.gemini/antigravity-cli/antigravity-oauth-token` under the HOME meshd uses is missing (a logged-out agy opens a Google login in the user's browser; with no agy installed at all nothing is blocked and `mesh usage` says it is not found): the probe reports "agy needs `/login`" as if it had been caught (a record that already holds is not rewritten, so its time, the hold and the alert's key stay). A probe's stderr comes back in its error; a pending permission prompt ends with the oldest one for a finished tool call (same tool and command), and a decision that arrives as the wait expires is still delivered. The token's age is not looked at, since a refresh is the normal path. An agy worker's own terminal is not a probe: it shows agy's login itself.
- **A prompt nobody answers:** an agent at `needs_input` (a permission prompt or a question) for `accountability.input_after` seconds (default 120; 0 never tells) tells the parent once per prompt what it asks (`[mesh alert input <id>]`) and that a person answers it in its terminal; the app lists it as waiting.
- **A stalled OpenCode reply:** an OpenCode agent at WORKING whose open reply (`opencode.db`: the message row and its newest part's `time_updated`) has not changed for `opencode.stall_after` seconds (default 900; 0 never tells) tells the parent once per stretch (`[mesh alert stalled <id>]`; `openCodeStalled`, `opencode.go`). A limit is read first, from the DB or the screen; a stalled stream shows no limit line. The poll looks at the DB when the terminal draws and, for a terminal with nothing new drawn, every `min(stall_after, 1 minute)` once it has been quiet that long. One long tool call looks the same (a part is written at its start), which the alert says. An agent the view already shows as UNKNOWN (ten minutes with nothing heard) is told by that alert alone: one hang is one alert; a stretch of the reply is told once, and a reply that recovers and stalls again is told again (keyed on the reply's update time, not the agent's activity).
- **A failed turn:** an agent whose last turn failed (`AGENT_STATE_ERROR`: an API error, a login that expired) with no report to its parent tells it at once (`[mesh alert error <id>]`, with the error and the last lines of its terminal). An expired login (an error reading as authentication) says to ask the user to run `/login` in its terminal, then send it a task, and the agent is not nudged (its turn would fail again on the same login); any other failed turn is also nudged like a silent one.
- **A turn without a report:** an agent at its prompt that was given a task or answer, and has sent no `plan`, `question`, `done` or `failed` since, with nothing unread in its inbox (the daemon's own mail aside, except a finished round's `[mesh answers]`, which counts), is nudged once after `accountability.nudge_after` seconds (default 30; 0 turns nudges off): an `info` from `mesh` saying how to report. If it then has a turn (the nudge's doorbell rang) that ends the same way another `nudge_after` later, its parent is told once; a nudge whose doorbell is held back (a user typing) is not counted against it (`[mesh alert silent <id>]`, with its work, the last lines of its terminal and, when it had declared a wait, that the wait is over). A new task or answer starts the count again, and so does a `wait` declared after the nudge: it answers it, so an agent woken by each of several background jobs and ending each turn still waiting (`mesh send parent --type wait` before each) is nudged again at most once per wake, never alerted, while one that ends a turn with no report and no fresh wait after its nudge is told to its parent as before.
- **A declared wait** (a `wait` message to the parent, which rings no doorbell) holds the nudge for `accountability.wait_max` seconds (default 4 h) from when it was sent, or until its own deadline when it has one (`mesh send parent --type wait --until 45m`: a duration or an RFC 3339 time, stored on the message as `wait_until`, capped at `wait_max`, refused when negative, zero, unparsable, on another message type, or on a wait to anyone but the sender's own parent), or until the next task or answer, **or until the agent wakes**: activity after the turn end that declared the wait (`waitTracker`: the pass's first reading of a wait is its baseline, so a wake before a daemon restart is missed and the wait then holds to its deadline), after which a turn that ends with no report is judged as any silent stop (one nudge, then the parent told). A wait with no deadline of its own that nothing the daemon can see would wake the agent from holds only `accountability.wait_unseen` (default 15 min; 0 off): a Claude agent's `run_in_background` command or Monitor sends a notification when it ends and is seen (a `bash -c` of a shell snapshot under its terminal, `background.go`), but a job started with `nohup … &` is neither (a root slept 2 h 51 min on gates that had finished), nor is anything of another CLI's agent; then it gets one nudge (`waitNudge`) that says why and asks for a report or a fresh wait with `--until`. A wake by a background job's notification is not told apart from any other (the job the agent waited for ends with one too), so the protocol has the agent declare a fresh wait at each turn it ends still waiting (`PROTOCOL.md`, "Waiting on purpose").
- **What an alert adds** (`evidence.go`; `bin/mesh`'s `evidence_line`, `wait_note` and `with_tail`): `Its work: 3 commit(s) past its base, pushed, PR #12 open, worktree dirty.` (commits, whether the tip is on its upstream, open PRs from "Pull requests" below, `no PR`, or `PRs not read` when GitHub was never read for it since the daemon started, a dirty worktree; git read-only, with no call to GitHub inside the exit write); the last 15 lines of the agent's screen for a `silent`, `unknown` or `error` alert (a repaint read as the delivery guard does). Dropped from `bin/mesh watch` on purpose: its exit codes and `--alerts`/`--any`, herdr pane states (held at a startup screen, a pane that runs no process), a report that sat unread with no doorbell rung (delivery retries, and the message is stored), and the retire and continue log lines (`mesh events` has them).
- **Unread instructions:** `SendMessage` refuses a `plan`, `question`, `done` or `failed` from an agent while a `task` or `answer` is unread in its inbox (`FailedPrecondition`, nothing stored): it would answer instructions the agent hasn't read. `mesh inbox` reads them; `info` and `wait` are not reports and go through.
- **The task a report answers:** a report (`plan`, `question`, `done`, `failed`) to the sender's parent is stamped with the sender's current task, the newest `task` sent to it (`Message.re`; `mesh inbox` shows `(m9, on task m3)`). A report that names a task (`mesh send --re <id>`, the id in the task's inbox header) must name the current one: for an older task, any report after a `done` for the task, or a second `failed` (a `done` after a `failed` goes through; a later `task` or `answer` opens it again), `SendMessage` refuses (`FailedPrecondition`, nothing stored) and names the current task; `--re` on any other message is `InvalidArgument`. A report with no `--re` is stamped and let through, as before. There is no separate dispatch id: a task sent again is a new message with a new id.

## Doorbell delivery

`bin/mesh`'s guarantees (design §3 and §11), kept by the daemon (`internal/daemon/delivery.go`, `internal/inputbox`, `internal/adapter/claude/inbox.go`). A message is stored first; the doorbell only tells the agent to read it, and a message counts as **delivered** (`MessageDelivered`, with `via` and `tries`) only when the agent is known to have taken the doorbell. Until then it is unread and undelivered, and the 2-second pass rings it again. **One exception:** a session the user adopted as a root (`mesh adopt`) has no hooks to take a ring from and no box to read, so its message counts as delivered (`via: socket`) once the frame is written into its inbox socket; a frame it drops is not rung again, and the root finds the message with `mesh inbox` ("Adopted roots").

- **Lanes.** A Claude agent's doorbell is written into its inbox socket (`DeliverNative`, setting `delivery.socket`): one JSON line `{"type":"user","message":{"role":"user","content":…}}`, which Claude Code takes as a prompt (an idle session starts a turn). It never touches the input box, so a user typing or a draft doesn't hold it. Every Claude launch carries `crossSessionInbound: accept` in its `--settings` (the root's too: it is launched by the daemon), which beats the user's own value, and the check reads the flag the process was *launched* with from its command line (`/proc/<pid>/cmdline`), so an agent started before the flag existed, or adopted, is typed to. The socket is used only when the process's own record (`<config dir>/sessions/<pid>.json`) names it and its `procStart` is the terminal's process start (a later process at a reused pid is not the agent), the path is a socket of this user, and the settings still accept: Claude Code's precedence is read as `inbound_setting` reads it (managed policy and `managed-settings.d/*.json`, then the flag, then the user's settings; a repo's `.claude/settings*.json` may only tighten it; an unknown value holds). A write is never repeated (Claude Code delivers a repeated frame again). Any other adapter, a Claude agent without such a record (`CLAUDE_CODE_HARBOR_KITE=0`, a wrapper script that doesn't `exec` claude, managed policy that holds), and a terminal whose frame wasn't taken (below) get the doorbell typed. `send_message` (the sender's `SendMessage`), its Stop-hook backing and `Watch.lost_report` of `bin/mesh` have no counterpart: they existed because a sender had to ring a bypass-mode root itself, while here the daemon writes every frame and the confirmation below catches a lost one.
- **Confirmation.** Every typed or written doorbell carries a fresh `(ref <token>)`. It is confirmed by the agent's first activity **after** the ring (a hook or poll event timed after it, so a late event of the previous turn doesn't count; `via` `turn`, or `socket` for a frame; for a frame as for a typed doorbell only once the agent has left its prompt, as an event with the agent still at the prompt may be a late or polled one, and then its token on the screen decides, `screen`), by the agent reading the messages (`read`, which marks them delivered, also after a doorbell was given up; one that read only some leaves the rest to be rung; a read doesn't count as the agent having seen the protocol pointer, so the next doorbell repeats it), or by its token showing above the input box (`screen`, read at every pass once there was activity, else once `delivery.confirm_after` has passed). Not confirmed by then, a frame is typed instead for that terminal for the next ten minutes (`nativeOffFor`; a policy the daemon can't read holds it; at worst one duplicate, and one more when the socket is tried again), and a typed doorbell is rung again with a new token, up to `delivery.ring_tries` doorbells (the socket write counts as the first, so the fallback to typing is within the cap); after that one `DoorbellFailed` event says so and nothing more is typed until the agent's activity moves or a new message arrives. A restart of meshd forgets the rings in flight: their messages are still undelivered and ring again (a duplicate doorbell at worst, never a lost one). The first doorbell of a process, which names the protocol, repeats the pointer until one is confirmed.
- **Never into a human's draft.** Before typing, the daemon reads the screen (a repaint, as a client attaching sees it) and asks the agent's adapter what its input box holds (`ReadInputBox`; `internal/inputbox` ports `bin/mesh`'s `typed_text`, `gutter_typed` and `ghost_styles`: Claude's rules box with a dim placeholder (and, when its terminal has the focus, the cursor it paints on the placeholder or the suggested prompt: the first character inverted, `\x1b[7m` … `\x1b[27m`, the rest dim, which is ghost text too: read as typed it held every chat prompt, "a draft: r" in an empty box), agy's with a colour-8 one, OpenCode's `┃` gutter box with its status block and `Ask anything…` placeholder). Typed text that isn't one of our own doorbells is a draft and holds the doorbell, which waits (the 15 seconds after a client's keystroke, `TypingQuiet`, still hold it too: they cover a user typing right now, the screen a draft left by someone who detached); after `delivery.draft_hold_alert` one `DoorbellHeld` event says so, and it is still never typed into the draft. A box of ours holding a doorbell nobody submitted gets Enter alone, not a second doorbell fused to it. Anything unclear (no box, which includes a dialog the hooks didn't report; no closing rule; a status block that can't be told from text) fails open for a first try, which types the line and Enter, as in `bin/mesh`; a **retry** types only into a box it reads as empty (or ours): with no box on the screen (a dialog, an alternate screen) it counts the try and waits, so Enter never lands on a dialog.
- **The same guard for typed commands.** A live `/compact`, a reset's `/clear` and its bootstrap line ask `quietToType` before they type: nobody typing, and no draft in the box (a box that can't be read doesn't hold them); they wait for it as long as their own timeouts allow.
- **One at a time.** Every write into an agent's terminal (a doorbell, a reopen, a stop) holds the agent's lock, which is `bin/mesh`'s per-pane `ring_lock`; the lock is never held across the wait for a confirmation.
- **A Claude agent relaunched outside the daemon** (`reopen_relaunched`) can't arise: `mesh-term` execs the CLI as the terminal's own process (no shell), so nothing relaunches a Claude in a daemon terminal without the daemon; a process the host lost is brought back only by the daemon's resume or reopen, which plans the launch again with the deny list. Both lanes address only the terminal's own process (the socket by its pid and start time), never another Claude session.

## Push

**Notifications** (`internal/daemon/notify.go`, run by the pusher's dispatcher after each commit) are decided once, by the host: each committed event may make a notice, which is stored as a `UserNotice` event (kind, title, body, agent, tab, `for_user`, tag) that the apps' notifications and Activity list and the phones' pushes all follow. `for_user` is the user's to act on or know: an agent at a prompt, at its usage limit or in error; a worker's plan to a lead only where the user approves plans (`Run.autonomy`, else `repos.user_approves_plans`: the same test as the lead's brief, `userApprovesPlans`); a message the lead put to the user (below); a PR that became ready to merge (open, not a draft, checks pass) where the user merges or held it; a permission prompt held for a lead that nobody answered in a minute; a lead or plain agent that exited; **finished**: a plain agent (no parent) that ended a turn, or a run whose lead ended a turn when every other agent is exited, retired or idle having sent `done` or `failed`, nothing waits on the user and no prompt or message to the lead is left (once, until the lead works again or an agent is spawned). Not `for_user` (Activity only): a worker's or reviewer's plan, question, report or failure to a lead that decides it, a worker's exit. `ListWaiting` marks each item `for_user` by the same rule, and the apps list only those. **`mesh send user --type question|plan|info`** (`SendMessage` with `to: user`, a lead only) stores a message in the run to the user, never delivered to an agent; a question or plan waits (`ListWaiting`) until the user answers the lead (`mesh send <lead> --type answer`), which reaches it as any answer.

Notifications that reach a phone with its app closed, through UnifiedPush (`internal/daemon/push.go`, docs/apps.md "Push"). The app registers one endpoint per host with `RegisterPush` (its distributor's URL, such as a ntfy topic, and the device's WebPush keys); meshd keeps one per device (migration 0010) and, for each notice the daemon decides on (`notify.go`, below) that is for the user and that the host's `app.notify.enabled` / `app.notify.events` let through, POSTs it to every registered endpoint. A device may choose its own list of kinds (`RegisterPush.events`, migration 0014, the Android app's settings): it is pushed by that list instead of the host's `app.notify.events`, which an empty list follows again; `app.notify.enabled` off still pushes nothing to anyone, and an unknown kind is refused.

- **Encrypted.** The push carries the notice itself (`{"v":1,"daemon","seq","kind","title","body","agent","tab","at"}`, the body cut to 200 characters), encrypted for the device's keys per RFC 8291 (`aes128gcm`), so the push server (ntfy.sh, say) sees ciphertext and the phone shows it without reaching the host. No VAPID. Headers: `TTL` one day, `Urgency` high for what waits on the user, `Topic` per agent (a newer push replaces one the server still holds).
- **Retries.** 2xx is delivered; 404 or 410 means the endpoint is gone and it is deleted; another 4xx drops that push (its error is noted, but it doesn't count as the endpoint failing); 429, 5xx and network errors are retried after 2 s, 10 s, 30 s, 2 min and 10 min (or the server's `Retry-After`, at most 10 min), then dropped. A registration whose every push has failed for 7 days is deleted at its next failure. The queue is in memory (32 pushes per endpoint, oldest dropped): a restart loses what was waiting. `OnCommit` only hands events over; one dispatcher reads agents and settings (and remembers agents from their `AgentSpawned`, since a failed launch deletes its agent in the transaction that reports the exit), one sender per device endpoint keeps its order, checks before every try that the device still has that endpoint (nothing goes to a revoked or replaced one), and stops when it doesn't. `RegisterPush` with a new endpoint, `UnregisterPush` and `RevokeDevice` stop the device's other senders at once (a replay of an old call doesn't), so pushes for a new endpoint never wait behind the old one's retries; new keys for the same endpoint stop its sender too (what it holds was encrypted for the old keys), and so does a `TestPush` that finds the endpoint gone. A stopped sender drops what it holds, and a shutdown starts no new one; a job encrypted for keys the registration no longer has is dropped.
- **Who.** `RegisterPush`, `UnregisterPush` and `TestPush` are open to DEVICE and READ_ONLY_DEVICE, each on its own endpoint; the host's own device may name another (`mesh unregister-push --device-id`, `mesh test-push --device-id`). An endpoint must be `https://` (plain `http://` only to a loopback host), and meshd connects only to a public address, checked on the address it dials after DNS (not loopback, private, link-local, unspecified, CGNAT (so a tailnet too) or another special-purpose range, nor NAT64 or 6to4 wrapping one) unless `push.allow_private_endpoints` is on (a ntfy on the host, the LAN or the tailnet; the tests turn it on). Only the host's own device may change that setting, since it guards the host against the paired devices. The client uses no proxy, keeps no connection open between pushes (each dial is checked) and follows no redirects, so meshd posts ciphertext to the URL the device gave and nowhere else, and a device sees only the push service's status, never its reply (that goes to meshd's log). `TestPush` records its mutation only once the push service took the push: a retry of a failed call sends again; a mutation id used for another call, or a request past its expiry, is refused before anything is sent. What is left, accepted for paired devices: a device can make meshd POST ciphertext to any public `https://` host (and, with the setting on, to the LAN or a loopback `http://` port), and tell a network error from an HTTP status in `TestPush`'s answer. A test push that went out is recorded even if its request expired, or its caller left, during the post (the post finishes regardless), so a retry doesn't push twice. No error names the endpoint's path or query: a network error says the host and what failed. An endpoint registered by a second device (the phone paired again) moves to it. `RevokeDevice` deletes the device's endpoint. `mesh devices` shows each one's host, last success and last error (the URL is a capability and never shown or logged).
- **Tests** run a fake push service on loopback (`push_test.go`) and decrypt with the device's key; `internal/webpush` is pinned by RFC 8291's own test vector, and Android's `DaemonE2ETest` decrypts a real meshd push with the UnifiedPush library's decryptor.

## Protocol and skills

`share/` is what a daemon agent reads and the skills it can use, written for the daemon's events (a message rings at the recipient's next idle; no watch process, no exit codes, no panes) and for the commands the Go CLI has. `internal/cli/share_test.go` fails when a file names a `mesh` command or flag that doesn't exist, unless its sentence says "yet" (and then gives the manual way).

- **`--share <dir>`** (default `../share` of the `meshd` binary, which is the installed `~/.local/lib/agent-mesh/share` or, in a dev build, this folder; ignored when it has no `protocol/`). Every agent gets `$AGENT_MESH_SHARE` (the absolute path).
- **The setup agent** (`internal/daemon/setup.go`): `StartSetup` (`mesh setup`, a device only) starts, or returns, the first-run setup agent: a lead agent (role root) in an open run flagged `setup` (title "Setup"), launched on the `mid` tier of the first installed CLI (`claude`, `agy`, `opencode`, `copilot`, or the `kind` asked for) in a scratch git repo of the host's own, `<state>/setup`, so the worktree machinery needs no special case. It is `setup-agent`; a retired or exited one is resumed on the next call, so the apps land on one agent. Its first message is a one-line task and its first doorbell names `protocol/SETUP.md` (not the root card): what it does is that file's markdown (read the host, ask what to connect, do it through `mesh`, ask before a restart or a file write), so extending it is editing the file. It is a root in every other way, with three more rights, and only while its run is open and flagged `setup`: `CreatePairing`, `ListDevices` and `TailnetStatus`, which only the host's own device may otherwise call (`requireHostOrSetup`; `RevokeDevice` and `StartRun` stay the device's). A daemon with no share folder, or one without `SETUP.md`, refuses with that reason.
- **Skills per launch:** a Claude agent is launched with `--plugin-dir <share>` when `<share>/.claude-plugin/plugin.json` exists, so the skills load for that session only (as `<plugin name>:<name>`), never into the user's own `~/.claude`. The user's own copy of the mesh's plugin (`agent-mesh` from the repo's marketplace) is turned off for that launch (`enabledPlugins` in its `--settings`, for any enabled plugin named like the share's, `agent-mesh` or `agent-mesh-daemon`; the user's other sessions keep it). Checked live (Claude Code 2.1.332): an inline plugin of the same name replaces the installed one, with no duplicates and no clash, but one of another name loads beside it and the agent lists two sets of skills. agy has no such flag: its protocol tells it to read the `SKILL.md`.
- **An untrusted PR head:** an asker or a reviewer may sit on a PR head nobody trusted. A Claude one is launched with `--setting-sources user` (`adapter/claude`): it reads the user's own settings, and neither the head's `.claude/settings.json` and `settings.local.json` (their hooks) nor its `.mcp.json`; the mesh's hooks and `statusLine` (`--settings`) and its plugin (`--plugin-dir`) are not settings sources and stay. The head's `CLAUDE.md`, skills, agents and commands still load. An OpenCode one gets `OPENCODE_DISABLE_PROJECT_CONFIG=1`: under it 1.19.6 returns no plugin, MCP server, command, formatter or permission from the head's `opencode.json` and `.opencode/` (`opencode debug config`, checked with a hostile one); the mesh's `OPENCODE_CONFIG_CONTENT` stays. Workers and planners keep their repo's own config, and agy's asker and reviewer already have their hooks replaced by the mesh's. The fake claude runs a project's hooks the way the real one does unless `--setting-sources` leaves the project out, so a test can put one in a repo.
- **The first doorbell of each process** (a new terminal: a spawn, a resume, a reopen, a restart of meshd) ends with `(first one here: read <share>/protocol/PROTOCOL.md once, and follow it)`; a root's names `ROOT_CARD.md`, which tells it to read `PROTOCOL.md` too. The path is absolute, since the agent's CLI doesn't expand variables in what is typed to it. Later doorbells of the same process don't repeat it. The global rules block (`rules/global-snippet.md`) says the same for agents that read it first: the file the doorbell names, else `$AGENT_MESH_SHARE/protocol/PROTOCOL.md`, else `~/.config/agent-mesh/PROTOCOL.md` (the installed copy, linked by `install.sh`).
- **The "How do I …" map:** `PROTOCOL.md`'s section of that name (`mesh protocol how-do-i`) is the one place that says how to watch, talk to, approve, attach to or see what waits. Every kind of agent is pointed at it: `mesh help` ends with its line, a worker's `PROTOCOL.md` holds it, the root card names it, and the user's own session gets a bullet of it in the global snippet and in the `delegate*` skills' hand-off (`mesh open <agent>` is a device's command: an agent can't run it and tells the user to).
- **Skills:** `delegate` (the user's own session starts a run and a root and stops; the root is the supervisor), `delegate-review` (a root runs the review), `self-review`, `check-plan`, `find-peers` (the user's session searches and registers peers with `mesh add-peer`), `harvest-peers` (a root asks the peers with `mesh ask --peers`, checks their findings and reports; `HARVEST.md` holds the briefs) and `make-concise` (rewrites a repo's rules files concisely, run by that repo's own agent).

## Protocol notes

- **Writes** carry `RequestMeta`: a repeated `mutation_id` returns the first response without running again, and a write past `expires_at` is refused. Events a write causes carry its mutation id.
- **Events** have a `seq` and the log's `generation`. `SubscribeEvents` with a cursor of the same generation resumes (`Resumed`, then the backlog, then live); anything else starts with a `Snapshot`. Only an `End` frame ends a stream on purpose; after any other close, resubscribe from the last cursor. A subscriber more than `events.LiveBuffer` events behind is dropped (`resource_exhausted`) and resumes the same way.
- **Activity frames.** A tool call that changes no state writes no event (the log would grow with every tool call), so the stream also carries `AgentActivity {run_id, agent_id, detail, time}` frames, to a subscriber that asks (`SubscribeEventsRequest.activity`: the desktop sets it, `mesh events` and the Android app don't, so they get state changes only): ephemeral, sent only to the live subscribers of the run once the write that changed the detail has committed (a rolled-back one sends none), told before the state event published after it, never stored or replayed after a resume (frames queued while the backlog or snapshot was sent are dropped: they are older than the events just sent), and skipped, not a reason to drop the subscriber, when one is more than `events.ActivityBuffer` behind. A client that wants the tool an agent runs now takes it from the frame (the desktop's dock does); one that ignores the frame loses nothing, since the state events are as before.
- **What waits on the user:** `ListWaiting {run_id}` returns `Waiting {kind, run_id, agent_id, message, detail}` rows, oldest first, plans and questions before prompts (`internal/daemon/waiting.go`; `mesh waiting`). A row is a PLAN or QUESTION sent to an open run's lead (its first root) that no later ANSWER to its author followed, unless the author exited (a retired one is woken by the answer, so it counts); or an agent shown as NEEDS_INPUT (a prompt left unanswered past the unknown threshold shows as unknown and drops out). A device or read-only device reads every open run; a lead reads its own run's, and a worker is refused. Read-only: no event, so a client re-lists after the events that change it (a message, a state change, an exit, a retire, a stopped run). The plans and questions come from the store's `waiting` table (migration 11), which `PutMessage` keeps: a plan or question adds a row on its first insert, an answer to its author removes the author's earlier ones, and a re-put (read, delivered) changes nothing; the first `Open` after the migration fills it from the stored messages (meta `waiting_backfill`). A listing therefore costs what is open, not the run's history.
