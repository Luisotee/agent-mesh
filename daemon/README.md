# daemon

The Go daemon that replaces herdr and the pane-handling parts of `bin/mesh` (`docs/apps.md`, "Order of work" step 1). It doesn't replace anything yet: the live mesh is still `bin/mesh`. `./install.sh --daemon` installs it beside the live mesh, opt-in (see "Installing" below); nothing else installs it or puts it on PATH.

## Layout

- `../proto/`: the API as protobuf. `agentmesh/v1` is the action registry (`MeshService`, each RPC with its allowed actor classes in the `action` option), `agentmesh/term/v1` the terminal host's API and WebSocket frames, `agentmesh/adapter/v1` the CLI-adapter plugin interface. `buf.yaml` and `buf.gen.yaml` live there.
- `gen/`: the generated Go code (committed; regenerate with `cd proto && buf generate`). Reviewers can skip it.
- `cmd/meshd`: the daemon (including optional `--listen` TLS and `--relay-url` outbound relay connector).
- `cmd/protoc-gen-flagdocs`: a `buf generate` plugin that writes the schema's field comments into `gen/` (`FieldDocs`) for `mesh help`; not shipped.
- `cmd/mesh-relay`: the self-hosted stream relay (`docs/relay.md`), static binary for VPS deployment (`packaging/relay/`, `packaging/systemd/agent-mesh-relay.service`).
- `internal/tlsutil`, `internal/pairing`, `internal/relay`: persistent ECDSA P-256 cert & SHA-256 fingerprint pinning, `agentmesh://pair` URI codec, and zero-trust relay server/connector/client.
- `internal/registry`: the action registry read from the descriptors; `testdata/actors.golden` pins what each actor class may call.
- `internal/auth`: tokens (stored as SHA-256), the interceptor that takes the actor from the token, and the browser refusal.
- `internal/store`: SQLite (pure Go, WAL), embedded numbered migrations, backed up before migrating.
- `internal/settings`: the host's settings table (`schema.go`): each leaf's key, type, default, summary and choices, and the check a value must pass.
- `internal/events`: the resumable event stream.
- `internal/daemon`: the server and its handlers (`agents.go`: spawning, hooks, adoption, doorbells, the terminal proxy; `cost.go`, `models.go`, `conflicts.go`: reporting); `internal/client`: how local callers dial it; `internal/statedir`: the state dir's files.
- `cmd/mesh-term`, `internal/termhost`: the terminal host. `internal/termclient`: the daemon's side of it (its API, terminal streams, starting it).
- `internal/adapter`: the CLI-adapter registry; `internal/adapter/claude`: Claude Code's adapter; `internal/adapter/agy`: Antigravity CLI's (`agy`) adapter. `internal/shellmatch`: publish-command matcher for `PreToolUse`. `internal/reducer`: the pure state reducer. `internal/hook` and `cmd/mesh`: the hook command and its spool. `internal/proc`: pids checked by start time.
- `internal/testutil/fakeclaude`, `internal/testutil/fakeagy`: the fake CLIs the tests run (turns and hooks, no network).
- `packaging/systemd/`: the two user units for production (`install.sh --daemon` installs them).
- `share/`: the protocol and skills daemon agents follow (`protocol/`: `PROTOCOL.md` for every agent, `ORCHESTRATE.md`, `ROOT_CARD.md`, `PLAN_TEMPLATE.md`; `skills/`; `.claude-plugin/plugin.json`), see "Protocol and skills".
- `cmd/mesh`, `internal/cli`: the CLI (`mesh`), generated from the registry at run time.
- `e2e/`: the end-to-end test of the real binaries (`TestEndToEnd`).

## Toolchain

Go (see `go.mod`), [buf](https://buf.build) for the protos, and for `go test -race` a C compiler. The code generators are pinned as `tool` directives in `go.mod`, so `buf generate` installs nothing. On the dev machine they are user-local, off PATH: Go in `~/.local/go`, buf in `~/.local/opt/buf/bin`, and `~/.local/opt/zigcc/cc` (a `zig cc` wrapper) as the C compiler. `scripts/check.sh` finds them there.

## Commands

```bash
daemon/scripts/check.sh                      # the CI equivalent: buf lint and breaking, gen current, vet, test -race, pytest (clears AGENT_MESH_*: an agent's own token would be refused by the tests' daemons)
cd daemon && go test ./...                   # the Go tests only
cd proto && buf generate                     # after changing a .proto
cd daemon && go test ./internal/registry -update   # accept a reviewed change of who may call what
cd daemon && go build -o bin/ ./cmd/...      # binaries into daemon/bin/ (gitignored)
```

## Installing

`./install.sh --daemon` (opt-in; a plain `./install.sh` never builds or starts the daemon) puts the daemon beside the live mesh, from this checkout's branch:

- It builds `cmd/meshd`, `cmd/mesh-term` and `cmd/mesh` into a temp folder first (a failed build changes nothing), then moves each binary into `~/.local/lib/agent-mesh/bin/` with one rename, so a running meshd or mesh-term is never broken by an upgrade. `daemon/share/` (the daemon's protocol and skills, once it exists) is copied to `~/.local/lib/agent-mesh/share/`. The installed daemon is versioned by install, not by the checked-out branch.
- It copies `packaging/systemd/agent-mesh.service` and `agent-mesh-term.service` into `~/.config/systemd/user/` (or `$XDG_CONFIG_HOME`), each with a drop-in `<unit>.d/path.conf` holding the `PATH` of the shell that ran the installer: a user unit's own `PATH` is short, and the agents' CLIs (`claude`, `agy`) must be found. Re-run it to refresh that `PATH` or to upgrade.
- It runs `systemctl --user daemon-reload`, `enable agent-mesh.service` and `restart agent-mesh.service` (meshd Wants the terminal host, which stays up across a meshd restart, with its terminals). Without a user session or `systemctl` the files are installed and it says how to start meshd.
- It links `~/.local/bin/meshctl` to the installed `mesh` (a real file there is left alone) until `bin/mesh` is retired.
- It never touches `~/.local/bin/mesh`, `~/.config/agent-mesh`, `~/.claude` or `~/.local/state/agent-mesh`. State is `~/.local/state/agent-mesh-daemon`.

`./install.sh --daemon --uninstall` stops and disables the units and removes the units, drop-ins, binaries, `share/` and the `meshctl` link, and keeps the state. A plain `./install.sh --uninstall` leaves the daemon alone. `tests/test_install.py` runs all of it in a temp HOME with `go` and `systemctl` stubbed.

## Running a dev instance

Always give it a state dir of its own: meshd has no default, so it can't land in a real one by accident. A unix socket path holds about 107 bytes, so keep the state dir path short: meshd refuses to start with a longer one.

```bash
state=$(mktemp -d)
daemon/bin/meshd --state "$state"            # socket at $state/meshd.sock, device token at $state/device.token
```

Every call needs a token. The host's own CLI uses the device token meshd writes on first start (`device.token`, mode 0600); each agent gets its own at spawn, in `AGENT_MESH_TOKEN`. The actor of every action comes from the token, never from the request. Requests that carry a browser's `Origin` or `Sec-Fetch-Site` header are refused, and `--tcp` binds loopback only. A worker, asker, or reviewer token reads only its own run; a root may list earlier runs (`ListRuns`, `ListAgents`, `GetAgent`, `ListMessages`) and resume stopped non-root workers from them into its own open run. A token without a run is not stored.

A run is one trust domain for events for now: every agent of a run receives its run's events, so a reviewer or asker sees the bodies of the `MessageSent` events between the run's other agents, though it can send only to its parent and children. `TODO.md` tracks revisiting it.

## mesh (the CLI)

Every action of the registry is a `mesh` command, built at run time from the compiled schemas: the command is the action's `cli` name, each request field is a flag (`snake_case` → `--kebab-case`; a bool is a switch, `--peek`; enums by short name, `--role worker`; message fields as JSON; `@file` or `@-` for text, `@@` for a literal leading `@`), `--json` gives the whole request (also before the command: `mesh --json '{…}' set`) and the other flags override it (a repeated field's first flag replaces the list the JSON gave, the next ones add to it), a `google.protobuf.Value` field takes any JSON or, when the text isn't JSON, the string it spells (`--value sonnet`, `--value 75`, `--value '["haiku","sonnet"]'`), and the response prints as JSON (a stream as one object per line), except `mesh inbox`, `mesh settings`, `mesh cost`, `mesh models` and `mesh conflicts`, which print short text by default (an inbox as a header line and the body of each message, settings as `key = value`, with the default after an override, and formatted tables/summaries for reporting) and give the whole response with `--format json`: the CLI's own view, the API is the same. Writes get a fresh mutation id unless `--mutation-id` is given. `--state` goes before or after the command; without it (and without `$AGENT_MESH_STATE`) the CLI uses `$XDG_STATE_HOME/agent-mesh-daemon` (else `~/.local/state/agent-mesh-daemon`), where the installed units keep the state, but only when `meshd.sock` is there (`meshd` itself has no default). `mesh help` lists the commands, `mesh help <command>` its flags, each with the schema's own comment on the field (generated into `gen/` by `cmd/protoc-gen-flagdocs`, a `buf generate` plugin). A command whose request has a string field `to` or `agent` takes it as its one bare argument, wherever it stands among the flags (`mesh send parent --type done --body @report.md`, `mesh approve <agent> --tier mid`); it is a convention of the schema, so an action added with such a field gets it, and giving it twice (argument and flag) is an error. Only `hook`, `statusline`, `version`, `whoami` and `dir` are written by hand: `mesh whoami` prints the caller's role, name, id, run, run folder and parent as JSON, and `mesh dir` the run's folder (`$AGENT_MESH_RUN_DIR`, or `--run <id>` for a device).

```bash
export AGENT_MESH_STATE=$state
daemon/bin/mesh start-run --title demo
daemon/bin/mesh spawn --run-id <run> --repo ~/projects/shop-api --slug fix-typo --task @task.md
daemon/bin/mesh agents --run-id <run>
daemon/bin/mesh send --to shop-api-fix-typo --type task --body "…"
daemon/bin/mesh events --run-id <run>                 # follow; resume with --cursor '{"generation":…,"seq":…}'
```

An agent's own shell has `AGENT_MESH_TOKEN` and `AGENT_MESH_STATE`, so the same commands act as the agent (`mesh inbox`, `mesh send parent …`). Its environment also holds `AGENT_MESH_RUN_DIR` (the run's folder, `<state>/runs/<run>/`, made when the run starts, with `plans/`, `reports/` and `tasks/` in it: where the protocol's files go) and `AGENT_MESH_CLI` (the absolute path of this `mesh`), and the folder of `meshd --mesh` is first on its `PATH` (whatever `--agent-env PATH=…` says), so a bare `mesh` in an agent is this CLI. The live `bin/mesh` hands over to `$AGENT_MESH_CLI` when it sees `AGENT_MESH_TOKEN` without `MESH_RUN` (a login shell's rc file can put `~/.local/bin` back ahead of the `PATH`), and fails rather than run the herdr mesh for an agent of the daemon's. `meshd --meshctl` is the old name of `--mesh`. Until the switchover is finished (`docs/apps.md`, "Switchover") nothing here replaces `bin/mesh`.

## Settings

The policy (`bin/mesh`'s `POLICY`, design §21) is host data, the same from every device and readable by the agents that run under it. `internal/settings/schema.go` is the one table: a leaf's key, type, default, summary, choices and whether it is read only at start. The settings screen is generated from it, and an app adds its own rows there (the desktop's `app.*`); it needs no action or event of its own. Only overrides are stored (the `settings` table, migration `0002`); a leaf nobody set is its default, so a new default reaches every host that never overrode it.

- `ListSettings {prefix}` returns `Setting`s: `key`, `value` (effective), `default`, `is_set`, `schema {type, summary, choices, restart}`, and who set it and when. Any actor class may call it. `mesh settings --prefix tiers.claude.`.
- `SetSetting {meta, key, value}` and `ResetSetting {meta, key}` write: only a device or a root, idempotent like every write, and each emits a global `SettingChanged {key, value, previous, to_default}` with the actor and the mutation id. The event has no run, so every subscriber gets it, a run's agents included. A `Snapshot` doesn't carry settings: a client lists them after one, then follows the events. `mesh set --key quota_stop --value 75`, `mesh unset --key quota_stop`.
- A value is checked against its type: `string`, `strings`, `int`, `percent`, `bool`, `seconds`, `effort`, `chain`, `slots`, `kinds`, `mb_or_auto`, `json`. A failure is `InvalidArgument` naming the rule (`quota_stop must be a whole number 0 to 100`); a key no leaf has is `NotFound`.
- The daemon reads a leaf with `Daemon.Setting(reader, key)` (the override, else the default; a stored value the leaf's rule no longer takes is logged and the default used; a failed read is an error), so a change applies to the next read. A write that changes nothing (the same value again, a reset of a setting nobody set) emits no event. `seconds` is capped at 1e9 so a `time.Duration` can't overflow. Not ported yet, with the herdr-only leaves (views, `side_panes`, `root_reset.*`, `compact.*`, `claude.*`): they wait for the switchover. `meshd` doesn't import `~/.config/agent-mesh.json`.

## Terminals

`mesh-term` owns the agents' PTYs, in a process of its own so a daemon restart leaves them running; at boot the daemon adopts what it finds (`AgentAdopted`), records exits that happened while it was down, marks an agent whose terminal is gone as `lost`, and never kills a terminal no agent claims.

- **Supervision.** In production both run as systemd user units (`packaging/systemd/`): `agent-mesh-term.service` holds the PTYs in its own cgroup, and `meshd --term-launch systemd` starts it when no host answers. Without systemd (and in dev and tests), `--term-launch detached` starts `mesh-term` in its own session; tests pass `--max-lifetime` so a killed test leaves nothing behind. One host per dir (a held lock), a token in `term/term.token`, and no pid is ever signalled without its start time matching.
- **Streams.** `OpenTerminal` gives a one-time ticket; the client opens `/v1/term/<agent>?ticket=…` on the daemon, which splices it to the host. Frames are `agentmesh.term.v1.TermFrame` (binary). The first client frame is `Attach`: `EXACT` (from an epoch and offset, falling back to a repaint marked `reanchored`), `TAIL` (mode preamble, then live) or `REPAINT` (preamble and the screen from the host's emulator, then live). The replay ends with `ReplayDone`; input sent before the client's `Ready` is dropped, so replayed queries draw no answers. While no client that can type is attached, the host's emulator answers terminal queries itself. The size is the smallest client's, clamped to 20-500 columns by 5-300 rows; only a client with input rights may resize after attaching; a resize moves the epoch. A client that falls behind is closed with code 4001 and reattaches by offset; the PTY is never paused.

## Agents and hooks

An agent starts with an allowlist of meshd's environment, not all of it: the shell basics (`HOME`, `PATH`, `LANG`, `TMPDIR`, `XDG_*`, `SSH_AUTH_SOCK`), what Claude Code needs to reach its model (`CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_*`, the proxy variables, the Bedrock and Vertex settings and credentials), OpenCode/OpenRouter provider keys (`OPENAI_API_KEY`, `OPENROUTER_API_KEY`, `OPENCODE_API_KEY`, inherited only by `opencode` agents whose model is not `opencode/*`, and never written into `OPENCODE_CONFIG_CONTENT` or logs), a terminal, and its own identity. `meshd --agent-env KEY=VALUE` adds more, and `--cli claude=<path>` pins the binary; without it a bare `claude` is looked up on the agent's `PATH` by meshd, not on `mesh-term`'s. A meshd run by a systemd user unit has only what the unit sets, so put the login variables there (or in `--agent-env`).

`SpawnAgent` makes a worktree on `mesh/<run>/<slug>`, started from `base` (default: the repo's `origin/HEAD`, such as `origin/main` as last fetched, so a worker never branches off the branch the user's checkout is on; a repo with none starts from its `HEAD`), mints the agent's token (in `AGENT_MESH_TOKEN`, and in `<state>/agents/<id>/token` for its hooks), and starts its CLI through the adapter. Claude Code gets a `--session-id` and per-launch `--settings` hooks that run `mesh hook claude --state <dir> --agent <id> <Event>`. Before the launch the worktree is trusted in Claude's global config (`projects[<worktree>].hasTrustDialogAccepted` in `$CLAUDE_CONFIG_DIR/.claude.json` or `~/.claude.json` of the agent's environment, written under the lock Claude takes, every other key kept; nothing when the worktree, its main checkout or a parent is trusted already, or the file doesn't exist): Claude shows its folder-trust dialog even under `--dangerously-skip-permissions`, fires no hook before it is answered, and its default answer is "No, exit". The launch also hooks `StopFailure`, which Claude fires on an API error instead of `Stop`: a `rate_limit` or `billing_error` whose message is a usage limit (`You've hit your session limit · resets 3pm (America/Sao_Paulo)`, `You're out of extra usage`) is `AGENT_STATE_LIMITED`, with the reset it names and whether it is the account's (session, weekly, usage, monthly spend: every model) or one model family's (`Opus limit`, `Sonnet limit`); any other failure (a capacity 429, a login error) is `AGENT_STATE_ERROR`. Antigravity (`agy`) resolves model+effort via `agy models` (never passing `--effort`), skips the folder-trust dialog with `--settings '{"trustedWorkspaces":[…]}'`, resolves an exact id named without an effort at its own effort (`DescribeModel`: `gemini-4-neon-low` runs as named), writes `.agents/hooks.json` into the worktree (a worker's repo's own committed hooks deep-merged beside the mesh's when that version is on one of the repo's own refs, a local non-mesh branch or an origin branch, with the mesh's own `"agent-mesh"` key replaced wholesale; an asker's, a reviewer's or one from a fork's head replaced; kept out of git by `--skip-worktree` on a tracked file, else by a self-ignoring `.agents/.gitignore` in that worktree alone), enforces read-only and planning rules locally in `PreToolUse` (fail-closed across every tool with `HookTimeout`, overriding `--dangerously-skip-permissions`: a payload it can't read whole is denied, and a session that isn't the agent's, its `$AGENT_MESH_AGENT` unset or another's, still has the rules checked but reports nothing; agents without deny rules wrap `PreToolUse` to exit 0 silently so hook failures never block tools), reports `PreToolUse` within a second without waiting on the spool lock (agy denies a tool whose hook outlives its timeout), becomes `IDLE` once its terminal has drawn and been quiet for `ReadySettle` (or 30 of them after its first output, for one that never stops drawing), records its `conversationId` from its first prompt's hooks (with `LookupSession` falling back to the newest top-level conversation of its worktree in `conversation_summaries.db` or `history.jsonl` that isn't older than the agent, looked up only for an action that uses the id (a resume or a reopen) by an actor allowed to act on the agent, before that action's write, never inside it), reads a `Stop` with `continuationActive` as activity, not the turn's end, and maps `Stop` `ERROR` with `RESOURCE_EXHAUSTED` / 429 to `AGENT_STATE_LIMITED` (ready for `SwitchAgent --next` on `--conversation`) and any other to `AGENT_STATE_ERROR`; an agent at either is at its input box and takes reopens and idle retire as an idle one does, and at `ERROR` doorbells too (at `LIMITED` a doorbell's turn would fail on the same quota: its messages wait for the switch). OpenCode (`opencode`) has no hooks: `installed("opencode")` checks the configured or `PATH` binary, expands `free` in tier chains to active zero-cost `opencode/*` models (`opencode models --verbose`), launches `--agent mesh-<hash> [-m <model>] [-s <session>] [--auto]` (omitting `-m` and `model` when no model is picked, e.g. a default root) with per-launch `OPENCODE_CONFIG_CONTENT`, `OPENCODE_DISABLE_AUTOUPDATE=1`, and ordered `OPENCODE_PERMISSION` when read-only or planning (lifted on `approve` or direct task in the same `-s` conversation, with a distinct `--agent` on each reopen), appends `--body @"<path>"` guidance to its tasks so backticks never expand in bash, tracks session IDs, turns (`MessageAbortedError` treated as an idle turn end), and limits (`FreeUsageLimitError`, `GoUsageLimitError`, `429`, `"Upstream request failed: Model is unavailable."` / status 400, and `┃`-gutter `[retrying ... attempt #3+]` banners after a model reply) by polling read-only `opencode.db` and `REPAINT` screen lines asynchronously when `LastOutput` advances, and rotates held models cleanly (`model_limits`, `limits.auto=switch`, `SwitchAgent --next`). The hook reads the daemon's address at call time and, when the daemon is down, spools to `<state>/spool/<agent>/`; the daemon drains the spool every few seconds. Hooks always exit 0 and print nothing (except an agy `PreToolUse` deny JSON; failures go to `<state>/hook.log`). The adapter turns each hook into neutral events and `reducer.Reduce` derives the state; a working agent, or one waiting on a prompt, that nothing was heard from for 10 minutes shows as unknown (Claude may fire no hook when a prompt is dismissed). A compaction remembers the state it interrupted and restores it when the compacted session starts (idle stays idle, mid-turn stays working); a resume's `SessionStart` does not make an agent idle. A spooled hook the daemon's drain gets an error for (not "unreachable") at least ten times over at least five minutes is dropped (kept as `.bad`, with a `HookDecodeFailed` event); the hook process's own drain never drops one; idempotency records of hooks are pruned after a day, others after two weeks. Messages are stored and announced by a one-line doorbell typed into the agent's terminal once it is idle and no client with input rights has typed in the last 15 seconds (it retries every 2 s); the agent reads them with `mesh inbox`. An asker or reviewer (and a planner) launches with a `--disallowedTools` list (Claude: `Edit` rules, which Claude applies to every tool that edits files, `NotebookEdit` included, and prefix rules for `git push` and the gh writes) and `PreToolUse` deny flags (agy: paths and publish commands; Claude: publish commands only), which hold under `--dangerously-skip-permissions`. Claude's prefix rules miss `git -C . push` and the like, so its `PreToolUse` hook (`--deny-publish`) also checks every Bash command with the shared `shellmatch` matcher, and a hook's denial is final in every permission mode (a hook that fails to run lets the tool through: the prefix rules stay as the backstop). The command check, for both CLIs, also unwraps `env`, `sudo`, `timeout`, `xargs` and the like, `sh -c` and `eval` strings, skips gh flag values (`gh pr --repo o/r merge`), and blocks `gh api` writes (a method other than GET, fields without one, a GraphQL mutation), and every gh command but an allowlist of reads (`pr list/view/diff/checks/status`, `issue list/view/status`, `release list/view/download`, `run view`, `search`, …: a gh command added later is denied until listed); it guards against an agent's mistake, not a determined one (a script it writes, a git alias).

**Lean Claude sessions** (`internal/daemon/lean.go`, `adapter/claude/lean.go`, design §11; `claude.lean`, on by default). A Claude agent starts without what a mesh doesn't use, about 39k tokens of its first call, re-read on every call: its launch gets one `--disallowedTools` (the read-only rules, then `claude.deny_tools`, or `claude.root_deny_tools` for a root, which keeps `AskUserQuestion`), `--settings` keys `skillOverrides` (`claude.skills_hidden`, and `claude.worker_skills_hidden` for a non-root: only a root starts a mesh), `syncClaudeAiSkills: false`, and `enabledPlugins: false` for the plugins of `claude.plugins_off` the user's settings enable, and `--strict-mcp-config --mcp-config <state>/agents/<id>/mcp.json` (mode 0600: a server's config may carry secrets) with the user's servers it loads: with `claude.mcp` `repo` the repo's own (its project entry in `~/.claude.json` and its approved `.mcp.json`), `claude.mcp_keep` (`context7`) and the spawn's `--mcp` names (`Agent.mcp`, kept by every reopen); claude.ai's connectors are off (`ENABLE_CLAUDEAI_MCP_SERVERS`). `claude.mcp` `inherit` loads whatever the user's config has, `claude.lean` false launches as before. `--mcp` is refused for a name the user's config lacks, a non-Claude agent, or when lean is off. Not ported from `bin/mesh` yet: `mesh tools add` and the shared-browser lease (`claude.mcp_exclusive`), in `TODO.md`.

## Same conversation: tiers, approve, switch, resume

A model change reopens the agent's own conversation (`claude --resume <session> --model … --effort …`), never a fresh agent briefed again, so it keeps its research (design §9, `bin/mesh`'s `swap_model`).

- **Tiers.** `SpawnAgent` takes a `tier` (`tiers.<kind>.<tier>` in the settings: the chain's first model at its effort) or a `model` the user named (at `effort`, else high). Neither is `InvalidArgument`: there is no default model, except for a root, whose model is the user's (it launches on the CLI's default unless one is named). A tier is checked whenever it is given. A named model leaves the agent no tier (the tier only gives the effort), so `next` is refused from it. A named model or effort with no plan phase is `pinned`.
- **Plan phase.** `plan` starts the agent `PLANNING`, a Claude agent under the same `--disallowedTools` list as a read-only one (`deny_edits`), optionally with a preset `exec_tier`. A `plan` sent by an agent with no phase that isn't pinned enters one, without a reopen (it plans on the model it is on, with no deny list).
- **`ApproveAgent`** (its parent or a device, only when its newest report since its last task or answer is a `plan`) stores the `approved` answer, sets `EXECUTING`, and reopens it on the execution tier (given, else the preset; or a named model) without the deny list. `keep_model` executes on the planning model; only the deny list goes, which is still a reopen. An agent with no plan phase is approved as it is. A task marked direct (it begins `Direct task`, as bin/mesh's does) sent with `SendMessage`, by the agent's parent or a device, ends a plan phase (the tier it runs on becomes the one `next` walks) and lifts a planner's deny list by a reopen on the same model, unless the role is read-only; any other task leaves a planner planning, under its list and with its preset execution tier; a `plan` from an agent that is executing, or has no phase and isn't pinned, enters the plan phase again, so its approval can name a tier.
- **Change tasks for askers and reviewers.** An asker or reviewer given a task that doesn't begin `Question (read-only)` or `Review (read-only)` (by `SendMessage` or `resume --task`, from its parent or a device) becomes a worker in the same conversation (`takeChange`): its role, its live tokens' class (read from the row on every call, so a running process follows) and an `AgentRoleChanged` event change, and a planned task (not direct, or `resume --plan`) puts it in the plan phase under the list it already has; the paths above then lift the list as for any worker (a direct task by a reopen, or at launch when it is stopped; approve by a reopen on the execution tier). An agent a worker started never changes role (a worker never gets a change worker): to it every task is a read-only follow-up. A refused resume of a stopped agent keeps the conversion with the stored task; a direct task that made an asker or reviewer a worker also lifts its list, so the next resume brings it back able to edit.
- **Asks and review rounds** (`mesh ask`; `internal/daemon/ask.go`, `review.go`, `collect.go`, `pr.go`). `Ask` (root or worker) starts a read-only agent or asks one the caller started: `ask --repo R --tier T --body …` a fresh asker (slug `ask-<words>`, task `Question (read-only): …`); `ask <agent> --body …` a task to an existing one (resumed if retired; a busy one is told the task waits); `ask --repo R --review <PR> --size S --tier T [--kind K]` one fresh reviewer at the PR's head; with `--reviewers auto|all|<kinds>` a **round**. The PR is read with `gh pr view <PR> --json number,url,headRefOid,headRefName,baseRefName` in the repo (the daemon only ever runs that: `Binaries["gh"]` is the fake in tests), its head is fetched (by id, else `pull/<n>/head`) so each reviewer's worktree starts on it, and the task names the diff command instead of embedding it. A reviewer's task is `bin/mesh`'s text (CI first, tests the change touches, findings with file:line and blocking or advisory), with `/code-review <review.level.size> <PR>` for a Claude one. `auto` fills `review.reviewers.<size>`'s slots with the first adapter registered and not picked, the PR author's CLI (the newest agent whose branch is the PR's head ref) last, a re-review with the last round's kinds minus `review.re_review.skip` (plus `keep.<size>`); a kind with no adapter is left out with a note. The record is an `Ask` (table `asks`, `ask.proto`), stored before its members start (`starting`: it can't finish until all are started, so a fast report is collected) with an id derived from the caller and the request's mutation id, and with derived mutation ids on each spawn, so a retried ask finds the ask it left, keeps its started members and starts nobody twice. A re-review asks again only a reviewer that answered the last round; one that didn't (a question, a crash, the timeout) starts fresh on the whole PR. **Collecting:** a round's members' `done` and `failed` to the caller are stored delivered and read (no doorbell) and settle the member; a `plan` or `question` rings as usual and settles it; an exit or silence alert settles it with the alert's first line (`alertParentTx`); the accountability pass settles a member whose agent was stopped without reporting, and every member still pending after `ask.timeout`. When none is pending (same transaction) `reports/review-<pr>-<stamp>.md` is written (bin/mesh's format; a file that can't be written is said in the message, and the answers stay in the ask) and the caller gets one `info` `[mesh answers <id>]` with who answered, the path and the rounds hint (`review.rounds.<size>`, a ceiling counted across runs: finished rounds of the PR with an answer). A re-review in the same run asks the earlier round's own reviewers again (resumed if retired; a clean worktree at the head they reviewed moves to the new one, else it stays and the task says why) and reads only what changed since; in another run (an agent reads only its own run) fresh reviewers of the same kinds read only the fix commits. Every launch asks `ReserveGuard` first (a retry whose spawn already went through skips it: the spawn replays). `RecordVerdict` (`mesh verdict`, root or device) stores a reviewer's verdict (counts, kind, model, tier) on the PR's newest round; `ListAsks` (`mesh asks`) lists them.
- **Standing peers** (`mesh peers`, `add-peer`, `edit-peer`, `remove-peer`, `import-peers`, `ask --peers`; `internal/daemon/peers.go`, tables `peers` and `peer_groups`, migration 0007). A peer is a cloned project kept as a standing read-only asker: the registry holds its clone, group, `about` (at most 400 characters), kind, upstream, a detached **worktree of its own** (`<worktrees>/peers/<name>`), the commit it last saw (`seen`) and its conversation id. `AddPeer` (root or device) clones a URL (https, ssh, git, file or `user@host:path`, never `ext::`; `GIT_ALLOW_PROTOCOL` pinned) into `peers.dir`/`<group>`/`<repo>` or uses the clone at a path, and names it `<repo cut to 20>-research`. `ImportPeers` reads bin/mesh's `peers.json` and never writes it: peers and group `about`s not registered yet are, each with a new worktree, **without their conversations** (bin/mesh keeps those, keyed by its worktrees' paths, and a daemon resume while bin/mesh can still ask the same peer would run two processes on one conversation), so they are unbriefed until their first round. An agent belongs to one run and reaches only its parent, so a peer is not one agent: each run that asks it gets an agent record of its own (role asker, `Agent.peer`, named as the peer) in the peer's worktree that **resumes the peer's conversation** (`--resume <session>`; a fresh one with a tier for an unbriefed peer), refused for a peer whose agent runs in another run (one process per conversation). `Ask` with `peers` (`all`, a group, or names) prepares each peer first (a 60 s fetch of its upstream, the checkout moved to the new head when clean, and the note "Upstream moved since you last looked: N commit(s) … `git log --stat`" or "hasn't changed" at the top of its task; `no_refresh` skips it), then collects like a round (`ASK_KIND_PEERS`) into `reports/peers-<stamp>.md` (question, then a section per peer: its repo at the head, upstream commits since last asked, `about`, answer). The registry records `seen`, the asking run and agent, the conversation id and the answers file. A peer's agent is never given a change task (`takeChange` skips it) and `StopRun` keeps its worktree. `remove-peer --delete-clone` deletes the clone only when the daemon made it (a URL's) and no other peer uses it. A peer's conversation has one process: a peer agent with a process (running, starting or a reopen asked for) in another run refuses an ask, a resume and a `send` from this one, and an ask of a peer is serialised per peer (the fetch, the checkout and the launch run under one lock, the check repeated inside the launch's transaction); a task stored for a peer agent that could not be resumed is marked read. An imported peer's group, upstream remote and branch are checked (an option-like one is left out) and its `about` capped.
- **`SwitchAgent`** moves it to a tier, a model, an effort alone, or `next`: the next model of its phase's tier chain (the quota move; never back to one before, and `FailedPrecondition` at the chain's end). It stores an `info` telling the agent where it is now (not a task: a planner switched before approval is still approved on its plan). A switch to a named model leaves the phase no tier, so `next` is refused from it rather than going back to the chain's first model. A model at a usage limit is persisted in SQLite (`model_limits`, migration `0005`: until the reset the CLI named, else `limits.hold` seconds; an account-wide limit holds every model of the CLI), and the chain is walked past held models (and agy models at `quota_stop`): a new agent, an approve and a switch to a tier take the first model with quota left (all held: the one freed first), and `next` the first free one after the agent's own (or for OpenCode when the chain changed, the first unheld one, refusing with the soonest reset when every candidate is held; other kinds fall back to `chain[0]` or `chain[i+1]`).
- **`ApproveAgent` on a stopped agent** is refused: approving never undoes a stop; resume it (it comes back planning), then approve.
- **Usage limits and quota reserve** (`limits.auto`, default `switch`; `limits.hold`; `quota_stop`, default 90%): a pass every few seconds looks at each agent at `LIMITED` that isn't a root (its model is the user's) and has no reopen pending, moving it to the next free model (`switch`) or continuing once the hold expires (`switch` / `continue`). Claude usage comes from Claude Code's `statusLine` command (`mesh statusline --state <dir>` recording `rate_limits`, chaining read-only to any user `statusLine` command) with OAuth endpoint and `.claude.json` `cachedUsageUtilization` fallbacks; agy usage comes from `agy -p /usage`. `ReserveGuard` blocks new tasks (`SpawnAgent`, `ApproveAgent`, `ResumeAgent --task`, `SendMessage` of a `TASK`) when a vendor window or model reaches `quota_stop` (while answers still deliver), until reset or `mesh reserve off` (`Run.over_reserve`). `GetUsage` (`mesh usage`) reports current windows and tier picks, `SetReserve` (`mesh reserve on|off`) toggles `over_reserve`, and periodic `reserveAlertPass` posts deduped `[mesh alert reserve …]` info messages to open runs' leads.
- **`ResumeAgent`** reopens a stopped agent (with a task it plans, a direct task, or as it was): it recreates clean removed worktrees, moves a change worker off an already merged or closed GitHub PR (when none is open) onto a fresh `mesh/<run>/<slug>` branch (`LeftPr`/`Notes` and task note), and lets a `ROOT` (or `DEVICE` naming `run_id`) resume a stopped non-root worker from a closed earlier run as a new follow-up `Agent` in the open run keeping the same conversation and worktree (`ResumedFromRunId`/`ResumedFromAgentId`), enforcing one live process per conversation/worktree across all runs (`StopRun` leaves worktrees held by live agents or active open runs untouched).
- **Reporting** (`internal/daemon/cost.go`, `models.go`, `conflicts.go`, `proto/agentmesh/v1/report.proto`):
  - `GetCost` (`mesh cost`) sums Claude JSONL token/USD spend (folded by `message.id`, attributed across phases and cold resumes by `Event_AgentSpawned`/`Event_AgentPhaseChanged`, with a root's pre-run window truncated at run start and an unstopped run capped at the last agent activity), agy conversation DB calls (`protowire`), OpenCode `opencode.db` token usage (with paid `cost` kept in its own `usd` column on token rows, separate from Claude's API-equivalent total), `--since`/`--until` global windows, and `mesh verdict` totals.
  - `CheckModels` (`mesh models [--check] [--ack <kind>:<family>]`) compares listed families against `tiers.<kind>.*` settings (caching checks for 24h in SQLite `meta`, populating `StartRunResponse.model_notice`, and exporting `Daemon.ModelNotice(ctx)` for `mesh brief`).
  - `CheckConflicts` (`mesh conflicts`) runs `git merge-tree --write-tree` pairwise across non-stopped run agents' worktrees sharing a repo (skipping stacked ancestors and caching `ancestry`/`changedFiles`, with `GIT_OPTIONAL_LOCKS=0`).
- **The reopen.** Each of these stores a `Reopen` on the agent (`pending_reopen`, event `AgentReopenRequested`); a newer request replaces one not done yet. It runs when the agent is idle or stopped and no client with input rights is typing, else at its next `IDLE`, before any doorbell: the old process is stopped (SIGTERM, then SIGKILL), its exit is not recorded as one, a new token is minted, and the conversation is relaunched in a new terminal labelled with the reopen's id (`AgentReopened`). The agent keeps its id, name, worktree and session; the message the action stored rings in the new process. A pending reopen survives a meshd restart; a terminal a reopen had started when meshd died is found by its label and recorded, never launched twice. `StopAgent` drops a pending reopen (`AgentReopenDropped`); a relaunch that fails leaves the agent `EXITED`, for `ResumeAgent` to try again.

## Retire, stop, caps

- **Retire** (design §18). `RetireAgent` (its parent or a device) stops an agent's process on purpose and keeps its conversation: state `RETIRED`, token revoked, worktree and branch kept, terminal acknowledged; no `AgentExited`. A pending reopen is dropped. Anything its dying process or its spool still says is ignored. `ResumeAgent`, or a message, brings it back.
- **A message to a stopped agent** (`RETIRED`, or `EXITED` with a session) stores the message and requests the reopen in the same write: a `task` marked direct (it begins `Direct task`) resumes it direct, as one sent to a live agent is (it ends a plan phase and drops the planning deny list), any other task brings it back as it was (a planner still planning); for a task it plans on a tier use `ResumeAgent` with `plan`, an `answer` or `question` brings it back as it was. An `info` is only stored; it is read when the agent is next resumed. The response's `resumed` is the reopen. The message is stored in any case: when the resume is refused (the cap, the memory floor, a closed run, no conversation to resume) the agent stays stopped and the response's `resume_error` says why, so a report to a retired parent is never lost to the cap. Nothing is queued: the launch is not retried.
- **Idle retire.** A pass every `RetireEvery` (10 s) retires an agent that is IDLE, whose newest report since its last task or answer is a `done` or `failed`, and that stayed idle `idle_retire` seconds (0 never) since the later of that report and its last activity. Not a root; not one with a reopen pending, unread mail (work is coming, or a doorbell was lost), a `plan` or `question` waiting on its parent, or a client with input rights attached to its terminal (someone is looking). The check is repeated under the agent's lock inside the retiring write, so a message that arrives meanwhile either keeps it open or finds it retired and resumes it.
- **`StopRun`** (a device) retires every agent of a run and closes it (`RunStopped`); nothing starts or resumes in a closed run. A clean worktree is then removed, and its branch with it unless the branch moved past the commit it started at (`Agent.base_commit`, so a branch another one stacks on still counts), or has a remote branch of its name (a branch started from `origin/main` has an upstream for free: that is not work); a worktree with uncommitted changes stays, with its branch. An agent spawned while it runs is retired too, a pending resume on a stopped agent is dropped, and the processes are stopped together (one `StopWait` at most, not one per agent). The response says what happened to each.
- **`caps.agents`** (default 8; 0 no cap) limits agent processes on the host: starting, running, or a stopped agent whose resume is pending. A spawn or a `ResumeAgent` past it is `ResourceExhausted` (a message that would resume one is stored with `resume_error`), checked inside the write that stores the agent or the reopen, where the one writer makes the count and the record one step, so a burst of spawns can't all pass. A switch or approve replaces a process and is never refused, and neither is the reopen a `Direct task` to a running planner requests to lift its deny list: each swaps one process for one, though the old one counts alongside the new until it exits. A direct task to a stopped agent is a resume and is refused like any (it stays as it was, planning).
- **The memory guard** (design §17) runs in the same places (with an early non-reserving check in `SpawnAgent` before creating a worktree, refreshed at `reopen` launch, released on closed-run cancellation, and seeded from adopted live terminals within `ReserveFor`): refused (`ResourceExhausted`) while memory plus swap free is under `min_free_mb` (`auto`: 10% of RAM plus 10% of swap plus 1 GB, at least 2 GB; 0 off) or `/proc/pressure/memory`'s `full avg60` is over `memory_pressure_max` (0 off). A launch that passes counts 400 MB used for 2 minutes, under its agent's id (a launch that fails gives it back), so four spawns in a row don't read the same free memory. `MeminfoPath` and `PressurePath` of the agent config point it at other files (tests); without them it reads `/proc`, and where there's no `/proc` it refuses nothing.
- **Process sweep and resource scopes** (design §17). On retire (`RetireAgent`, idle retire, crash-recovery adopt) and `StopRun` (before removing worktrees), `sweepWorktrees` waits briefly for the worker's own agent to exit and then sends `SIGTERM` followed by `SIGKILL` (checked by `StartTicks`) to leftover process trees in its worktree that hold no terminal and no agent CLI and hang off `init`/`systemd`, never touching main checkouts or roots. Every non-root agent launch (`startTerminal`) pins the process and its descendants to the least-held `worker_cpus`% core window (default 25%; `0` or `100` off) and, when `worker_memory_high` > 0 (default 0), places them into a transient `systemd --user` scope (`mesh-<name>-<pid>.scope`) with `MemoryHigh`. Adopted live non-root terminals restore their CPU holders on daemon restart. Both are abstracted behind `AgentConfig.Sys` (`SystemOps`) so tests never invoke real `busctl` or touch unrelated host processes.

## Worker accountability

What `bin/mesh watch` did with exit codes (design, "The watchdog"), done by the daemon. A parent hears of its children as an `info` from the daemon (actor `mesh`, a message like any other: stored, doorbell at the parent's next idle). Nothing here reopens, switches or retires an agent: acting on a limit is the limits pass's job, this only tells the parent.

- **Exit and lost:** an agent whose process ends (or whose terminal is gone, `lost`) with no report to its parent since its last task or answer tells the parent how (`[mesh alert exited <id>]`: exit code, signal, or lost), in the transaction that records the exit. One that had reported first is not alerted about. A stop someone asked for is told too.
- **Quiet and limited:** the pass (every `AccountEvery`, default 5 s) tells the parent once per stretch of silence that a child went `unknown` (`UnknownAfter`, default 10 min; `[mesh alert unknown <id>]`) or stopped `LIMITED` (`[mesh alert limited <id>]`, naming `mesh switch <name> --next`). The same alert is not repeated until the agent's next hook (its `LastActivity` moves): one that recovers by itself and hangs again before any hook is not told twice.
- **A turn without a report:** an agent at its prompt that was given a task or answer, and has sent no `plan`, `question`, `done` or `failed` since, with nothing unread in its inbox (the daemon's own nudge aside), is nudged once after `accountability.nudge_after` seconds (default 30; 0 turns nudges off): an `info` from `mesh` saying how to report. If it then has a turn (the nudge's doorbell rang) that ends the same way another `nudge_after` later, its parent is told once; a nudge whose doorbell is held back (a user typing) is not counted against it (`[mesh alert silent <id>]`). A new task or answer starts the count again.
- **A declared wait** (a `wait` message to the parent, which rings no doorbell) holds the nudge for `accountability.wait_max` seconds (default 4 h) from when it was sent, or until the next task or answer. The wait carries no deadline of its own yet (`TODO.md`).
- **Unread instructions:** `SendMessage` refuses a `plan`, `question`, `done` or `failed` from an agent while a `task` or `answer` is unread in its inbox (`FailedPrecondition`, nothing stored): it would answer instructions the agent hasn't read. `mesh inbox` reads them; `info` and `wait` are not reports and go through.

## Protocol and skills

`share/` is what a daemon agent reads and the skills it can use, written for the daemon's events (a message rings at the recipient's next idle; no watch process, no exit codes, no panes) and for the commands the Go CLI has. What the CLI lacks (`reset`/`brief`) the files say plainly, with the manual way; `internal/cli/share_test.go` fails when a file names a `mesh` command or flag that doesn't exist, unless its sentence says "yet". The herdr mesh's `protocol/` and `skills/` are untouched until PR 6 of the switchover.

- **`--share <dir>`** (default `../share` of the `meshd` binary, which is the installed `~/.local/lib/agent-mesh/share` or, in a dev build, this folder; ignored when it has no `protocol/`). Every agent gets `$AGENT_MESH_SHARE` (the absolute path).
- **Skills per launch:** a Claude agent is launched with `--plugin-dir <share>` when `<share>/.claude-plugin/plugin.json` exists, so the skills load for that session only (as `agent-mesh-daemon:<name>`), never into the user's own `~/.claude`. agy has no such flag: its protocol tells it to read the `SKILL.md`.
- **The first doorbell of each process** (a new terminal: a spawn, a resume, a reopen, a restart of meshd) ends with `(first one here: read <share>/protocol/PROTOCOL.md once, and follow it)`; a root's names `ROOT_CARD.md`, which tells it to read `PROTOCOL.md` too. The path is absolute, since the agent's CLI doesn't expand variables in what is typed to it. Later doorbells of the same process don't repeat it. The global rules block (`rules/global-snippet.md`) says the same for agents that read it first: the file the doorbell names, else `$AGENT_MESH_SHARE/protocol/PROTOCOL.md`, else `~/.config/agent-mesh/PROTOCOL.md` (a herdr agent).
- **Skills:** `delegate` (the user's own session starts a run and a root and stops; the root is the supervisor), `delegate-review` (a root runs the review), `self-review`, `check-plan`, `find-peers` (the user's session searches and registers peers with `mesh add-peer`) and `harvest-peers` (a root asks the peers with `mesh ask --peers`, checks their findings and reports; `HARVEST.md` holds the briefs).

## Protocol notes

- **Writes** carry `RequestMeta`: a repeated `mutation_id` returns the first response without running again, and a write past `expires_at` is refused. Events a write causes carry its mutation id.
- **Events** have a `seq` and the log's `generation`. `SubscribeEvents` with a cursor of the same generation resumes (`Resumed`, then the backlog, then live); anything else starts with a `Snapshot`. Only an `End` frame ends a stream on purpose; after any other close, resubscribe from the last cursor. A subscriber more than `events.LiveBuffer` events behind is dropped (`resource_exhausted`) and resumes the same way.
- **What waits on the user:** `ListWaiting {run_id}` returns `Waiting {kind, run_id, agent_id, message, detail}` rows, oldest first, plans and questions before prompts (`internal/daemon/waiting.go`; `mesh waiting`). A row is a PLAN or QUESTION sent to an open run's lead (its first root) that no later ANSWER to its author followed, unless the author exited (a retired one is woken by the answer, so it counts); or an agent shown as NEEDS_INPUT (a prompt left unanswered past the unknown threshold shows as unknown and drops out). A device or read-only device reads every open run; a lead reads its own run's, and a worker is refused. Read-only: no event, so a client re-lists after the events that change it (a message, a state change, an exit, a retire, a stopped run).
