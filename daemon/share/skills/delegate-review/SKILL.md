# delegate-review

Get a review for the user's request: `$ARGUMENTS` when the user typed the command, otherwise the request that brought you here. You are the user's own session, not an agent of the mesh: a reviewer started with no parent has nobody to report to, so the review runs under a **root** that starts the reviewers, collects their answers and checks each finding against the code.

1. **The PR:** the link or number given. Otherwise the current branch's PR (`gh pr view --json url -q .url`). If there is none, ask the user which PR.
2. **The reviewers:** Claude, agy, Copilot and OpenCode have daemon adapters; a CLI that isn't installed here, or Copilot at its quota or refused by its policy, is left out with a note and the root picks from what is left. Every CLI named (vendor words: Gemini, Hydrogen, Flash, Argon → agy; GPT, Copilot → copilot; OpenCode, Big Pickle, DeepSeek, GLM, free models → opencode; Opus, Sonnet, Fable → claude), `all` for every installed one, or none named: the root picks by the PR's size from `review.reviewers.<size>` (`mesh settings --prefix review`), what is installed and the quotas. The practice is **one outside reviewer for a small PR, two for a large one** (`review.reviewers.large` has two slots): the size picks the reviewers, the PR's risk their model: a routine PR of any size is reviewed on tier `mid`, OpenCode's mid tier first when the slot lists it (free, another family than either author), else the CLI that isn't the author's, else the author's CLI in a fresh session; a risky PR (money, data that matters, secrets or the machine exposed to others, a deploy: ORCHESTRATE "Tiers" defines it; concurrency and the mesh's own internals are not; any size, a one-file billing change included) gets a **relay** instead, one `strong` reviewer at a time (the other CLI on the whole PR, the author fixes, the other family on the whole PR at the new head, the author fixes, the first again on only the fix commits with `--since`; at most 3 steps, one command run again after each fix: `mesh ask --repo <path> --review <PR> --relay`, see "A relay for a risky PR" in ORCHESTRATE's "Questions and reviews"), never two at once.
3. **The size:** by hand-written files, never by lines: `small` for up to about 10, `large` for more (`gh pr diff <PR> --name-only` lists them; generated code, lockfiles, fixtures, golden files and pure moves or renames don't count). Size sets how many reviewers and how deep; risk (ORCHESTRATE "Tiers") sets their strength and the relay, whatever the size.
4. **Start the run and its root** (or adopt this session as the root when the user asks for it, as the `delegate` skill's step 4 says) as the `delegate` skill's steps 1 to 4 say (`mesh hello`, `mesh start-run`, the request file, `mesh spawn --role root`), with a request file saying: review `<PR link>` (size, reviewers or `auto`, tier `mid` or `strong` by the PR's risk); follow "Questions and reviews" in `ORCHESTRATE.md`; run one round (`mesh ask --repo <path> --review <PR> --size <size> --tier <tier> --reviewers <auto, all or the kinds>`: the answers come as one message with the file) and end your turn until it arrives; check every finding against the code; give the user the merged, checked findings with each reviewer's name and your verdict on each (agree, agree with a different fix, or disagree and why); fix nothing unless the user asks. Pass the repo's checkout as `--repo`.
5. **Tell the user** the run id and the root's name; the root reports the findings to them in the app (or, to watch it in a terminal, `mesh open <root name>`). A re-review after a fix is the same request again in the same run: `mesh send <root name> --type task --body "re-review <PR> at <new head>"`; the root runs the same round again and the same reviewers read only the fix.
