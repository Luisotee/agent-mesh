# android

The agent-mesh Android app: Kotlin and Jetpack Compose. It is step 4 of `docs/apps.md` ("Order of work"); the plan, the principles it follows and what is decided are there. Nothing here is installed or put on PATH.

The app is a client of the daemon (`daemon/`). Everything it does to a host is a call on the host's action registry (`proto/`, ConnectRPC with a generated client), so an agent or the CLI can do all it can. It has no account, no hosted service and no telemetry, and talks only to the hosts it is told about.

## What the first version does

Hosts (several, each with routes tried in order), a connection per host with a banner and a log, runs and agents live from the event stream (each run a tree from its lead, state icons whose shape differs by state, a plain status sentence), the host's settings generated from its schema, and six themes (Dracula by default, chosen per device) in the desktop's look: bundled Geist and JetBrains Mono, a colour per project, vendor marks in their brand colours, syntax-coloured code blocks, skeleton loading and motion that stands still when the system asks for none. A read-only terminal per agent, plans, questions and reports, and notifications (`TODO.md` lists what's next).

## One navigation

A drawer holds everything you move between (`ui/Sidebar.kt`; the rules are the desktop's `sidebar.ts` (desktop PR #193), ported as `derive/Projects.kt` with its cases). It slides over home and the open agent; from 840 dp wide (a tablet, a folded phone) it stays open beside them. From the top:

- **Search** over projects, runs, agents, CLIs and models.
- **Waiting on you**, only while something does: a plan or a question opens in place with Approve or an answer; a prompt in a terminal opens its terminal.
- **Projects across all hosts**, in one list: your pins first (in pin order), then those with something waiting on you, then the latest activity. A project is a repo a run is led from, or works in ("Also working here"), or one you added (**+ › Add a project**, from the host's `ListProjects`). Under it each run shows as its lead, its workers under that, and reviewers and askers folded into a chip ("·2 reviews") rather than rows. Finished and closed runs fold under **Earlier**. The same folder on two hosts is two rows; with more than one host paired each carries its host's name, and a host that is down says so in one line. A project's menu (⋮ or long press): New lead here, Pin, Hide (it comes back while something in it waits on you; hidden ones are under "Hidden projects"), Copy the path. Held down, a run offers Add an agent. Pins and hides are kept on this phone only.
- **Quota**: a meter per window and host (Claude's windows, agy's fullest row), green, amber from the reserve, red when used up; a tap opens Usage and cost.
- **Settings**, **Live** and **+**.

**Home** is what needs you and the live runs of every host as their leads, with **New lead**. Hosts are in Settings › Hosts (a host's settings, usage, log, address, remove; pairing). Opening an agent from the drawer, home or a notification replaces the open one, so Back from any agent goes home.

## The terminal

**Project terminals:** under each project in the drawer, `>_` (or "New terminal here" in its menu) starts a plain login shell in its folder on the host (`OpenShell`, a device with the input right; it keeps running when the app is closed), and each running shell is a row ("Terminal", or "Terminal · 14:02" when a project has several) that opens its screen: the terminal with the key row and keyboard on, ⋯ › End the terminal… (asks first; Back only leaves it running). A shell opened here is sized to this screen: its columns and rows go with every attach (also with the keyboard hidden: hiding it reattaches at the taller view) and a `Resize` follows while you type, when the view changes (the keyboard comes up, a pinch); with the keyboard hidden the host only hears of a change at the next attach, since only a client that types may resize. The host sizes a terminal to its smallest client, so a desktop attached to that shell sees it at the phone's size while the phone is attached. A shell of the desktop's is attached at size 0, like an agent's terminal. The list follows `ShellChange` frames and is read again after a reconnect.

An agent's terminal (the `>_` button in its top bar) shows its CLI's screen as the host holds it, live, with 2,000 lines of history to scroll (drag; the view stays on the lines being read as new ones arrive; "Latest" jumps back). Pinch to zoom and pan, double tap to fit the host's width to the screen. A read-only device gets a "Read only" chip and only watches: the app asks for no input right and sends nothing but the attach, so the host answers terminal queries itself. A shell opens with its **Keyboard** on; an agent's terminal opens to be looked at, and the **Keyboard** chip turns typing on (Hide in the key row turns it off): the terminal then opens its stream with the input right (`input: true`) and shows the soft keyboard and a **key row** (sticky Ctrl and Alt, Esc, Tab, Shift-Tab, `^C` `^D` `^Z` `^L` in one tap, the arrows, Home, End, PgUp, PgDn, Del, Enter, `/ - | ~ \\`, **Paste**, **Hide**); `KeyEncoder` gives xterm's sequences (the arrows follow the program's application-cursor mode), a paste is the program's own bracketed or plain form (the emulator encodes it), and text from the keyboard goes through an invisible field that holds one character so typing and Backspace both show as a change. Input is sent only after the replay (`Ready`), as the host expects. **An agent's terminal is never resized by the phone** (the attach stays at size 0 and no `Resize` is sent; only a shell this phone opened carries a size). While a client with input is attached the host leaves answering the program's queries (device attributes, cursor position) to it, so a shell this phone opened **answers them with the phone's emulator, from the replay's end on** (a reply made while the replay was drawn is dropped: the host drops input before `Ready`); an agent's terminal or a shell of the desktop's does not (the desktop's emulator answers for itself, and a second answer would reach the program as typed input), so with the Keyboard on and no desktop attached a program that waits for such an answer waits: turn the keyboard off to let the host answer. A **long press** selects the word under the finger, dragging extends it, **Copy** puts it on the clipboard and a tap clears it (the selection is kept to the same text while output scrolls).

How it follows the host's protocol (`docs/apps.md`, "Terminal protocol"; `term/TermClient.kt`): the first attach asks for a repaint; after a drop it continues from the last (epoch, byte offset) with a fresh one-time ticket and a growing wait (the host falls back to a repaint, marked reanchored, when it can't); a "slow" close (4001) reattaches at once; a `Resized` frame moves the screen to the new size and epoch in place (Termux's `resize`, no reattach); output of another epoch with no such frame (an older host) means someone resized, so it repaints and takes the new size. An agent's terminal attaches with size 0 ("unknown"), so a phone never shrinks the terminal the desktop is using (only a shell this phone opened carries a size); the host's size is drawn, fitted to the width and panned when that would be unreadable. The emulator is Termux's `terminal-emulator` module (Apache-2.0) copied into `terminal-emulator/` (its README says what changed); the drawing is ours (`ui/TerminalCanvas.kt`).

## One agent screen

The agent screen has no tabs: the chat is the screen. The top bar has the agent's vendor mark and state, `>_` (swaps the chat for its terminal and back; Back from the terminal is the chat) and ⋯, which opens **Details**, a bottom sheet: its pull requests (with Hold), the agents of its run (a tap opens one), the run's cost folded to one line (read when opened), the branch, worktree (Copy) and conversation id, **Send a message…**, and **Stop** or **Retire** (each asks first; not for a read-only device). Under the bar are the model chip (a tap changes it) and a strip of the agent's tree (its lead and workers, live state on each, a tap switches agent in place with no slide; reviewers and askers as one chip, "·2 reviews", that opens the details). A long press on a message: Copy, Quote in reply, Select text. A copy says so in a toast on Android 12 and earlier (13 and later show the system's own). A held-down drawer row offers the same: a run's Add an agent, Rename, Stop the run and Delete the run (an ended run only, confirmed first; the host keeps any work in git); an agent's Open, Open its terminal, Stop, Retire and Copy the worktree path; a read-only device sees only Open and Copy. `StopAgent`, `RetireAgent`, `RenameRun` and `StopRun` are registry actions pinned in `RegistryPinTest`. `chat/Timeline.kt` merges the messages into the transcript by time (a pure function with tests). Device settings are grouped cards with a line on each setting, and the themes are swatch cards.

## Chat, the live dock, usage, model, pull requests, starting runs

The desktop's agent screens, laid out for a thumb (the same rules, ported as pure code with its test cases: `chat/Transcript.kt`, `Dock.kt`, `Usage.kt`, `Models.kt`; every call is a registry action a device may call, pinned by `RegistryPinTest`).

- **Sending** (`PromptAgent`): what you send is a bubble under the conversation at once, before the host has answered (`HostRuntime.say`, `chat/Outbox.kt`): "Sending…"; then the host's own queue bubble takes its place (it says what the prompt waits for: "Sent when it finishes its turn", "Sent when it runs again", with Edit and ×), or, when the host typed it at once, "Sent" until the record shows it (the desktop's rule: the next new user prompt after what the chat held ends it, at most 30 s). Without a connection the bubble says "Not connected: sent when it is back" and goes when the connection returns (Edit takes it back into the box, × drops it); a refusal stays on the bubble as "Not sent: <the host's words>" with Retry, Edit and ×. Prompts go to the host in the order they were sent, and what is unsent is kept on the device across a restart (one that was out when the app closed comes back as not sent: the host may have it). A prompt sent while offline is held, and so may be sent late: look at the bubbles after being offline.
- **Chat** (`ReadTranscript`, `PromptAgent`; the agent screen is the chat, see "One agent screen" below): the agent's CLI record as blocks: what you typed (a bubble in the project's colour), the reply as Markdown, the mesh's messages as cards at their place by time (the CLI's own doorbell line gives way to its card once the run's messages are loaded), tool calls folded into "Ran 3 tools: Bash ×2, Read" (tap to see each call and its answer, a few lines of each with Show all). Markdown is parsed ahead (a cache by text: a message keeps its height as the list scrolls), its blocks sit close together, and a table has columns as wide as their text, wrapped cells and a sideways scroll. It reads the tail first, "Load earlier" reads back, and it reads on 300 ms after an event of the agent, every 2 s while it works, and 0.3 s and 1.5 s after you send. The composer types into the same running process as its terminal does. It is Markdown-aware (below), Enter adds a line and Send is the button. Sending never fails for the agent's state: when the agent works, waits at a prompt (which offers to open the terminal), has a draft in its box or is starting, the host queues the prompt and types it at the next idle; it shows under the conversation as a dimmed bubble saying what it waits for, with Edit (takes it back into the box), × (`WithdrawPrompt`) and, when a draft in the agent's box holds it, Send anyway (names the draft, then `SendPromptAnyway`), read with `ListPrompts` and kept by the `Prompt*` events. While the agent works (Claude Code only: the host knows its interrupt key; not at a prompt, where Esc would deny the dialog) an empty box has Stop (`InterruptAgent`) where Send is; typing turns it back into Send. The composer is off for a read-only device and a stopped agent. What is typed is kept per agent on the device (`DevicePrefs`) across navigation and restarts, and cleared when sent. The host reads a record for Claude only; other CLIs show the terminal's note. The chat reads only while it is on screen.
- **The composer** (`ui/chat/MarkdownField.kt`, the chat's box and the same field in Send a message, Answer and Ask for changes): Enter on a list item (`-`, `*`, `+`, `1.`, `1)`, `- [ ]`) starts the next item and on an empty one ends the list; while focused, a row above the keyboard wraps the selection in `**`, `_` or `` ` `` (and unwraps it), turns the lines it touches into a list or a checklist (and back), or makes a link. A hardware keyboard has Ctrl/Cmd+B, I, E, K and Tab/Shift+Tab to indent a list item. The rules are the pure `chat/MarkdownEdit.kt`; the Enter, Tab and wrapping cases are `shared/markdown-edit/cases.json`, which the desktop's `composer-keys.test.ts` reads as well. The field grows to 40% of the screen height, then scrolls.
- **Live dock** (**Live**, on home and in the drawer): a tile per live agent of the open runs, the ones that need you first, each with the tool it runs now and the last thing it said; a tap opens its chat, or its terminal at a prompt. The tool comes from the ephemeral `AgentActivity` frames the app asks for (`SubscribeEventsRequest.activity`): they change a working agent's detail and nothing else, are never replayed, and the next state change overrides them. It spans every host, the host's name on each tile.
- **What waits on the user** (home, and the drawer's "Waiting on you"): What waits on the user is the host's own list (`ListWaiting`, read again after a plan, question, answer, state change or run stop, as the desktop does), so both apps agree; until the host has answered (or on a host too old to have it) the app derives it from the messages. The PRs are read at connect and every minute (`ListPullRequests`, which the host caches for two minutes), and a `PullRequestChanged` event updates one at once. The agents are listed again every 30 s, so a quiet agent shows as unknown. A waiting plan or question opens in place on that list, with its Approve or answer (not for a read-only device), bound to the very plan or question shown: if its author sent a newer one meanwhile, the tap is refused with that reason instead of answering the newer one. Actions never wait for a connection: offline, Send, Switch and Hold merge are off, and nothing is kept to be sent when it returns.
- **Usage** (a tap on a host's meters in the drawer, or Settings › Hosts): Claude's windows and agy's rows against the reserve line (the host starts nothing new on a window past it), read again each minute, and the spend of the last 24 hours, 7 or 30 days or one run, with the tokens first and the dollars only as what the Claude sessions would cost at API prices, beside them (`GetUsage`, `GetCost`).
- **Model and effort** (a chip under the agent's top bar): the CLI, model and effort it runs on, "Switching to …" while a reopen is under way, and **Change** (not for a read-only device): a tier, a model of the host's list for its CLI (read from `CheckModels` when the sheet opens; any model id may be typed), or an effort alone. The host reopens the same conversation (`SwitchAgent`) and its refusal (already on it, at the quota reserve) is shown in its words.
- **Pull requests** (the agent's details, ⋯): each PR with its state and checks, **Open** on GitHub, and **Hold merge** or **Release** (`HoldPullRequest`: a root never merges a held PR; the hold shows through the PR's event).
- **Start a lead, add an agent** (home's **New lead**, the drawer's + menu, a project's **New lead here**, and a held-down run's **Add an agent**; not for a read-only device): the desktop's forms. A new run is a title and, unless unticked, its lead (`StartRun`, then `SpawnAgent`); an added agent is a lead if the run has none, else a worker. The repo is one of the host's projects (`ListProjects`) or a typed path, the name (from the title by default) names the branch and the agent, the CLI is chosen, the tier is one of the host's for it (a worker always has a tier or a named model; a lead may take the CLI's default), and an optional first message. The host's refusal (the agent cap, the quota reserve) is shown in its words.
- **Settings:** `app.keys.*` (key chords for a keyboard) are not listed, with a line saying so; edit them in the desktop app.

## Plans, questions, reports and notifications

An agent's conversation with the rest of its run is in its chat, as cards in Markdown at their place by time; **Send a message…** in the details (⋯) sends a task, answer or info. A plan or question that waits on the user (derived as on the desktop: sent to the run's lead, nobody has answered its author since, the author is still there) shows its form in place: **Approve** (`ApproveAgent`, which moves a planning worker to its execution model in the same conversation and takes any other agent's approval; the host takes it only while the agent's newest report is a plan nobody has answered, so a lead that answered first wins), **Request changes** (`answer` "changes: …") and **Send answer**. Home's "Waiting on you" opens the chat, or the terminal for an agent at a prompt. History is paged in with `ListMessages` after each sync, then kept by events.

Notifications are local first: the event streams stay open while the app is in the background (a foreground service with a quiet notification of its own; a device setting turns it off), and a live `UserNotice` event for the user becomes a notification (`notify/Notice.kt`: the host decides once, in the daemon's `internal/notice`, and the pushes, the desktop and this follow it; only live ones, judged by the host's clock; one per agent; the kinds `input`, `plan`, `question`, `report`, `failed`, `exited`, `limited`, `error`, `finished` and `ready`), filtered by the host's own `app.notify.enabled` and `app.notify.events`. **Activity** (the drawer's footer, with the count of what is unread on this phone) lists every `UserNotice` since the app connected, across hosts, newest first: the ones for you ("for you") and the ones that only inform (a worker's plan to a lead that decides it); a tap opens the agent, and looking at the list counts it as read. What waits on you (home, the drawer, a host's count) is only what the host says is for you (`Waiting.for_user`); the run's own chat still opens every plan and question to answer. A plan notification has **Approve**, a question an inline **Reply**, a tap opens the agent; a failed action says why in the notification.

**What to be told of.** Settings → "What to be told of" follows each host's own list (`app.notify.events`) until the phone chooses: one list of the ten kinds (`input`, `plan`, `question`, `report`, `failed`, `error`, `limited`, `exited`, `finished`, `ready`) for notifications on the phone and for pushes, whatever a host's own says; at least one stays on (none at all is the host's `app.notify.enabled`, which silences everything). It is sent to every host with the push registration (`RegisterPush.events`, kept per device on the host, migration 0014, and sent again when the choice changes) and applied to the live notifications (`notifies`). An agent that reaches its usage limit (`limited`, off by default as on the desktop: the daemon usually moves it on by itself) or ends a turn in an error (`error`) notices like the other kinds, the same rules as the desktop's `notify.ts` and the daemon's `internal/notice`.

**Push (notifications with the app closed).** With a UnifiedPush distributor on the phone (the ntfy app, pointed at the user's own ntfy server or ntfy.sh), the hosts push instead, with no connection kept open: Settings → "Notifications with the app closed" turns it on (the library picks the distributor, asking when there are several), shows each host's state, and sends a test. How it fits together:

- `notify/PushChannel.kt` wraps the UnifiedPush library. The app registers one *instance* per host (the instance is the host's id), so each host has its own endpoint and keys.
- The distributor hands the endpoint to `notify/MeshPushService.kt` (Android starts the process for it), and `notify/PushRegistrar.kt` gives it to the host with `RegisterPush`, then again on every connection that becomes ready, so a new endpoint or a host that lost it heals. Endpoints are kept sealed with the Keystore key, like tokens.
- A push is the notice itself, encrypted by the host for this phone's keys (RFC 8291) and decrypted by the library; one it couldn't decrypt isn't from the host and is dropped. `notify/PushPayload.kt` reads it, and `AppContainer.onPush` posts it as the live stream would (the host already applied its notify settings). A push from a daemon other than the host's, or for the agent on screen, isn't posted.
- The same event can come from the live stream and from a push: `Notifier` posts each (host, event seq) once: the push's `seq` is the `UserNotice` event's own, the same number the live stream brings.
- Turning push off drops the instances at the distributor at once, then tells each reachable host (`UnregisterPush`) in the background. A host's `RegisterPush` and `UnregisterPush` calls go one at a time, in the order asked (`PushRegistrar`), and a registration re-checks that push is still on once its turn comes, so quick toggles end as the switch says. Removing a host drops its instance, and the host deletes the endpoint once the push server says it is gone. The connector forgets the chosen distributor when its last instance goes, so `UnifiedPushChannel.unregister` puts it back: otherwise a host added after removing the only one would never register.

With push on, "Stay connected in the background" can be turned off. What wasn't run here (no phone, no emulator): the distributor hand-off and the system showing the notification on a device. `DaemonE2ETest` covers the rest end to end: a real meshd's push, decrypted with the library's own WebPush code.

## Performance

The message list is a lazy list keyed by message id with a content type per message type, so a transcript of any length composes only the rows on screen (`MessagesTest`: 2,000 messages compose at most 40 rows). Plain bodies are plain text and a long one is cut to a preview until "Show all", so a row has its final height at once and the list doesn't shift under the user's thumb; only an expanded long body is parsed off the main thread. The list follows new messages only while the user is at the bottom. What can't be measured on the JVM is the frame-time half of the bar in `docs/apps.md`: a 2,000-message transcript streaming for 10 minutes with no dropped frames and no memory growth. To check it on a phone: connect to a host, start a run whose lead and workers exchange messages (or replay a transcript with `mesh send` in a loop), then watch `adb shell dumpsys gfxinfo dev.agentmesh.android.debug` (janky frames) and `adb shell dumpsys meminfo dev.agentmesh.android.debug` over the ten minutes.

## Connecting a host

A host is a machine running meshd. The usual way is **pairing**; adding an address and a device token by hand still works (for a debug host, or one you already have a token for).

**Pairing.** On the host, `mesh pair --name "my phone"` prints a link (`agentmesh://pair?v=1&h=…&fp=…&t=…`, with the routes the host offers; `docs/relay.md`, "Pairing flow"). `mesh pair` draws the link as a QR code in the terminal too (`--format json` prints the whole response). In the app, tap **Pair with a host** and then **Scan the QR code**, or paste the link; or open the link on the phone (a camera app that reads the QR code offers to open it with agent-mesh). The screen shows which host the code names and where the app would reach it, and nothing is sent until you tap **Pair**: the app then redeems the one-time token (`PairingService/RedeemPairing`) on the code's first route that answers, checks that the host is the one the code names, and saves it with its routes, the certificate pin and the new device token (the Keystore seals both the device token and the relay token). A code works once and expires after ten minutes by default: if the host accepted it and something then failed, make a new one. Pairing the same host again gives its entry the new token and the code's routes (a route with the same address takes the code's version) and keeps the routes the code doesn't name, such as a Tailscale address you added by hand. A host reached only through a relay can be edited with the address left empty.

**Removing a host** asks whether to also unpair the phone: when the host is connected, the box is ticked, and the app calls `RevokeSelf` (`mesh revoke-self`) so the host revokes this phone's token, streams and relay token before the app forgets the host. If the call fails the host stays, with Try again (which only retries the unpair, and waits while the host is unreachable) and Remove here only; a host that isn't reachable can only be removed here, and its owner revokes the device with `mesh revoke-device`.

**Routes.** A pairing code can carry two, tried in order, so the same host is reached at home and away:
- *Direct*: `https://` to `meshd --listen`'s TLS address (a LAN or tailnet address), pinned to the daemon's certificate. A host's built-in Tailscale node (`meshd --tailscale`) puts its tailnet address (`100.x`, or a `*.ts.net` name) in the link: the app labels such a route "tailnet" and says the Tailscale app must be on the phone. The phone can't read the node's status (`TailnetStatus` is for the host's own device).
- *Relay*: your own `mesh-relay`'s raw TCP endpoint. Every connection sends `MESH1 <host id> <relay client token>`, waits for `OK`, and then runs TLS to the host on the same socket, pinned to its certificate, so the relay only splices bytes (`net/RelaySocketFactory.kt`; the relay's refusals, such as the host being offline or the token not accepted, are shown in its own words). A token the relay refuses is shown with an auth message (pair again); with other routes the app keeps trying them, and stops only once every route was refused in a row.

- `http://` is accepted only for `localhost`, `127.0.0.1` and the emulator's `10.0.2.2` (a debug host: `adb reverse tcp:<port> tcp:<port>`, then `http://127.0.0.1:<port>` with `meshd --tcp`).
- Anywhere else the address is `https://`: for a machine on your tailnet, `tailscale serve --https=443 http://127.0.0.1:<port>` gives it a real certificate. A host with its own certificate takes its SHA-256 as a pin, and then only that certificate is accepted.
- **The QR scanner's camera wiring is untested here** (`pair/QrScanner.kt`, CameraX): there is no emulator or phone on the machine that built it. What is tested is everything around it: ZXing decoding a generated QR code of a real link at several rotations (`QrDecoderTest`), the paste, deep-link and pairing flow, and the relay and TLS routes against a stand-in relay (`RelayRouteTlsTest`) and the real `mesh-relay` and `meshd --listen` on loopback (`PairingE2ETest`). The first time on a phone: Pair with a host, Scan, the permission prompt, and a code from `mesh pair`.

## Layout

- `app/src/main/kotlin/dev/agentmesh/android/`: `net/` (routes and pinning, the relay socket, pairing links, the one client wrapper `MeshApi`, `HostConnection`; the only package that reaches the network), `pair/` (the QR decoder and the camera scanner), `store/` (`HostState` and `applyFrame`, built only from snapshot and events), `derive/` (run trees, status sentences, what waits on the user), `hosts/` (the host list, sealed tokens, the pairing flow), `notify/` (local notifications and their actions, the background service, push through UnifiedPush), `theme/`, `ui/` (Compose screens), `HostRuntime.kt` (one host's connection and state), `MeshApp.kt` (what lives as long as the process).
- `app/src/gen/`: generated Java (protobuf lite) and Kotlin (ConnectRPC) code, committed; reviewers can skip it.
- `../shared/themes/`: one JSON file per theme, shared with the desktop and built into the APK as `assets/themes/`.
- `app/src/test/`: JVM tests; `DaemonHarness` runs a real meshd with the fake `claude`.
- `scripts/`: `setup.sh`, `env.sh`, `gen.sh`, `check.sh`, `protoc-gen-connect-kotlin`.

## Toolchain

`scripts/setup.sh` installs, under `~/.local/opt` and with no sudo: the Android SDK (command-line tools, platform 37.2, build-tools 37.0.0), a Temurin 21 JDK (the machine had a JRE only, and the generated Java needs `javac`) and the Gradle distribution that bootstraps the wrapper. `scripts/env.sh` puts them on PATH for the other scripts and points `GRADLE_USER_HOME` at `~/.local/opt/gradle-home`. Go (`~/.local/go`) and buf (`~/.local/opt/buf`) are the daemon's, as in `daemon/README.md`.

## Commands

```bash
android/scripts/setup.sh      # once: the SDK, the JDK, Gradle
android/scripts/check.sh      # the CI equivalent: generated code current, unit + Compose + meshd end-to-end tests, lint, debug APK
android/scripts/gen.sh        # after a .proto change: regenerate app/src/gen
cd android && source scripts/env.sh && ./gradlew testDebugUnitTest      # one task
```

`check.sh` builds `app/build/outputs/apk/debug/app-debug.apk` and `app/build/outputs/apk/release/app-release.apk`: the release-type one is run through R8 without shrinking or renaming (`app/proguard-rules.pro`; how much R8 optimizes under `-dontshrink` is not measured), not debuggable, with the libraries' baseline profiles compiled in, and signed with the debug key so it installs beside the debug one; Compose is much slower in a debug build, so judge speed by this one. It has been built but not run on a device. The end-to-end tests build meshd, mesh-term, mesh, mesh-relay and the fake `claude` with Go into `app/build/e2e-bin`, then give each test a state dir, HOME and loopback ports (and, for pairing, a relay with its own secret) of its own under a temp dir: they read and write nothing of yours, and are skipped when Go isn't found or `SKIP_E2E=1` is set. Dependencies are pinned by `gradle/verification-metadata.xml`; after adding one, run `./gradlew --write-verification-metadata sha256 testDebugUnitTest lintDebug assembleDebug writeCodegenTools` and review the diff.

## Emulator

There is no emulator run in `check.sh`: Compose screens run on the JVM under Robolectric. Maestro flows (`maestro/`) drive the installed APK on an emulator or a phone; WSL needs `/dev/kvm`, and this user isn't in the `kvm` group, so they haven't run here.
