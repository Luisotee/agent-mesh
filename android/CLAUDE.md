# android/: rules for agents

The Android app: Kotlin and Jetpack Compose, minSdk 26, a client of the daemon (`daemon/`), step 4 of `docs/apps.md`. Nothing here is installed or put on PATH. `README.md` is the full reference (what the app does, connecting a host, the toolchain); `docs/apps.md` has the plan and what is decided ("Stack", "Decided"). context7 and WebSearch/WebFetch are available to every agent: check Compose's, connect-kotlin's and the Android SDK's current API there (the app targets SDK 37) rather than from memory.

## Toolchain

All of it lives under `~/.local/opt`, off PATH, with nothing global: the Android SDK, a Temurin 21 JDK (the machine has only a JRE, and the generated Java needs `javac`) and the Gradle distribution that bootstraps the wrapper. `scripts/setup.sh` installs them, needs no sudo and is safe to re-run. **`source scripts/env.sh` before any `./gradlew`**: it puts them, Go and buf on PATH and points `GRADLE_USER_HOME` at `~/.local/opt/gradle-home`. The scripts source it themselves.

## Commands

Run from `android/`.

```bash
scripts/setup.sh                             # once: the SDK, the JDK, Gradle
scripts/check.sh                             # the CI equivalent: gen current, unit + Compose + meshd e2e tests, lint, debug APK
SKIP_E2E=1 scripts/check.sh                  # without the meshd end-to-end tests
scripts/gen.sh                               # after a .proto change: regenerate app/src/gen
source scripts/env.sh && ./gradlew testDebugUnitTest                                       # the JVM tests
source scripts/env.sh && ./gradlew testDebugUnitTest --tests 'dev.agentmesh.android.StoreTest'   # one class
source scripts/env.sh && ./gradlew lintDebug assembleDebug
```

The end-to-end tests (`DaemonE2ETest`, through `DaemonHarness`) build meshd, mesh-term, mesh, mesh-relay and the fake `claude` with Go into `app/build/e2e-bin`, and give each test its own state dir, HOME and loopback port, so they touch nothing of the user's; they are skipped when Go isn't found or `SKIP_E2E=1` is set. Run `scripts/check.sh` before you report a change here: the repo runs no hosted CI.

## Layout

Code is in `app/src/main/kotlin/dev/agentmesh/android/`: `net/` (routes and pinning, `RelaySocketFactory`, `Pairing` links, `MeshApi`, `HostConnection`), `pair/` (the QR decoder and camera scanner), `store/` (`HostState`, `applyFrame`, and `HostRefresher`: what the stream doesn't carry), `chat/` (the transcript and its sync, `Timeline.kt` the merged timeline, `MarkdownEdit.kt` the composer's rules), `derive/` (run trees, status sentences, the dock, usage and models, what waits on the user, `Projects.kt` the drawer's projects across hosts, a project's identity hue `Hue.kt` and the vendor of a CLI or model `Vendor.kt`), `hosts/` (the host list, sealed tokens, `PairingFlow`), `notify/` (notifications and their actions, `ConnectionService`, UnifiedPush: `PushChannel`, `MeshPushService`, `PushRegistrar`), `theme/`, `ui/` (Compose screens: `AppNav.kt` one drawer around the screens, `Sidebar.kt` the drawer, `Home.kt`; the look: `Type.kt` the bundled fonts and the type scale, `Motion.kt`, `Shimmer.kt` skeletons, `VendorIcon.kt`), `res/font/` (Geist and JetBrains Mono, OFL, licences in `android/licenses/`), `HostRuntime.kt` (one host's connection and state) and `MeshApp.kt` (what lives as long as the process). Generated Java and Kotlin is in `app/src/gen/` (committed), one JSON file per theme is in `../shared/themes/` (shared with the desktop; the build adds `../shared` as an assets dir), JVM tests are in `app/src/test/`, and Maestro flows are in `maestro/`.

## Conventions

- **Only `net/` reaches the network** or the generated client, and every method it calls must be a `MeshService` action a device may call (`net`'s `UI_ACTIONS`), apart from `PairingService/RedeemPairing`, the one call a device makes before it has a token. `RegistryPinTest` checks both, so a new call starts there. Anything the app does is an action an agent or the CLI can call too (`docs/apps.md`, "Principles"): a new capability is a registry action first (`proto/CLAUDE.md`).
- **State** is built only from the snapshot and events (`applyFrame`, pure), and a live stream and its replay must give the same state (the parity test in `StoreTest`). What waits on the user is the host's (`ListWaiting`, kept by `HostRefresher` like the desktop's `refresh.ts`, with the PRs and the agents listed again); `derive/` derives it only until the host has answered. An `AgentActivity` frame changes a working agent's detail and is the one thing not in the replay parity.
- **Same behaviour as the desktop:** the connection rules (handshake, heartbeat, backoff, generation fence) and their test cases mirror the desktop's `src/connection.ts`, and the theme files are the desktop's own (`shared/themes/`: change a token there and both apps change). The theme follows the `app.theme` of the first host (list order) that has set one itself (an unset host reports its default, which is no choice), unless the device chose one.
- **Secrets** (a device token, a relay client token, a pairing code's token, a push endpoint and its keys) are sealed with an Android Keystore key (`hosts/`) or held only in memory; never store them in the clear, in saved state or in a log or `toString`. A pairing link only fills the screen: nothing is sent until the user has seen the host it names and taps Pair.
- **Generated code:** never edit `app/src/gen/` by hand. Regenerate it with `scripts/gen.sh`; `check.sh` fails when it is stale.
- **Dependencies** are pinned by `gradle/verification-metadata.xml`. After adding one, run `./gradlew --write-verification-metadata sha256 testDebugUnitTest lintDebug assembleDebug writeCodegenTools` and review the diff.
- **The look is the desktop's (`docs/apps.md`, the Android "Themes" bullet):** fonts, type scale, a project's hue (`hueOf`, the desktop's FNV-1a), vendor marks and brand colours (`VendorMarks.kt` holds the strings of `desktop/src/vendor-marks.ts`) and the theme tokens `hue-1…8`, `vendor-*` and `glow` come from the same files; `HueTest` and `VendorTest` pin them (a mark or a case changed on one side fails the other). Everything that moves reads `LocalReducedMotion`; a loading state is a skeleton, never a "Loading…" text; a moving shimmer must use `withInfiniteAnimationFrameMillis` (a plain frame loop keeps Compose from ever being idle in a test).
- **One navigation:** a drawer (`Sidebar.kt`) holds projects across hosts (`derive/Projects.kt`, the desktop's `sidebar.ts` (desktop PR #193) rules), what waits on the user and the quota; it slides over home and the agent below `WIDE_DP` (840 dp) and stays open beside them from it. Pins and hidden projects are device-local (`DevicePrefs`). Opening an agent (drawer, home, notification) replaces the one on screen (`popUpTo` home), so the stack is home, agent. Hosts live in Settings › Hosts. A new screen goes through the drawer's actions, not its own host list.
- **One agent screen:** no tabs: the chat is the screen (`ui/AgentScreen.kt`), with `>_` for the terminal, a model chip, the tree strip (`AgentTree.kt`) and Details (`Details.kt`); the mesh's messages are cards in the chat (`chat/Timeline.kt`). Anything that stops an agent or a run, retires or renames asks first (`AgentActions.kt`); the composer's Stop only interrupts a turn, as Esc does, and does not ask. `Tab` is only a hint for which view opens (the terminal, else the chat).
- **One composer:** every multi-line field is `ui/chat/MarkdownField.kt` on a `TextFieldState`; the Markdown rules (list continuation, wrapping) are the pure `chat/MarkdownEdit.kt`, pinned by `shared/markdown-edit/cases.json` (Android's `MarkdownEditTest` and the desktop's `composer-keys.test.ts` read it). A chat's draft is device-local (`DevicePrefs.draft`). The queue of a chat is host state kept by the `Prompt*` events (`HostState.prompts`, listed again after a snapshot), never a client-side list.
- **Insets:** the app is edge-to-edge, so the soft keyboard doesn't resize it. A Scaffold's body is `Modifier.inScaffold(pad)` (`ui/Insets.kt`), or `inScaffoldWithKeyboard(pad)` when it has text fields; never a bare `padding(pad)` above an `imePadding()`, which counts the navigation bar twice (a blank band over the keyboard). A `ModalBottomSheet` needs nothing: its default `contentWindowInsets` (`modalWindowInsets`, M3 1.5) is the safe drawing area, keyboard included. `KeyboardInsetsTest` lays a screen out with a bar and a keyboard.
- **Notices are the host's:** `notify/Notice.kt` only turns a `UserNotice` event (for the user, live) into a notification; it works nothing out from states or messages (the daemon's `internal/notice` does, once, for the pushes, the desktop and the Activity list). `HostState.activity` keeps every `UserNotice` (capped at 200) for `ui/ActivityScreen.kt`; "unread" is a per-host `seq` in `DevicePrefs`. What waits on the user is `waitingFor` (only `for_user`); the run's chat uses `waitingAllFor`.
- **Project shells:** the host's plain shells in a project's folder (`OpenShell`, `ListShells`, `CloseShell`) are `HostState.shells` (listed after a snapshot, kept by `ShellChange` frames; a frame while a list is out makes it ask again), rows under their project in the drawer and a screen of their own (`ui/ShellScreen.kt`: the terminal, ⋯ to end it with a confirmation, Back leaves it running). `TermClient` takes a `shell` target; a shell the phone opened (`DevicePrefs.markPhoneShell`, kept across restarts) is attached with the view's columns and rows (also with the keyboard off) and resized by `Resize` when the view changes, any other terminal at size 0 and never a resize. A shell opens with its keyboard on, an agent's terminal to be looked at; the client of a phone-opened shell answers the program's queries (the host's emulator is silent while a client types: `ReadOnlyOutput.reply`, set at `Ready`), others do not (the desktop answers, and a second answer would be typed input).
- **Markdown in a list:** a row must be as tall when it is composed as it ever is, or the list jumps under the thumb. Every Markdown body goes through `ui/messages/MarkdownCache` (an LRU of parses: `Markdown(State)`, never the library's `Markdown(text)`, which parses off the main thread and lays out empty first); a page of the transcript is warmed off the main thread before it is shown (`ChatSync`'s `warm`), a short body missed is parsed in place, a long one shows a placeholder once. A message card animates its size only for the user's own Show all. Nothing scrolls inside the chat's list (a tool's answer is a few lines and Show all). Tables are the app's own (`MeshTable`: columns as wide as their text up to a cap, cells wrap, the table scrolls sideways). `MarkdownRowsTest` pins this.
- **Screenshots:** `ShotsTest` renders the seeded screens to `app/build/shots/` (or `$SHOTS_DIR`) in a dark and a light theme, for looking at before and after a UI change. They are not goldens: nothing compares pixels.
- **No emulator here:** this user isn't in the `kvm` group, so Compose screens are tested on the JVM under Robolectric (`ScreensTest`), and the Maestro flows are written but haven't run. Don't report a Maestro flow as passing unless one actually ran.
- A change to these commands, the layout or the conventions updates this file in the same PR.
