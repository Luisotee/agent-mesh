# agent-mesh orchestration

The shared procedure behind `/delegate-agy` and `/delegate-claude`, for changes, questions, PR reviews and whole task lists. `/delegate-review` uses only its "Questions and reviews" section.

- **The root** is the agent running the command (typed by the user, or picked by the agent for the user's request), usually in the middle of its own work in its own repo. It keeps doing its own repo's part itself, and spawns one *worker* per **other** affected repo.
- **Each worker** loads its repo's `CLAUDE.md` / `AGENTS.md`, skills and hooks. Depending on the task's size, it either does the task directly, or researches it, sends the root a plan to review and, once the plan is approved, carries it out **itself**, with all the context its research built up.
- **Workers never spawn agents** of their own.

Read `PROTOCOL.md` as well: it applies to you too.

## Modes

| Mode | Worker | Plans on | Executes on |
|---|---|---|---|
| `agy` | `--kind agy` (also what `mesh spawn` does with no flags) | the first of Argon → Claude Opus → Flash with quota left, high effort | Flash, medium effort |
| `claude` | `--kind claude` | Opus, high effort | Opus, medium effort |

The mode sets the CLI for new workers, and the table is what a **large** task gets.

- **Models per phase:** with no `--model` (that is, `--model auto`), a large task's worker plans on a strong model. It moves to the execution phase when you approve its plan with `mesh approve`: agy moves to Flash, while Claude stays on Opus and only lowers its effort. It stays in the **same conversation**, so it keeps its research.
  - Effort follows the phase: high while planning, medium while executing (`--effort` / `--exec-effort`).
  - **Planning is enforced for Claude:** a Claude worker on a large task (or resumed with a task it plans, or an asker given one) runs with the asker's deny list (no file edits in its worktree or your checkout, no `git push`, no `gh pr` writes) until `mesh approve` reopens it without it. The shell stays open, so set-up and tests still run. A named `--model` doesn't skip that. agy has no deny list: its planners are held by the prompt alone.
  - For agy, `mesh` reads `agy -p /usage` and skips any model with 10% or less left. `mesh usage` shows the quotas (Claude's too) and what `auto` would pick.
  - **The quota reserve:** mesh keeps 10% of every quota for the user (`MESH_QUOTA_STOP`, 90% used). Past it, `spawn`, `ask`, `resume` with a task, `send --type task` and `approve` are refused for that vendor, and nothing is started or sent: tell the user which window and when it resets, and wait. Answers still go. Only when the user says to finish the run anyway, run `mesh reserve off` (`on` undoes it).
- **User overrides:** if the request names a model, agent or effort ("use Argon", "do it with Claude"), pass it as `--model`. That one model then runs the whole task, with no switch (default effort high). A named effort goes in `--effort` and covers planning and execution alike, with or without `--model`. Otherwise don't pass `--model`.
  - **Fable** (`--model fable`, Claude only) runs the whole task on Claude Fable 5.1, Anthropic's strongest model, which pays off on ambiguous root-cause hunts and architecture decisions. Use it only when the user names it: it draws on a capped share of the user's Claude limits.
- **Resolution:** `mesh` resolves the agy families `argon` / `flash` / `opus` / `sonnet` to the newest matching model. `mesh model --kind agy` shows what a spawn would use, and why.

### Sizes

Size every task, and pass `--size` on every `mesh spawn` and `mesh ask`. Only large work pays for a plan; the rest goes out as a direct task. Claude workers run Opus at every size, and agy saves its quota by running small work on Flash.

| Size | For | Claude worker | agy worker | Plan? |
|---|---|---|---|---|
| `trivial` | translations, copy, config, a version bump | Opus, medium effort, in the background | Flash, low | no |
| `small` | a bug fix, a UI tweak, a test, a contained refactor | Opus, medium effort, in the background | Flash, high | no |
| `large` (the default) | a feature, a cross-repo contract, anything you'd want to review before it's built | the mode table, in a pane | the mode table, in a pane | yes |

- **No plan** means the task goes out as a `Direct task (no plan)`: the worker makes the change, verifies it and opens the PR. If the task turns out bigger or less clear than described, it sends a `question` before changing anything.
- **A task-list group** (two or more tasks) gets one size for its combined work, from this table, as if it were one task: the smallest that fits, never above what it needs. Independent trivial and small tasks grouped for shared context stay `small` (`trivial` when all are) and go out as one direct task. A group is `large` when one of its tasks is, when its tasks build on each other or share a design decision the plan should settle, or when the combined change is one you'd want to review before it's built. The number of tasks alone never makes it large. A task in no group gets its own size ("Task lists" step 3).
- **When unsure, go up a size.** A wrong small task costs a redo, and a wrong large one only costs a plan review.
- **Questions:** `small`, unless answering needs research across the whole repo (then `large`, which plans on the strong model).
- **Reviews:** sized by the PR: `small` for a PR of up to a few hundred lines in a few files, `large` for anything bigger or riskier (auth, money, data migrations). A fresh reviewer runs at high effort whatever its size: checking is its whole job. The size sets how many reviewers it gets ("Routing") and the level of a Claude reviewer's `/code-review` (`medium` for a small review, `high` for a large one). A **tiny PR**, the PR of a trivial or small task or group (one with no plan) of at most **150 changed lines** (additions plus deletions, tests included) that touches nothing risky, gets no reviewers at all: you review it yourself (Root step 8). A large task's or large group's PR, or any bigger one, isn't tiny. Reading that much costs you less than two agents reading the repo in.
- **More effort is your call:** a fix round or a stuck worker gets more effort only when you judge the problem needs it, never by rule: most review fixes are a few lines the worker's current effort handles. A live worker keeps the effort it has (`mesh send` changes neither model nor effort), so to raise it, close it first with `mesh retire <name>` (not `mesh stop`, which ends the whole run), then resume it:
  - **Claude:** `mesh resume <name> --effort high …`, which runs the whole fix on Opus at high.
  - **agy:** `mesh resume <name> --model argon …` (or `opus` when Argon is out of quota). A named `--effort` alone keeps it on the family it last ran, which after execution is Flash.
  - A bug whose cause is still unknown is `large`.
- **Plan reviewed by the user:** for a large Claude task whose plan the user wants to approve themselves, pass `--plan-review user`. The worker plans in plan mode on Opus, in a pane, and the user approves it in that pane; Claude Code then executes it on Opus, in the same conversation. This task has no execution phase, so it runs at high effort throughout, unlike the medium a root-approved plan executes at. You don't review that plan, and you don't run `mesh approve`.

### Where workers run

- **Panes:** large tasks run in herdr panes, where the user can watch them and type into them.
- **Background:** Claude workers for trivial and small tasks run as background sessions (`claude --bg`). They don't take up the screen, but they're still recorded workers, which you can ask again, resume and review like any other.
  - `mesh status` shows them, and so does Claude Code's own `claude agents` view.
  - `mesh open <name>` attaches to one from any pane.
  - `--view pane|bg` overrides the default.
  - A fresh reviewer (`mesh ask --review`) gets a pane at any size, so the user sees the review.
- **When background falls back to a pane:** it needs a Claude root (it reports to you as a cross-session message), a repo Claude Code already trusts, and settings there that don't hold cross-session messages (`crossSessionInbound`). When one is missing, the worker opens in a pane instead, and the spawn output says why in `notes`.

### Routing

The command sets the CLI. You may *propose* routing a task to the other CLI, in the proposal (Root step 3; for a task list, its board), when it saves the user something:

- **Under `/delegate-agy`:** a large task can go to Claude when `mesh usage` shows Argon and Claude Opus both under the threshold.
- **Reviews:** each PR gets one or two reviewers by default (except a tiny PR, which you review yourself, see "Sizes"), picked by the review's size ("Sizes") and agy's quota. A `small` review gets **one**: agy while it has quota, else Copilot, else Claude. A `large` one (a big PR, or a risky one: auth, money, data migrations) gets **Claude plus one other**, run side by side since another model catches what the first one missed: agy while it has quota, else Copilot. `mesh` picks them itself (`--reviewers auto`, "Questions and reviews"): "agy has quota" means the model an agy reviewer of that size would run on (Flash for a small one, the plan chain for a large one) has at least `MESH_MIN_QUOTA` left by `mesh usage`'s reading, and "Copilot" means `copilot` is installed. A small PR gets one review round and no re-review ("Questions and reviews" step 2). A large PR's re-review after a fix goes to the same reviewers again except Copilot, whose credits are kept for first looks at the PRs that matter (so Claude alone after a Claude + Copilot round). A request that names reviewers gets those instead. The reviewers are a default, not a proposal: they need no confirmation.

A routing proposal is only a proposal: it goes into the proposal the user's go confirms (Root step 3). A request that names an agent or model is never re-routed.

## Root

1. **Start the run:** `mesh init --mode <mode> --request "<one-line summary>"`.
   - Under Claude Code, `init` records your session's address (`address` in its output). Claude workers' reports then arrive in your session as cross-session messages, so nothing is typed into the pane the user works in, and background workers become possible. If your session is reopened, your next mesh command records its new address.
   - How a report reaches you depends on what your session takes without the user's approval (design §11). Under a `crossSessionInbound: accept` setting, or in a mode that asks for permissions, `mesh` writes every report into your session itself, an agy worker's too. In bypass mode, a Claude worker passes it on with `SendMessage`, and an agy worker's doorbell is typed into your pane. A `hold` or `refuse` setting sends every report to your pane, and `init` and `status` warn about it (your settings are yours: mesh never changes them). If `address` is null (an agy root), every worker uses doorbells.
2. **Find the scope:** which repos the request touches (usually under `~/projects/`). Ask the user only if that's genuinely ambiguous.
   - **Your own repo** (the one you're running in) stays **yours**: you do its part yourself, in your current checkout and branch, exactly as you would without a mesh. Its rules are already loaded in your session. Spawn a worker for it only when the user explicitly asks to delegate it too.
   - **Every other repo** gets a worker.
   - **Work an earlier worker did** (its PR got review comments, "make it Y instead of X"): resume that worker instead of spawning a fresh one. See "Follow-ups" below.
   - **A question, a PR review or a peer ask** (`mesh ask --peers`; "how does shop-api do X?", "review the PR we just made") changes nothing: use `mesh ask` instead of steps 3 to 9. See "Questions and reviews" below.
   - **A list of tasks** ("work through these", a TODO list, issues): see "Task lists" below.
3. **Size and route each task** (see "Sizes" and "Routing"), then **propose the work and wait for the user's go.** Start nothing before it: no worktree, no spawn, no edit of your own repo's part.
   - **The proposal:** what you do yourself in your own repo, then one line per worker: its repo and slice, size, CLI and model, pane or background, and any routing. For a task list it is the board ("Task lists" step 1), groups included.
   - **One go covers the run:** its PRs' reviews (a default, see "Routing"), fix rounds on them, answers to workers, and the calls "Decide, don't ask" leaves to you. So do fixes in the run's own PRs (review findings, failing checks), a follow-up the user asks for on an earlier worker's work (the request is the go), and a small follow-up a worker proposes and builds in its own open PR. Other new work (a task added to the list, another repo, a follow-up big enough to plan) is proposed again.
   - **No proposal** for a read-only question, a PR review or a peer ask the user asked for (step 2 sends those past this step): the request is the work, and nothing changes.
   - **Running autonomously:** when the user says to go on without them ("I'll be out, keep going and merging as you see fit"), still write the proposal, for the record, write that instruction into `$(mesh dir)/notes.md` as a standing one (so a reset root keeps it, "Your own context"), and start without waiting.
4. **Spawn one worker per other repo.** Write a task file per repo in `$(mesh dir)/tasks/` and start the worker in a fresh worktree:
   ```bash
   mesh spawn --kind <kind> --size <size> --repo <path> --worktree <slug> \
     --task-file "$(mesh dir)/tasks/<repo>.md"      # plus --model/--effort only if the user named them
   ```
   The slug names both the branch (`mesh/<run>/<slug>`) and the agent (`<repo>-<slug>`), so make it short and descriptive: `fix-reactions`, not `task1`. The task file contains:
   - that repo's slice of the request, with the user's own words quoted where the wording matters
   - what you know from your own work that it needs: the contract your repo expects (field names, API shapes, error cases), with file paths in your repo it can read for reference
   - dependencies on other repos (what to wait for, and what the other workers will need from this one)
   - what you know about that repo and what you only assume, with the assumptions marked so the worker checks them
   - what is out of scope: files, behaviour or other repos it should leave alone
   - for a large task: "send your plan for review before changing anything"; for every task: "report `done` with the PR link"

   **Exit 4** from `spawn` (or `ask`, `resume`, `approve`, `switch`): the worker waits at a startup screen mesh doesn't answer (the `ALERT` names it and ends with the pane's last lines, e.g. a Settings Warning for a malformed `.claude/settings.json` rule). Its message is stored. Tell the user to clear it in that pane; don't answer it yourself. Start the watch as usual: it rings the doorbell once the screen is gone, and doesn't alert on that screen again (an agy root runs `mesh ring <worker>` once the user says it's cleared). After `ask`, `mesh watch <worker>` rings it and waits for the answer.

   Tell the user, in one line per worker, its size, model and where it runs (pane or background). When the spawn output has `notes` (for example "gemini-4-argon-high has 0% left"), add that in a few words.
5. **Supervise:**
   - **How reports reach you:**
     - Under a Claude root, a report arrives as a cross-session message (from `mesh`, or a Claude worker's `SendMessage`) and wakes you if you're idle.
     - agy workers ring a doorbell in your pane.
     - Either way, the full text is in your mailbox: run `mesh inbox`.
   - **Claude root:** start one `mesh watch --any --alerts --timeout 7200` with `run_in_background` after spawning. It ignores reports, which reach you anyway, and takes on each worker you spawn, resume or ask after it started (from its next poll), and lets a retired one go. It exits with 0 once every worker it watches has reported and ended or been retired (nothing to do, including workers it retired itself idle after their report, `auto-retired <names>`; not while a worker is retiring, within 2 minutes of a retire it wasn't resumed from, nor while a `mesh resume` is still compacting, so a group's retire and resume don't end it; started while that's under way, it waits too), with 0 once `mesh stop` starts (`run <run> stopped`, not alerts on the panes it closes; a `mesh watch <worker>` does the same, and a `mesh ask` stopped before its answer exits 1), with 0 at once when a watched worker's `plan`, `question`, `done` or `failed` is still unread in your mailbox (its doorbell was lost: read it with `mesh inbox`), or on an alert:
     - 3: a worker stopped without reporting (a `plan`, `question`, `done` or `failed`), and stayed silent after the one nudge the watch gave it ("its nudge was not delivered" if that doorbell didn't ring, with the reason when there is one: "someone has a draft typed in its pane" means the user is typing there, so leave the pane to them, "its task is still unread" or "its answer is still unread" if it never picked it up; a worker that was never seen working is judged 4 × `--grace` after its last task or answer) (a Claude worker's own Stop hook usually gave that nudge, the line says so; a background worker whose hook didn't gets a line with the `mesh send … --type info` to nudge it yourself, then pass its `send_message` on);
     - 4: it's blocked on a dialog (the alert ends with the pane's last lines: a stray menu, or a real question to answer);
     - 5: it's gone (herdr lists no agent and its pane runs no `claude`/`agy`, or herdr still reads it working over a bare shell); `--any` raises it too for a worker already gone when it starts that owes a report, once per task;
     - 6: timeout;
     - 7: quota, or a Claude worker at its usage limit or with an expired login;
     - 8: it may be hung: it reads working, but its transcript hasn't changed for 40 minutes (`--hang`, `MESH_HANG_AFTER`; a test or a server in watch mode that never returns). Look at its pane; tell the user, and leave it running unless it is plainly stuck. The watch never stops it, and raises this once per task.

     A worker that ended its turn to wait on a long command it started (a test suite) may declare it: a `wait` message in your mailbox (no doorbell), `Waiting until <time>: <why>`. Until that time the watch doesn't nudge it or raise 3 or 8 for that task (a usage limit or an expired login is still 7); after it, the usual rules apply, and the exit-3 line says the wait ended. A wait covers one turn end: a worker that wakes early and stops again without reporting ends it there, gets one reminder, and then the usual rules apply (the exit-3 line says "ended when it woke"). A new task or answer, or any report, ends a wait. A `wait` is not a report: don't answer it. Exits 3 and 5 also say what the worker's branch shows (`its work: 2 commit(s) past its base, pushed, PR #31 open, worktree dirty`), so you can tell a worker that finished and didn't say so from one that never started. `spawn`, `resume`, `approve`, `switch` and `ask` warn on stderr when a worker that owes a report has no `mesh watch` covering it and no `--any` watch runs: start one. A worker that looks gone gets its own line (`mesh watch <name>`, which exits 5, or resume or retire it), and none once a watch has raised it as gone for that task.

     Investigate with `mesh status` (and `mesh log --agent <name>` for what happened in order), then `herdr agent read <name>` for a pane or `claude logs <bg id>` for a background worker. Start the watch again after handling the alert, or once it has exited; a running `--any` watch needs no restart when you spawn or resume a worker. A restarted watch doesn't raise exit 3 again for a task already alerted on: only once the worker works again, or gets a new task or answer. Exits 7 (usage limit, expired login) and 8 are raised once per task too, until a new task or answer. A worker herdr has lost track of while its pane still runs its CLI (seen after a Claude Code auto-update) reads `unknown` in `mesh status`, and isn't called gone.
   - **Reserve reached** (exit 7, `ALERT Claude is at 91% of its five-hour window … starts no new Claude work`): tell the user in one line. Stop or retire nobody: running workers finish their current task. Start nothing new on that vendor until the reset (mesh refuses it anyway), unless the user says to go on (`mesh reserve off`).
   - **Quota hit** (exit 7, `ALERT <worker> hit its quota on <model>`): run `mesh switch <worker>` right away, without asking. It reopens the worker's conversation on the next model with quota left, and tells it to continue. Then tell the user in one line, for example "Argon ran out; <worker> continues on Opus".
     - If switch says no model is left (a Flash executor with Flash exhausted), tell the user the reset time and wait.
     - A Claude worker at its usage limit (`ALERT <worker> hit Claude's usage limit (resets …)`, without the time when only Claude's usage-limit notice showed it) has nowhere to move: the limit is the account's. Tell the user the reset time (or that it's unknown), wait for it, then send the task the line gives (`continue where you stopped`); that task re-arms the alert.
     - A Claude worker whose login expired (`ALERT <worker>'s Claude login expired`) is stuck the same way until the user logs in: ask the user to run `/login` in its pane (or `mesh open <worker>` for a background one), then send the task the line gives (`continue where you stopped`). Expect the same of every Claude worker on the account, and of yourself.
     - A quota hit is not a `failed`.
     - If `mesh approve` or `mesh switch` itself fails to reopen the worker, the worker is marked `swap_failed`, the watch alerts (exit 5), and the same command can be run again (approve's check for a waiting plan lets the retry of a failed approval through, not an approve after a failed switch).
     - If `mesh approve` can't start the move (its conversation isn't found, or it stays busy), nothing is sent, and the error suggests `mesh approve <worker> --keep-model`: it then executes on its planning model, and a later `mesh switch` moves it to the execution model. Use that rather than `mesh send … --type answer`, which leaves it recorded as planning, and tell the user it executes on its planning model.
     - A Claude worker plans under its deny list, which only a reopen lifts, so `mesh approve` always reopens it, `--keep-model` too (same model and effort). If that can't start, the error says to run `mesh approve` again once its turn has ended; `--keep-model` is no way around it.
   - **agy root:** rely on the doorbell, and check `mesh status` each time you wake. While the user has a draft typed in your pane, doorbells wait for it for about a minute, then give up (the sender's `mesh send` exits 2); those reports are still in your mailbox, and `mesh status` and the watch still show them.
   - **What's waiting on whom:** `mesh status` derives it for every worker, rows that need you first: a plan or question unanswered (and for how long), a task still unread ("doorbell failed": `mesh ring` it), a worker held at a startup screen (since when: the user clears it), or past one with its first doorbell unrung (`mesh ring` it), a `done` with its PR's state and checks, or "no commits, no PR" (legitimate when the bug turned out not to be one, so read the report), "in review" while its reviewers work. `mesh log [--follow]` prints the run's events as a timeline.
   - **Keep working** on your own repo while workers run; their reports queue until your current turn ends. If your work depends on a worker's change, build against the contract you gave it, or wait for its `done` (its branch is `mesh/<run>/<slug>`) when you can't.
   - **Keep your own context lean:** you live longest, so your context costs the most. Read plans and reports, not workers' transcripts. Look at diffs only where the plan says the risk is. When it grows big anyway, reset it (see "Your own context" below).
   - **Blocked on a dialog** (exit 4): a stray menu (a picker, a `/` command the worker opened) you may dismiss yourself with `herdr agent send-keys <name> esc`, then read the pane again. A real question, a permission prompt or a startup screen goes to the user.
6. **Review every plan** (`plan` messages; large tasks only). Read the plan file and check it against the request, the repo and the other workers' plans:
   - Does it solve what was asked, and only that? Are the files and functions real (spot-check the code)?
   - Is the *done when* a real check (tests, lint, build), not "looks right"?
   - Do cross-repo contracts match (field names, API shapes)?

   Then reply **once**:
   - **approved:** `mesh approve <worker>`, with `--body "<notes>"` if you have any. This also moves a worker on `auto` to its execution model. It refuses unless the worker's newest report since its last task or answer is a `plan`: after a `question` or a `changes:` answer, the worker must send its plan again, changed or not, before you can approve it.
   - **changes:** `mesh send <worker> --type answer --body "changes: <specific list>"`. The worker revises and sends the plan again, still on its planning model.

   Ask the user only when a plan raises a real product decision; otherwise decide yourself.
7. **Answer questions** with `mesh send <worker> --type answer`:
   - pass cross-repo facts between workers (a field name, an API shape)
   - make the call yourself whenever the request or the code settles it
   - ask the user only for real product decisions, missing credentials, or a destructive choice
8. **Check every `done`** before passing it on; a worker's word is not proof.
   - **A large task:** compare the PR diff (`gh pr diff <url> --name-only` first, then the risky files) against the plan you approved. A trivial or small task or group had no plan to check it against, so its reviewers check it against the task (each of a group's tasks against its PR section; for a tiny PR, you do).
   - **A tiny PR** ("Sizes": a trivial or small task or group, at most 150 changed lines by `gh pr view <url> --json additions,deletions`, nothing risky) gets your review instead of reviewers: read the whole diff, check it against the task, and send the author any fixes (a `Direct task (no plan)`); once you've checked them, it's done.
   - **Otherwise start its reviewers** (one or two), so every PR the run makes is reviewed without the user asking: picked by the review's size and agy's quota (see "Routing"), all in **one** command, a review round: `mesh ask --repo <repo> --review <PR> --size <by PR size> --reviewers auto` (a Claude root runs it with `run_in_background`, an agy root in the foreground). It wakes you once, with every reviewer's answer in one file ("Questions and reviews"). Handle their findings as "Questions and reviews" step 2 says. A PR is done when its reviews have nothing left that you agree with, or after its review rounds: one for a small PR, at most two for a large one (step 2 there).
   - If something's wrong, `mesh send <worker> --type task --body "<specific fixes>"` (start a small fix with `Direct task (no plan)`); a fix it should plan goes by retire + resume (see "Follow-ups", step 2).
9. **Close what you're done with:** once a worker's `done` checks out and you have nothing more for it, `mesh retire <worker>`. Its pane closes, and its conversation stays resumable (`mesh resume <worker>` brings it back with everything it knew), so an idle agent never sits open just in case. Mesh does it for you too: a worker idle 15 minutes after its `done` or `failed` (`MESH_IDLE_RETIRE`, seconds; 0 turns it off) is retired, unless a message waits in its mailbox, it declared a `wait`, the user has a draft in its pane, or the user is looking at it (attached with `mesh open`, or its pane focused in herdr). A `plan` or `question` waiting on you keeps it open. A message to a retired worker reopens it: `mesh send` (a `task`, `answer` or `question`) and `mesh ask` resume it (same conversation, compacted when large, deny list by the task as `mesh resume` sets it), then deliver, so a fix after an auto-retire is sent as usual. An `info` is only stored (exit 2): it reads it when next resumed. A retired peer is asked with `mesh ask <peer>`, never sent to. If that resume fails (it says why, and exits 1), the message stays stored: `mesh resume <worker>`, then `mesh ring <worker>`. An agy root runs no watch, and a Claude root's may have ended: a worker's `done` or `failed` also starts the run's retirer, which does the same for the workers no watch covers, so it happens whatever the root.
10. **A stuck worker** asks before it gives up: a `question` saying what blocks it, what it tried and its options. Answer it with a hint, a decision, or, when the task proves too costly or isn't needed any more, "drop it" (for that, ask the user when the call is theirs); more effort is yours to add if you judge it helps ("Sizes"). Its work stays with it: a buggy or unpolished result is a fix for the same worker, never a reason to hand the task to another.
   - **`failed`** is only for what nobody in the run can fix: missing credentials or access, a decision only the user can make (a usage limit isn't one: see "Quota hit" above). Tell the user what blocked it, and resume the same worker once that's resolved.
   - **Another CLI** (agy → Claude) only when the user asks for it: retire the worker (`mesh retire <worker>`) and start the new one **in the same worktree** with `--cwd <worktree>`, giving it the plan and what blocked the first. It gets the old name plus `-2`.
11. **Finish:** when every worker has reported, its PR's reviews are settled and your own part is done, tell the user:
    - one line per repo with the PR link and the worker's name (so it can be resumed later), plus what you changed in your own repo (it follows that repo's usual flow, not the mesh's)
    - what's left for them to do (review, test, deploy)
    - anything that failed or was restarted
    - the follow-ups you added to a repo's list of open work, or did in the run

    Then run `mesh stop`. It closes the panes, stops background workers, removes clean worktrees (branches with commits are kept) and archives the run log. It never touches your own checkout. Workers can still be resumed after it.

### Your own context

Every turn re-reads your whole context: at a twentieth of the input price while the prompt cache is warm, at the cache-write price (2× the input price on the 1 h cache, 1.25× on the 5-minute one) for all but the system prompt's ~25k (cached across sessions) once it has expired (an hour on a Claude subscription within its plan usage, five minutes on usage credits or an API key; mesh reads which from your session file). A big root woken cold by a report pays for all of it. `mesh reset` gives you a fresh session that rebuilds its picture from the run's files, and costs only the fresh session's small start, whenever you run it.

- **The signal:** root commands (`status`, `inbox`, `spawn`, `approve`, `switch`, `resume`, `ask`, `watch`) print a `mesh: root context …` line when a reset pays: you're over 300k tokens (`MESH_ROOT_RESET_AT`) and your cache is cold, or you're about to wait on workers; or you're over twice that while still warm. `mesh status` shows your size and cache state in its header.
- **Act on it without asking the user**, at a quiet point:
  - **best:** big and about to wait: you have just approved plans or started workers, and nothing waits on you. Large workers often take longer than the cache lives, so their reports would wake you cold.
  - **cold and nothing waiting:** reset before you do anything else.
  - **warm:** only at a phase boundary (a batch of PRs settled, a task list finished).
  - **never** with a plan or question waiting on you (`mesh reset` refuses), with a review's findings half-checked, or with your own repo's work neither committed nor written down.
- **How:**
  1. Bring `$(mesh dir)/notes.md` up to date: the user's standing instructions for this run, the decisions you made and why, and what you were about to do. It's what the files can't tell your next session. Keep it current as you go (write a decision down when you make it), not only before a reset.
  2. `mesh reset --next "<what to do next>"`, then **end your turn at once**. It returns right away. Once your turn has ended and your input box is empty, it types `/clear` into your pane, then a prompt telling the fresh session to run `mesh brief` and go on with `--next` (or the next step in notes.md). It never types while you're working or while the user has a draft in your box, and gives up after 30 minutes (`MESH_RESET_WAIT`); a failed or cancelled reset shows up once, in the next root command's line. If herdr has lost track of your pane (it reads `unknown`), the reset goes by your Claude process's own status; when it can't (an agy root, or `--compact`), it fails after 30 seconds and says so: then `/clear` by hand, or restart herdr's agent detection.
  - `--compact "<focus>"` types `/compact <focus>` instead of `/clear`: for a root that still has its own repo's work in flight, while its cache is warm. A pure supervisor (a task list) clears.
- **After a reset or any compaction** (Claude Code's own included), run `mesh brief` first: one bounded view of the run (request, notes.md, board.md, each worker's state, what waits on you, PRs, unread mail headers, the old transcript's path), with a command for whatever it leaves out. Trust it and `mesh status` over what you remember; read the old transcript only for a detail they don't have. If it says no watch covers a worker, start `mesh watch --any --alerts` again.
- **Idle reset (opt-in):** with `MESH_ROOT_AUTORESET=1`, your own `mesh watch` resets you while you're idle, over the threshold, with a cold cache and no unread report, so the next report wakes a small session. It can't tell that you're waiting on the user, so when you end a turn with a question to the user while it's on, write the question into notes.md first: the prompt after an idle reset tells you to look there and ask again.
- Claude Code's `/autocompact <tokens>` is the user's own fallback; mesh doesn't rely on it, since it can compact cold or in the middle of a review.

**Root-only commands:** `mesh reset` resets only the root itself. `mesh approve`, `switch` and `retire` act only for the worker's parent (you), and `mesh stop` refuses any worker. They find you by your pane, as every command does; the user acting for you from another terminal passes `--run <run> --as <your name>`.

**Messages to a worker:** always send them with `mesh send` (or `mesh approve`). A Claude worker's doorbell is written into its session by `mesh` itself (`via: socket`), so nothing is typed into its pane; an agy worker's is typed. A Claude worker launched by a mesh from before this keeps the old lane until you `mesh retire` and `mesh resume` it: a pane one is typed to, and a background one's `mesh send` (or `mesh ask`, which then doesn't wait, even with `--wait`) prints a `send_message` you pass on with the `SendMessage` tool, exactly as printed; `mesh ask --peers`, which can't hand one back, reports such a peer not reached. A Claude pane worker that something other than mesh relaunched (a herdr restore after a power outage runs plain `claude --resume`, without its hooks or deny list) is first reopened in the same conversation with them: you see a new pane and a `swap` with `why: relaunched`. If it can't be (its turn goes on), the message is stored, not rung, and `mesh send` exits 2 saying so; the next message tries again (`mesh ring` won't ring it), or `mesh retire` then `mesh resume` it.

## Task lists

When the request is a list of tasks ("work through TODO.md", "fix these five issues"), you supervise and **write no code yourself**, in your own repo too. The tasks go in a few themed **groups** (step 3), each one worker in its own worktree with one PR (and one plan, for a `large` group). Workers run as strong a model as you do, so one can take on a whole batch, and a worker already at home in a repo does the next task there far more cheaply than a fresh one that has to read the code in.

1. **Triage:**
   - Read each task, and just enough of the code to know its theme and what it depends on: the worker does the research.
   - Write the board to `$(mesh dir)/board.md`, with one row per task: task, repo, group (its worker's slug), depends on, and later the worker's name; one line per group with its size, CLI and model and pane or background (any routing you propose goes there), and a task in no group gets its size too. Its PR and status aren't kept there: `mesh status` derives them.
   - It is your proposal (Root step 3): show it to the user and get **one** go, including any routing, groups and sizes you propose. Don't start before that, unless the user said to run autonomously.
2. **Order:** only a real dependency orders tasks. A task that builds on another's change goes in the same group, after it, or on a branch stacked on the earlier one's (`--base mesh/<run>/<earlier slug>`; its PR then targets that branch). Tasks that only touch the same files still run side by side: a conflict that shows up is rebased when the PRs merge. A dependency between repos follows Root step 4's contract rules.
3. **Groups:** a group is two or more tasks in one assignment: one worker, one worktree, one branch and **one PR** for all its tasks, and **one plan** when the group is `large` ("Sizes").
   - **What to group:** tasks that share a theme, or where what one task teaches the worker helps with another. A small task with no theme of its own joins some group rather than get a worker of its own. There's no size cap: lean towards fewer, bigger groups. Keep a task out of any group only when the request wants it merged on its own (an urgent fix) or no group fits; it is then a task in no group, never a one-task group, and is spawned at its own size ("Sizes").
   - **Spawn** the worker once, with the whole group: `--size` by the group's combined work ("Sizes": a group of independent small tasks is `small`, with no plan), its slug naming the group (`export-features`). The task file has a `Group` section listing every task in the order to do them, each with what you know about it, and says: one plan for all of them (for a `large` group), one commit (or more) per task, one PR with a section per task, one `done`.
   - **One plan** (a `large` group): the worker researches every task and sends one plan covering each. Review it once (Root step 6); `mesh approve` then executes the whole group. A **"Maybe"** task (an idea to weigh, not a task to do for sure) rides in its themed group: the plan says do or decline, with the evidence, and a declined one is reported in the `done`, so its line can leave the list (where the repo records rejected alternatives, the PR adds it there). In a group with no plan, its worker argues do or decline in its `done`, and asks first (a `question`) when doing it is a judgment call that is yours; a Maybe that is large work makes its group `large`.
   - **A group with no plan** (`trivial` or `small`) goes out as one `Direct task (no plan)`: its worker does the tasks in order, a commit (or more) each, and opens one PR with a section per task. A task that proves bigger or less clear than described is asked about (a `question`) before that task's change; the tasks that don't depend on it go on (as for "A stuck task" below).
   - **Reviews** start once, on the group's PR, sized by the whole PR.
   - **A stuck task** in a group doesn't stall the others: its worker finishes the tasks that don't depend on it, then asks (Root step 10). Dropping a task is your call; tell the worker to take that task's work out, along with what depends on it, and it works out how.
   - **More work for a group** (a task added to the list, once the user's go covers it, or a follow-up its worker proposed; Root step 3 says which needs a new go) goes to the same worker, on its branch and in its open PR: by `mesh send <worker> --type task` only a `Direct task (no plan)` while it's live; a task it should plan, once its current `done` is in, by `mesh retire <worker>` + `mesh resume <worker> --task-file …` ("Follow-ups" step 2), so it plans under its deny list.
4. **Cap:** keep at most **4** workers working at once. A group counts as one. A fix round (an author resumed or sent review findings) takes a slot like any working worker; reviewers don't. Start the next one when one reports.
5. **Supervise** as in the Root steps, which start each PR's reviewers (Root step 8). After each `done`, also run `mesh conflicts`.
6. **Reviews:** check each finding before you act on it (see "Questions and reviews", step 2), then send the findings you agree with to the author (see "Follow-ups": `mesh ask <author> …` or a `task`), not to the reviewer. A small PR gets one review round and no re-review (a tiny PR gets your own review and no reviewers); a large one's re-reviews after a fix go to its first round's reviewers except Copilot (see "Routing"). A PR is done when its reviews have nothing left that you agree with, or after its rounds (one small, at most two large).
7. **Conflicts:** `mesh conflicts` lists the run's branches that conflict with their default branch or with each other.
   - Below them it notes workers that change the same files, committed or not (in `--json`, rows with `"kind": "overlap"`; real conflicts are `"kind": "conflict"`). Overlap alone needs nothing: a conflict it turns into is rebased when the PRs merge.
   - Nobody merges, so report a merge order that avoids them.
   - When the user says a PR was merged, send each worker whose branch now conflicts a task to rebase onto the new default branch and push.
8. **The board is the plan, `mesh status` the state:** change `board.md` only when the plan changes (a task re-sized, split, re-ordered, or given a worker). After your context is reset or compacted, rebuild your picture with `mesh brief`, not from memory.
   - Read `mesh status`, `mesh agents` and `mesh inbox` with `--json` rather than parsing their tables.
   - `mesh agents --run <run> --json` lists the run's workers and reviewers with their PRs, resumed ones included: gather PRs there, not by looping `gh pr list` over the repos.
9. **Report:** the board as a table, with each task's PR, worker name, status (from `mesh status`) and review outcome and size; a group's tasks share one PR and worker. Then the suggested merge order, and what's left for the user.

## Questions and reviews

A question about another repo, or a review of a PR, goes to a worker as well, so it can be asked again later and can take the change on itself. `mesh ask` starts or reaches the worker, gives it a read-only task and, unless the answer comes by `SendMessage`, waits for its `done` and prints it.

```bash
mesh ask --repo <path> --size small --body "<question>"       # a fresh agent in that repo
mesh ask --repo <path> --size small --review <PR link | number>  # a fresh reviewer, with the PR head checked out
mesh ask <name | branch | PR link> --body "<question>"        # a worker you already have, live or past
mesh ask <name | branch | PR link> --review <PR link>         # it reviews a PR without leaving its branch
mesh ask --repo <path> --size <size> --review <PR> --reviewers auto|all|claude,agy,copilot   # a review round
```

- **A review round** (`--reviewers`) is how every review of a PR starts, yours and the user's: one command runs all its reviewers at once, `auto` picking them by `--size` and agy's quota ("Routing"; it says on stderr what it picked and why), or the CLIs named. Their answers don't come one by one: it blocks until each has answered or alerted, prints one line per reviewer and the path of **one** answers file (`reports/review-<n>-<stamp>.md`), and closes the reviewers that answered. So a Claude root runs it with `run_in_background` and wakes once; an agy root runs it in the foreground. A reviewer that alerts (hung, stopped, held at a startup screen, out of quota) gets its line there with what to do, stays open, and its later answer comes to your inbox as usual. Run the same command again after a fix, in this run or a later one: it asks the PR's earlier reviewers again (for `auto`, minus Copilot, and minus agy without quota, Claude taking its place) on the commits since, and starts a fresh one only for a CLI the PR had none of. `--model` and `--view` are refused for a round of more than one CLI.

- **No run needed:** without one, `ask` starts it (mode `--kind`, default agy; for `--kind copilot` or a review round, your own CLI).
- **Your own repo too:** a review of your own PR goes to a fresh agent in your repo (`--repo .`). It's a second pair of eyes that changes nothing, so it doesn't conflict with doing your repo's part yourself.
- **A fresh agent** follows the mode table and `--size`, like a spawn, except that a fresh reviewer opens in a pane at any size and runs at high effort when it is trivial or small ("Sizes"). Pass `--kind` for the CLI, and `--model` / `--effort` only if the user named them.
- **Copilot** (`--kind copilot`: a default reviewer of a first review while agy is out of quota, otherwise only when the user names it) answers questions and reviews, nothing else. It runs headless inside the `ask` call, with no agent pane of its own: `--size` sets only its effort, and on a plan that offers only `auto` (Copilot Student), Copilot picks the model. `ask` waits for it and prints its answer, so a Claude root still runs it with `run_in_background`; while it works, a pane beside yours follows it (`mesh peek <name> --follow`) and closes once it has answered, and `mesh stop` waits until it has answered. Ask it again with `mesh ask <name>`, which resumes its session; it can't be resumed into a change.
- **Asking an existing worker** reuses all its context: the agent that wrote a PR knows why it's written that way.
  - A PR link names the worker that opened the PR (the one on its head branch); a reviewer is found by its name.
  - A worker busy on another task answers once that's done: `ask` then returns at once, and the answer comes later.
  - A past worker is resumed, and its conversation is compacted first when it's large (see "Follow-ups").
- **The question:** give it what you know, as you would in a task file (use `--file` for anything long): what you're working on, what you need back, and in what form.
- **Waiting:**
  - **A Claude worker under a Claude root:** `ask` returns once the question is delivered (pass `--wait` to block anyway), and the answer arrives as a cross-session message.
  - **An agy worker, Claude root:** run `ask` with `run_in_background`, and the answer arrives as the notification.
  - **agy root:** run it in the foreground, or pass `--no-wait` and wait for the doorbell.
  - Exit codes are those of `mesh watch`; on 7 (an agy quota), `mesh switch` the worker and `mesh watch` it; on a Claude usage limit, wait for the reset, and on an expired login, have the user log in, as in "Supervise".
  - Exit 4 with `ALERT <name> is waiting at a startup screen` comes before any waiting: the agent's pane stopped at a screen mesh doesn't answer (a Settings Warning for a malformed `.claude/settings.json` rule, say), and the question is stored. Tell the user to clear it in that pane, and don't answer it yourself. Then `mesh watch <name>` rings it once the screen is gone and waits for the answer; read it with `mesh inbox`, then `mesh retire <name>` once you have no follow-up for it.

Then:

1. **Relay the answer** to the user with the worker's name, so they can ask it again. `mesh ask` closes an agent it opened once it has answered (`--keep` leaves it open); asking again reopens the same conversation. When the answer came by `SendMessage` or after `--no-wait`, `mesh retire <name>` it yourself once you have no follow-up for it. Spot-check claims that matter against the code, as you would a `done`.
2. **A review:** a finding is a claim to check, not an order (`PROTOCOL.md` rule 9). Reviewers mark each one **blocking** (a defect with the input that makes it fail) or **advisory**. For each one, check against the code that the bug really happens (trace it, or run the failing case) and whether the suggested fix is the best one, then decide: agree, agree with a different fix, or disagree and why. Fix your own repo's PR yourself. Send findings on another worker's PR, with your opinion on each, to the worker that made it (see "Follow-ups"), not to the reviewer.
   - **Every review is of one commit:** the task names the PR's head (`Review (read-only) of <PR> at <sha>`), and the reviewer records it. After a fix to a large PR, ask the **same** reviewers again, except Copilot: the same review-round command does it. The task names the new head and the one it read before, so it checks the fix commits and whether its earlier findings are fixed, instead of the whole PR (unless the branch was rebased or merged its base since: then the task says to review it whole).
   - **Rounds by size:** a `small` PR gets **one** review round. Once its author has fixed the findings you agreed with, check the fix commits yourself (`git diff <reviewed head>..<new head>`), and the PR is done: no re-review, unless the user asks for one. A `large` PR gets at most **two** review→fix rounds, each fix re-reviewed. If findings you agree with are still open after the last round, stop: give them to the user with your opinion on each, rather than starting another round. Don't turn them into a follow-up PR that starts its own rounds: unless the user asks for one, they go on the repo's list of open work, or to the user.
3. **More questions:** `mesh ask <name> --body "…"` again. The worker still has everything it read.
4. **Turning the answer into a change** in that repo: send the same worker a normal task (`mesh send <name> --type task --file …`, or `mesh resume <name> --task-file …` once it's gone). From there it's an ordinary worker.
   - A Claude asker runs with a deny list (no file edits in its worktree or your checkout, no `git push`, no `gh pr review` / `comment` / `merge` / `edit` / `close`, no `gh issue comment`). A change task it plans keeps the list, now as a planner, with no reopen, until `mesh approve` lifts it. A `Direct task (no plan)` lifts it at once: `mesh send` waits for its turn to end, reopens the same conversation on the same model without the list (the output says `read_only_lifted`), then delivers the task. A question or review sent the same way leaves it in place. An asker `mesh ask` already retired (its usual state) is reopened by the `mesh send` itself, as `mesh resume <name> --task-file …` would: compacted when large, under the list only for a task it plans. If a background asker's reopen fails, its task is already stored: `mesh resume <name>` with no task brings it back to read it. An agy asker has no deny list: only its prompt holds it. `mesh` itself refuses any worker every command but its own (`send` to its parent, `inbox`, `whoami`, `dir`, the readings).
   - A large asker plans, you `mesh approve`, and it executes on its branch `mesh/<run>/<slug>` and opens a PR. Supervise it as in steps 5 to 11.
   - A small asker has no plan phase: make the task a `Direct task (no plan)` by starting it with that line.

**Standing peer askers** (`mesh peers`): askers registered for good, one per cloned peer project, outside any run. The registry is machine-wide; groups (`orchestrators`) pick a subset. Ask one by name like any worker (`mesh ask <peer> --body …`), or several with one command:

```bash
mesh peers                                       # names, groups, what each last read, each one's last answers file
mesh ask --peers all|<group>|a,b --file q.md     # one question to all of them
```

- `mesh peers` says what each peer and group is and what it's worth asking about: pick a group or names from it.
- Each ask fetches the peer's upstream, moves its checkout to the new head and tells it what changed since it last looked. `--no-refresh` skips the fetch.
- `ask --peers` blocks until every peer has answered or alerted, so a Claude root runs it with `run_in_background`. Their answers don't come to your mailbox one by one: read the **one file** whose path it prints (also shown by `mesh peers`), never N inboxes. Its stdout is one line per peer. A peer that didn't answer (held at a screen, asked back, stopped) stays open with its line saying what to do, then `mesh retire` it. One held at a startup screen is waited for 5 minutes (`MESH_HELD_WAIT`, seconds), not the whole `--timeout`: once the user clears the screen, `mesh ring <name>`, and its answer comes to your inbox, so watch it. A peer still busy with an earlier question isn't asked: ask it again once it has answered. Those that answered are closed.
- A peer only answers; a change to that project goes to an ordinary worker there. Add one with `mesh peers add <git-url | path> --group <g>`. To find projects worth adding (search, rank by shared mechanisms, register them on the user's yes), use the `find-peers` skill; for a research round by them (the first brief, or a follow-up hunting ideas and our bugs, each finding checked in our code), the `harvest-peers` skill.

`mesh stop` deletes a branch that never got a commit or a push, such as an asker's. Resuming that worker starts the branch again at the same commit.

## Follow-ups

When the request is about something a worker already built, in this run or an earlier one, resume **that worker**: it still has its research, plan and reasoning, so a fresh one would only rediscover them.

1. **Find it:** `mesh agents <PR link | repo | branch>` lists past workers with their run, branch, PRs and whether their conversation was found. With several matches, the newest is usually the one that last touched the PR.
2. **If it's still running in this run**, give it by `mesh send <worker> --type task --file …` only a task it just does (a fix request; start it with `Direct task (no plan)`). A task it should **plan** goes, once its `done` is in, by `mesh retire <worker>`, then `mesh resume <worker> --task-file …` (step 3), or by `mesh send` once it's retired (by you or by the watch), which resumes it the same way: that plans it on the planning model at the planning effort and, for Claude, under the deny list (no edits, no push) until `mesh approve`. A task sent by `mesh send` is planned, if the worker sends a plan, on the model and effort it's on and held only by its prompt: `send` never reopens a worker to add the list. `mesh approve` then still moves it to the execution model (a worker spawned with a named `--model` / `--effort` stays on it). A worker retired mid-plan and resumed with no task comes back as the planner it was, under the list, unless it already reported `done` or `failed` on that task; a `Direct task (no plan)` ends its plan phase.
3. **Otherwise resume it:** `mesh init` first if you have no run, then
   ```bash
   mesh resume <name | branch | PR link> --task-file "$(mesh dir)/tasks/<repo>.md"
   ```
   It reopens the worker's own conversation (on the planning model when the task has a plan phase, see below), in its old worktree and branch (recreated if `mesh stop` removed it), as your worker. A background worker comes back in the background. If the worker's PR was merged or closed, a change task gets a new branch instead (from the default one after a merge, from the old branch's tip after a close), and a note at its end saying so (see `notes` in the output). The task file contains:
   - what to change: for a review, the comments themselves (`gh pr view <url> --comments`, `gh api repos/<owner>/<repo>/pulls/<n>/comments`) and **your opinion on each one**: agree, disagree and why, or what to do instead. Ask it to check each finding itself before fixing it (`PROTOCOL.md` rule 9) and to say in its plan which it fixes, how, and which it declines and why
   - "plan first; push to the same branch so the PR updates; report `done`" (for a small follow-up: start it with `Direct task (no plan)`)
4. **Compaction:** an old conversation has lost its prompt cache, so every turn of the follow-up would pay for all of its context again. `resume` (and `ask`) compact it first, headless, keeping what the new task needs:
   - with `--compact auto` (the default): a Claude conversation over 300k tokens (`MESH_COMPACT_AT`) or an agy one over 100k (`MESH_AGY_COMPACT_AT`), twice that for a read-only question; an agy one whose size can't be read is compacted when it comes back from an earlier run;
   - `--compact yes|no` forces it either way;
   - `--focus "<what matters>"` replaces the default focus when you know better ("the restockedAt contract and why we chose ISO dates");
   - the output's `compaction` shows the context size before and after.
5. Supervise and review it exactly like a new worker.

A conversation can't move to another CLI. If the user wants a different agent (agy → Claude), spawn a fresh one with `--cwd <worktree>` and give it the old plan and report, as Root step 10's "Another CLI" says. `mesh resume --model` changes the model within the same CLI. A resumed worker keeps the model it ran on, except for a task that has a plan phase (not a `Direct task (no plan)` or a question, and no `--model` / `--effort`): that one plans where a spawn would (the first of Argon → Opus → Flash with quota for agy, Opus for Claude, at high effort), and `mesh approve` then moves it to the execution model and effort: agy to Flash at medium, Claude to medium effort. On a quota hit, `mesh switch` still works.

## Worker

You start inside your own worktree, on branch `mesh/<run>/<slug>`. It holds the same code as the main checkout (for a reviewer, the PR's head), so research there.

**Reporting.** Every message to your parent goes through `mesh send parent …`, which stores it. If its output has a `send_message`, your parent is a Claude session that you reach with the `SendMessage` tool (load it with ToolSearch if it isn't loaded). Send it with `to` and `message` exactly as printed, then end your turn as usual.

**Read-only tasks.** A task that starts with `Question (read-only)` or `Review (read-only)` comes from `mesh ask`. Skip the plan (steps 4 to 9): research, then answer. Change no files, commit nothing, push nothing, switch no branches, and post nothing on GitHub. Install dependencies only if you need them to answer (to run a test, for example). Report one `done`:
- **A question:** the answer, with the file paths and functions that back it, and what you're unsure of.
- **A review:** findings ranked by severity, each with file:line, a concrete failure (the input or state, and what goes wrong), why it matters and a suggested fix, and marked **blocking** (a defect you reproduced or traced, with the input that makes it fail) or **advisory** (everything else), then what you checked (the tests you ran, say). Report only what you've confirmed in the code, mark anything you couldn't confirm as unverified, and leave out style preferences the repo's rules don't ask for. A review task names the commit it is of; when it also names the one you reviewed before, review what changed since and say which of your earlier findings are fixed. A Claude reviewer's task also asks it to run Claude Code's `/code-review` skill on the PR (or on the commits since its last review) and check each of its findings like any other claim; it never passes `--fix` or `--comment`.

Then end your turn. A later task may ask more, or ask you to make a change, which follows the steps below as usual.

**Direct tasks.** A task that starts with `Direct task (no plan)` skips steps 4 to 6: research (step 3), then execute, verify, publish and report (steps 7 to 10). If the research shows the task is bigger or less clear than it says, send a `question` with what you found and end your turn before changing anything.

**Plan reviewed by the user.** A task that starts with `Plan review by the user` runs in plan mode: write your plan as Claude Code's plan mode asks, and the user approves it in your pane. Don't send a `plan` message. Once approved, continue from step 7.

1. **Follow the repo's rules.** The repo's `CLAUDE.md` / `AGENTS.md` apply to everything repo-specific: task tracking, branch and commit conventions, contract checks, the PR process. **Never edit files or switch branches in the main checkout**, and never touch another agent's worktree.
2. **Set up:** a fresh worktree has no installed dependencies and no untracked files such as `.env`. Install what the repo needs. Don't copy secrets in unless the task says to.
3. **Research** until you know exactly what to change: read the code, run the existing tests, reproduce the bug if there is one. Check every assumption the task marks before you rely on it. **Change nothing yet.** A Claude worker can't: until `approved`, mesh denies it file edits in its worktree and `git push` (set-up and tests in the shell still run). That denial is expected; don't route around it with shell writes.
4. **Plan:** write `$(mesh dir)/plans/<your-name>.md` from `~/.config/agent-mesh/PLAN_TEMPLATE.md`. It is written for a reviewer who hasn't read the code: say what you found and where, name the exact files and functions, the invariants, the steps, the done-when command, and your open questions. For a group (your task file has a `Group` section), one plan covers every task, a section each. Then run the `check-plan` skill on it: it checks the plan's load-bearing claims in the code, attacks it, and fixes it (and its Self-check section) before your parent reads it.
5. **Ask for review:** `mesh send parent --type plan --file "$(mesh dir)/plans/<your-name>.md"`, then **end your turn**. Don't start implementing while you wait.
6. **On the answer:**
   - `approved` → go on.
   - `changes: …` → update the plan file, send it again as a `plan`, end your turn.
   - Any other answer while you plan (to a `question`, say) → send the plan again as a `plan`, even unchanged, and end your turn: only a plan sent since the last answer can be approved.
7. **Execute** the approved plan (or the direct task) yourself, in your worktree. Commit on your branch with clear messages. If the code turns out different from the plan in a way that changes its scope, stop, send a `question` and end your turn. Small corrections you can just note in the report.
8. **Verify:** run the plan's done-when command and the repo's lint, test and build. Fix what fails. After two honest attempts at the same failure, send a `question` instead of guessing.
9. **Publish:** push your branch and open the PR with `gh pr create`, following the repo's own PR rules (title, body, attribution, base branch). The PR body includes what changed, the commands that passed, and anything the reviewer should look at. Then do whatever the repo's rules require after a PR.
   - **A follow-up** to work you already published goes on the **same branch**, so the existing PR updates. Open a new PR only if the task asks for one, or a note from mesh at its end says your PR was merged or closed.
   - **A stacked task** (your worktree started from another worker's branch) opens its PR against that branch.
   - **A group** (your task file has a `Group` section listing several tasks): once the one plan is approved (at once, for a `Direct task (no plan)` group), do the tasks in order, each as its own commit(s), and open one PR for all of them, following the repo's PR rules, with one section per task (what changed, the check that passed, any issue it closes).
10. **Report:** stop any server or watcher you started (PROTOCOL rule 2), run `mesh inbox` once more, then send **one** `done` to your parent (`--file` under `$(mesh dir)/reports/`) with the PR link, a summary, the checks that passed, and any deviations from the plan. If you're stuck, send a `question` (what blocks you, what you tried, your options) and end your turn: your parent decides. In a group, finish the tasks that don't depend on the stuck one first, then ask. Send `failed` only for what nobody in the run can fix (missing credentials or access, a decision only the user can make). Don't run `mesh stop`: the root does that.

## Rules for everyone

- **Workers push only** their own `mesh/<run>/<slug>` branch and open PRs. Nobody merges a PR or deploys.
- **No sub-delegation:** workers never run `mesh spawn`, start `claude --bg` sessions, or spawn agents in any other way. The run is the root plus its workers.
- **Quiet supervision:** a working agent needs no check-ins. Act on reports, doorbells and watch alerts only.
- **Concise messages:** details go in `--file` reports and plans, not in chat.
- **Decide, don't ask:** the root makes every call that the request, the code or a sensible default settles: sizes, reviewers, effort, which review findings to fix and how, retries, wording, merge order. Ask the user only when their answer would change the outcome in a way you can't judge yourself: a product decision, a trade-off only they can weigh, missing credentials, or anything destructive or outward-facing. Report what you decided, briefly, so they can overrule it. The one go before any work starts (Root step 3) stays.
- **Fix it in the PR it came from:** review findings, and follow-ups that a worker or reviewer finds while working on a PR, are fixed in that same PR, on its branch, by the worker that made it (resumed if it's gone, see "Follow-ups"). That holds after you've called the PR done too: you check the new commits yourself, with no new review round. Don't open a new PR and branch for them: it gets reviewers of its own, whose findings bring more PRs, and so on without end. Only very rarely does one warrant its own PR, when it's unrelated to that PR's change or bigger than the PR itself; then it's a new task you decide on, never the default.
- **New work goes to the agent that knows the code:** when a worker proposes something new and you agree (a small follow-up in its own PR needs no new go; anything bigger is proposed to the user first, Root step 3), that worker builds it, in its open PR when it has one: as a `Direct task (no plan)` by `mesh send` while it's live, or, if it needs a plan, once its current `done` is in, by `mesh retire` + `mesh resume --task-file` ("Follow-ups" step 2). Any other small new task goes to an existing worker that already knows that code too, after its current task if it's busy, not to a fresh agent, which would have to read the code in first. Spawn a fresh one only for work no worker has context for.
- **Follow-ups land somewhere:** work that you or a worker discover but the request didn't ask for (a worker's report notes it, see `PROTOCOL.md` rule 3), and that isn't a fix for one of the run's PRs (above), goes on that repo's own list of open work, wherever its rules track it. Whoever works in that repo adds it: you in your own repo (outside a task list), otherwise a worker of the run that made a PR in that repo (not a reviewer), as a task (it adds the line in its PR). If it's small and close to that worker's task, it can do the work itself instead. A follow-up for a repo with no worker in the run goes in your Finish report, marked for the user to file. Never leave it only in chat.
