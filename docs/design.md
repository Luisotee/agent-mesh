# Design notes

The decisions behind agent-mesh, roughly in the order they were made, and the alternatives that lost.

## 1. Interactive panes, not headless `-p`

Both CLIs have a print mode (`claude -p`, `agy -p`): run one prompt, print the answer, exit. It's the obvious way for one agent to drive another, and it has three problems:

- **Invisible:** you can't watch the work or type into it.
- **One-shot:** the agent can't stop to ask a question and keep its working context. You have to resume the conversation with `-c`, and "most recent conversation in this workspace" is ambiguous once several agents share a repo.
- **No back channel:** the child has no way to reach its parent.

herdr runs every agent as a normal interactive session, and its CLI can start an agent in a pane (`agent start`), type into it (`agent prompt`), read it and wait for state changes (`agent wait`: `working` / `idle` / `done` / `blocked`). That covers visibility and delivery. The rest of agent-mesh is the conventions on top.

Since 0.7 small Claude tasks may run as Claude Code background sessions (`claude --bg`, §11). These aren't `-p` runs: each one is a full interactive session without a terminal, which keeps its conversation, takes messages, and can be attached to (`mesh open`). So all three objections still hold for headless runs, and none of them applies to background sessions.

## 2. Agents live inside the repo

The first design had one central Claude writing plans for every repo. It was rejected: a planner outside the repo doesn't load that repo's `CLAUDE.md`, skills or hooks, and it would have to absorb every repo's conventions into one context window. Instead the root spawns a **fresh** agent in each affected repo. It's fresh so that your existing sessions keep their own context and never receive mesh traffic.

It also keeps the root's context small: each repo agent sends up a plan and a short report, not its research.

## 3. Mailbox plus doorbell, not raw typing

Typing a message straight into a terminal is unreliable. Other projects hit the same problem: [initech](https://pkg.go.dev/github.com/nmelo/initech) exists because tmux `send-keys` has no delivery guarantee, and one lost "done" message stalls the whole chain. The failure modes are real:

- the recipient is stopped at a dialog (herdr rejects the prompt with `agent_blocked`)
- you're typing in that pane
- the TUI mangles a long paste

So the message goes to a file first, and the terminal only gets a one-line doorbell:

- `mesh send` retries the doorbell with backoff for about a minute, but first reads the pane: a busy agent queues the doorbell even when herdr reports `agent_prompt_stalled` or `timeout`, so one that shows up above the input box since the first try counts as delivered (text still in the input box doesn't). The check never confirms from a pane it couldn't read before the first try, or one whose input box (a rule with `>`/`❯` at column 0 under it) it can't find: those fall back to retrying, which at worst duplicates a doorbell, never loses one
- every rung doorbell carries a `(ref <token>)`, new each time, and only that token counts in the pane. An earlier doorbell from the same sender, submitted between two reads, used to confirm a new one still sitting in the input box, because the old check matched the doorbell's first 25 characters (`📬 [mesh] task from <sender>`). The token goes early, after the sender (or, in a first doorbell, right after `run <id>`), so a CLI that shortens a long queued prompt keeps it, and the start of a first doorbell, which resume searches for (§6), stays as it was. A queued doorbell that shows up before the next retry counts too
- retrying stops once the message has moved to `read/`: the agent read it after an earlier doorbell, and another one would cost it a turn on an empty inbox. A doorbell that got through is logged as `rung`, with `via` (`working`, `pane` or `read`) and the number of tries; one that didn't, as `doorbell_failed`
- a human's draft holds the doorbell. herdr 0.8.2 submits a prompt fused to the draft in the box (both CLIs got `hello draftPROBE one`), so each try reads the pane with `--ansi` and doesn't type while the input box holds text that isn't dim (Claude's `Try …` placeholder is dim; a coloured slash command isn't, so it counts as typed). A doorbell of ours left in the box isn't a draft: typing after it fuses two doorbells, which one `mesh inbox` answers. The hold fails open: no box found, no closing rule under the input line, an escape other than SGR or OSC in the box, or an unreadable pane types, and a draft that outlasts the retries ends in exit 2 (`human_draft`), never in a queue. Rove deleted a broad composer gate after it left a worker stuck for 11 hours, and Cyclops dropped its fail-closed composer proof after a pane waited 16 hours. Two gaps remain: the user can start typing between the read and the type (closing it needs an input lease in herdr), and a draft hidden for one redraw frame isn't seen (Cyclops reads twice 300 ms apart; mesh reads once, since herdr serves its own parsed screen and a second read would slow every ring)
- one ring at a time per pane: herdr merged three concurrent prompts into one message, out of order (`PROBE concurrent 1PROBE concurrent 3PROBE concurrent 2`). Each try holds an `flock` on `$MESH_HOME/locks/ring-<pane>.lock` (never across the backoff sleeps), waits at most 60 s for it and then types anyway: a merged doorbell is a nuisance, a dropped one is a lie
- the preview drops backticks, `$` and double quotes (an apostrophe becomes `’`), so it never reads as shell
- if the doorbell still fails, `mesh send` exits 2, but the message is safe and `mesh ring` can retry later
- one-line doorbells make typing collisions much less likely
- the mailbox doubles as an audit log of who said what

A live test showed that a doorbell typed while agy was busy wasn't lost: agy queued it, as Claude Code does. The agent had already sent `done` by then, though, so it reported on instructions that were out of date. Hence the protocol rule: **empty your mailbox right before reporting**.

The watchdog depends on it too: it credits each report to the newest task or answer logged for the worker (`since_last_task`), so a `done` for task 1 sent after task 2 arrived counted as task 2's, and the worker could then end task 2 silently, never nudged or alerted. So `mesh send` enforces the rule: while a `task` or `answer` is unread in the sender's mailbox, a `plan`, `question`, `done` or `failed` is refused, nothing stored, with the waiting messages listed, and `--unread-ok` overrides it. An `info` always goes, for a partial result that can't wait. Matching reports to tasks by lineage (Rove's way) would need a `read` event per message and turn ends mesh can't see; the guard gets the same result from what the mailbox already knows. The root never receives tasks or answers, so it's unaffected.

## 4. Addressing by herdr name

herdr shows Claude Code's session id for Claude panes but nothing for agy panes, so session ids can't address every agent. Every mesh agent gets a herdr name, and its pane id is kept as a fallback.

Names are meant to be read in herdr's agents tab, so they say what the agent is, not which run it belongs to:

| Agent | Name |
|---|---|
| root | `<repo>-lead` (`shop-web-lead`), unless you already named that session, in which case it keeps your name |
| worker | `<repo>-<worktree slug>` (`shop-api-restocked-at`) |
| restart in the same worktree (e.g. on a stronger model) | the same name plus `-2` (`shop-api-restocked-at-2`) |

herdr requires names to match `[a-z][a-z0-9_-]{0,31}` and to be unique among live agents, so long parts are cut and a clash with another run gets `-2`, `-3`. The run id lives in the environment and in branch names (`mesh/<run>/<slug>`), not in agent names. `mesh stop` clears the name the root was given.

**Beside the root first.** A pane worker opens as a split in the root's own tab: the first splits the root's pane, later ones split the biggest worker pane, so the root keeps its half and the user sees the workers from the space they're working in. The run's own tab in the project's workspace used to be the only placement, and it hid the work from the user. Past `MESH_SIDE_PANES` workers (3) the panes get too small to read, so the rest go to the run's tab below; a swap (approve, switch) splits the side worker's own pane, so it reopens where it was whatever the count; if the root's tab is gone, it goes to its project's workspace. Only panes still open count (one the user closed frees its place), and background workers have none. Placement holds a per-run lock (`.panes.lock`) from the count through the split to recording the pane on its agent: `/delegate-review all` starts three `mesh ask` calls in one turn (two reviewer panes and a Copilot peek pane), which would otherwise all count the same panes and split the root three times. The run's tab takes the same lock from looking it up through creating it to recording it and the pane, since `mesh ask --peers` places its peers from parallel threads, which would each create the tab.

**Then one workspace per project.** Past that, agents open in the project's existing herdr workspace, found by label (case-insensitive) or by a pane whose directory is inside the repo, so a workspace labelled `shop` is found for `shop-api`. Each run gets one tab per workspace, labelled from the request (`mesh: add restockedAt to shop-api`). A workspace is created only when no workspace matches, and a lock stops two workers spawning at once from creating two. A peer asker (§14) is the exception: its tab goes in the root's workspace (`worker_workspace`), since a peer is a clone the user never works in, and asking ten peers made ten workspaces.

## 5. Models are preferences, not code

Model ids go stale (Gemini 3.8 Flash, then 3.9…), so the skills name **families**:
- `argon` / `flash` / `opus` / `sonnet` for agy, which `mesh` resolves to the newest matching `gemini-<version>-<family>-<effort>` or `claude-<family>-<version>-<effort>` in `agy models`
- `opus` / `sonnet` for Claude, which the CLI resolves itself

The modes are two skills rather than a flag. They used to be explicit-only (`disable-model-invocation`), so a casual "have agy do X" never started a mesh. That made the user remember a command for the thing the mesh exists for, and an agent asked "have the shop-api agent fix it" would edit shop-api itself or refuse. Now agents invoke them like any skill when a request fits the description: work, a question or a review for another repo. The mode comes from the CLI the user names, or the agent's own CLI when none is named. Two limits stay: a worker never invokes them (1:N, §7), and outside herdr, where no mesh can start, a read-only ask is one headless `agy -p` from B's directory. Within a mesh, the root picks the model *size* per task (§11), but never a model family the user didn't ask for.

## 6. The mesh is process-agnostic

Task trackers, branch conventions and PR checklists differ between repos. The mesh files never name any of them. A worker follows whatever its repo's `CLAUDE.md` / `AGENTS.md` says, because it runs inside that repo.

## 7. From 1:N:N to 1:N

Up to 0.2 a run was three levels deep: root → a planner per repo → executors in worktrees. In practice the planner did the expensive part, reading the repo until it understood the change, and then handed a written plan to an executor that started cold and had to rediscover the same code. Plans can't carry everything research learns, so executors asked questions the planner already knew the answers to, and the hand-off cost a second round of reading.

Since 0.3 a run is the root plus **one worker per other repo**. The worker researches, writes the plan, and sends it to the root as a `plan` message. It changes nothing until the root answers `approved`; then **the same agent** executes, verifies and opens the PR. Review moved up a level, from planner-reviews-executor to root-reviews-plan, and it now happens *before* any code is written.

The typical run is two repos: you're working with an agent in repo A and find that the change also needs repo B. The root therefore keeps its own repo, working in your checkout as before, and spawns a worker only for each *other* repo. A worker for the root's own repo is started only when you ask for one.

Until 0.4 the default worker was the newest Gemini Flash at **high** effort, for the whole task. Since 0.5 a worker plans on a stronger model and executes on Flash (§9). A model named by the user still runs the whole task, and more effort or a stronger model for a fix is the root's call (§11, "Stuck, not failed").

## 8. Resuming workers

Since 0.4 a worker's conversation outlives its run. The usual follow-ups (a PR review to address, "make it Y instead of X") are about work a worker already researched, and briefing a fresh worker repeats the cold hand-off that 0.3 removed. So `mesh resume` reopens **the same conversation** as a worker of the current run, and `mesh open` reopens it in the user's own terminal.

- **Finding the conversation:**
  - **Claude Code** takes `--session-id`, so `mesh spawn` picks a UUID, passes it, and records it in `run.json`. `--resume <id>` reopens it.
  - **agy** can't be given an id, but its conversation index (`conversation_summaries.db`, SQLite) has each conversation's id, first prompt (`preview`) and workspace from the first prompt on. Mesh's first doorbell names the agent and the run (`You are <name> (worker) in agent-mesh run <run>`), so it pins the conversation even when a restart shares the worktree; the newest conversation in the worktree is the fallback. agy sometimes replaces `preview` with the conversation's title (seen on 1.4.7 too, cause unknown; every doorbell-started worker so far kept its doorbell), so mesh records an agy worker's `session` on its first `mesh send`, while the doorbell is still there, and only when the doorbell pinned it. `--conversation <id>` reopens it. Mesh opens the db read-only (agy keeps it in WAL mode, so that never blocks agy) and falls back to `history.jsonl`, which it used alone until agy (2026-10) stopped writing a `conversationId` with a conversation's first prompt, so a fresh worker's conversation couldn't be found until it got a second prompt.
  - **Older runs:** Claude workers spawned before 0.4 are found the same way, through the doorbell in their session file.
  - **Main checkouts:** for a worker that ran in a main checkout, only the doorbell counts. A "last prompt in this directory" fallback there could pick up the user's own session.
- **Same path:** Claude stores sessions per working directory, so a worktree that `mesh stop` removed is recreated **at its old path**, on its kept branch. It joins the new run's worktree list, so that run's `mesh stop` cleans it up again.
- **Finding the worker:** the root and the user think in PRs, not agent names. `mesh agents`, `resume` and `open` accept a name, a branch or a PR link. When several runs match, the newest wins. A PR link names the worker whose branch is the PR's head (`gh pr view --json headRefName`): its recorded branch first, then the branch its worktree is on (a worker may follow its repo's naming), in the PR's repo (a worker repo with no remotes at all matches any; one whose remotes are all off GitHub matches none). The `reviews` exclusion applies on the worktree-branch pass only, so an author that reviewed its own PR is still found by its recorded branch. Only when `gh` can't answer or no branch matches are PR links read from the worker's own messages (its `done` report), as they were before (Rove maps a PR to its task the same way).
- **A merged or closed PR:** a follow-up pushes to the same branch so the PR updates, but once the PR is merged (or closed) that would push to a dead PR, or recreate a branch deleted on merge, with pre-squash commits that conflict with the default branch (Gas Town's agents rebuilt merged work this way). So `resume` asks `gh pr list --head <branch> --state all`, counting a PR only when its head commit (`headRefOid`) is in the branch and not in the commit the worker started from (`base`), so an old PR from a reused branch name doesn't count, merged or not; one whose commit isn't here (squash-merged, never fetched) still does, since telling would take a fetch, and when no PR from the branch is open any more it moves the worktree to a new branch, `mesh/<run>/<slug>`, keeps the old branch, records the new base, and appends a note to the task. After a merge the new branch starts at the default branch of the PR's own remote (the one whose URL names the PR's repo, `upstream` in a fork; `<remote>/HEAD`, else `gh repo view --json defaultBranchRef`), freshly fetched (the fetch never prompts for credentials and gives up after a minute); with no such remote, `origin` and `default_base` as before. After a close, whose work never landed, it starts at the old branch's tip, so the commits come along to a new PR; when the branch no longer has the PR's head (deleted, then recreated at its base), mesh fetches `pull/<n>/head`, which GitHub keeps, and starts there, and when that fails too it starts at the tip and the note says the old commits aren't available. In a main checkout, or a worktree with uncommitted changes after a merge, the note tells the worker to do it. Only a resume with a change task is checked: a read-only task needs no branch, a resume without a task would move the branch without the worker hearing of it (the next one with a task checks again), and a repo with no GitHub remote has no PR. `gh` missing or failing never blocks a resume: it goes on as before, with a note.
- **One process per conversation:** both commands refuse while a live agent sits in the worker's worktree. Two CLIs on one conversation would fork it. herdr's registration isn't proof either way: after a Claude Code auto-update herdr showed no agent for a live, working Claude (firstmate #6832, where the relaunch then typed into the live composer). So `live_holder` also reads the process table (`/proc`, one scan per command): any `claude`/`agy` of the worker's kind working in its worktree holds it, and in a shared main checkout one whose command line names its session. Processes are matched by `argv[0]`'s name, never the binary's path, which an auto-update moves. Without `/proc` (macOS) it asks herdr what the worker's old pane runs. When herdr can't be asked at all (not installed, its server down, any failure), the process table alone answers on Linux; without `/proc` too, nothing can tell, so the command fails, except `mesh open` from a plain terminal, which warns that it can't tell whether the worker still runs and opens it. The watch uses the same proof the other way: a pane worker herdr doesn't know is `gone` only when its pane no longer runs its CLI, and `unknown` otherwise; when herdr can't read the pane, its registration stands, since the refusal above is what prevents a fork.
- **`mesh open` is the user's session:** it strips the `MESH_*` environment, and it doesn't add `--dangerously-skip-permissions`, because the user is at the keyboard and their normal settings apply. The protocol tells an agent that finds itself outside a run to work with the user directly.
- **Untouched branches:** since 0.6 a worktree records the commit it started from. `mesh stop` deletes a branch only if it still points at that commit and has no upstream, which is what an asker (§10) leaves behind. Deleting it loses nothing, and resume starts it again at the same commit, at the same path.
- **The CLI is fixed:** a conversation can't move between Claude and agy, so changing agent means a fresh worker in the same worktree, only when the user asks for it (§11, "Stuck, not failed"). The model can change within the same CLI.

## 9. Models per phase

Flash is cheap and good at typing code and running tests, but weak at the research and planning that decide whether the change is right. Since 0.5 a worker on `--model auto` (the default) plans on a strong model at high effort and executes at medium effort, in **one conversation**. agy workers also move to the cheap Flash; Claude workers stay on Opus:

- **The switch happens at approval:** the plan is the boundary between deciding and doing, and the root is already there to approve it. `mesh approve` waits for the worker to finish its turn, opens a pane next to it, closes the old one, and reopens the conversation with `agy --conversation <id> --model <flash>` / `claude --resume <id> --model opus --effort medium`. It reuses the session lookup from §8, so the executor keeps the research. This is not the 0.2 cold hand-off. For Claude the model doesn't change, so the reopen exists only to pass `--effort medium`: don't skip it when the model matches. Approve skips it only when model and effort both match (a named `--effort` covering both phases).
  - **Planning is enforced, not only asked for (Claude):** a planner used to be only *told* to change nothing until approval. Plan mode would enforce it, but fits root-approved plans badly: leaving it needs a human in the pane (the worker reads `blocked`), and its plan goes to Claude Code's own plan file, not `$(mesh dir)/plans/`. So a Claude worker that plans runs with the same deny list as a read-only asker (§10), under a second reason, `planning`, beside `read_only`. Spawn sets it for a large task (a named `--model` doesn't skip the plan, so a pinned one too), and resume for a task it plans (no task: a worker in a plan phase that hasn't reported `done` or `failed` on its task comes back planning, so `retire` + `resume` mid-plan keeps it, and gives it to one whose plan phase began with a sent plan; a direct task sent to it ends the phase, list or not; an asker stays read-only). Answers, re-sent plans and `switch` keep it. `approve` lifts it: the reopen it does anyway for the execution effort costs nothing more, and where it wouldn't reopen (`--keep-model`, a pinned worker, model and effort already equal) it reopens on the same model and effort for this alone. So `--keep-model` is no escape for a Claude planner whose turn never ends: the error says to retry. `--plan-review user` is in plan mode already, and a direct task has no plan: neither gets it. `send` never reopens a worker to *add* the list: a worker that finished and is sent a new task that wants a plan stays prompt-only, since that task can't be told from a fix request it just does (below). The root gives such a task by `retire` + `resume` instead, which also plans it at the planning effort. Adding the list when the worker sends its `plan` lost: the list guards the research, which is over by then, and a worker that slips sends no plan at all; the reopen would run inside the worker's own `mesh send`, waiting for the turn it's in to end, and race the reopen of the `approve` that plan may get at once; it costs a second reopen per plan; and the plan would still be made at the execution effort. Marking `planning` at the plan without a reopen would make `approve` reopen to lift a list that was never applied. agy has no deny list (§10): its planners are held by the prompt.
  - **Who may approve, and what:** `approve` refuses unless the caller is the worker's parent (the root), and unless the worker's newest report since its last task or answer is a `plan`. Without the first, a worker could approve itself (its `MESH_SELF` makes it the caller); without the second, a worker that sent a `question`, or whose plan got a `changes:` answer and wasn't sent again, or was approved already, would be "approved" and reopened on its execution model. A worker whose background swap failed at approval already has its approval in its mailbox, so a `swap_failed` worker still planning passes, for the retry, but only when its newest `swap_failed` event's `why` is `plan approved`: a failed quota `switch` while planning leaves the same status with nothing approved. `switch` and `retire` get the same caller check, and refuse the root as a target. `stop` refuses any worker; with a run id to stop, the caller is read from the flags and the environment only, without `identity`'s side effects (the pane map names only roots; a pane worker that lost its environment is found by its pane, §11), and refused as a worker of any run it names (`--run`, `MESH_RUN`) or of the target, with a `--run` other than the target refused outright; with no identity at all it's the user in a shell, and goes ahead. `--as` is taken as given: the check is against the accidental call, not a lie.
  - **When the swap can't start** (no conversation found, or the worker never finishes its turn), approve sends nothing and suggests `mesh approve --keep-model`: the approval is delivered and the worker is recorded as executing on the model it planned on, so a later `mesh switch` moves it to the execution model. It's never automatic, since a worker that planned on Argon or Opus would then execute there unnoticed. A plain `mesh send --type answer` would leave it recorded as planning, and a quota `switch` would then walk the plan chain.
- **Quotas, not a fixed model:** the user's strongest model (Argon) runs out for days at a time. For agy, the planning model is the first of Argon → Claude Opus (through agy's Claude pool) → Flash with at least `MESH_MIN_QUOTA`% (default 10) left in every limit that covers it.
  - The limits come from `agy -p /usage`, whose rows are a group, a label, the percent left and the reset time. A group ending in "models" covers ids by vendor prefix ("Claude and GPT models" → `claude-`, `gpt-`); any other group covers the model of that name ("Gemini 4 Argon").
  - Unreadable quotas never block a spawn: the chain's first model is used.
- **Detecting a quota hit:** agy keeps the session alive and logs `RESOURCE_EXHAUSTED … Resets in 138h17m29s`. Each agy worker gets its own `--log-file`, so `mesh watch` can scan only that worker's new log lines and exit 7. The root then runs `mesh switch` without asking: a quota hit says nothing about the task, so moving on can't hide a real failure. `switch` re-reads the quotas, skips every model that already hit its quota, and tells the worker to continue.
- **No fallback for execution:** the user chose Flash only for execution. A Flash quota hit stops the worker and the root reports the reset time, rather than spending the Claude pool on typing code.
- **Effort follows the phase too:** high while planning, where thinking pays, and medium (agy's own default) while executing an approved plan. agy bakes the effort into the model id (`gemini-3.8-flash-medium`); Claude takes `--effort medium` on the resume.
- **A resumed worker** gets the same two phases when its follow-up task has a plan: it plans where a spawn on `auto` would (the plan chain with quota, at high effort), not on the model it last ran on, and `mesh approve` moves it to the execution model and effort. An asker that answered on Flash and then gets a feature would otherwise plan it on Flash, which is where the plan matters most; a worker coming back from an earlier run has lost its prompt cache anyway, so reopening it on another model costs no more than on its own (and a large one is compacted first, §12). It used to keep one model throughout, so a resumed agy worker executed a whole review's fixes at high effort, which is the cost the phases exist to avoid. A direct task, a question, or a named `--model` / `--effort` gets no phase, as in a spawn.
- **A live worker that sends a plan** while it has no plan phase (a small asker given a change, a worker that finished and got a new task) enters one then, so `mesh approve` moves it to its execution model and effort. The trigger is the worker's `plan`, not the root's task: a fix request after `done` is just done (PROTOCOL rule 2), and a worker marked as planning for a task it never planned would, on a Flash quota hit, `switch` down the plan chain, against "no fallback for execution". It plans on the model it's on: `send` doesn't reopen a live worker. To plan on the strong model and under the deny list, `mesh retire` it and `mesh resume` it with the task (ORCHESTRATE's "Follow-ups" makes that the way to give a running worker a task it plans).
- **A named model or effort is kept:** spawn and resume record `pinned` when `--model` / `--effort` covers the whole task (no execution phase), and such a worker, like a user-reviewed one, never gets an execution phase later. A sized reviewer's own high effort isn't a named one.
- **`switch` while executing** uses the execution effort, so a worker approved with `--keep-model` (still at its planning effort) moves to Flash at medium on a quota hit.
- **Claude workers** plan and execute on Opus; only the effort changes. Prompt caches belong to one model, so a switch to Sonnet would re-read the whole planning context on the first execution turn, and most of a worker's tokens are cache reads, which cost the same on both ($0.20/M on Opus 5.5 and on Sonnet 5.5), leaving Sonnet a small saving (on writes and output only) for a weaker executor. A resume that changes only `--effort` keeps the cache: measured on 2026-10-24, the medium-effort resume read the full previous prompt from cache and wrote 65 tokens. Claude Code's usage isn't visible to mesh, so there is no quota choice for them; `mesh switch --model` still works by hand. A usage limit is detected, though: the watch matches the pane's last 20 lines against Claude Code's limit screens (Gas Town's patterns, from real panes: `You've hit your … limit`, `limit · resets 7pm`, the rate-limit options menu), each anchored to the start of its line, after glyphs, numbers and spaces only, so the agent's own output quoting one doesn't count (a quote mark or backtick before it, straight or curly, ends that prefix), and reads the session file's last reply, where Claude Code records an API error as a synthetic entry with an `error` code (`authentication_failed`, `rate_limit` and `server_error` were seen). A prompt sent while limited gets `rate_limit` with `You've hit your session limit · resets 2:20am (…)`, but a plain rate limit may share that code, so there too the text decides. A limit reached mid-turn writes no error: Claude Code adds a meta user entry with `usageLimitNote: "wrap_up"` (`[Usage limit reached; a short grace allowance remains…`), the worker takes a few more steps and ends its turn (seen on 2026-10-26, in this run), and the first turn after the reset opens with `usageLimitNote: "release"`. The newest note decides (a `wrap_up` with no `release` after it is the limit, with no reset time), read when the worker reads idle, as every limit check is; the session file's tail is read up to 1 MB, since that grace turn wrote up to 150 KB after the notice. A plain rate limit (`API Error: Rate limit reached`) is left out, as agy's `QUOTA_RE` leaves it out: it is transient, not a limit with a reset. That second reading covers background workers, which have no pane. Without it, a limited worker read as stopped (nudged into the limit screen, then exit 3), blocked (4), or working with a frozen transcript (Gas Town #4887, where their stuck detector killed a healthy worker). It exits 7 with the reset time, once per task, and the root waits: the limit is the account's, so there is no model to move to, and a task saying "continue" at the reset re-arms the alert. An expired login looked the same (an idle or stopped worker, exit 3, 4 or 8) and is just as stuck until something outside the worker changes, so it is read the same two ways, `… · Please run /login` at the start of one of the pane's last 20 lines (`Login expired`, `API Error: 401 {…}`), or a last reply with the `authentication_failed` code (seen on 2026-09-25, with the text `Login expired · Please run /login`), and gets exit 7 too, as its own `login` alert once per task: the line tells the root to have the user run `/login` in that pane (or `mesh open` a background one), then send `continue where you stopped`. There the code is enough on its own, since it names nothing else. The pane can't tell an old login line from a current one (the user logs in, the worker replies briefly and stops, and the line is still in the last 20), so a readable session file decides the login: a later ordinary reply means it's over, and the pane is read for it only when there's no session file. Both ways a usage limit is recorded are now known (the `rate_limit` error, the `wrap_up` note), so a readable session file decides the usage limit too, when it holds a usage-limit record: a `wrap_up` (the limit) or a `release`, or a limit error with a reply after it (over), so a limit screen left on the pane after the reset doesn't count. With no such record the pane's screen still counts, since a limit menu may write nothing to the file. While a task's limit or login alert stands, exit 8 is held off only as long as `limited` still reads it, so a worker the user logged in by hand that hangs later on the same task is still raised.
- **Opus at every size, medium by default (2026-10):** small Claude tasks used to run on Sonnet at low or medium effort to save tokens. Once quality mattered more than tokens, the measured numbers decided it (Anthropic's sweep on a SWE-bench Pro subset):
  - Opus 5.5 solves 87.4% at low ($0.11 a task), 92.8% at medium ($0.21), 95.3% at high ($0.29) and 96.7% at xhigh ($0.74). Sonnet 5.5 at medium scores about 7 points below its own high, and Sonnet at high (87.6%) only matches Opus at low. So every Claude size runs Opus, at medium.
  - Raising effort mostly buys verification and edge cases, not a better approach. Anthropic measured that running at medium and re-running only the failures at high (about 97%) beats running everything at high, and the mesh already has the failure signal: plan reviews and PR reviews. So effort goes up where checking is the job (planning, reviews), and for a fix when the root judges it needs it (§11, "Stuck, not failed"), not for every task. That fix is a `mesh resume`: Claude with `--effort high`, agy with `--model argon`, since a named effort alone would keep an agy worker on Flash.
  - xhigh and max aren't defaults: Anthropic recommends them only where evals show a gain, and max is prone to overthinking. Claude Fable 5.1 isn't one either: Max plans cap it at half the weekly limit, and other models can't read its thinking, so a Fable planner handing over to an Opus executor would lose its reasoning. It runs only when the user names it, for a whole task.
- **The root's model is the user's:** mesh never changes the root session's model.

## 10. Questions and reviews are workers

Not every cross-repo need is a change. Often the root needs to *know* something about another repo ("how is restockedAt computed?"), or wants a second pair of eyes on a PR it just opened. The global rule already allowed a headless `agy -p` for that (§5), but a headless answer is a dead end. You can't watch it, it can't ask back, and its context is lost for the next question or for the change the answer leads to. Picking that conversation up later would need a second lookup path next to §8's.

Since 0.6 `mesh ask` gives the question to an **ordinary worker** instead. It's spawned exactly like one (same role, same first doorbell, same `auto` plan phase), and its first task starts with `Question (read-only)` or `Review (read-only)`. The protocol says that such a task gets no plan and no edits, only one `done` with the answer. Everything else comes for free:

- **Follow-ups** are more `mesh ask` calls to the same agent, which still has everything it read. Once it's closed (below) or after `mesh stop`, `ask` resumes it (§8).
- **Turning it into a change** is a plain task. The asker is still in its plan phase, so it plans, `mesh approve` moves it to its execution model, and it opens a PR from the branch it already has. That's the same "no cold hand-off" argument as §7.
- **Existing workers answer too:** the agent that wrote a PR is the best one to ask why. An existing worker reviewing a PR mustn't leave its branch, so it reads the PR from `gh pr diff` / `FETCH_HEAD`. A fresh reviewer gets a worktree at the PR head, so it can run the tests. Asked again after a fix, it is moved to the new head (`plan_move`, `apply_move`: its run branch reset there and recorded as its `base`, so `mesh stop` still sees it untouched), but only its own review checkout of that PR (`review_checkout`, set when `ask --repo` made it; never an author or a peer), still at its recorded `base` (clean, no commits of its own), and not running mid-task in any run: a checkout under a working agent could change files it is reading, and a reviewer idle in herdr may still owe its report (a `/code-review` it declared a wait for runs over that worktree). Moving from its `base`, not from the head it last reviewed, lets a later ask move one a first ask couldn't. Otherwise it stays, and the task says why and to read the new head with `git show`. Whether it moves is decided before anything starts, the move is made just before the reach (which may reopen it, after which a checkout is no longer safe), and undone if the reach refuses or fails. Every review task carries the PR's diff (up to 100,000 characters; a longer one is left for the reviewer to read), so the reviewer starts from the whole change instead of piecing it together over its first turns. It is the diff of the head the task names: `git diff <merge base>..<head>`, with the PR's base branch fetched from the remote `pr_head` fetched the head from (`upstream` in a fork), not `gh pr diff`, which shows the PR as it is now and so may hold a push the author made after the head was fetched; the task's own words name that command too. Without that head, or when gh can't name the base branch, git can't fetch it, or the diff is empty (the base already holds the head, as after a merge commit), the task falls back to `gh pr diff` and says the PR may have moved past the head. Both fetches go through a ref of the call's own (`fetch_commit`), not `FETCH_HEAD`, which parallel asks on one clone would read from each other (and which is the user's).
- **Reviews run at high effort:** a fresh trivial or small reviewer gets `REVIEW_EFFORT` (high) instead of its size's effort, and a large one plans at `DEFAULT_EFFORT` (high) anyway. Checking is all a reviewer does, and its findings decide whether a fix round happens (§9). REVIEW_EFFORT isn't passed to a large reviewer: it would read as a named effort and carry into the execution phase of a fix the reviewer is later given. The size still picks its plan phase and view, and a named `--effort` wins. Copilot keeps its own per-size effort.
- **One command:** the cost of a question was the ceremony (init, task file, spawn, watch, inbox), not the model time. `ask` starts a run if there's none, delivers, waits like `mesh watch` (same exit codes) and prints the answer. A Claude root runs it in the background and gets the answer as the notification.

Two details keep this from leaving a mess:

- **Reviewer vs author:** a reviewer's `done` quotes the PR link, which used to make `mesh resume <PR>` pick the newest match, the reviewer. Workers now record the PRs they reviewed, and PR matching skips those. A PR link is now matched by the PR's head branch first (§8), which a reviewer is never on; the exclusion still covers the message-link fallback.
- **Empty branches:** every question creates a branch with no commits. `mesh stop` deletes those (§8).
- **Idle agents:** an asker used to stay open after answering, in case of a follow-up, so panes piled up for the rest of the run. Since resuming is cheap and keeps the whole conversation, `ask` now closes an agent it opened (started or resumed) once it has answered, and the next `ask` reopens it under the same name. A worker that was already open, mid-change, is left alone, and `--keep` overrides. When the answer comes by `SendMessage` or `--no-wait`, `ask` has returned before it, so the protocol tells the root to retire the agent itself, as it does a change worker it has nothing more for.

**Read-only by more than the prompt.** A prompt asking for read-only behaviour is a request, and a reviewer sits in a worktree at the PR head with `gh` signed in as the user, one `gh pr comment` away from the outward-facing actions only the user may authorise (PROTOCOL.md, "Authority"). So a Claude worker started or resumed on a read-only task (`read_only` in its entry) gets `--disallowedTools`: `Edit(//<worktree>/**)` and `Edit(//<main checkout>/**)`, plus the same publishing commands Copilot is denied (`PUBLISH_COMMANDS`: `git push`, `gh pr review` / `comment` / `merge` / `edit` / `close`, `gh issue comment`, as `Bash(<cmd>:*)`).

- **Checked live** (Claude Code 2.1.310): deny rules win over `--dangerously-skip-permissions`; an `Edit(path)` rule stops the Write tool too; they hold in a `--bg` session and in the copy `--bg --resume` with full flags forks; and they aren't saved in the conversation, so a reopen without them can edit again. (A flag-less `claude --bg --resume <id>` continues the session with its own saved options, deny list included; mesh always passes full flags.)
- **By path, not the whole tool:** the asker still writes its report under `$(mesh dir)`, so its `done` goes out as usual. Bash stays open so it can run tests, and a shell command can still write (`>`, `sed -i`, `git commit`); the list stops the tools that edit and the commands that publish, the same line Copilot's `--deny-tool` draws. It is best-effort, not a sandbox: a `Bash(<cmd>:*)` rule matches how a command starts, so `git -C <dir> push` or `gh api` with a POST gets past it, and the prompt stays the primary guard.
- **Lifted by reopening, at approval or for a direct task:** turning an asker into a changer is a plain task (above). A task it plans keeps the list, since a planner runs under it anyway (§9): the reason just moves from `read_only` to `planning`, with no reopen, and `mesh approve` lifts it. A `Direct task (no plan)` can't wait for that, so `mesh send --type task` waits for its turn to end and reopens the same conversation on the same model without the list (`swap_model`, as `mesh approve` reopens a worker), then delivers the task; the same lifts a planner re-scoped to a direct task. `mesh resume` sets the list from the task in the same way. A retired asker, which is what `mesh ask` leaves, is resumed by `send` itself (§18), so it comes back the usual way (compaction, a `resume` event) rather than through a model swap. A background lift that fails after storing the task (a copy's opening prompt is its doorbell) says so and points to `mesh resume <name>`, so a retry doesn't file the task twice. A quota `switch` keeps whatever it had; `approve` drops it. A changer asked a question (`mesh ask <live worker>`) isn't reopened: it is held by the prompt, as before.
- **agy has no deny list:** `agy --help` offers only `--sandbox` (terminal restrictions), so agy askers stay prompt-only for their files. A Claude or Copilot reviewer is the one to pick for a review that must not slip.
- **Mesh state is guarded by `mesh` itself, for every worker.** Neither deny list covers `mesh` (Bash stays open), and the PR #33 agy reviewer, trying the PR out, ran `mesh peers add` against the machine's real `MESH_HOME`. So `main` checks every command before it runs (`check_worker`): a caller that is a worker of a live run may run only its own commands and the readings (`WORKER_COMMANDS`: `send`, `inbox`, `whoami`, `dir`, `hook`, `status`, `log`, `agents`, `conflicts`, `peek`, `brief`, `model`, `usage`, `peers list`), and is refused everything else, which starts agents or changes another agent's or the machine's mesh state, with a `refused` event. An allowlist rather than a call in each root-only command, since one such call was easy to miss (`watch` was, which spends a sibling's one nudge and records alerts that quiet the root's watch), and a command added later is the root's until it is listed (a test fails until it is placed on one side). `stop` keeps its own check (`OWN_WORKER_CHECK`), which also counts a worker of the run it's asked to stop. `send` is a worker's, but only to its parent (`refuse_foreign_send`): a `Direct task` to itself or a sibling would otherwise reopen it without its deny list (`lift_read_only`). The caller is told apart by `worker_caller`, `stop`'s too: from the flags and the environment, a pane worker herdr restored without its variables by its pane (`pane_worker_entries`), and an environment identity `inherited_identity` rejects isn't that worker. The refusal says how to try mesh out instead: temp `MESH_HOME`, `MESH_WORKTREES` and `MESH_PEERS_DIR`, and `MESH_HERDR` and `MESH_CLAUDE` at a missing binary, as the tests do (this repo's CLAUDE.md says the same), and how the user in a shell left with a worker's variables gets past it (`env -u MESH_RUN -u MESH_SELF …`). The check reads the run from the current `MESH_HOME`, so under a temp one the worker's run isn't there and its trial runs, against the temp state. Two alternatives lost. A prompt line only: the incident happened under a prompt that already said to change nothing, and a line about `MESH_HOME` in every asker's task would name agent-mesh's own testing in a process-agnostic prompt. Starting askers under a sandboxed `MESH_HOME`: their own `send` and `inbox` must reach the real run, so every command would need a second home and every launch path the plumbing, for askers only, while the guard covers planners and changers too. `--as <root>` still gets past it, as it does `stop`: it stops an agent trying things out, not one set on impersonating.

**Reviews are of one commit.** A review used to name only the PR, so after the author pushed a fix nobody could tell which reviews were stale, and a reviewer asked again re-read the whole PR. Now the task says `Review (read-only) of <PR> at <sha>` (`pr_head`, which a fresh reviewer's worktree starts at; for an existing worker it is fetched into the shared object store, and left out if that fails), and the reviewer's entry records it in `review_heads` next to `reviews` (which stays a list of links, for `worker_prs`). Asked again at a new head, the reviewer is told the head it read before and to review `git diff <old> <new>` and say which of its earlier findings are fixed (the whole PR again when the branch was rebased or merged its base in between, see below). The protocol caps the rounds by the PR's size: one for a small PR, whose fix commits the root checks itself without a re-review (the user found one round enough for a small change), and two for a large one. What is still open after the last comes to the user, an explicit stop rather than a loop or a quietly lowered bar (ccswarm caps its loops the same way). Each finding is marked **blocking** (a defect the reviewer reproduced or traced, with the input that makes it fail) or **advisory**, so an unsupported assertion asks for a check rather than a veto, and the root knows which findings justify another round.

**Claude reviewers run `/code-review`.** Claude Code bundles a review recipe, `/code-review [low…max] [<PR#|branch|path|range>]`: a fixed set of finder angles (a line-by-line scan, removed behaviour, callers of changed functions, reuse, simplification, efficiency, altitude, and the CLAUDE.md rules the diff breaks), each finding with a concrete failure scenario. A mesh review task carried its own detailed instructions, so a reviewer never reached for it. Now `ask_task` appends `CODE_REVIEW` to a Claude reviewer's task (fresh or asked again, `--kind claude` only; agy and Copilot are unchanged), which has it run `/code-review <level> <target>` first and treat the result as candidates. What shaped the prompt, checked live (Claude Code 2.1.310, Opus 5.5):

- **It runs in the background.** It's a forked skill: the Skill tool returns at once, one `general-purpose` subagent runs the recipe with the reviewer's context, and the findings come back as a task notification, often minutes later (3 min 11 s, 20 tool calls for `high` on a 24-line PR). A reviewer that ended its turn there would be idle with no report: the Stop hook would push it to report and the watchdog would count it idle. So the prompt has it read the change and run the tests meanwhile, and declare a `wait` before ending a turn while the review runs. Making it synchronous (`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`) would also turn off background test runs, and needs launch plumbing (TODO.md).
- **Levels:** `low` is one pass over the hunks (4 findings); `medium` and `high` run 8 angles inline in the fork (10 findings); `xhigh` adds two more angles and a gap sweep (15), still inline; `max` runs each angle and one verifier per candidate as its own Agent (dozens). The recipe also depends on the model (`medium` gave the `high` recipe here). Every review got `high` at first, at every size. The cost study of run mb3c1 (`docs/cost-research/README.md`, ledger #2) found the `/code-review` fork was 34% of reviewer spend, so a small (or trivial) review now runs it at `medium` and a large one at `high` (`REVIEW_LEVEL`, by the size `mesh ask` was given or, asked again, the reviewer's own), first review and re-review alike. Anthropic's effort guidance keeps `xhigh` for long-running agentic work (over 30 minutes, millions of tokens), while `high` took about 3 minutes and 97k tokens here. Higher levels broaden coverage, which mostly adds speculative findings the reviewer then has to check itself. `max` would also fan out into dozens of agents, and its CONFIRMED / PLAUSIBLE verdicts never reach the output. The level is always named, since without one the skill reuses the last level the user typed. Typing one also sets what the user's own bare `/code-review` reuses (except in a `-p` run), so after a mesh review that is `high`: harmless, since mesh always names it.
- **The reviewer is the verify pass.** At these levels the recipe deliberately skips verification ("err on the side of surfacing"), and its output is a JSON list of `{file, line, summary, failure_scenario}` with no verdict. So the reviewer checks each candidate itself, marks it blocking or advisory as before, drops the ones it refutes with one line each, and adds its own. That is PROTOCOL rule 9 applied one step earlier, and it keeps the root from receiving the recipe's recall-biased raw list.
- **Findings stay in the `done`.** Each recipe says not to call `ReportFindings` (a findings list only a host app like the desktop app asks for); in a terminal the result is text. The prompt still says the `done` file lists every finding, whatever reports elsewhere.
- **Targets:** a first review names the range `<merge base>..<head>` (the merge base with the PR's base branch, fetched from the remote the head came from, as for the embedded diff), so the fork reads the PR's change and not the worktree's own branch. Not the bare PR number: `/code-review` hands its target to the model as text, and a number is resolved by `gh` against the worktree's default repo, which in a fork clone may be `origin` rather than `upstream`; a range is resolved by git alone, and the skill parses it itself (it sizes the review from its `git diff --numstat`). When git can't give the range (`head_diff`), the target is the bare number where the PR's remote is `origin`, as before, and the PR's link in a fork, where the number may name `origin`'s PR. Either way the fork never reviews the worktree's own branch (wrong for an existing worker reviewing another PR, which is also told to check findings with `git show <head>:<path>`: the head `pr_head` fetched is in the shared object store, where a later fetch can't move it as it moves the per-worktree `FETCH_HEAD`). A re-review names the range `<last>..<head>`, so it reviews only the fix commits, and the reviewer checks its earlier findings at the new head itself. The cross-file angle still follows changed functions into code the fix didn't touch. When the branch was rebased or merged its base since (`fix_commits`: `<last>` isn't an ancestor of `<head>`, or a merge commit lies between), that range would hold more than the fixes, so the target is the whole PR again (its merge-base range) and the task (any reviewer's, `REVIEW_AGAIN_WHOLE`) says to review the whole PR.
- **Only with the head in the worker's repo:** the range is of commits in the worktree's repo, and the fork reads files from it, so a review of another repo's PR (where `pr_head` refuses) or one whose head couldn't be fetched gets no `/code-review` at all: a hand review from `gh pr diff <url>`, as before, rather than a silent review of the wrong PR.
- **Read-only:** the prompt forbids `--fix`, `--comment` and `ultra` (billed, user-triggered), and says a denied tool is expected. Claude Code documents subagents as inheriting the session's deny rules, but whether a forked skill keeps `--disallowedTools` wasn't checked live (TODO.md). Without `--fix` the recipes never edit.
- **Fallback:** an older Claude Code, a user's `skillOverrides` set to `user-invocable-only`, or a project skill named `code-review` replacing the bundled one: if the Skill tool doesn't list it or the call fails, the reviewer reviews by hand as before.

**Findings are claims.** Reviewers are often wrong: they flag code paths that can't happen, or suggest a fix that treats a symptom or fights the repo's design. An agent that applies every finding turns a review into a source of bugs. So the protocol (PROTOCOL.md rule 9) makes every agent that receives findings, the root deciding on them and the author fixing them, check that each bug is real and that the fix is the best one, and say which it fixes, how, and which it declines and why. The root's own opinion on a finding is held to the same test. The reviewer is asked for a concrete failure per finding and to mark what it couldn't confirm, so each claim can be checked.

Reviews post nothing on GitHub. That's outward-facing, so it needs the user's own word (PROTOCOL.md, "Authority").

**One command for reviews.** A review the user asks for used to go through `/delegate-claude` or `/delegate-agy`. That named the wrong thing ("delegate to Claude" when Claude only reviews), and it loaded the whole orchestration procedure for one `mesh ask`. Worse, three skill descriptions all claimed "review a PR", so which one fired was a toss-up. Now `/delegate-review` is the only skill whose description covers a review the user asks for. It takes the reviewers as arguments (any of `claude`, `agy`, `copilot`, or `all`), so there's one skill and not one per CLI, and it reads only "Questions and reviews". Several reviewers run at once as one review round (`mesh ask --reviewers`, below), in one run it starts when there is none, each under its own name (`review-<n>-<cli>`): two `ask`s for the same PR would otherwise race for the same name and worktree (several reviewers used to be one `mesh ask` each, with its own `--name`). Even with one name, `free_slug` picks the slug and claims it in `run.json` (`slugs`) under the run lock, so of two `ask`s started at the same moment the second gets `-2`, for its branch and its agent name alike (the slug is cut so `-2` fits the name's 20-character suffix); checking the branch alone raced, since `add_worktree` creates it later. The skill then merges what they found; a finding several reviewers agree on is likelier, but still checked. The delegate skills keep the reviews their runs give their own workers' PRs, since those are part of supervising, not something the user asks for. Every PR a run makes gets them, a single large change too, not only a task list's: the root's own check compares the diff with the plan it approved, which catches drift from the plan but not the bugs the plan never anticipated.

**One root wake per review round.** Each reviewer used to be its own `mesh ask`, run in the background, so every reviewer's `done` woke the root, and each wake re-read the root's whole context (repowire counted ~1.4 extra wakes per PR over 69 runs; reviewer `done`s were about 38% of root-bound reports). `mesh ask --repo <checkout> --review <PR> --reviewers auto|all|<kinds>` (`ask_reviewers`) now runs a round as one command on §14's collect path: one run made up front (`ask_identity`), each Claude or agy reviewer started or asked again in a thread under the call's `collect` mark (`fresh_asker` / `reach_worker`, with the same task `cmd_ask` builds, `asker_task`), so `deliver` stores its `done` without a doorbell, all watched by `watch_each`, and Copilot in a thread of its own, headless as ever. The answers go into one `reports/review-<n>-<stamp>.md` (`write_answers`, shared with `ask --peers`), the reviewers that answered are closed (`retire_answered`), and stdout is one line per reviewer and the file's path, which is the root's one notification. What it trades: the root waits for the slowest reviewer and can't start on the first one's findings early, and it checks all findings together, which it should anyway. Alerts are kept: a reviewer that hangs, stops, is held at a startup screen or runs out of quota gets its own outcome and line, loses its mark so its later answer rings as usual, and stays open; the root's `--any` watch still raises the same alerts as they happen. An interrupted round clears its marks and stops its Copilot (`stop_copilot`). A re-review is the same command again: `auto` asks the earlier reviewers again (`earlier_reviewers`: the newest reviewer of each CLI that `ask --repo` started at that PR, `review_checkout`, which a resume carries along, across every run, live or archived, so after `mesh stop` or under a new root too), minus Copilot and minus an agy one whose own model is short of quota (Claude takes its place; a large re-review always has Claude), on the commits since, each in its own clone with the head fetched there; a named CLI reuses the newest reviewer of that CLI when there is one. With no `--size`, the round takes the size those reviewers were given (else large). `--model` and `--view` belong to one CLI, so a round of several kinds refuses them; each reviewer gets the round's size (a Copilot's effort follows it). An interrupted round sets an event its Copilot thread checks before and after claiming the asker, so it never starts copilot late, then stops a running one and waits briefly for its `failed`. `--reviewers` is explicit, not the default of `ask --review`, so a single `--kind` review keeps working as before.

**Reviewers by size and quota.** Small PRs got Claude and agy, and large or risky ones all three, Copilot beside them, on the grounds that each vendor catches what another misses. The cost study (ledger #2) found reviews were 22% of Claude spend even after the tiny-PR rule (a tiny PR, a trivial or small task's or group's PR of up to 150 lines touching nothing risky, gets the root's own review instead, §11), and with agy at 0% Claude sat on every PR. So `pick_reviewers` now gives a small review **one** reviewer, agy while it has quota, else Copilot, else Claude, and a large one **Claude plus one other**, agy while it has quota, else Copilot: a second vendor where the risk justifies it, and Claude's spend only where it does. "agy has quota" is the reading a spawn would make (`agy_has_quota`: `choose_agy_model` on Flash for a small reviewer, on the plan chain for a large one, from the cached `agy -p /usage`; unreadable counts as available, agy not installed doesn't), so the root never parses `mesh usage` itself; "Copilot" is its CLI on the PATH, since its credits have no cheap pre-check and running out shows as that reviewer's `failed`. A small PR loses the second model; the root still checks its fix commits. A re-review after a fix (large PRs only) asks the first round's reviewers again except Copilot (Claude alone after a Claude + Copilot round): it checks a few fix commits, which doesn't need another vendor's first look, and a fresh reviewer added then would read the whole PR rather than the fixes. Copilot's credits are kept for first looks (mesh puts no cap on them itself). The tiny-PR limit stays at 150 lines: raising it would move a small review from one agy run (no Claude spend while agy has quota) onto the Claude root, whose context then carries the diff for every later call.

**Copilot reviewers are headless.** It breaks two rules above on purpose, and only for read-only tasks:

- **No pane (§1):** herdr could start Copilot in a pane (`--kind copilot`), but a pane worker has to follow the mesh protocol and report with `mesh send`, and the global rules that teach it that are installed only for Claude Code and agy. Headless, Copilot needs none of it: its JSON output carries the answer and the model, so mesh files the answer itself. The cost is that nobody can step in, which a read-only review can do without. Watching is `mesh peek <name> [--follow]`, which prints its tool calls and messages from the events file Copilot writes per session (`~/.copilot/session-state/<id>/events.jsonl`). The user wants to see a review work, so `mesh ask` opens a pane beside the root running `mesh peek --follow` for as long as Copilot answers, and closes it after (`mesh stop`, or the next `ask` of that reviewer, closes one a killed `ask` left). It is a view only, never a second agent, and only beside the root: when that tab is full it is skipped rather than sent to the run's tab, where nobody is looking. `mesh ask` runs `copilot --output-format json` in the reviewer's worktree, with the prompt on stdin, and files the last thing it said as its `done` (`failed` on a non-zero exit or no answer). While it runs, `mesh status` and `mesh watch` see it as `working`, and `mesh stop` refuses to remove its worktree and archive the run from under it. The reviewer still gets the PR head checked out, the diff in its task and the repo's `AGENTS.md` / `CLAUDE.md`, which Copilot loads on its own.
- **Not a dead end anyway (§10's objection):** mesh picks the session id at spawn and passes the same `--session-id` on every ask: Copilot starts the session the first time and resumes it after that, so follow-ups keep what it read. `mesh open` reopens it interactively (`--resume`). While an ask runs, the entry carries the `mesh ask` process's pid and, once Copilot starts, Copilot's, so a second `ask` or an `open` on the same conversation is refused, and so is `mesh stop`. Copilot runs in a session of its own: a timeout, a Ctrl-C, a SIGTERM or a hang-up of `mesh ask` kills its whole process group (the tools it started too) and files the asker's `failed` ("interrupted" for the last three) before releasing it, while a `mesh ask` killed with SIGKILL leaves it answering, and its recorded pid keeps the asker busy until it exits. Its answer isn't lost: Copilot writes each ask to its session's `events.jsonl` as a `user.message` holding the prompt, the turn, and a `session.shutdown` when it exits on its own, the same `assistant.message` events its JSON output carries, so the answer is rebuilt from there with no file of mesh's own (checked against every ask on hand: each filed answer came out the same). The claim records the events file (the `COPILOT_HOME` that `mesh ask` gave Copilot, whoever reads it later) and its size then, and only what Copilot wrote past that counts: its last `user.message` must be the task, and the turn ends at its `session.shutdown`. So an earlier ask of the same question, or a later ask's answer, is never taken for it. Whoever next finds the entry still `running` with both processes gone files it as the asker's `done` (`failed` when Copilot never got the task, was killed before it finished, or said nothing): the next `ask` of that asker, a `mesh watch` on it (which then ends with the report instead of calling it gone), the root's `mesh inbox`, or `mesh stop` (into the run it archives). It checks and files under one run lock, so the answer is filed once, and not at all when its `mesh ask` died after filing it (a watch checks without the lock first, since it asks every poll). `mesh status` only says a report is waiting: it derives, and never writes (§13). Each pid is recorded with its process's start time (`/proc/<pid>/stat` field 22, `ps -o lstart=` elsewhere), so a later process given the same pid never counts as it; a `running` whose processes are both gone counts as stale. `send`, `ring`, `approve` and `switch` refuse a Copilot asker outright, since nothing reads its mailbox and it has no pane to swap.
- **The prompt goes on stdin,** not as `-p <task>`: a review's task carries up to 100,000 characters of diff, and Linux caps a single argument at 128 KiB. A line at the end tells Copilot that there is no `mesh send` and its final message is the answer, since it never reads PROTOCOL.md. What it can't do is take the change: `mesh resume` refuses it, and the change goes to the PR's author or a fresh worker.
- **Read-only** is the review prompt plus `--deny-tool`: `write`, and the shell commands that would publish or merge (`git push`, `gh pr review` / `comment` / `merge` / `edit` / `close`, `gh issue comment`). A shell rule needs the `:*` form (`shell(gh pr comment:*)`): Copilot ignores a bare three-word `shell(gh pr comment)`, checked live. Shell stays allowed otherwise so it can run tests, and a shell command can still write (`>`, `sed -i`, `git commit`), the same line a Claude reviewer's deny list draws (above). Unlike theirs, a slip happens out of sight, but only in its own throwaway worktree, which `mesh stop` keeps when it's dirty.
- **Models:** Copilot Student offers only `--model auto`, which refuses an effort but takes a routing profile (`--auto-tier intelligence`). A named model (`--model`, `MESH_COPILOT_MODEL`) gets `--reasoning-effort` from `--size`. mesh records the model Copilot reports it used.

## 11. Native transport, sizes and task lists

By 0.6 mesh had its own copies of things Claude Code now does natively: typing doorbells into panes, polling `mesh watch`, and one fixed model per mode. 0.7 uses the native pieces where they're better, and keeps mesh where they don't reach (agy, mixed runs, quotas, resume across runs).

- **The mailbox stays the record, Claude Code's cross-session inbox becomes the transport.**
  - A doorbell to a Claude session goes into its cross-session inbox instead of being typed into a pane. A worker's report no longer lands in the middle of what the user is typing in the root's pane, and a background worker, which has no pane, can be reached at all.
  - Every message is still written to the mailbox first. PR lookup (§8), `ask`'s reply, the watchdog and the audit trail all keep reading the mailbox.
  - **mesh writes the doorbell into the socket itself** (`write_inbox`, logged `rung via=socket`), as repowire and ACC do: one JSON line, `{"type":"user","message":{"role":"user","content":…}}`, the frame Claude Code's own debug log documents. So any sender reaches a Claude session, an agy root or worker and the watch's nudges included, with no tool call for the sender to forget, and none of a pane's hazards (a human's draft, merged prompts, `ref` tokens). An idle session starts a turn; a busy one takes it between two tool calls. 0.7 handed the Claude sender a `send_message` to pass on with `SendMessage`, since mesh can't call a tool: that only covered Claude senders, and cost each message a second tool call.
  - **Which lane** (`native_route`, by the inbound policy below): a Claude worker whose process was launched with `crossSessionInbound: accept` is written to at its socket while it runs (a background one's process from `claude agents`, with the flag recorded as its `inbound` at launch; a pane one's the Claude leading its pane, when mesh started it, `mesh_launched`, and its `--settings` carry the flag, `launched_accepting`). A worker started by a mesh from before the flag would hold such a frame (bypass, no mode asserted; the root's smoke test on 2.1.310 saw exactly that hold), and the checkout is symlinked, so every live worker is one at an upgrade: a background one keeps the `send_message` a Claude sender passes on (an agy sender's message is stored unrung, with `mesh retire` then `mesh resume` as the fix, which relaunches it accepting), and a pane one is typed to. A background worker launched accepting never gets a `send_message`: if its socket is gone or its settings hold since, `SendMessage` would be held too, and expire. A root is written to when it takes a frame that asserts no permission mode: its settings say `accept`, or with none set the newest prompt in its session file ran in a prompting mode (`root_class`, from `permissionMode`). A root in bypass mode holds such a frame, so there a Claude worker still gets a `send_message`: `SendMessage` asserts the sender's mode, the same class. Anyone else, and any root whose setting holds or refuses, rings the pane.
  - **No receipt, no retry.** The socket never answers, so a write that went through counts as rung, the same confidence `SendMessage` gave. It is never repeated: Claude Code delivers a repeated frame again (ACC 797cc804). A failed write (no socket, a path that isn't this user's socket, `EPERM` from a sandboxed sender) is logged `inbox_failed` and the pane is rung instead, or a background worker gets the stored-but-unrung error. A worker that never picks its task up is caught by the watch as before. The root's mode read can be stale (it switched mode after its last prompt): a frame then waits behind a dialog in the root's own pane, as a mismatched `SendMessage` did before, and the root's `mesh watch` returns on the report anyway.
  - **No auth line.** In 2.1.310 the socket requires one only on Windows (`authRequired` is the platform check), and mesh is POSIX-only. The token lives in each session's environment and its `sessions/<pid>.<hash>.key`; mesh records neither.
  - **`CLAUDE_CODE_HARBOR_KITE=0` turns Claude Code's inbox off** (ACC's capability notes). Such a session has no socket and no `messagingSocketPath`, so the lookups find none and its doorbell is typed into its pane (a background worker is unreachable, and a root without one gets panes for its workers). mesh doesn't read the variable: the recipient's environment is what counts, not the sender's, and a missing socket already says it.
- **Address by socket, not by name.** Claude Code retitles a session as its conversation moves on, and a send to the old name fails. Every session also listens on `cc-socks/<pid>.sock`, and `SendMessage` accepts that address.
  - **Found as Claude Code finds it, never rebuilt** (`socket_address`, `claude_process`). A session's own socket is `CLAUDE_CODE_MESSAGING_SOCKET`, which Claude Code sets for its tools; another process's is the `messagingSocketPath` in its `sessions/<pid>.json`, trusted only while the file's `procStart` is that pid's (`process_record`). Claude Code binds under `XDG_RUNTIME_DIR`, a temp folder without it, or `/tmp/cc-socks-<uid>` past 103 bytes, so the path mesh used to rebuild from `XDG_RUNTIME_DIR` was wrong wherever that was unset (ACC §5). `MESH_CC_SOCKS`, a folder of `<pid>.sock`, stands in for the records in tests.
  - `mesh init` records the root's socket with the pid of its Claude process and that process's start (`CLAUDE_PID`, else the first process up the tree with a socket). A later process could reuse the pid and get a live socket at the same path, so `native_route` takes the root's socket only while that process still runs (`root_reachable`: ACC #276 found half its recorded Claude pids taken by other programs). The start time, not the session, since a `/clear` keeps the process and its socket.
  - A background worker's socket comes from the pid in `claude agents --json`.
  - A socket that's gone (the root restarted) falls back to the doorbell.
  - The socket belongs to the process, not the conversation, so a root reopened with `--resume` has a new one. Every mesh command the root runs re-records its current socket (`refresh_root_address`), so a reopened root heals on its next `mesh inbox` or `watch` with no extra step. Only the root's own process does: a command run `--as` the root from another session (the user acting for it from another terminal, a Claude elsewhere, a nested `claude -p` in its pane) would otherwise point the workers at that session's socket until the root's next command put it back. So it refreshes from the root's pane only as the process leading it (`pane_runs_this_claude`; when herdr can't say, the pane is trusted, as the pane map does), which also keeps the root's recorded `session` (`mesh init` records it) current after a `/clear`. Outside that pane only the root's own conversation counts, and only once its pane runs no Claude (`pane_probe`: gone, or back to its shell): a root reopened in another pane (`claude --resume`, then `--as`, since the pane map is keyed by the old pane) runs under its recorded session and heals, while a short-lived `claude -c` the user starts beside a live root carries the same session and would point the workers at a socket that soon dies. When herdr can't say whether the root leads its pane, the pane is trusted for the session as for the address, so the check isn't repeated on every command. A root inside tmux/zellij in its pane is neither (it doesn't lead the pane, and a nested `claude -c -p` there could carry its session), so it isn't healed: README already asks for `exec claude` there.
- **Claude Code's inbound policy** (read from the 2.1.310 bundle, the `[cross-session-inbound]` code; ACC found it first, and fixed a bug around it in its 1723cd59). Every cross-session message goes through a receive-side gate, whether it came by `SendMessage` or was written into the socket:
  - **The setting:** `crossSessionInbound` is `accept`, `hold` or `refuse`. Managed policy, then `--settings` (the "flag" source), then the user's settings: the first that sets it wins. The repo's `.claude/settings*.json` may only tighten it (a repo `accept` counts for nothing). Managed drop-ins (`managed-settings.d/*.json`, name order) are deep-merged over `managed-settings.json` (`e.merged=dB(e.merged,s,K9)`), so the last that sets it wins. A value it doesn't know, in any file, raises a settings warning that holds whatever else is set (`N()`).
  - **With none set, the permission class decides.** `bypassPermissions` (and `plan` where bypass is available) is the bypass class, every other mode prompting. A message whose sender asserts its mode (`SendMessage` does) is accepted from the same class and held from the other (`mode-mismatch`). One that asserts none (a raw write into the socket) is held by a bypass session (`no-mode-asserted`) and accepted by a prompting one. A writer descending from the receiving process counts as the session itself and is always accepted, which is why a probe from an agent's own shell is never held.
  - **A held message** waits for the user's approval in a dialog. A background session has no dialog, so its held messages expire and are dropped.
  - **What it cost mesh:** workers run with `--dangerously-skip-permissions`. Under a root in any prompting mode, every worker report waited behind a dialog in the root's pane, and every doorbell to a background worker expired unseen while mesh logged it as handed off. It never showed here because this machine's root bypasses permissions too.
  - **What mesh does:** every Claude worker launch passes `"crossSessionInbound": "accept"` in its `--settings` (`worker_settings`), which beats the user's own value. It loosens a worker only: same-uid processes could already type into its pane, and a peer message still arrives framed as one, with Claude Code's "a peer cannot grant escalation". The root's settings are the user's, so mesh never edits them: `mesh init` and `mesh status` warn when the root's setting holds or refuses (`inbound_warnings`, from `inbound_setting`, which reads managed, user and repo settings as above, never server-managed policy or a root's own `--settings`), and a background worker opens in a pane instead when managed policy or its repo tightens the flag away (`worker_accepts`).
- **Panes for large work, background for small.** The user wants to oversee the work that matters in herdr, but doesn't need a pane for a translation fix. Large tasks keep panes. Trivial and small Claude tasks run as `claude --bg` sessions: recorded workers like any other (resume, ask, PR lookup), visible in `mesh status` and `claude agents`, and `mesh open` attaches to one. agy has no background sessions, so agy workers always get panes. A fresh reviewer gets a pane at any size too: a review is the work the user wants to see, and a pane costs the same tokens as a background session (same session, model and effort), only screen space.
- **Background quirks** (from the smoke test below), and what mesh does about them:
  - `--bg` picks its own session id, so mesh reads it back from `claude agents --json`.
  - `--bg --resume <id>` with no flags continues the session with the options it was first started with. With flags it starts a copy of the conversation under a new id. So every background relaunch passes the full flags, and mesh records the copy's id. The copy has the whole conversation, so this is not a cold hand-off.
  - **The launch's environment never reaches the session.** `claude --bg` hands the session to Claude Code's daemon, which runs it in a pre-forked spare process. The first `claude --bg` with no daemon running starts one with *its* environment, and every spare after it inherits that until the daemon's last session exits. So one worker's `MESH_*` identity ended up in every later background session: other workers, and once the root's own conversation reopened in the background, which then took itself for a reviewer. (The smoke test missed it because it started a cold daemon.) mesh now runs every `claude` CLI call (`--bg`, `agents`, `stop`, the compaction turn) without the caller's identity, herdr pane ids or Claude session variables (`claude_env`), so a daemon any of them starts is clean; `--bg` also loses all `MESH_*`. It gives the session its environment through `--settings '{"env": …}'`, which reaches the spare and overrides its values: the identity, and every `MESH_*` config key (`MESH_CONFIG`), empty when the launch has none, since settings can only set a variable and an empty one counts as unset. The herdr pane ids are set empty for the same reason. Everything else (PATH, a virtualenv, direnv or repo-specific variables, tokens) still comes from whoever started the daemon.
  - **Safety net:** `identity()` ignores a `MESH_RUN` / `MESH_SELF` from the environment when it names a Claude worker whose recorded session isn't this one (`CLAUDE_CODE_SESSION_ID`, which Claude Code sets for its tools), and falls back to the pane map. A `MESH_RUN` that names no live run is ignored too: a daemon outlives the run whose worker started it. So is one naming an agy or Copilot agent, which a Claude session can never be (an agy pane has no `CLAUDE_CODE_SESSION_ID`, and a Copilot asker runs without any `MESH_*` identity). A pane worker's session can change legitimately (`/clear`, plan mode's "clear context"), so in its own pane it is trusted when this session's Claude process is the one running there, and the entry is re-recorded; when herdr can't say, the pane is trusted. An entry still `starting` is skipped for five minutes, since its new session isn't recorded until the launch returns. A name passed with `--as` is never second-guessed, and every pane refusal names `--run`/`--as` as the way past it. When the pane map then resolves, the command acts as that pane's agent, run and name together, says so on stderr and logs `identity_ignored`.
  - **A worker that lost its environment:** a herdr restore (after a power outage, say) brings every pane back under the same id and relaunches its Claude as `claude --resume <session>`, with herdr's variables and none of mesh's, so a pane worker had no identity left. Measured on herdr 0.8.2: a pane id is the workspace id plus a public pane number, both kept in `~/.config/herdr/session.json` with the pane's `agent_name`, `managed_agent_kind` and `agent_session`, and the root's pane kept its id across the 2026-10-26 outage (its pane map still resolved); `claude --resume` keeps the session id. The pane map names only roots, so `pane_worker` looks through the live runs (not `archive/`; only the `--run` one when given) for a Claude worker, not retired, whose recorded pane and session are this session's, and takes it only when this process leads the pane's foreground group. All three are needed: a nested `claude -c -p` keeps the pane and the session but leads nothing; a pane id herdr reused after losing its session (counters start over) could match a stale entry of a run never stopped, which the session rules out; and `mesh resume` into another run records the same session in both, which the pane tells apart (two matches are refused, by name). Unlike the pane map, a pane herdr can't vouch for is refused: it's a fallback, and `--run`/`--as` still works. A name passed with `--as` is kept: the pane worker is taken only when it's that one. `stop` asks it too, across every live run whatever `--run` says, so a restored worker isn't taken for the user in a shell, nor let through by naming another run; matching several workers refuses the stop too, as the first of them. agy workers are left out: herdr's agy integration reports no session, so a restore has nothing to resume them with (the root `mesh resume`s them, which sets the variables again), and an agy process carries no session id of its own to confirm it by.
  - **What a restore drops:** the relaunch is plain `claude --resume <session>` (assumed from herdr's binary; its session.json keeps no command line), so the worker also loses everything mesh starts it with: the Stop and SessionStart hooks, the deny list of a planner or a read-only asker (`claude_deny`), its model and effort. The deny list is the risk: a planner could edit and push. The relaunched Claude sits idle (assumed: herdr types no prompt into it), so its next turn comes from mesh's next doorbell, or from the user typing into it. `deliver` checks there, before the doorbell: `herdr pane process-info` gives the pane's foreground command lines (verified), and the Claude leading the pane (when herdr names no leader, the pane's one Claude; several: can't tell) whose `--settings` don't carry this worker's Stop hook (`hook stop --run <run> --as <name>`, run by any `mesh`) wasn't started by mesh (`mesh_launched`, `relaunched_outside_mesh`; spawn, resume and every swap pass it). The restore drops the settings and the deny list together, so the hook tells it alone: comparing the script's path or today's deny list (`claude_deny`) would take every running worker for a relaunched one after an upgrade that adds a rule, or when another checkout's `bin/mesh` delivers. A new rule reaches a running planner at its next reopen. Only workers are checked: a root's Claude is the user's own. It is reopened through `swap_model` on its model and effort, keeping its deny list (`why: relaunched`), which waits for its turn to end and closes the old pane before starting the new process; if that fails or times out, or herdr has lost the agent (its turn can't be waited for), the message is stored but not rung (exit 2), since ringing would hand it a turn without its list, and the next message tries again. One delivery reopens it (`relaunching`, a claim honoured while its process lives); another meanwhile, or while the new pane is still starting or held at a startup screen, only stores its message for that doorbell (and if the reopen fails, the next message retries), so two `claude --resume` never share the conversation and nothing is typed into a pane that isn't ready. `mesh ring` refuses such a worker and points at `mesh send`. Checking in the watch would cost a `process-info` per worker per poll and still leave a window before the root acts; `mesh status` stays a reading (it calls `process-info` only for a pane herdr lost); and the worker's own first command comes too late, inside a turn already running without its list. That costs one herdr call per doorbell to a Claude pane worker. A `/clear` after the reopen is rebound as usual (environment and hooks are back); one the user types into the restored pane before mesh's first message to it isn't followed: `pane_worker` misses the unrecorded session, and the reopen resumes the recorded, pre-clear conversation, the one mesh knows.
  - **Which process runs in a pane:** anything started in a pane carries its ids: a daemon the user started in the root's pane with `claude --bg`, or a Claude started by an agent's tool (a `claude -p` in a worker's pane, which also inherits the `MESH_*` identity). The root records no session, so the pane map is checked too, and a Claude session never stands for an agy root. herdr's `agent_session` can't be the judge: its Claude hook (SessionStart only) reports whatever session starts with the pane's ids, and while herdr ignores a `startup` report once the pane has a session, it takes `resume`, `clear` and `compact` from anyone (measured on herdr 0.8.2), so a nested `claude -c -p` or a resumed background session overwrites it. Claude Code's session variables don't tell either (`CLAUDE_CODE_CHILD_SESSION` is set for every tool, `CLAUDE_CODE_SESSION_KIND` for neither). The kernel does: `herdr pane process-info` gives the pane's foreground process group, which the pane's agent leads, and `CLAUDE_PID` (which Claude Code gives its tools) must be that leader (`pane_runs_this_claude`). Claude runs each tool in a session of its own and background sessions under its daemon, so neither leads a pane's group; a `/clear`ed or resumed agent does. Only the leader counts, since MCP servers share the group: accepting any member (or `CLAUDE_PID`'s own pgid) would also accept a Claude an MCP server started, which would then rebind the root's session. The cost is a root behind a launcher script that doesn't `exec` claude, or inside tmux/zellij in the pane (whose Claude is in no group of the pane at all); `time claude`, `env` and `direnv exec` exec into Claude and lead the group. The refusal says to `exec` it or pass `--as`, and README's identity notes say so too. A session refused by the pane map gets that error from `mesh ask` too, rather than a new run over the root's pane map, and `mesh init` refuses a Claude that isn't the pane's process. An earlier take walked the process tree for a second Claude socket; stale `<pid>.sock` files at reused pids fooled it, and so would a herdr server started under a Claude. `claude_address` likewise takes `CLAUDE_PID`'s socket rather than the nearest one up the tree.
  - `--bg` refuses a folder Claude Code was never trusted in. A worktree of a trusted repo counts as trusted; otherwise the worker opens in a pane, where the trust dialog is handled as before.
- **No plan gate for small tasks.** A plan review costs a round trip and a strong model's research, which is worth it for a feature and not for a typo. Trivial and small tasks are `Direct task (no plan)`. They still run on their own branch, verify, and open a PR. A tiny PR (a trivial or small task's or group's, up to 150 changed lines, touching nothing risky) gets the root's own review; any other, one or two reviewers by its size (§10). How many tasks made the diff doesn't change that: a group of small tasks with no plan counts as a small task ("Groups" below). Two agents reading a repo in to check a 30-line fix cost more than the root reading the diff, and in run m916b the root's own check of such PRs (#57's one-line test fix, the docs PRs) was enough. The worker must ask first if the task is bigger than described, and a wrong size costs one redo.
- **Nothing starts until the user says go (run m6a37, 2026-10-27).** Only a task list used to wait for a confirmation; any other request went from sizing straight to spawning. So for every request that starts work the root first proposes it (its own part, each worker's repo, size, model, view and routing) and waits. A wrong size, group or routing costs nothing to fix before a worker has read the repo in, and a run's spend is the user's call. One go covers the run's reviews, fix rounds and the root's small calls; new work is proposed again. A read-only ask, review or peer ask the user asked for needs none: the request is the work and changes nothing. A user who says to run autonomously gets the proposal for the record, kept as a standing instruction in `notes.md` (§15), and no wait. It stays a protocol rule, not a check in `spawn`: mesh can't tell a go from any other message.
- **Sizes are a table, not a judgement call in code.** `SIZE_DEFAULTS` maps (CLI, size) to model, effort and view. The root picks the size; the user's named model or effort still wins.
- **User-reviewed plans.** `--model opus --permission-mode plan` does natively what `mesh approve` does for Claude: Opus plans, and Claude Code leaves plan mode after approval and executes on Opus, in the same conversation. It used `opusplan` (Sonnet executes) until quality outranked tokens (§9). With no `mesh approve` there's no execution phase, so the task runs at high effort throughout: the exception to "execute at medium", accepted because the user chose to supervise this one. herdr shows the waiting dialog as `blocked`, so the watchdog excuses that one worker. It's opt-in, for when the user wants to approve a plan themselves. By default the root reviews plans and Claude stays on Opus (§9).
- **Task lists:** a list of tasks makes the root a supervisor.
  - It triages into a board, the proposal the user says go to once (above), writes no code itself, runs at most four workers at a time, and gives each PR one or two reviewers, picked by its size and agy's quota (§10), as every run does, but a tiny PR the root reviews itself.
  - **Groups:** the tasks go in a few themed groups, each one worker with one branch and **one PR**, and **one plan** when the group is `large` (sized by its combined work, below). A group is tasks that share a theme, or where what one teaches the worker helps another, and small unrelated tasks join one rather than get a worker. There's no size cap. A fresh worker per task rediscovered what the previous one had learnt, and the stacked PRs that kept them apart needed a rebase whenever an earlier one changed. The peers agree: firstmate's squash merges strand stacked children (#4504), Gas Town replaced stacks with integration branches, and Rove's owner batches items into one PR, one section per item.
    - **Why groups got big (run m916b, 2026-10-26):** a TODO list of about 24 lines, mostly bug fixes plus five "Maybe" ideas, became 17 PRs from 49 agents (17 workers, 32 reviewers), 41 resumes and about ten rebases, for a repo whose tasks nearly all land in the same few files. The old rules caused it: group only tasks that build on each other or change the same code, never on one shared file alone, at most four per group, independent tasks on their own workers. Each worker is as strong a model as the root, and one already reading the repo does the next task far more cheaply than a fresh one reading it in, so the rules now lean the other way. File-overlap analysis at triage and diff-size caps lost too: the root can't know a diff before the work, and a conflict costs one rebase at merge, not a reason to split the work.
    - **The whole group is one task:** the worker gets every task in one task file, researches them all, and (in a `large` group) sends one plan, reviewed once; then it does them in order, a commit each, and opens one PR. Feeding a group one task at a time (check each `done`, `mesh retire`, `mesh resume` with a focus) put a check, a reopen and often a compaction on the root for every task. That per-task gate was the root's busiest work in m916b, and it bought little: a worker that drifts into the next task is doing approved work. A "Maybe" rides in its group, its do-or-decline argued in the plan, instead of a large worker of its own (four of m916b's five "Maybe" workers each planned on Opus only to decline). A group is two or more tasks, and a task in no group keeps its own size (run m6634 spawned a docs-only trim, checkable by `wc -c`, at `large` as a one-task group).
    - **A group is sized by its combined work (run m6a37, 2026-10-27):** a group used to plan always, whatever its tasks' sizes, so two two-line fixes grouped together got an Opus high-effort plan phase in a pane. The plan pays for how tasks fit together (one builds on another, a shared design decision) and for work you'd want to see before it's built; independent small tasks grouped only so one worker reuses its reading of the repo have neither. So a group gets the size its whole assignment needs, from the same table: `small` (or `trivial`) for independent small tasks, one `Direct task (no plan)` with a commit each and one PR; `large` when a task is large, the tasks interact, or the combined change needs a design review. The count alone never makes it large. A misread task in a direct group costs one fix round on the same PR, and the PR is still reviewed.
    - **Stuck, not failed:** in every run on this machine up to m916b, workers sent 336 `done`, 5 `question` and one `failed` (a usage limit). So a worker that hits a wall asks the root, which gives a hint or a decision, or drops the task when it's too costly or no longer needed; `failed` is only for what nobody in the run can fix. The old path (a `failed`, an automatic retry at higher effort, then a fresh agent on the other CLI) handed work away from the agent with its context. A dropped task is taken out by its worker however it sees fit, with no git recipe in the protocol, and more effort for a fix is the root's judgment, not a rule: most of m916b's fix rounds ran at high for a few lines each.
    - **New work goes to the worker with the context:** a worker's own proposal, a follow-up, or a small new task goes to an existing worker that knows that code (live, or resumed into its open PR), never to a fresh agent.
    - **What lost:** one PR per task (the reviews per task cost two or three agents each, and the PRs conflict with each other in the docs every one of them updates); a group fed one task at a time (above); and parallel workers kept to disjoint files, which serialises a one-module repo for conflicts a rebase handles.
  - It checks conflicts with `git merge-tree --write-tree` (`mesh conflicts`), which needs no checkout, and skips stacked pairs.
  - merge-tree only sees commits, so `mesh conflicts` also notes overlap: two workers whose changed files intersect (the branch's own commits, counted from its recorded base so a stacked worker doesn't claim its parent's files, plus the worktree's staged, unstaged and untracked files from `git status --porcelain=v2`). That tells the root two workers edit one file before either commits. It's a note, listed apart, and asks for nothing: overlapping files often merge cleanly, and a conflict is rebased when the PRs merge (§11, "Groups"). Pairs that already conflict list only the shared paths merge-tree didn't report. mcp_agent_mail's file reservations solve this for agents sharing one checkout; ours each have a worktree, so deriving the file sets from git needs no reservation step and can't go stale.
  - The overlap check stays a command the root runs after each `done`, not an alert from `mesh watch --any`: on agent-mesh's own run of 16 open PRs, 90 of the 120 pairs overlapped (one script, one test file), none of which needed acting on, and one check took seconds, longer than a poll.
  - mesh's git reads run with `GIT_OPTIONAL_LOCKS=0` (`git_env`, which `git()` uses). They read other agents' worktrees (`changed_files`, `work_evidence`), and `git status` otherwise refreshes the index and writes it under `index.lock`, failing the worker's own `git add` or `commit` meanwhile.
  - `stacked` asks every pair of branches both ways whether one contains the other, so one call asks the same questions many times: an `Ancestry` per repo resolves each ref once and asks `git merge-base --is-ancestor` once per pair of commits (on a run with 49 worktrees, 4,175 asked, 870 run; 7.6 s down to 2.4 s). It reads each branch at the tip it resolved first, so a worker committing meanwhile is judged on one commit throughout.
  - The board lives in the run directory, so a root whose context was compacted can rebuild its picture from it instead of from memory. It holds only the plan (tasks, groups, order, workers); each task's state comes from `mesh status` (§13).
- **What we don't use:**
  - Claude Code's `-w` worktrees: mesh's worktrees record their base, name their branch after the run, and are recreated at the same path on resume, which Claude needs to find the session (§8).
  - `/batch` and agent teams: a worker never spawns agents (§7), teams can't include agy, and neither can be resumed across runs.
  - `notify_when_idle` for stalls: it works, but each subscription is one-shot and its notice waits until the root's turn ends, so a busy root would have to re-subscribe to every worker after every turn. `mesh watch --any --alerts` covers every worker with one background command, reads `claude agents` for background workers, and also catches agy quota hits.

## 12. Compaction on resume

Resuming a worker is the point of §8, but an old conversation is expensive to resume. Its prompt cache expired long ago, so the first turn re-reads everything at full price, and every later turn re-reads it from cache. A 150k-token conversation resumed for a 30-turn fix reads about 4.5M cached tokens before it does anything new.

- **Compact first, headless:** before reopening, mesh runs `/compact <focus>` on the stopped conversation in print mode, in the worker's own directory, without its `MESH_*` identity so the compaction turn can't message anyone: `claude -p --resume <id>` / `agy --conversation <id> -p`. Both CLIs expand slash commands in print mode. The worker then reopens on the compacted conversation, in a pane or in the background as before.
- **Only when it pays:**
  - **Claude:** mesh reads the context size from the session file (the last reply's `usage` since the last compact boundary), and compacts above `MESH_COMPACT_AT` (300k). For a read-only question the threshold doubles, since a question or two doesn't repay a compaction. It was 100k until every model had a native 1M window and cache reads fell to $0.20/M on Opus 5.5: compaction throws away the detail of the worker's research, which is what resuming is for, so it now waits until the re-reads are large.
  - **agy:** it documents no context size, so mesh reads it from agy's own conversation file (`~/.gemini/antigravity-cli/conversations/<id>.db`, SQLite with protobuf blobs). Field 9 of a step's `metadata` is a model call's usage: 2 the input read fresh, 5 the input read from cache, 3 the output. The context is 2 + 5 of the last call, and a step of type 23 (it holds a compaction's `<summary>`) is the compact boundary, after which it starts again at 0. This was checked against `agy -p --output-format json`, whose `usage` is the sum over every call of the conversation (so it can't give the size, and asking would add a turn), and against 16 compactions in the user's conversations, each of which dropped the context from 226–266k to 11–30k. That range is agy compacting itself, so the threshold is lower than Claude's: 100k (`MESH_AGY_COMPACT_AT`), twice that for a question. Reading an undocumented format is a bet, so a conversation whose size can't be read falls back to the old rule: compacted when it comes back from an earlier run, never for a read-only question.
  - **Within a run:** approve and switch never compact; the context is warm and the task is the same.
- **Focused on the next task:** the default focus keeps the repo facts, the decisions and their reasons, the branch and the PR, and names the new task. The root can replace it with `--focus` when it knows what matters.
- **Never a failure:** a compaction that fails is a note, and the worker resumes as it was.

## 13. State is derived, not kept

A root that kept each worker's status by hand (the board's old status column, "update it on every event") paid context for it, drifted when it missed an event, and after a compaction trusted what it had written over what happened. The projects surveyed in run `mac82` say the same ("a coordinator that remembers is a coordinator that is wrong", Rove; "discover, don't track", Gas Town). So `mesh status` works it out on every call, from what the run already records:

- **The log** gives each worker's newest report since its last task or answer (`last_report`): a `plan` or `question` waits on the root, with its age, and `, unread` while it's still in the root's mailbox; no report means the worker has the ball (`, waiting until 14:30` while it has declared a wait), `task unread` while the task sits in its mailbox (`, doorbell failed` when the log says so and no doorbell has rung for it since, which the root fixes with `mesh ring`). A worker `held` at a startup screen (Other startup screens, below) waits on the root, since only the user clears it: `held at a startup screen (Settings Warning) since 03:01 (4m), task stored`, from the hold its start recorded, while herdr reads it `blocked` or `unknown` (`deliver`'s test for still at the screen). A hold outlives its screen until a ring or the worker's own `mesh inbox` drops it, so it counts only while its message is still unread and no report has come since it: past that the usual row shows, whatever herdr reads. A worker that reads idle or done with its held message unread got past the screen, but its first doorbell never rang (no watch was running), so its usual row ends `, its first doorbell never rang: mesh ring <name>` and waits on the root; working, or rung, the usual row is back.
- **Git and `gh`** describe a `done`: the PRs it names, with their state and checks (`gh pr view`, side by side, cached two minutes in `pr-state.json`; a failed fetch keeps the last value, else `unknown`, and is retried after a minute, so an offline `gh` doesn't slow every call; a `done` with no link takes its newest earlier `done`'s), or, with no PR, the commits past its base, whether they're pushed and whether the worktree is dirty (`work_evidence`, which the watch's exit 3/5 evidence uses too). "no commits, no PR" is information, not an error: the bug may have turned out not to be one. A `done` to a read-only task is `answered`.
- **Reviews:** a `done` whose PR a live reviewer of the run is still reviewing (the PR of its current task: `reviews` keeps every PR it ever reviewed; a follow-up question asked without `--review` counts as the review it follows, unless a change task came in between, so nothing new is recorded for it) shows `in review (…)` and waits on the reviewers, not on the root.
- **Order:** rows that need the root first, longest-waiting first, then those waiting on a worker, then the finished ones. A worker that owes a report but is gone, blocked or failed a swap needs the root.

Nothing of it is stored, so nothing can go stale; `pr-state.json` is only a cache. `mesh log [--follow]` prints the same log as a timeline, for watching a run in a side pane or debugging one after.

`log.jsonl` is append-only and written without the run lock, so a kill or a full disk can leave a torn last line. Readers skip a line that doesn't parse and warn once, and `log_event` ends a torn line before appending, so the next event isn't glued to the fragment and lost with it.

## 14. Standing peer askers

Run `mac82` cloned eight similar projects and gave each a Claude asker. They turned out to be the most reused agents of all: asked again a run later, each answered in about two minutes from research it already had. Asking them was still hand-work. Their names lived in `TODO.md` prose. The fan-out was a shell loop of eight `mesh ask &`, whose outputs put ~6k tokens of JSON into the root, then eight `mesh inbox` and eight `mesh retire`. Every ask recreated a worktree at the 2026-10-25 commit, the clones were never refreshed, and ccswarm's own malformed `.claude/settings.json` stopped its pane at a Settings Warning every time, for the user to press Continue.

- **A registry, not a second store** (Alternatives, "A second store"): `$MESH_HOME/peers.json` holds only what no run records: the clone, the asker's worktree, its group and upstream, and `seen`, the upstream commit the asker was last told about. Its conversation, messages and status stay in runs. `run` / `as` say where its newest entry is, so a resume that got a `-2` name isn't lost; `find_worker` does the lookup as for any past worker. The registry is machine-wide: a peer serves whoever asks, and groups pick a subset. Per-repo ownership was tried and dropped, since peer research is useful from any repo.
- **Asking reuses `ask`:** `mesh ask <peer>` is a past-worker ask (§10) plus the peer steps, and `ask --peers` runs the same `reach_worker` / `spawn_peer` for each peer in a thread pool. Shared state is all behind flocks, which exclude threads too, since each lock call opens its own file.
- **A `mesh stop` mid-fan-out** doesn't lose the answers already in: unlike a plain watch, which ends at the stop's first sign, `watch_each` holds its ticks while the stop closes the panes (they'd read as alerts), still counting answers from the log, and waits for how it ends. Archived, the peers left with no answer in the archive are "stopped before it answered" (exit 1, as `ask` with no answer), and the answers are read from the archive and the report written there, never into a recreated live folder; failed, watching goes on.
- **A detached worktree that outlives runs:** a peer's resume doesn't add its worktree to the run's `worktrees`, so `mesh stop` leaves it, and it has no branch to keep or delete. Its path never changes, because Claude keys sessions by cwd: the adopted askers keep `worktrees/mac82/<name>`. Moving it would mean moving Claude's session files. Adopting from a run that isn't archived yet takes the path off that run's `worktrees`, so its `mesh stop` leaves it too. An asker that ran in the clone's own checkout keeps that cwd and is marked `in_clone`: mesh never checks out there or removes it, and its upstream note says to read the newer code with `git show`.
- **The upstream note:** each ask fetches the clone (a failure is a note, never a stop), moves a clean worktree to the new head with `git checkout --detach`, and appends to the question what changed since `seen`: the count, `git log --oneline` capped at 30 and `--shortstat`, or "unchanged". A dirty worktree stays put, and the note says how to read the new code. The clone's own checkout is never touched. An asker that isn't told can't know its answer is stale, and one that is told only re-reads what moved.
- **Settings Warning, for peers only:** the warning lists the rules it skipped, and its default "Continue" keeps the rest of the file in effect. In the user's own repo the fix is theirs, so a worker still holds there (exit 4). A peer's repo is someone else's project that nobody here fixes, so `clear_startup(..., peer=True)` presses Enter while the cursor is on "Continue". `--setting-sources user` was rejected: it drops the project's settings wholesale, and with them, as in the SDK, probably the clone's `CLAUDE.md`, the asker's best guide to the code.
- **Compaction at the plain threshold:** §12 doubles the threshold for a question, since one or two don't repay a compaction. A peer is asked question after question, each time cold, so it compacts at `MESH_COMPACT_AT` (or the agy one), with `PEER_FOCUS`. That focus keeps what it learned about the project, with its file:line references, rather than the next task.
- **One bounded result:** under a Claude root, N Claude peers would each `SendMessage` the root, and invite N inbox reads. So the fan-out marks each asker's entry `collect: {to, pid, start}`, and `deliver` stores a `done` / `failed` from it to the root without a doorbell (a `collected` event). A `question` still rings, since the root has to answer it. The mark counts only while that `mesh ask` process lives (`pid_alive` with its start time). The fan-out also clears it in a `finally`, with SIGTERM and SIGHUP turned into an exit, and a single `mesh ask` clears a stale one. So a killed fan-out never leaves an asker whose later reports go unrung. A peer still working on an earlier question is skipped with "busy" rather than asked: its next `done` answers that question, and filing it under the new one would be a wrong answer in the one place the root trusts. `watch_each` gives every peer its own outcome, the watch's exit codes plus one for a plan or question sent instead. A peer held at a startup screen mesh doesn't answer gets its own exit 4 once held `MESH_HELD_WAIT` seconds (300): a watch stays quiet while a worker is held, since its start already said so, which would keep every other answer waiting until `--timeout` (30 min) for a screen nobody may be looking at. Only a peer still at its screen counts (it reads `blocked`, and no first doorbell is being retried after the user cleared it), never a retired one (5). A peer given up on, by any outcome but an answer, is let go at once: its watch lock closes and its `collect` mark goes, so the answer its alert promises rings the root instead of being collected into a file already written, and `warn_unwatched` sees it. The answers, found by `take_reply` through the log, go into one file. stdout is one line per peer and the path, which `peers.json` keeps (`record_answers`) as `answers`, the newest of any round, and on each peer that answered as its own `answers`, its last round: `mesh peers` shows both. Each is kept as `{run, file}` in the run's folder, not an absolute path, since `mesh stop` moves the run under `archive/` and the path would dangle; `answers_file` resolves it live or archived (and an older peers.json's absolute path likewise).
- **Saying what each is:** whom to ask is only obvious to whoever cloned the projects. So each peer has an `about` and each group one in `groups` (at most `ABOUT_MAX`, 400 characters: a line, not a report), shown by `mesh peers` and repeated in the answers file. A new peer's default is its GitHub description, marked `about_from: github` since it's the project's own pitch. The adopted eight were written from their mac82 reports, which carry the facts that decide whom to ask (Gas Town dropped for Gas City, `mcp_agent_mail` superseded by its Rust port), rather than by asking each asker, which would cost eight cold resumes of up to 318k tokens.
- **Adoption needs a closed asker:** `peers add` refuses a same-named worker that is still open in a live run (retire it first), since the next ask would move its worktree under it. Adopting a retired one from a live run takes its worktree off that run's list and deletes its untouched run branch, as that run's `mesh stop` would have. A single `mesh ask` to a peer a live fan-out is collecting is refused, and one the log says still owes a report is skipped by a fan-out, even if its pane reads idle, unless it is gone (asking reopens its conversation). An asked worker whose last task the log shows unanswered (`owes_report`), peer or not, resumed or idle in its pane, gets `UNANSWERED_NOTE` on the new one: answer this task first, in a `done` of its own, then the earlier one if still owed, since the ask's watch takes its next `done` as this answer. One still working gets no note, so its work isn't cut short. A background peer counts as gone only when `claude agents` answered at all, since a failed call reads as gone too.
- **Coping with a broken peer:** a clone deleted or moved, an entry edited by hand, or an empty `--peers` spec is a clean error for that peer (a `broken` row in `mesh peers`, a fan-out outcome, a `MeshError` for a single ask), never a traceback for every peer. `peer_problem` names what an entry lacks, or a `repo` or `cwd` that isn't a path: a fan-out keeps such an entry in its selection and reports it, a single ask or edit refuses it, and `peers remove` drops it, saying what may be left. So does a peer whose clone is gone, whose checkout git can no longer remove. `peers remove` refuses a peer still running, its clone gone or not, since the check reads only run.json. A single ask refuses a gone clone (`refuse_unaskable_peer`), or a past worker with neither its checkout nor its clone, before it can start a run. A removed peer's conversation can still be asked as a past worker. Every ask records what its checkout is at on the worker's entry (`base`), and `peers remove` writes the peer's `seen` there too (with `peer`, and no branch, on an adopted entry never asked), so `ensure_worktree` recreates the detached worktree at the code it last read. It is still a peer by its entry's `peer` (`worker_peer`, which takes the registry entry only for the same clone, since a later `peers add --name` can reuse the name), so it still refuses a change task, compacts with `PEER_FOCUS`, takes a Settings Warning's Continue, and `mesh open` recreates it detached too, never on the branch an adopted one's old run still lists. A worktree recreated for it has no registry entry to keep it, so the asking run lists it with no branch, and that run's `mesh stop` removes it once clean (it never removes a registered peer's worktree or a clone's own checkout). Adopting from a live run does the git steps of `release_worktree` before it takes the worktree off that run, so a failed one leaves it with its run.
- **Only answers:** `resume_worker` refuses a peer a change task (it knows a peer by its entry's `peer` too, so a `-2` copy is one), `lift_read_only` refuses `mesh send <peer> --type task`, and a Claude peer is always `read_only` (the deny list). A change to the project goes to an ordinary worker there, in its own worktree and branch.
## 15. The root's own context

§12 compacts workers on the way back, but the root never leaves: after a 12-PR run it sat at ~450k tokens, and once its cache expired every report woke it at full price. Prose ("keep your own context lean") didn't stop that, so the root now measures itself and resets itself, with nobody typing.

- **When a reset pays.** A `/clear` never re-reads the old context: it costs the fresh session's prefix (CLAUDE.md, `mesh brief` and the first turns: 28–44k written after a root reset, measured in run m6f06) whenever it happens. What it saves is the next turns of the big session: once cold, all of it but the static prefix rewritten at the cache-write price; while warm, all of it read at a twentieth (Opus 5.5: $4/M input, $0.20/M cache reads, 1 h cache writes at 2x; the TTL is below). The static prefix (system prompt and tools, S ≈ 25k: a session's first reply reads 24.7k–26.8k from cache, p10–p90 over 296 sessions on this machine) is shared by every session on the machine, so it stays cached while any of them used it within its TTL. A cold turn of N tokens thus costs (N − S) × $8/M + S × $0.20/M: ~$3.40 at 450k, ~$2.20 at 300k; a warm one ~$0.09 at 450k; the reset ~$0.25–0.35. The threshold still compares N, not N − S: S is ~8% of 300k, so counting it would move the threshold by about 25k, within the knob's precision, and whether S is still cached at the next cold turn depends on the machine's other sessions, which nothing can know ahead. Hence the hint's rule (`root_line`): over `MESH_ROOT_RESET_AT` (300k), reset when cold, or when about to wait (after `spawn`, `approve`, `switch`, `resume` or `ask`, with nothing waiting on the root: large workers often take longer than the cache lives); while warm, only past twice the threshold, at a quiet point. A warm big root also loses quality ("context rot", worse with near-duplicate distractors such as many similar reports), which argues for resetting at phase boundaries even when cheap. The cache state is the session file's age against the TTL the session used: Claude Code picks it once per session (1 h on a subscription within plan usage, 5 min on usage credits, an API key or a cloud provider), and each reply's `usage.cache_creation` records what it wrote at which (`ephemeral_1h_input_tokens`, `ephemeral_5m_input_tokens`), so `transcript_usage` takes the newest main-chain reply that wrote anything (a reply read wholly from cache says nothing: 57 of 29,230 replies on this machine; a subagent's always writes 5 min), up to `TTL_LOOKBACK` replies back, else 1 h (`CACHE_TTL`, also agy's). Assuming 1 h called a root on usage credits warm for 55 minutes after its cache had gone. An explicit `MESH_CACHE_TTL` still wins, so a live check can fake a short one.
- **Measuring.** Claude: the root's session is the one its own process is in. Claude Code keeps a file per running process, `sessions/<pid>.json` under its config folder, whose `sessionId` follows a `/clear` or `/resume`; the process is the one leading the pane's foreground group (`herdr pane process-info`, as for `pane_runs_this_claude`), and the file counts only while its `procStart` is that process's start (`leader_session`; on Linux both are `/proc` start ticks, while off Linux `proc_start` reads `ps`, which may never match, and then the older rule below applies). Nothing else in the pane changes it, and every caller (a root command, the watch, the detached reset) gets the same answer without comparing files. Only when that can't be told (herdr gives no leader, no such file) does the older rule apply: herdr's reported `agent_session` for the root's pane (it follows a `/clear`: seen live), and a command the root itself runs may use its own `CLAUDE_CODE_SESSION_ID` (which follows a `/clear` too). Either can be stale: a root watch that outlived a reset runs under the old session (and would otherwise tell the fresh root to reset again), while herdr takes a session report from anything in the pane (a nested `claude -c -p`). The session the root's last `reset` event confirmed joins them (the log is read only then), so the watch and the detached reset, which have no session of their own, aren't left with herdr's word alone. The root's is then the one whose session file was written last, since a root command runs inside a live turn and an idle root's last turn came after a nested run it started; a nested Claude writing at that very moment can still win this pick, which is why the process's own file comes first. The reset's own before and after (`leader_session`) read the process file too, so a nested Claude can't fake the `/clear`. A worker's session is never used. Its file is found under the root's cwd, else across `~/.claude/projects`. `transcript_tokens` reads it backwards from the end, since a root's file reaches tens of MB and every root command measures it (`context_tokens` uses it too). agy: nothing ties a conversation to a pane, so an agy root is measured only after its first reset, which records the new conversation.
- **`mesh reset` is detached.** The root can't clear itself mid-turn, so the command starts a process (holding the run's `reset.lock`, handed down so two resets can't start) and returns; the root ends its turn. The process waits until herdr reads the root `idle`/`done` on two reads in a row and its input box reads exactly empty (dim ghost text, such as Claude's prompt suggestion, is empty; a draft or an unreadable box holds), re-checks under the pane's `ring_lock` that no plan or question has arrived (a worker stores before it rings, so a report on its way is seen; else `reset_cancelled`), types `/clear`, confirms it, and rings the bootstrap prompt through `ring()`. Every outcome is a `reset*` event; a failed or cancelled one is reported once, by the next root command's line (which logs `reset_noted`).
  - **Confirming the clear.** The root's process file moving to a new session confirms it, which a nested Claude can't fake. How soon that file follows a typed `/clear` wasn't measured, so herdr's report moving counts too, as it did before the file was read: at once when there is no file, else once the file has had `CLEAR_FILE_GRACE` (5 s) more to follow. The file is compared only with the file's own session before the clear, and a herdr report only counts when it is neither herdr's earlier report nor the file's old session, so mixing the two sources can't pass the old session off as new. herdr's first new report is kept, since its next reads may flicker, and the wait is bounded (`CLEAR_CONFIRM` plus the grace). The grace keeps the file's word first in the usual case, and a slow file never fails a reset that worked; the nested Claude it would let through would have to report a session in those seconds, while the root sits idle.
  - **A root herdr has lost** (it reads `unknown` for good) used to wait out `MESH_RESET_WAIT` and fail. The process file of the Claude still leading its pane also carries Claude's own `status`: `busy` through a turn, a foreground tool call included (checked live on a background session: `busy` during an 8 s foreground `sleep`), `waiting` with a `waitingFor` (a dialog, a permission prompt, a question to the user, which a typed `/clear` would answer), `idle`, and `shell` (seen live on a root that herdr read idle while its watch ran in the background). So a lost root's turn is over when its process reads `idle` or `shell` (`TURN_OVER`) and has for `STATUS_STILL` (5 s, from `statusUpdatedAt`), with the box read empty twice, as for herdr's idle. An earlier take read the session file's last entries instead (`end_turn`, `turn_duration`), but Claude writes many entry types after a finished turn (attachments, local-command output, artifact and worktree state), so a list of them always lagged and a finished turn read as in progress. When the process can't tell (no Claude leads the pane, no process file, an agy root) or the reset is a `--compact`, whose confirmation waits on herdr's status, the reset fails with what to do (restart herdr's agent detection, or `/clear` by hand), but only once herdr has read `unknown` for `LOST_AFTER` (30 s): a passing `unknown` while herdr re-detects the agent just holds it.
- **Live findings** (2026-10-26, Claude Code 2.1.310 on Haiku, agy 1.4.7, herdr 0.8.2, a throwaway root in a scratch tab):
  - `/clear` typed into an idle Claude pane gives a new session within ~2 s; herdr's Claude integration reports it as `agent_session`, the new `.jsonl` exists at once, and the Claude process, its pane's foreground group and its `cc-socks/<pid>.sock` stay. So the root is still the root (`by-pane` plus `pane_runs_this_claude`, which compares pids, not sessions), its address doesn't change, and a worker's `SendMessage` reached the cleared session. `herdr agent prompt --wait --until working` returns `agent_prompt_stalled`: a clear is no turn, so it is confirmed by the session change instead.
  - **`/clear` typed into a busy Claude runs at once and throws the turn away**; it isn't queued like text. Hence the positive idle check: never "not seen working", always "seen idle, box empty, twice".
  - A background task of the old session (`run_in_background` `sleep`) survived the clear. `mesh brief` still prints `warn_unwatched`'s line, so a fresh root whose watch did die restarts one.
  - agy has an interactive `/clear` (print mode refuses it as "not available in print mode"); typed into its pane it starts a new conversation, seen as a new `<id>.db` in agy's conversations folder, since herdr reports no session for agy. Another agy may start one in the same seconds, so the root's is the new conversation whose first prompt (agy's index keeps it as `preview`) carries the bootstrap's token, even when only one new one shows (it may be the other agy's, with the root's not indexed yet); failing that, mesh records none rather than measure someone else's.
  - herdr's `agent read --lines N` is the screen's last N rows, blank rows under the content included: on a tall pane with little on it (a root just cleared) a 60-row read misses the input box, so the reset reads 200.
  - The bootstrap prompt was handled: the fresh root ran `mesh brief` and `mesh inbox` and carried on; its next `mesh status` measured the new session. With `MESH_ROOT_AUTORESET=1` and a 5 s TTL, the root's watch reset the idle root on its first poll.
- **The bootstrap** is a `📬 [mesh]` line (so `human_draft` treats a leftover copy as ours) that says the agent is the run's root with no parent to report to, then: run `mesh brief`, then `--next` (or the next step in `notes.md`). The global snippet says the same, since it otherwise reads a doorbell as a worker's.
- **`notes.md` and `mesh brief`.** What the files can't derive (the user's standing instructions, decisions and why, what's next) goes in `$(mesh dir)/notes.md`, kept by the root. `mesh brief` is one bounded read (§13's derivations, capped, each cut part naming the command for the rest), in the spirit of Rove's budgeted read ("a field stays only if the coordinator would act differently without it") and firstmate's file-built digest; it gives the old transcript's path as an untrusted reference, like Rove's handoff, since the files and `mesh status` are authoritative.
- **Idle trigger, opt-in** (`MESH_ROOT_AUTORESET=1`): the root's own watch, once a minute, resets a root over the threshold that reads idle, has a cold cache and no unread report at all (stricter than `mesh reset`, as no judgment is involved), at most once an hour (`AUTORESET_BACKOFF`, fixed: a failing reset on a 5-minute cache shouldn't retry every 5 minutes). It can't see a root waiting on the user (a root's turn always ends in text, so "the last entry is a reply without a tool call" says nothing), so ORCHESTRATE has the root write such a question to notes.md, and the prompt after an idle reset says to look there. A root busy in a long foreground command (a fan-out `ask`) reads working in herdr, and its session file is still, which is why idle is read from herdr and not from the session file. A Claude root herdr reads `unknown` is judged by its process's own status instead, as `mesh reset` does (`lost_root_quiet`: `idle` or `shell` for 5 s); when nothing can tell, no reset starts and the next poll looks again, so `LOST_AFTER`, which bounds how long a started reset waits before it gives up, has nothing to bound here.
- **`--compact [focus]`** types `/compact <focus>` instead, confirmed by the pane going working and then idle: for a root with its own repo's work in flight, while warm.

## 16. Skills of our own

Besides the `/delegate-*` entry points, four skills hold a discipline rather than a mesh procedure. Run `m6f06` surveyed the skill suites (Matt Pocock's, Superpowers, Compound Engineering, gstack, antiagree, naysayer) and found none that fits a mesh agent as it is.

- **`check-plan`, a worker's self-check before its `plan`.** The root reviews every plan, but it reviews prose: checking a claim against the code means reading the code, which the worker has just done and the root hasn't. So the worker attacks its own draft first: the 3 to 7 claims the plan stands on, each checked now and marked FACT or GUESS, a prior-art search (the repo first, outside it when the plan builds something new), the strongest objection and the cheapest check that settles it, a verdict (GO / FIX / RETHINK), then the plan fixed and a short `Self-check` section in it (PLAN_TEMPLATE). A wrong premise found there costs one edit; found by the root, a `changes:` answer and another plan round. It edits only the plan file under `$(mesh dir)`, so it runs under the planning deny list, and it asks nobody: a worker's only channel to a human is a `question` to its parent, and it never spawns agents. It's bounded (a few claims, a search or two) and skipped on direct tasks, which have no plan. The bones come from antiagree (MIT): load-bearing claims only, confidence labels, prior art before design, "don't perform harshness", credit the plan's own safeguards, declare that you're anchored.
- **`find-peers`, the discovery half of §14.** `mesh peers add` registers a peer (and briefs it, with `--body`), but which projects to add was only obvious to whoever ran the survey: run `mac82` found its eight by hand. The skill does that part: name the repo's 4 to 6 core mechanisms, search several surfaces per mechanism (GitHub search and topics, code search, awesome lists, plugin directories, registries, the web), read each survivor's source, and rank by mechanism overlap with the file that shows each, stars only breaking ties. Popularity says little about whether a project solved the same problem: tmux-orchestrator (3 stars) still answered the Stop-hook question. Registering, and cloning under `~/research`, wait for the user's yes, since each peer costs a large first brief; reading a candidate's code before ranking takes only a throwaway clone in a scratch directory. Peers are added without `--body` (which asks each in turn and waits) and left unbriefed: briefing is `harvest-peers`' job, which the user starts when they choose to spend a first round. Search and judgment are agent work, so it's a skill, not a `mesh peers find` command; it's root only (mesh refuses a worker `peers add` anyway), and its steps up to the shortlist work in any repo, with or without agent-mesh.
- **`harvest-peers`, the asking half.** After the first brief nothing asked the peers again with a purpose, and every run that did turned answers into work by hand (`TODO.md`'s "From run" sections). The skill is that round, repeatable: the first-round brief (run mac82's, generalized) for peers with no conversation yet, else a follow-up naming what changed here since the oldest `asked` among them and 3 to 5 of our riskiest mechanisms by file and function, so a peer compares code instead of retelling its README. Every finding is checked in our code before the user sees it, labelled real, already tracked, already rejected (with the design section) or wrong: a peer reads its own project well and ours from a distance. It needs no new state: the variant follows the peer's conversation (`session`), since a peer adopted from a hand-researched asker has one but no `asked`; `asked` (UTC, set on every ask) dates the follow-up; and each peer's last answers are its own `answers` in `mesh peers --json`, since the global newest answers file may be another group's. `find-peers` never starts it, since a first round costs a few hundred thousand tokens per peer and the user picks when; a one-off question still goes through `/delegate-*`.
- **`make-concise`, rules files rewritten without losing a rule.** Repo rules files are read on every call (3.7% of a week's spend in the cost study), and some pass agy's 24,000-byte truncation (career-ops' 88.9 KB `AGENTS.md` is read only to its first 24 KB). The third-party rewriters drop what rules files need: caveman-compress removes connectives, hedges and duplicate examples, squeez deletes "maybe" word by word (turning advice into a rule), and `claude-md-improver` only adds and ignores `AGENTS.md`. So the skill's rules keep every rule with its reason, examples of different cases, plain sentences and the strength words, and borrow only caveman-compress's idea of a before/after check. `validate.py` makes the mechanical part fail loudly (fenced and marked blocks byte-identical, every code span, URL, path and `@` import kept somewhere in the rewritten files or an `--also` document, the size cap, `--keep` for text code matches on; a lost bare file name only warns, since `Next.js` looks like one); meaning is left to a word-diff read and to the repo's own reviewers, which is why it runs as the repo's own agent with one PR per repo. Two real `CLAUDE.md`/`AGENTS.md` files stay two: merging them is the owner's call.

**Concise writing for agy.** Claude Code's built-in `Concise` output style is set globally (2026-10-28, `docs/cost-research/README.md`, "Language"), but agy has no such mode, so the global snippet carries a four-line "Writing" rule with the same points: lead with the result, no narration or recap, keep every fact, reason and caveat that changes an action, and code, paths, commands and errors verbatim. It reaches Claude too (one block for both CLIs; `install.sh` writes no per-CLI block), which costs a few dozen tokens a session and agrees with the style. Third-party steering (caveman) was skipped: its rules exempt files and agent-to-agent messages, which are what mesh agents write.

## 17. Many agents on one machine

On 2026-10-27 WSL froze twice (03:43 and 03:50) with its 15.5 GB of RAM and 4 GB of swap full: allocations failed and nothing was OOM-killed. Measured idle afterwards, 22 sessions held 8.4 GB: `claude` about 195 MB each, the MCP servers each session starts (playwright ~83 MB, claude-code-explorer ~36 MB, shadcn ~76 MB) another 38 %, herdr and the pane shells ~0.3 GB; before the freeze, workers had also left four `next dev`/`next start` servers running (~1.5 GB). A `--bg` worker is the same process with the same servers, so fewer panes saves little. The machine got 32 GB of swap, `vm.swappiness=100` and earlyoom; mesh got three things.

- **A memory floor at start.** `memory_guard` refuses a new agent process (in `spawn_worker`, `reopen_worker` and `cmd_ask`'s Copilot branch, where mesh starts one on the root's behalf; `mesh open`, which the user types to take a conversation over, is left unguarded on purpose) while MemAvailable plus SwapFree is under `min_free_mb`: `MESH_MIN_FREE_MB`, else 10 % of RAM plus 10 % of swap plus 1 GB, at least 2 GB. 10 % + 10 % is where earlyoom's defaults start killing (both must be under 10 %), and where a machine without it thrashes; the extra GB is the agent itself (~400 MB idle with its servers) and a build in it. A fixed default would sit above earlyoom's line on one machine and below it on another (4 GB is under this machine's 4.8 GB). An agent just started hasn't grown into MemAvailable yet, so a root spawning four workers back to back, one `mesh` process each, would read the same free memory four times: each pass records a reservation in `$MESH_HOME/reservations.json` (under `.reservations.lock`, so `ask --peers`' threads queue too), and every reservation younger than `RESERVE_FOR` (120 s, about how long an agent takes to reach its idle size) counts as `AGENT_MB` used. A start that fails after the guard but before anything was launched takes its reservation back (`release_memory`), a resume restarts its reservation's clock at the launch (`refresh_memory`, since its worktree and compaction steps can outlast `RESERVE_FOR`), and a Copilot asker's goes once it has answered. The check runs last before the guarded path's own side effects; `cmd_ask` (for `--repo`, Copilot, a first peer ask, or a worker that's retired or in an archived run: `not_live`) and `ask_peers` (when one of its peers is) also check before `ask_identity`, so a refused ask usually makes no run, though an ask to a past worker of a live run is refused only when its resume begins. Swap counts, as the request asked: not counting it would refuse almost always here (4.6 GB available with no run going), though deep swapping slows WSL well before the floor, which the root can raise. Copilot askers aren't exempt: they don't stay, but at the moment they start they're a node process with its own servers and the tests it runs, as much a risk as a Claude one. A model swap (`approve`, `switch`) closes one process for each it opens and isn't guarded.
- **The sweep of leftovers.** `retire_worker` (one call at its end) and `stop_run` (before it removes worktrees) run `sweep_worktrees`: what a worker left running in its worktree is TERMed, given a few seconds, then KILLed, and logged as `killed`. "In its worktree" is the process's cwd, which every process a worker starts inherits (its shell, `claude`, its MCP servers, `pnpm` → `next-server`); but a live pane's shell, a live agent and its MCP servers, or a user's own shell are there too. What sets a leftover apart is that its parent died: `leftover_processes` keeps a process only if its chain of parents inside the worktree holds no agent CLI and hangs off an init (pid 1, WSL's `/init` subreaper, a `systemd --user`). On WSL a terminal's login shell and a daemonized tmux server also hang off the `/init` orphans go to, so a tree in which any process holds a terminal (`tty_nr`), or is an agent, is never a leftover; checked on this machine, an orphaned `nohup … &` from a tool shell, and the tool shell itself (a session leader with no terminal, so `sid == pid` would have spared the very tree the sweep is for), hold none. The sweep first waits (a few seconds, by count) for the worker's own agent to exit (an agent CLI whose command line names its session, or for agy, which starts without one, its own `--log-file`), since its children hang off it until then. An agent still there after that, lingering or another's (a `spawn --cwd` restart, the user's own `claude`), keeps its tree, and the orphans are swept anyway; a server such an agent started with `nohup` hangs off `/init` too and goes with them. The terminal rule fails safe the other way: a worker's own `tmux new -d 'pnpm dev'` holds a pty, so it's left running. Only `$MESH_WORKTREES/<run>/<slug>` and `peers/<name>` paths are swept, never a main checkout or the root's cwd, and the sweep never raises. PROTOCOL rule 2 asks workers to stop what they started before reporting; the sweep is the backstop.
- **MCP servers stay the machine's business.** A stdio MCP server is one process per session, so its cost multiplies by the agents running. The fix is configuration: run a server that can be shared once (playwright's `--port`, as a user service the user-scope entry reaches by URL) and scope the rest to the projects that use them. A mesh-side allowlist (`claude --strict-mcp-config --mcp-config <subset>` per worker) was declined: it drops the repo's own `.mcp.json` servers with the heavy ones, which §2 rules out (an agent runs with its repo's config); mesh can't know which servers a task needs, so the root would guess per spawn; and agy has no such flag. Revisit if a heavy server can be neither shared nor scoped.

## 18. Idle workers are retired

On 2026-10-27 WSL froze twice from memory exhaustion: 22 Claude sessions of two runs were alive, ~195 MB each plus ~145 MB of their MCP servers, most of them idle (reviewers waiting on a re-review, workers that had reported `done`). The root was told to retire what it was done with (ORCHESTRATE step 9), but nothing made it, and a worker waiting on a follow-up that may come looks like one worth keeping. An idle process buys nothing over a resume, though: the transcript is on disk, and the prompt cache keys on content, so a resume within the cache's TTL (1 h on a subscription) with the same model and tool set reads the old prefix (design §9 measured an effort-only resume writing 65 tokens; run m6f06's cache research says the same of a resume). So the root's watch retires idle workers, and a message to a retired worker resumes it.

- **Who is retired** (`retirable`, `Watch.maybe_retire`): a worker whose newest report since its last task or answer is a `done` or `failed`, idle `MESH_IDLE_RETIRE` seconds (900) since. Idle is counted from the later of that report and its last transcript write (`last_progress`; with no file to read, the watch's own first idle reading), and it must read idle on that poll, so a restarted watch doesn't start the count again and a worker tidying up after its `done` stays. Not one with a `plan` or `question` waiting on the root, a task it hasn't reported on, a declared `wait`, unread mail (work is coming, or a doorbell was lost), a fan-out collecting it, one starting, held at a screen or being reopened, a headless Copilot asker (no process), or a pane with a human's draft in its box. The root is never watched. A report the root hasn't read yet doesn't hold it open: retiring loses nothing (the report is in the mailbox, the conversation resumable), and a report unread for 15 minutes means the root is away, which is when the sessions piled up. Peers kept open after an ask (`--keep`, `--no-wait`) follow the same rule; asked again, they are resumed as before.
- **Who does it:** the root's `mesh watch` (`retire_after`), and the run's retirer when no watch covers the worker; `mesh ask`'s watch returns at the answer (and closes what it opened), and a fan-out retires its peers itself. A failed retire is logged (`auto_retire_failed`) and not tried again for that report, so a herdr error isn't retried every poll; a background session `claude stop` couldn't stop counts as failed (its status is restored), since marking it retired would leave its memory held and its next resume refused as still running. A retire a new message called off (`still`) is tried again once the worker is idle after it. A success logs `retire` then `auto_retire`.
- **The run's retirer** (`ensure_retirer`, `start_retirer`, `run_retirer`, `retire_pass`; `mesh retirer`): an agy root runs no watch (it relies on doorbells), and a Claude root's ends at its `--timeout`, so a retire that only a watch does left their workers open. A worker's `done` or `failed` (`cmd_send`, not one a fan-out collects) starts one detached retirer per run, unless one runs (it holds `retirer.lock`) or `MESH_IDLE_RETIRE` is 0. It polls every `RETIRER_POLL` seconds (30) and keeps running for any worker whose newest report since its last task or answer is a `done` or `failed`, that isn't retired, whose retire after that report didn't fail (its own, or a watch's: the newest `auto_retire_failed`, not retried as above), and that didn't read gone `RETIRER_GONE_POLLS` polls (3) in a row: a state that only holds the retire for now (unread mail, a declared wait, held, `starting` during an approve or switch, `retiring`) keeps it going, since nothing would start it again. It reads each such worker no `mesh watch` (or `ask`) covers (`watched`), and while `retirable` names it runs the watch's own path (`Watch.idle_tick`: the `idle_at` bookkeeping, then `maybe_retire` with that report; `tick`'s idle branch calls the same), so every condition above, the viewers and the race below hold as they are. A worker read gone three polls in a row after its report is let go, as a watch counts it finished: one bad read (a failed `claude agents`, which `read_claude_agents` tells apart and skips that poll for, or a herdr error) doesn't, and gone counts whatever its status (a `swap_failed` worker whose pane closed), except while it is being reopened or retired (`gone_counts`: `starting` within `STARTING_GRACE`, `relaunching`, `held`, `retiring`). It is still read while the retirer runs, so one resumed with no task counts again, and `resume_worker` starts a retirer for a worker it reopened whose last report is final. One that leaves (a new task, retired) loses its `Watch`, so a stale idle count can't retire it after a burst of work. It takes a watched worker over once that watch ends, and never nudges or alerts. While a `mesh stop` is under way (`stop_under_way`) it retires nothing but keeps running, so a stop that fails leaves the run its retirer. It exits once nothing keeps it, the run is gone or stopped, or idle retire is off; a poll that fails on an error is tried again at the next one; before exiting it lets go of the lock and looks once more, and takes the lock back if a report landed meanwhile (a `send` logs its report before trying the lock, so either that look sees it or `send` finds the lock free and starts a new one). It runs as nobody, from the run dir: started from a worker's shell with only the `MESH_*` ids dropped, its pane id would make `worker_caller` name it that worker (refused by `check_worker`), and from the worktree, `sweep_worktrees` would stop it as a ttyless orphan at the first retire. Triggers weighed and dropped: the agy root's own commands (`send`, `approve`, `inbox`) are sporadic and stop exactly when the root is away, which is when sessions piled up, and the retire is due 15 minutes later anyway; a worker's Stop hook exists only for Claude workers, and an agy root's are mostly agy; a detached `mesh watch --any` for an agy root would also nudge and alert, by exit codes nobody reads. Its cost: one stdlib Python process per run while a reported worker is open, one `run.json` and log read per poll, plus one herdr read (or one `claude agents`) for each reported worker no watch covers.
- **The watch's exit:** an auto-retired worker leaves an `--any` watch as a retired one does, but is named apart (`auto-retired <names> (idle since its report)`), not as "retired without a report". Once every worker is done and idle, a `--any --alerts` watch thus ends about 15 minutes after the last report instead of at `--timeout`, after `RETIRE_SETTLE` as for any retire: there is nothing left to watch. Restarted, it says `no live workers to watch`, so it can't loop; `send`'s resume warns when no watch covers the worker it reopened.
- **Messages reach a retired worker** (`deliver`, `send_resumed`, `resume_stored`): `mesh send` stores the message first, then `deliver` reads the target's status under the run lock, waiting out a retire under way (`settled_status`). A retired worker isn't rung: the delivery says `retired`, and `send` resumes it through `resume_worker`, with the stored message (`stored`), so there is one resume path (compaction, events, the name kept). A task decides its deny list and model as `mesh resume --task` does (a task it plans is planned under the list on the planning model, a direct task gets none, a question stays read-only); an `answer` or a `question` resumes it as it was (an asker still read-only, a planner mid-plan still planning), and its first doorbell names that message's type. An `info` is stored without a resume (`send` exits 2, saying so): a reopen, maybe a compaction, for a "thanks, nothing more" brings back what the watch just closed; the worker reads it when it is next resumed. A retired peer asker is refused by `send` before anything is stored, pointing to `mesh ask <peer>`, which refreshes its worktree first (`prepare_peer`); one retired between the check and the store gets its message stored, not rung, with the same pointer. The resumed worker's first doorbell says it is the same run, same parent, worktree and `mesh dir` (`doorbell_text` when `resumed_from.run` is this run), since a resume into the same run, rare before, is now the usual one; its start, up to `run <id>`, is unchanged, as agy's conversation lookup matches it. A `task_note` from `leave_finished_pr` can't go into a task already stored, so it follows as an `info`. `mesh ask` already resumed a retired worker (`reach_worker`); a worker retired between its state read and the store is resumed the same way. A failed resume (the memory guard, say) leaves the message stored, says so, and exits 1, pointing to `mesh resume` then `mesh ring`; for a task it first sets the entry as that resume would have (`unresumed_task`: a direct task clears `read_only`/`planning`, as a failed background lift does; a planned one marks the plan phase and `planning`; a question `read_only`), so the resume with no task comes back with the right list and phase. `ask`'s own closing of the askers it opened (`cmd_ask`, `ask_peers`) treats a failed retire as a warning: the answer is already in, and a background session that `claude stop` couldn't stop but that is gone counts as stopped (`bg_status`). The refusal `send` used to give a retired asker under a deny list goes: it was there to make the root resume it rather than lift its list by a model swap, which the resume now does by itself.
- **The race:** auto-retire's check (`retire_worker`'s `still`, under the run lock) re-reads the log and the mailbox before marking the worker `retiring`; `deliver` stores, then reads the status under that lock. Either the check sees the message and the worker stays open, or the status read sees `retiring`/`retired` and the message goes to a resume. Checking the status before storing left a window where a message landed in a pane being closed. The cost is one locked read per delivery to a worker. A retire still under way when the wait (`RETIRE_WAIT_MS` plus half a minute) runs out isn't rung either: the delivery (`retiring`) says the message is stored and to `mesh resume`, then `mesh ring` once it is retired; `send` exits 2 with that, and `ask` fails with it rather than wait for an answer that can't come. The wait's deadline is kept per worker for the process (`SETTLE_DEADLINES`), so `lift_read_only` and `deliver` don't wait it twice. `lift_read_only` waits out a retire the same way, and goes on as for an open worker when that retire failed.
- **Viewers** (`viewer`): a worker the user is looking at isn't retired; the hold is checked last, once the retire is otherwise due, and logged once per report (`retire_held`, with why), and it is retired at the first poll after the viewer leaves, if still idle. A background worker is held while a `claude attach` client of its session runs. Claude Code's daemon keeps its attach clients in memory (`attachers`, which its own job retire honours) and exposes them nowhere: not in `claude agents --json`, its control socket's `list`, `~/.claude/sessions/*.json`, `daemon/roster.json` or `jobs/*/state.json`; `daemon/attach-journal/` holds attach-latency beacons, deleted once the attach completes. But the client is a process while it is attached, so it is read from the process table: a `claude` process whose argv is `attach <arg>` (`mesh open` runs `claude attach <bg_id>`), `<arg>` being the job id, the session id or part of the session name, which is the worker's name. Checked live on 2026-10-27 (Claude Code 2.1.312): `claude attach attach-probe` under a pty read `claude attach attach-probe` in `/proc/<pid>/cmdline`, and was gone once its terminal was killed. A short part of a name (`claude attach agent-mesh`) holds every worker it matches: holding is the safe side. A pane worker is held while herdr has its pane focused (`herdr pane get` → `focused`; one pane at a time, kept with no client attached): the user went there. A herdr error holds nothing, as an unreadable pane shows no draft.
- **Limits:** an attach from Claude Code's agent view (`claude agents`, then a session) runs in that TUI's own process and can't be tied to a session from outside, and without `/proc` (macOS) there is no process table: those viewers don't hold a retire. A pane in view but not focused (a split) isn't seen either; a pane left focused is held for as long as it stays focused, and keeps the run's retirer polling meanwhile.
- **What it costs:** a resume takes a new pane and a few seconds, and may compact a large conversation first (§12). A resume that changes the tool set (a task it plans adds the deny list, a direct task to a planner drops it) is a cold turn, as the live reopen it replaces would be. A planned task sent to a live worker never got the list (`send` doesn't reopen a live worker to add it, §9); one sent to a retired worker does, since it comes back through resume's rules.

## 19. Spend per agent

`mesh cost [run]` prices what a run's agents spent, and `mesh cost --since <when> [--until <when>]` every session on the machine in a window, mesh or not: per agent, per kind (root, worker by size and view, reviewer, peer, asker, each one's subagents; outside a run `user`, `headless` and `worker (unmapped)`) and per phase (plan, exec). It exists so the cost study's checks (`docs/cost-research/README.md`) are one command instead of a scratch directory of scripts.

- **Source:** Claude Code's session files, `message.usage` of each reply: input, cache writes by TTL (`cache_creation.ephemeral_1h/5m_input_tokens`), cache reads, output. Claude Code writes one record per content block (thinking, text, each tool call), each carrying the whole reply's usage, so calls are folded by `message.id`: summing records overcounted Gas Town's ledger 1.76–3.26×. The fold is across every file one report reads, since a background swap or resume (`launch_bg`) copies the conversation into a new session file with the same ids, as a forking `/resume` does: a file run state names goes first, then oldest first (on a tie, the one whose calls end first: the original stops where its copy goes on), and the rest of each file still times its gaps, so a copy's first own call reads as the cold resume it is. Per file, the cost study's first round over-counted its week by 7.3%. Files are read line by line with no length limit, since a reply holding a large tool call is one line of megabytes (Gas Town's 64 KB scanner dropped those). agy has tokens only (field 9 of a step's metadata, as §12 reads it, timed by field 1): its quota formula is unknown, so no dollars. Copilot isn't measured.
- **Attribution is by time.** A conversation isn't one run's: a peer keeps one across runs, and a root's is the user's own session, before and after its run. So each agent of each run is a segment of its sessions (its `session`, the ones swaps copied from, a root's every `reset` session), starting at its spawn or resume (a root: its run's `created`) and ending at its run's `stop` (a run never stopped: an hour, `CACHE_TTL`, after its last event, or where the next run in its root's directory starts; fixed, so a report doesn't change with the clock). A segment starts at the agent's first `spawn` or `resume` event in its run (a resume in the same run writes a fresh entry); a call goes to the segment that started last before it, and one before every segment (the session's life before mesh) to none; a root's calls count only while its run is open, the rest is `user`; a call between one run's stop and the next segment's start (the headless `/compact` a resume runs first) goes to the later one. A root session a hand-typed `/clear` started is named by nothing in run state, so a session that ran a root command (`mesh spawn`, `approve`, …) in a root's cwd while its run was open counts as that root, as the study's classifier did.
- **Phase** comes from the models history: a `plan approved` ends a plan phase, a `planned task` starts one, a `plan_phase_ended` event (a direct task) ends one; what an entry started in is told by its first change.
- **Prices** (`PRICES`, with the date and source in `PRICES_AS_OF`): API-equivalent dollars, standing in for what the subscription limit counts, which is undocumented. A model is priced by family.
- **Cold resumes:** a call after a gap longer than the TTL its session last wrote at that writes at least `COLD_WRITE_MIN` (20k) tokens; counted per agent and kind, since a large session resumed cold is the expensive pattern (§12, §14).
- Measured against the study's baseline week (2026-10-21 → 10-28): $1,527, the same calls as the study's data deduped across files ($1,614 as the study reported it, ~$1,504 corrected), in 3.5 s. Its kinds differ where it splits by time: roots' calls outside their run's window are `user`, and a run never stopped ends an hour after its last event.

## Code map

The names in `bin/mesh` behind each mechanic that spans several files, for finding the code; the why is in the numbered sections above. `CLAUDE.md` keeps a short gist of each: change a mechanism, update both.

- **Run state** lives in `$MESH_HOME/<run>/` (default `~/.local/state/agent-mesh`): `run.json` (agents, models history, worktrees), per-agent mailboxes, `log.jsonl` events, and the `RUN_FOLDERS` agents write into (`plans/`, `reports/`, `tasks/`: made by `init_run`, and by `mesh dir` for an older run). Mutate it only through `editing_run(run_id)` (locked, atomic write); `editing_run(run_id, folder)` edits an archived run (the folder `all_runs` gives), as `read_log` reads one.
- **Mailbox plus doorbell:** `mesh send` writes the message file first, then types a one-line `📬 [mesh]` doorbell into the recipient's pane via `herdr agent prompt`, with retries (`ring_stored` logs `rung` or `doorbell_failed`). Each rung doorbell carries a fresh `(ref <token>)` early in the line (`ring_token`), and only that token above the input box confirms it (`ring_needle`, `doorbells_shown`, `above_input_box`), so a doorbell a busy agent queued isn't typed again; retrying stops once the message is in `read/`. Each try reads the pane with `--ansi` and holds while the box shows a human's draft (`typed_text`, `human_draft`: dim ghost text and an unclear box don't count), under a per-pane `ring_lock`, since herdr fuses a prompt into a draft and merges concurrent ones. A lost doorbell loses nothing. `cmd_send` refuses a report (`REPORT_TYPES`) while the sender has an unread task/answer (`refuse_stale_report`, `--unread-ok`), since the watchdog credits a report to the newest task. `approve` / `switch` / `retire` take only the worker's parent or root (`require_parent`), `approve` only a waiting `plan` (`refuse_no_plan`), and `stop` refuses a worker caller. Before any of that, `main` runs `check_worker`: a worker of a live run (`worker_caller`, which `stopping_worker` uses too) runs only `WORKER_COMMANDS` (its messages and the readings), and `send` only to its parent (`refuse_foreign_send`); everything else is refused with a `refused` event and a message naming the temp dirs to try mesh out in (design §10).
- **Native transport** (design §11): a Claude recipient's doorbell is written into its inbox socket by `mesh` (`write_inbox`, `rung via=socket`). `native_route` picks the lane: a worker's socket (`worker_settings` passes `crossSessionInbound: accept`); a root's (`address`, `pid`, `start` from `claude_process`) if it takes unattested frames (`inbound_setting`, `root_class`), else a `send_message` for a Claude sender; else the pane. Before ringing a Claude pane worker, `deliver` checks its pane's process (`relaunched_outside_mesh`, workers only: the pane's leader, or its one Claude when herdr names none, lacks this worker's Stop hook (`hook stop --run <run> --as <name>`, any mesh path), `mesh_launched`) and reopens one that something else started (a herdr restore) with `swap_model(why="relaunched", lost_ok=False)` under a `relaunching` claim (`reopen_relaunched`), keeping its deny list, or stores the message unrung; `mesh ring` refuses it. `refresh_root_address` re-records a reopened root's socket on its next command: from the root's pane as its leading process (which also records its `session`), or elsewhere under its recorded session once its pane runs no Claude (`pane_probe`), never for `--as` from another session. The mailbox stays the record either way.
- **Views and sizes:** a worker runs in a herdr pane or as a `claude --bg` session (`view`); a Copilot asker is `headless` (below). `SIZE_DEFAULTS` maps (kind, size) to model, effort and view for trivial / small tasks, which have no plan phase and get `DIRECT_PREFIX` (Claude runs Opus at every size; design §9). `large` is the `auto` flow below. A fresh reviewer gets `REVIEW_EFFORT` at trivial and small sizes, and a pane at any size. Background helpers (`launch_bg`, `bg_status`, `stop_bg`, `swap_bg`) read `claude agents --json --all`. A `--bg` session runs in a daemon's spare process, which never sees the launch's environment, so `launch_bg` passes the identity and every `MESH_CONFIG` key (empty when unset) through `--settings` env (`worker_settings`), and every `claude` call runs on `claude_env()` (no identity, pane ids or session variables). Every background relaunch passes full flags, which forks a copy, and mesh records the copy's session id.
- **Identity** comes from `MESH_RUN` / `MESH_SELF` / `MESH_PARENT` / `MESH_ROLE`, injected into each pane at spawn (a background worker gets them through `--settings` env). `inherited_identity` drops an environment identity naming no live run, an agy or Copilot agent (inside Claude Code), or a Claude worker whose recorded session isn't `CLAUDE_CODE_SESSION_ID`. In its own pane a Claude worker is rebound only when its `CLAUDE_PID` leads the pane's foreground process group (`pane_runs_this_claude`, from `herdr pane process-info`; herdr's `agent_session` is spoofable), and the `by-pane` map, which names only roots, is checked the same way (`foreign_to_pane`), so a nested `claude -p` or a background session carrying the pane's ids is never its agent, unless named with `--as`. A Claude pane worker with no identity in its environment (a herdr restore relaunches it without `MESH_*`) is found by `pane_worker`: a live run's worker whose pane and session are this one's, confirmed by `pane_runs_this_claude` (strictly: `None` refuses); `stopping_worker` uses its scan (`pane_worker_entries`) and refuses a stop on any match, even several. Such a refusal (`PaneRefused`) never makes `mesh ask` start a run. Agents are addressed by herdr name (`<repo>-lead`, `<repo>-<slug>`), with pane id as fallback.
- **Topology:** a root keeps its own repo; one worker per other repo, in its own git worktree under `$MESH_WORKTREES` on branch `mesh/<run>/<slug>`. Workers never spawn agents (1:N, not 1:N:N; see design §7).
- **Models per phase** (design §9): `--model auto` plans on the first model in `PLAN_CHAIN` with quota (agy quotas parsed from `agy -p /usage`, threshold `MESH_MIN_QUOTA`) at `DEFAULT_EFFORT`, then `mesh approve` calls `swap_model`, which closes the pane and reopens **the same conversation** (`agy --conversation <id>` / `claude --resume <id>`) on `EXEC_MODEL` at `EXEC_EFFORT`. agy encodes effort in the model id (`gemini-<ver>-<family>-<effort>`). `mesh watch` exits 7 on a `RESOURCE_EXHAUSTED` quota line in the worker's own `--log-file`; the root then runs `mesh switch`.
- **Questions and reviews** (`mesh ask`, design §10): an asker is an ordinary worker that got a read-only task (`ASK_PREFIX` / `REVIEW_PREFIX`), so follow-ups, `resume` and turning it into a change need no special case. `ask` composes `init_run` (`ask_identity`), `spawn_worker` / `resume_worker` (`reach_worker`), `deliver` and `watch_agent`. A PR link finds its author by the PR's head branch first (`find_worker`, `opened_pr`, via `gh`); a reviewer records the PR in `reviews`, which `worker_prs` skips so the message-link fallback still finds the author, and the head it read in `review_heads` (the next review task names both; a fresh reviewer asked again moves to the new head when it's its own clean checkout of the PR and not mid-task, `plan_move` up front and `apply_move` just before the reach, undone if it fails). A Claude reviewer's task also gets `CODE_REVIEW` (`ask_task`, once `cmd_ask` knows the kind; `asker_task` builds it for `cmd_ask` and a review round alike): run `/code-review` at the review's size (`REVIEW_LEVEL`) on `<merge base>..<head>` (`head_diff`, fetched through private refs, `fetch_commit`; not the bare PR number, which `gh` may resolve against `origin` in a fork; without the range, the number where the PR's remote is `origin`, else the PR's link), or on `<last>..<head>` when asked again (unless `fix_commits` says the branch was rebased or merged, then the whole PR, `REVIEW_AGAIN_WHOLE`), and check its findings itself; only with the PR head in its repo (no head: a hand review). A review round (`--reviewers`, `ask_reviewers`, `review_round`) picks its kinds with `pick_reviewers` (`agy_has_quota`, `copilot_available`; a re-review by `review_checkout`), reaches them as `ask --peers` does (`collector`, `watch_each`, `write_answers`, `retire_answered`), with Copilot in its own thread (`copilot_asker`, then `copilot_ask`), and stops that copilot when interrupted (`stop_copilot`); `reached_outcomes` and `clear_marks` are shared with `fan_out` / `ask_peers`. A Claude worker on a read-only task has `read_only`, and one planning has `planning` (spawn of a large task, resume with a planned task or, with none, of a worker in a plan phase that owes its task (`owes_plan`); a direct task ends the phase in `cmd_send`, `end_plan_phase`; design §9): either runs with `claude_deny`'s `--disallowedTools` (pane, `--bg`, resume and swaps alike). `swap_model(..., lift=True)` reopens it without the list and clears both (`lifted`): `cmd_approve` always passes it, and reopens a denied planner even when the model and effort stay. `lift_read_only` in `cmd_send` makes the list follow a change task: a planned one turns `read_only` into `planning` with no reopen, a direct one lifts it. `send` never reopens to add it.
- **Copilot askers** (design §10): `ask --kind copilot` (`ASK_KINDS`; `spawn` / `init` still take only `KINDS`) goes to `ask_copilot` instead. `copilot_ask` runs `copilot --output-format json` in the asker's worktree with the prompt on stdin, the same `--session-id` every time (it starts the session, then resumes it), and files the last message (`copilot_answer`) as its `done`. While it runs, the entry holds the `mesh ask` pid (`claim_copilot`, checked and set under one run lock) and Copilot's, which `run_cli(started=…)` starts in a session of its own (`copilot_ask` turns SIGTERM and SIGHUP into an exit, `signals_raise`, so only a SIGKILLed `mesh ask` leaves it running), each with its start time (`proc_start`, so `pid_alive` never takes a reused pid for it); `live_holder` reports it busy while either lives, `agent_status` says `working` and `cmd_stop` refuses. Once both are gone, `file_orphan` (from the next `ask`, a headless `Watch.tick`, the root's `inbox` and `stop`; `status` only shows it) files the owed answer under the run lock, rebuilt from Copilot's `events.jsonl` past the end `claim_copilot` recorded (`copilot_turn`, `CLAIM_KEYS`), and releases the entry through `release_copilot`, which `copilot_ask` also runs in a `finally` (an interrupted ask files `failed`). `refuse_headless` keeps `deliver`, `swap_model`, `ring`, `approve` and `switch` away from it. `COPILOT_DENY` lists the denied tools (`shell(<cmd>:*)` form). `mesh peek` reads Copilot's own `events.jsonl` for the session; while it answers, `open_peek` runs `mesh peek --follow` in a pane beside the root (only there; it first closes one a killed `ask` left), and `close_peek` closes it after. `beside_root` counts, splits and records the pane on its agent under `.panes.lock`, so parallel `mesh` calls don't split the same pane; `new_pane` holds it from the run's tab lookup through its create to recording the tab and the pane (`record_pane`), so a fan-out's threads make one tab.

Each ask writes the checkout's commit on the worker's `base` (`set_worker_base` on `peers remove`), so a removed peer's conversation reopens at the code it last read and, by its entry's `peer`, still refuses a change task. An asker adopted from the clone's own checkout is `in_clone` (never checked out or removed). `ask --peers` (`ask_peers`, `fan_out`) skips a peer still working, prepares and reaches the rest in threads (`reach_worker`, `spawn_peer`), and marks them `collect` (`collector`: its pid and start, honoured by `collecting` only while it lives, cleared in a `finally`), so `deliver` stores their `done` without a doorbell. It waits with `watch_each` (a peer still at a startup screen only `held_wait()`, `MESH_HELD_WAIT`, then exit 4; one given up on loses its mark and watch lock at once) and writes one `reports/peers-<stamp>.md`, recorded by `record_answers` and found again by `answers_file`. The fan-out reads each peer's log and status once (`asker_status`: a failed `read_claude_agents`, None, is retried once a second later, then `unknown`) and passes them to `owes_answer` and `reach_worker`.
- **Resume onto a finished PR** (design §8): `leave_finished_pr` moves a change task's worktree to a new `mesh/<run>/<slug>` when no PR from its branch is open (`finished_pr`): from the PR remote's default branch after a merge, from the old tip (or `pull/<n>/head`) after a close.

Outcomes are `reset_requested` / `reset` / `reset_failed` / `reset_cancelled` events; `root_hint` shows a failure once (`reset_noted`). `caller` names the caller only for its own run, so `status <run>` / `watch --run-id` never touch another run. `maybe_autoreset` (the root's own watch, `MESH_ROOT_AUTORESET=1`) does the same for an idle, cold, big root owed nothing (a Claude root herdr reads `unknown` by `lost_root_quiet`). `mesh brief` renders `brief()`: request, `notes.md`, `board.md`, `status_rows`, needs-root, PRs, unread headers, the last reset's transcript, each capped (`capped`, `capped_list`).

Both outputs go through `hook_text`, capped under `HOOK_OUTPUT_MAX` (Claude Code's 10,000-character hook cap, less `print`'s newline) by a cut from the middle that keeps the last line, with no wall-clock text. After a `clear`/`compact` reminder or a `rebind`, `mesh inbox` shows `current_task` again once (`session_reset`, `inbox_again`), unless the `last_report` on it is final.
- **Derived status** (design §13): `mesh status` recomputes what each worker owes or waits on every call (`waiting_rows`: `last_report` over the log, mailbox files, `work_evidence` from git, `pr_states` from `gh`, cached in `pr-state.json`), needing-the-root first; nothing of it is stored. `read_log` skips a torn line (warning once) and `log_event` seals one before appending. `mesh log` prints the log as a timeline.
- **Watchdog:** `watch_agents` polls one `Watch` per worker (`mesh watch <name>` or `--any`); `--alerts` keeps going through reports. `--any` re-reads the run each poll (`Roster`: an unwatched worker that owes a report, is `starting` or has a new `spawned` joins (`joins`), a retired one leaves) and holds the `ANY_WATCH` lock; its "nothing left" exit waits out `settling` (a `retiring` worker, one about to join, a recent `retire` not resumed from, or a `resuming` event with no `resume` / `resume_failed` yet). A watch whose run `mesh stop` is stopping returns 0 (`stopped_line`): from its `stopping` event, honoured while the stop's process lives and until a `stop_failed` (`stop_under_way`, each poll and on an alert), and once archived (`run_stopped`, each poll and on a failed read or write mid-poll); `run_lock` never makes a run's folder, so such a write can't bring an archived run back; `cmd_ask` exits 1 on that line with no answer. `watch_each` too. A worker is stopped after `--grace` seconds idle with no report (`REPORT_TYPES`) since its last task/answer (`since_last_task`); a pane worker first gets one `nudge` through `deliver` (`claim_nudge` logs a `nudge` event per task under the run lock), and alerts 3/4 carry `pane_tail`. A worker never seen working is judged once its last task/answer is `start_grace` old (`idle_from_start`: 4 × `--grace`, at least `SETTLE_GRACE`), unless a watch already alerted on that task (`record_alert` logs an `alert` event per task; a `working` reading or a new task re-arms it). A Claude worker at its usage limit or with an expired login (`limited`: `error_limit` on `transcript_stop`, the session file's last reply or its newest `usageLimitNote` (`wrap_up` until a `release`); `login_expired` on the pane tail only with no readable session file, `usage_limit` unless the file records the limit as over, `LIMIT_OVER`) gets exit 7 instead of 3/4/8, as alert kind `limit` or `login`, and a `working` worker whose `progress_files` stay unchanged for `--hang` (`HANG_AFTER`) gets exit 8 (`hung`, held off only while the limit or login it was alerted for lasts); all are `alert` events with a `kind`, once per task. A `wait` (`send_wait`, `declared_wait`: a deadline for the current task, not a report) holds off idle counting, exit 8 and the Stop hook's nudge until it ends, at its deadline or at the first turn end after a wake (`wait_turn` / `wait_over`, logged by the hook, or for agy by the watch's `agy_wait`; then one reminder, `WAIT_OVER` when the nudge is spent); exits 3/5 carry `evidence_line`. Each watch holds `hold_watch`'s shared flock per worker, and root commands `warn_unwatched`. `agent_status` and `live_holder` check herdr against the process table (`pane_probe`, `agent_processes`, `process_holder`), since herdr can lose a live agent's registration. `mesh conflicts` uses `git merge-tree --write-tree`, and one `Ancestry` per repo caches `merge-base --is-ancestor` by commit. `git()` and the other git reads run on `git_env()` (`GIT_OPTIONAL_LOCKS=0`), so reading a worker's worktree never takes its index lock.
- **Resource guards** (design §17): `memory_guard` (`meminfo` from `MESH_MEMINFO` or `/proc/meminfo`, `min_free_mb`, `AGENT_MB` per reservation in `reservations.json` younger than `RESERVE_FOR`) runs last before the side effects of `start_worker` (under `spawn_worker`, which `release_memory`s on a failure before launch), `reopen_worker` (`refresh_memory` at launch; `resume_worker` releases) and `cmd_ask`'s Copilot branch, and with `reserve=False` in `cmd_ask` and `ask_peers` before `ask_identity`. `sweep_worktrees` (from `retire_worker` and `stop_run`) reads `process_table` (which `agent_processes` filters too), waits for the worker's own agent (`own_agent`, among `agents_in`) to leave the worktrees `sweepable` allows, and TERMs then KILLs (`kill_process`) what `leftover_processes` finds, logging `killed`.
- **Idle retire** (design §18): a worker's final report starts the run's retirer (`cmd_send` → `ensure_retirer` → `start_retirer`, `retirer.lock`; `cmd_retirer` → `run_retirer`, polling `retire_pass`: `retire_poll`: kept by a final `last_report` not retired, not tried (`retire_tried`, `auto_retire_failed`) and not gone `RETIRER_GONE_POLLS` in a row (`Watch.gone_polls`, `gone_after`, `gone_counts`); it skips what `watched` and a poll's bg workers when `read_claude_agents` fails, and feeds `Watch.idle_tick` what `retirable` names; `resume_worker` calls `ensure_retirer` after a reopen with nothing new). `mesh watch` passes `retire_after` (`idle_retire()`, `MESH_IDLE_RETIRE`, `IDLE_RETIRE`) to every `Watch` (and `Roster` to those that join); `Watch.maybe_retire`, from `tick`'s idle branch, retires a worker `retirable` says reported a final (`last_report`) with no unread mail, wait or collector, idle since the later of that report and `last_progress` (else `idle_at`), with no `human_draft` in its pane and no `viewer` (a `claude attach` process of a background worker from `process_table`, a pane `focused` in herdr; `retire_held` once per report, `Watch.retire_held`), once per report (`retire_tried`; `auto_retire` / `auto_retire_failed` events). `retire_worker(..., still=)` re-checks under the run lock before marking `retiring`. `Roster.auto` and `Watch.auto_retired` name them in the exit line. `deliver` reads the status after storing (`settled_status`, which waits out `retiring`) and returns `retired` unrung; `cmd_send` (`send_resumed`) and `reach_worker` then call `resume_stored`, which runs `resume_worker` with `stored` (path, type): `reopen_worker` rings that file (bg: its opening prompt; held: `hold(stored=)`) instead of recording the task, refuses when the name would change, and sends a `task_note` as an `info`. `lift_read_only` leaves a retired worker to that path.
- **Spend** (design §19): `cmd_cost` → `run_cost`: `cost_segments` (every run's agents as segments of their sessions, `cost_kind`, `reviewed_pr`, `phase_marks`), `claude_calls` (one pass per session file, folded by `message.id`; `prompt_text`, `ROOT_COMMAND_RE`) and `agy_calls` (`protobuf_fields`), each call placed by `segment_at` (else `root_fallback`, else a non-mesh kind), summed by `tally_session` into a `CostTally` (cold resumes by `CACHE_WRITES` TTL and `COLD_WRITE_MIN`, each new session's first call), priced by `call_cost` (`PRICES`), shaped by `cost_report`. `parse_since` reads `--since` / `--until`.
- **Conversation lookup** (`find_session`): Claude workers get a `--session-id` UUID recorded at spawn; agy conversations are found in agy's `conversation_summaries.db` (its `preview` column), then `history.jsonl`, by the first doorbell text (`You are <name> (worker) in agent-mesh run <run>`), and recorded as `session` on the worker's first `mesh send` (`record_session`). Changing that doorbell wording breaks resume.

## Lessons from the live tests

- **Trust dialogs:** a fresh worktree triggers a folder-trust dialog in both CLIs. agy highlights "Yes" by default, while Claude Code highlights **"No, exit"**. Blindly pressing Enter would quit Claude, so `mesh` finds the cursor and moves it to "Yes", then reads the screen again and presses Enter only with "Yes" selected (a lost arrow would otherwise confirm "No, exit"; Cyclops does the same). It does this only for trust dialogs, in directories mesh chose.
- **Other startup screens** (2026-10-25, Claude Code 2.1.310, herdr 0.8.2): a fresh pane in a repo whose `.claude/settings.json` has a malformed rule (ccswarm's `"Bash(rm -rf /)*"`) shows a **Settings Warning** after the trust dialog. `agent start` returns `agent_not_ready` within seconds for a screen like this (herdr keeps the name, status `blocked`), but mesh then waited for `idle` after the trust dialog, which never came: `herdr timeout` killed the spawn after the pane was up, with the doorbell unrung. Now `start_agent` classifies the screen (`startup_screen`): trust, a known blocking dialog (`STARTUP_DIALOGS`: a heading plus one of its own option or footer lines, so a diff quoting the heading doesn't match, as firstmate found), or unknown; after Enter mesh waits (bounded) for the trust dialog to leave the screen, since the dialog itself reads `blocked` and a state wait would return at once, and only then waits for idle, done or `blocked`, so a second screen is classified; a screen it doesn't know is read a few more times before it is held (a slow start, a state still showing the dialog's `blocked`), a CLI that exited at startup is an error with the pane's last lines, and `timeout` is never retried into a running CLI. mesh answers none but trust, even when the default (Settings Warning's "Continue") looks safe: what the user's settings say is the user's call. The message is stored and the worker marked `held`; the command exits 4 with the screen, like watch's exit 4. Messages sent meanwhile are stored without a ring (typing would answer the screen); a hold whose agent already reads idle or working (the user cleared the screen and prompted it) is stale, so `deliver` drops it and rings the first doorbell. The worker's own `mesh inbox` (not `--peek`) drops it too, since reading mail proves it got past the screen: otherwise a later permission prompt (`blocked`) or a lost registration (`unknown`) would look like the screen to `deliver`, which would store its mail without a ring. The watch, which the root runs anyway, rings the first doorbell once the agent reads idle and has unread mail (`mesh ring`'s rule), keeps the hold when that ring fails so the next poll or `mesh ring` tries the first doorbell again (after 3 polls its nudge does), and counts the start grace from that ring (taking `held` under the run lock, so two watches ring once), and stays quiet while it waits there, since the root was already told; an agent that exits instead reads as gone (5). The doorbell is the first one, with the worker's identity, because agy's conversation lookup keys on it.
- **Late messages:** doorbells that arrive while an agent is working are queued and handled after the current turn. They aren't lost.
- **Dirty worktrees:** a worktree with untracked files counts as dirty, and `mesh stop` keeps it. That's the safe default, and repos that ignore their caches don't hit it.
- **Typing can be lost silently.** A prompt typed while Claude Code was still redrawing after its trust dialog disappeared, and herdr reported success. Every doorbell now uses `agent prompt --wait --until working`: an idle agent that doesn't start working within 5 seconds didn't receive it, so mesh retries. A busy agent counts as delivered, because it queues the doorbell, but herdr doesn't always see it as busy (see "Duplicate doorbells" below).
- **Duplicate doorbells.** Busy panes got up to 7 copies of one doorbell: 1 try plus the 6 retries. agy's `history.jsonl` has every copy, so agy accepted each one. herdr counts agy as working only on its `esc to cancel` footer or a spinner, and an agy waiting on a long command shows neither; a Claude pane running a command queued the doorbell and herdr still timed out. So `ring()` reads the pane before retrying. A live check in both CLIs showed the queued doorbell above the input box (Claude Code: `❯ 📬 …` under the spinner; agy: `> 📬 …`, with its task panel under the box).
- **Drafts and concurrent prompts.** With herdr 0.8.2, Claude Code 2.1.310 and agy 1.4.7, `herdr agent prompt` over a draft appended to it and submitted both, with exit 0, and three concurrent prompts to one idle Claude pane were merged into one message, out of order. `--ansi` keeps the markers: Claude's input row is `❯` plus an NBSP (the submitted echo has a plain space on a grey background), its placeholder is dim (SGR 2) and was seen only before a session's first turn; agy's row is a blue `>` and shows no ghost text. Wrapped drafts continue inside the box on rows with a two-space gutter. Hence the draft hold and the per-pane lock in §3.
- **Idle blips mid-turn.** A reviewer that had thought for 6 minutes was reported as stopped (exit 3) while it was between two steps; 5 seconds later its pane showed `Running command...` again. A single idle reading was enough to alert. Now a worker must read idle for `--grace` seconds (30), and a `plan`, `question`, `done` or `failed` sent since its last task or answer counts as a report (an `info` doesn't end a turn), so a `done` sent just before the watch started isn't a silent stop either.
- **The turn-end guard.** A worker whose turn ends silently gets one nudge (claimed as a `nudge` event per task under the run lock, so a restarted or concurrent watch doesn't nudge again; a concurrent one waits `--grace` after that nudge before it alerts) before the root is alerted. The nudge, the watch's or the Stop hook's, names the task (`task_line`: its gist past the standard prefixes, or a review's first line): a worker compacted mid-task may no longer know which one it owes (repowire restored a body snippet in its reminders for the same reason). The watch is a subprocess and can't use `SendMessage`, so it can't reach a running `--bg` session.
- **The Stop hook.** A Claude worker's turn end is known the moment it happens, to Claude Code: every Claude worker (pane or `--bg`, on every launch, swap and resume) is started with `--settings` hooks, and its `Stop` hook runs `mesh hook stop`. When the worker has received a task, and has unread mail or has sent no `plan`, `question`, `done` or `failed` since its last task or answer, the hook prints `{"decision": "block", "reason": …}`, which keeps the turn going with the reason as its next instruction. It claims the task's nudge (`via: stop-hook`), so it blocks at most once per task and the watch doesn't nudge again (the watch then alerts "nudged once by its Stop hook"). Mail the worker hasn't read while its last task or answer is itself unread (an answer that lands as its turn winds down), or mail after a report, gets a block of its own that claims no nudge, once per set of unread files (`hook_mail`): spending the nudge there would leave the answer it then reads with none; it never blocks in plan mode (`permission_mode`, or a user-reviewed worker when that's missing). A turn that already continues because of a hook (`stop_hook_active`) gets no mail block without a new unread file, but can still get the nudge: a worker that reads the mail a block pointed it to and works on in that continuation, then ends silently, would otherwise lose the nudge the mail block kept. The nudge's once-per-task claim and the mail dedupe are what bound the blocks. Gas Town's version blocked at every turn on the same condition and filled the context; tmux-orchestrator's used `systemMessage`, which only the user sees. The reason tells a worker deliberately waiting on a background command to declare the wait and end its turn. A declared wait lets one turn end through, and the first after a wake gets one block (below). The hook command names the worker (`--run … --as …`), since only sessions mesh starts for it carry the hook, and it always exits 0: Orca's hook that exited 1 outside its tool broke every session. Claude Code shows a block as `Stop hook error: <reason>` in the pane; that label is cosmetic. The watch stays the fallback: agy (no hooks), a crashed session, a worker that ignores the block.
- **A declared wait** (firstmate). The live check showed both CLIs move a long command to the background and end their turn, so a long test run reads idle with no file changes: a nudge, then exit 3. `mesh send parent --type wait --until <time>` records a deadline (at most `MAX_WAIT`, 4 h, so a forgotten wait can't hide a stuck worker for a day) for the current task: until then the watch doesn't count idle time or raise 8 (a Claude usage limit is still looked for, once per `--grace` of idle), and the Stop hook lets the turn end without spending the task's nudge (unread mail still blocks it). A wait is in none of `REPORT_TYPES`, `RECEIVED_TYPES` or `FINAL_TYPES`, so nothing that asks "has it reported?" changes, and a new task or answer, or any report, ends it. It's refused while a task or answer is unread, since it would belong to that task (by the reports' check, `refuse_stale_report`, though `--unread-ok` lets only a report through). It rings no doorbell: it asks nothing of the root. A wait covers one turn end, the one that declared it; the first turn end after a wake ends it (`wait_over`), and that turn end is judged as if there had been no wait, with one reminder: the task's nudge if it's unspent, else `WAIT_OVER` ("send a fresh wait if you're still waiting"), once per wait. So the common case, a job that finishes early and wakes the worker, which works and then stops without reporting, is caught after one grace instead of at the deadline. "Seen working again" can't be the rule, since it would end the wait at the wake for the job's own completion, before the work it wakes for; blocking every turn end under a wait would be Gas Town's noise again; and a reminder only from the task's nudge would send a worker nudged before it declared its wait (the usual way in, since the nudge says to declare one) straight to the root on its first legitimate re-sleep. A worker woken for something else (one of several jobs, the user asking how it's going) costs one block and a fresh wait. Two log events carry the rule, each once per wait under the run lock: `wait_turn` (the declaring turn end, let through) and `wait_over`; `declared_wait` reads them as `turned` and `over`, and `waiting_until` (the hook, the watch, `mesh status`) holds only before both the deadline and `wait_over`. A Claude worker's Stop hook sees each turn end and logs both. For agy, which has no hooks, the watch logs them by observation (`Watch.agy_wait`): idle for `--grace` is the declaring turn end, a `working` reading after it a wake, and idle for `--grace` again `wait_over`, judged at once by `stopped()` (the nudge, or the `WAIT_OVER` doorbell when it's spent, then exit 3). A wake shorter than one poll, one within `--grace` of the turn end that declared the wait, or one no running watch saw (the wake is held in the watch's memory) is missed, and the wait holds to its deadline, which fails quiet. The watch never ends a Claude worker's wait by observation, since the hook runs first and is exact; so a Claude wait ends early only through its Stop hook, and a turn end the hook returns on before the wait rule (plan mode, a user-reviewed worker without `permission_mode`, a hook that didn't run) holds it to its deadline as before.
- **Is a watch running?** Each watch (`mesh watch`, and `mesh ask`'s own) holds a shared `flock` on `<run>/watching/<name>.lock` per worker, which the kernel drops when the process dies, so there's no stale pid file to judge. Per worker, and one more (`--any`) held by a running `mesh watch --any`, which re-reads the run every poll (`Roster`): a worker it doesn't watch joins, with its own `Watch` and lock, when it owes a report and wasn't raised as gone on that task (a gone one is then raised, exit 5, once), is `starting` (a spawn, resume or swap its start read as gone), or has a new `spawned` (spawned or resumed since); a retired one leaves, releasing its lock. Joining on what a worker owes rather than only on a new `spawned` is what keeps a worker the start-up snapshot missed from being dropped for good. Root-side commands warn about workers that owe a report and whose lock is free, unless the `--any` lock is held: every such worker joins at that watch's next poll, so the lock stands for the one poll before pickup (they still name a gone one at once), so the check costs a few file opens; only those few are asked whether they're gone, since `--any` leaves a gone worker out and the advice differs. Exit 5 logs a `gone` alert per task, and a worker alerted gone isn't warned about again until a new task or answer.
  - **No early exit between a retire and a resume.** An `--alerts` watch exits 0 once everything it watches has reported and ended or been retired, but a fix round or a new task for a worker is often `mesh retire` then `mesh resume` of the same worker, and the resume compacts first (up to `COMPACT_TIMEOUT`) before its entry changes. Exiting only on a poll where nothing changed wouldn't cover that gap, so the watch holds that exit (`settling`) while a worker is `retiring` (`retire_worker` waits up to a minute for its turn to end before it logs `retire`), while the run has a worker the next poll takes on, for `RETIRE_SETTLE` (2 minutes, the root's turn between the two commands) after a `retire` event not followed by that worker's `resuming`, and while a `resuming` event (logged by `resume_worker` before its worktree and compaction steps) has no matching `resume` or `resume_failed` (logged when the resume raises), bounded by `COMPACT_TIMEOUT` plus the settle. `settling` reads the run and the log afresh, since the poll's reads can predate a retire its ticks saw or a resume that ended meanwhile; it runs only on polls where every watch has finished. An `--any` watch started with nothing to watch waits the same way, then says `no live workers to watch`. Alerts and the timeout are unaffected; the cost is a watch that ends a couple of minutes later when the root really is done. Run-entry state (marking the old entry `resuming`) was the alternative: it needs clearing on every failure path of a resume, and a crashed `mesh resume` would leave it set, where an event ages out.
- **Evidence in exit 3/5.** The alert says what the branch shows (commits past `base`, pushed, an open PR by `gh pr list --head`, asked only when there are commits, a dirty worktree), so the root tells "finished and didn't say so" from "never started" without opening the pane. `work_evidence` is the same function as `mesh status`'s.
- **Reminders after a reset.** Gas Town's workers lost "report when done" to compaction (969083b4). A `SessionStart` hook for `compact`, `clear` and `resume` runs `mesh whoami --reminder <source>`, whose plain output Claude Code adds to the context: name, run, parent, run dir, the current task (its gist and file) and the phase (planning, plan or question waiting, executing, a direct or read-only task, reported). It logs a `reminder` event, and after a `clear` or `compact` reminder (or a pane worker's `rebind`) newer than its last task or answer, the worker's next `mesh inbox` shows the current task (its last `task` and the answers since) again, once (`inbox_again`; `--all`, which shows it anyway, marks it and counts too; only messages it had read are marked `again`), unless it already reported `done` or `failed` on it. The commands the reminder prints carry `--run … --as …`: a cleared background session has a new session id and no pane to be rebound by. A `--bg` copy (every background swap and resume) fires no `SessionStart resume`; its opening prompt, the "again" doorbell, says who it is and sends it to `mesh inbox`, so `startup` isn't hooked, which would also double every first doorbell.
- **Hook output is bounded and deterministic** (from the m6f06 memory-tools research, claude-mem's `ContextBudget`). Claude Code caps a hook's text (plain stdout, `additionalContext`, `systemMessage`) at 10,000 characters each; past it, the session gets the text saved to a file, its path and a 2,000-character preview, and nothing tells the model to read the file (Claude Code's hooks docs, "JSON output"). The Stop hook's `reason` isn't named there; it's held to the same cap. Both hooks are short by construction (a 160-character task gist, mail counted by type, fixed nudge texts), and `hook_text` cuts either under `HOOK_OUTPUT_MAX` anyway (less the newline `print` adds), from the middle at a line end, keeping the last line: the reminder's commands, which carry `--run … --as …` that a cleared background session needs; a test renders both over a 55k-character task and 200 unread messages. Neither carries wall-clock text (the reminder's only time is the stored message's own), so two renders of the same state match: claude-mem's minute clock in injected text was blamed for cache collapses (its #2872). Where it lands matters less than it might: the Claude Code source appends a `resume` hook's output after the history (`conversationRecovery.ts`, `messages.push(...hookMessages)`), and `clear`/`compact` start a new prefix anyway.
- **A worker that reads `working` forever.** herdr's `working` was taken on trust, so a hung tool call (firstmate's regex that hung one bash call for 25 h behind an unchanging "Working..." footer), a test or server in watch mode, or a registration herdr kept after the agent died, ended a watch only at `--timeout`. The footer's elapsed-time counter changes the pane every poll, so pane hashing can't tell. The transcript can: Claude appends to its session file on every tool call and result, so a long but live turn keeps it moving and a hung call stops it cold. agy's conversation db (with its `-wal` and `-shm`, since the WAL vanishes at a checkpoint) and its `--log-file` stand in for it; the newest mtime counts. A live check (2026-10-25) showed both CLIs move a long command to the background (agy after 10 s) and end the turn, so such a worker reads idle or done, not working: exit 8 is left for real hangs. After `--hang` seconds (40 min) of silence since the last task or answer, with nothing reported since (a worker that reported may leave a stale `working` behind), the watch exits 8 once per task with the pane tail, or 5 when the pane shows only a shell. It never stops the worker: a turn can legitimately run that long.
- **Reports nobody read.** The watch's baseline is the finals already sent, so a `done` sent while no watch ran (its doorbell lost, or the root's session gone) was never returned, and an unread `plan` left the watch waiting for an answer nobody would give. The mailbox is the queue and `mesh inbox` the acknowledgement, so a watch now starts by returning on any report from a watched worker still unread in its parent's mailbox, with no new state; `--alerts` too, which is the case of a lost `SendMessage`. `mesh ask` keeps its own baseline and reads the reply itself.
- **Turns the watch never saw.** The watch first judged a turn only after a `working` reading, so a worker idle from its first poll was never nudged: a turn shorter than one poll that ended silently, a task it never picked up, or a watch started after the turn. Now a worker that reads idle for `--grace` while its last task or answer is 4 × `--grace` old (taken from the log, not the watch's start) with nothing reported since goes through the same nudge-then-alert. The grace is longer because nothing proves its turn started: a pane boots, a doorbell retries, a root passes a background worker's `send_message` on. A plan or question sent since still means it is waiting, however long, and the alert says when its task or answer is still unread. Exit 3 logs an `alert` event per task (under the run lock), and this path skips a task that has one: otherwise the root, restarting its watch after the alert as ORCHESTRATE says, was alerted again every `--grace` (a background worker, which isn't nudged, at once). A `working` reading or a new task or answer re-arms it.
- **`agy models` hits the network and can hang**, and it ignores SIGTERM. One failed TLS handshake to Google stalled a spawn. The list is now cached for 6 hours, a stale cache is used when a refresh fails, and an exact model id skips the lookup.
- **Side effects come last.** A spawn that failed while resolving the model had already created its worktree. Everything that can fail without side effects now runs first.
