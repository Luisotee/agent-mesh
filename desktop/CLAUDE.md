# desktop/: rules for agents

The desktop app: Electron, React and TypeScript, styled with Tailwind and shadcn/ui-style components on Base UI. It is a client of the daemon (`daemon/`), step 2 of `docs/apps.md`, and nothing here is installed or put on PATH. `README.md` is the full reference (what the app does, the host bridge, trying it by hand); `docs/apps.md` has the plan and what is decided ("Stack", "Decided"). context7 and WebSearch/WebFetch are available to every agent: the stack (Electron 45, React 19, TypeScript 7, Tailwind 4, Base UI, Vite 8, Vitest 5) is newer than most training data, so check its current API there rather than from memory.

## Toolchain

Node (from nvm) and pnpm 11, both on PATH. Run every command from `desktop/`. `pnpm install` also fetches Electron's binary. `pnpm gen` and the e2e tests also need buf and Go, which are off PATH (`daemon/CLAUDE.md`, "Toolchain"); `scripts/check.sh` adds them itself.

## Commands

```bash
scripts/check.sh              # the CI equivalent: locked install, generated code current, typecheck, tests, build, e2e (waits for room in the host-wide gate queue before the typecheck: root CLAUDE.md, scripts/gate-slot.sh)
SKIP_E2E=1 scripts/check.sh   # without the end-to-end tests
pnpm test                     # unit tests (vitest, jsdom): src/**/*.test.ts(x) and electron/**/*.test.ts
pnpm test src/store.test.ts   # one file
pnpm typecheck                # the renderer and the main process (two tsconfigs)
pnpm gen                      # TypeScript from ../proto after a .proto change
pnpm build && pnpm e2e        # the end-to-end tests: the built app over CDP, against a real meshd
pnpm pack:win                 # a Windows zip (builds on Linux without wine); the NSIS installer (`pnpm pack`) needs wine or a Windows host, see README "Packaging"
pnpm pack:dir                 # the unpacked installer app in release/ (electron-builder.json; `pnpm pack:check` builds the deb and checks its agentmesh:// entry, opt-in)
```

The e2e tests open a real Electron window. `pnpm e2e` (and `scripts/check.sh`) runs `scripts/e2e.sh`, which puts it on a virtual display with `xvfb-run` when installed, `DISPLAY` set or not: never set `DISPLAY=:0` to see it, since under WSLg that is the user's Windows screen. `E2E_VISIBLE=1` uses `DISPLAY` instead; without xvfb `DISPLAY` is required. They build meshd, mesh-term, mesh and the fake claude from `daemon/` into a temp dir and give every run its own state dir, HOME and user-data dir, so they touch nothing of the user's. Run `scripts/check.sh` before you report a change here: the repo runs no hosted CI.

## Layout

- `electron/`: the main process, kept thin: `main.ts` the window (`window-input.ts`: zoom, the text menu and find in page, pure), `bridge.ts` and `socket.ts` the host bridge, `route.ts` and `pair.ts` how a paired host is reached (pinned TLS, direct or through the relay) and how a pairing link is redeemed, `hosts.ts` the saved host list, `local.ts` finding the daemon on this machine for the first run (a state dir, or a WSL distro through `wsl.exe`; the renderer passes ids, main runs fixed commands), `links.ts` pairing links the OS opens the app with (read in main, shown for the user to confirm, never redeemed on their own), `shell.ts` notifications and the tray (it knows nothing of agents), `preload.cts` the API the renderer gets.
- `shared/api.ts`: types only, the contract between main and the renderer.
- `src/`: the renderer. `transport.ts`, `connection.ts`, `store.ts`, `refresh.ts`, `derive.ts`, `cli.ts` (the CLIs a host says are installed (`HelloResponse.clis`, else those it has tiers for), by name), `usage.ts` (the usage and cost screen's rows), `actions.ts`, `workspace.ts` (tabs and the dock's marks), `dock.ts`, `sidebar.ts` (the one sidebar's projects across hosts), `commands.ts` (the palette's entries and the shortcuts' commands), `keys.ts`, `shortcuts.ts`, `transcript.ts` (the chat: an agent's view, its mesh messages inline), `notify.ts` (a host's `UserNotice` event as a notification: the host decides what notifies, the app only shows it and lists every notice in `components/activity-list.tsx`), `shells.ts` (a project shell's tab is a tab whose id is `shell:<terminal id>`; `components/shell-panel.tsx` shows it), `composer-keys.ts` (the markdown field's keys, `components/ui/markdown-field.tsx`), `composer-commands.ts` (the composer's `/` popup rules, pure; the hooks are `components/composer-assist.tsx`, the popup `components/command-popup.tsx`), `attachments.ts` (images in a prompt, which CLIs take images and rewind), `highlight.ts` (the chat's code highlighting), `components/` (shadcn-style primitives in `components/ui/`), `terminal/session.ts` (the terminal stream protocol, with no xterm or Electron in it), `theme.ts` (loads the six theme files of `../shared/themes/`, shared with Android, and applies the host's `app.theme`).
- `src/gen/`: the generated TypeScript (committed).
- `electron-builder.json`: the installers (a `protocols` entry registers `agentmesh://`); `scripts/check-package.mjs`: the opt-in deb check. Only `ws` and `electron-updater` (`electron/updates.ts`, installed apps only) are `dependencies` (the main process's); everything the page uses is a `devDependency`, as Vite bundles it.
- `e2e/`: the end-to-end tests and their harness.

`README.md` "Layout" says what each file holds.

## Conventions

- **Styling:** Tailwind classes and shadcn/ui-style components on Base UI only. No CSS beyond Tailwind's one entry file, `src/index.css`. The primitives in `src/components/ui/` are copied into the repo so we own them: restyle them there rather than wrapping them. Colours are theme tokens (`theme.ts`), not literals; a theme is a JSON file in `shared/themes/`, never CSS. A project's colour is its identity hue (`hue.ts` `hueStyle` on the element, then `*-identity` classes), a vendor's is `*-vendor-<name>`, waiting on the user is `glow`; `theme.test.ts` holds every theme to 4.5:1 for muted text and 3:1 for these. Text is 12px or more (the letter in a vendor badge, an icon, is the one exception), meta is `Chip`s (not "a · b · c" strings), loading is a `Skeleton`, and a hint on an icon button is a `Tip`. Motion answers the user (rows and tiles coming and going: `m.*` under the app's `LazyMotion`, popups by Base UI's `data-starting-style`/`data-ending-style` transitions) and always has a reduced-motion form. The theme follows the selected host's effective `app.theme` (its default included); Android follows the first host that set one itself, so with several hosts the two may differ.
- **The renderer never reaches a host.** meshd refuses any request with an `Origin` header, and a token in the renderer would defeat that. The main process holds the tokens and forwards calls (`electron/bridge.ts`, `electron/socket.ts`). Keep the renderer sandboxed, with context isolation, its CSP, no navigation and no new windows.
- **A paired host's certificate pin is the whole check.** `electron/route.ts` hands a connection on only after its leaf certificate matched the pin from the pairing link; never add a fallback to an unpinned or unverified connection, and keep the pairing link's parsing in main (the renderer sends text).
- **Every call to a host** goes through `src/actions.ts` and must be a `MeshService` action a device may call. Only `src/transport.ts` reaches the network. `src/registry.test.ts` checks both, so a new call starts in `actions.ts`.
- **The palette and the shortcuts run commands** (`src/commands.ts`): one that acts on a host calls a function of `actions.ts` (`commands.test.ts` runs them against a recording client), the rest only change what the window shows. A shortcut is an `app.keys.<id>` host setting (`prefs.ts` `DEFAULT_KEYS` mirrors the daemon's defaults; a new one is a leaf in `AppLeaves` and a command in `keyedCommands`). `shortcuts.ts` `commandFor` leaves a Ctrl+letter key to a focused terminal (the same key with Shift runs it, ahead of a command bound to that Shift form; Cmd always runs it, as a macOS shell never gets Cmd; main's zoom keys follow the same rule, told by `terminalFocus`) and a key without Ctrl or Meta to a field being typed in. A row's actions are one `MenuEntry` list (`components/ui/menu.tsx`) that the right-click menu, the ⋯ button and Shift+F10 all open. Chat and terminal both reach one agent process: the composer is `PromptAgent`, never a message or a second process. An agent's views are its chat and, by the tab bar's Chat | CLI switch (a split pane's title row has its own), its own CLI (`AgentTab`); there are no other sub-tabs. A multi-line field a person writes to an agent in is a `MarkdownField`. The composer's commands and Claude's suggestion are the host's (`ListAgentCommands`, `GetPromptSuggestion`): the app keeps no command list of its own. Markdown is `components/markdown.tsx` only (Streamdown with `skipHtml`, no images, links through `openExternal`): keep those three when it changes.
- **Local detection runs only fixed commands.** `electron/local.ts` takes an id and one of two fix names from the renderer and runs fixed argv (`wsl.exe -d <listed distro> -e sh -l -s` with the script on stdin, `mesh pair` inside the distro); never build a command from renderer text. A change to what it runs updates `README.md` "The first run" and its tests.
- **The UI has no abilities of its own** (`docs/apps.md`, "Principles"): anything the UI does is an action an agent or the CLI can call too. A new capability is a registry action first (`proto/CLAUDE.md`).
- **State** is built from the snapshot and events (`store.ts`). What the host derives, the app asks the host for rather than deriving it twice: what waits on the user is `ListWaiting` (`refresh.ts` lists it again after the events that change it), kept as `waiting` (the rows for the user, `for_user`: the list, the counts and marks) and `waitingAll` (every row: the chat's open cards, since a user may step in for a lead that decides a plan), the held permission prompts are `ListPermissions` (listed again after a `PermissionChanged` event; the host keeps them in memory only), an agent asking to show a view is an ephemeral `view` frame (`model.ts` `offerView`: a toast, or an automatic switch only with `app.open_views` on and never while the user types), and an agent that went quiet shows as `unknown` only when the agents are listed again (every 30 s).
- **The window's layout is device-local:** the open tabs, panes, the folded sidebar, the projects taken off it and the panels are kept in the renderer's own storage (`layout.ts`, never sent to a host), and restored minus agents the host no longer has once its first snapshot arrives (it also keeps the dismissed dock tiles and the pinned projects, per host); what other devices or agents should see belongs in an `app.*` host setting instead.
- **App preferences are host settings:** a new `app.*` row is a leaf in the daemon's `internal/settings/schema.go` (`AppLeaves`), with no action or event of its own. The settings screen is generated from the schema (`settings-form.ts`, `components/settings-panel.tsx`): a new leaf needs a `Label`, a `Group` and, if it is tuning, `Advanced`, and no desktop code; a shortcut's label names the action in the palette's words, without its state ("Live dock" for "Show the live dock"). The per-repo lists are not rows (`PER_PROJECT` in `settings-form.ts`): they are set in the project settings dialog.
- **Generated code:** never edit `src/gen/` or `electron/icons.ts` by hand. Regenerate them with `pnpm gen` and `node scripts/make-icons.mjs`.
- **Code style:** follow the existing code: single quotes, no semicolons, two-space indent (`@/` resolves to `src/`). There is no formatter or linter, so `pnpm typecheck` and the tests are the gate.
- **Trying it by hand:** give meshd a temp state dir, as `README.md` "Trying it by hand" shows. Never point the app at the user's real state dir.
- A change to these commands, the layout or the conventions updates this file in the same PR.
