# desktop

The agent-mesh desktop app: Electron, React and TypeScript, styled with Tailwind and shadcn/ui-style components (Base UI), no CSS beyond Tailwind's one entry file. It is the second step of `docs/apps.md` ("Order of work"); the plan, the principles it follows and what is decided are there. Nothing here is installed or put on PATH.

The app is a client of the daemon (`daemon/`). Everything it does to a host is a call on the host's action registry (`proto/`, ConnectRPC with generated clients), so an agent or the CLI can do all the UI can. It has no account, no hosted service and no telemetry, and talks only to the hosts it is told about.

## What the first version does

Hosts (a daemon on this machine by its state dir, or another machine by a pairing link: the app redeems the one-time link for its own device token and reaches the host over TLS pinned to the host's certificate, directly or through the relay; a loopback address with a pasted token saved by an earlier version still works), a connection per host with a banner and a log, and the lead-agent view: each run as a tree from its lead, workers and their read-only agents under it, each row with its role, a plain status sentence, repo and model, and a state icon whose shape differs by state. An idle agent says what it really waits on in the chat's status line (`GetAgentProgress`'s `wait`, read while it is idle: its background job, a wait it declared and until when, the answer it asked for, a report it sent, or a message and from whom), not one fixed "waiting for a message". The side panel's pull requests list the open ones, and fold the merged and closed under a count, with the checks as an icon. The sidebar is one list of the projects of every connected host (`sidebar.ts`): a project is a repo a run is led from or works in, or one the user pinned (the sidebar's Add a project +, which checks a typed path with the host first, or its menu's Pin), pinned first, then those with something waiting on the user, then by latest activity. The same folder on two hosts is two projects; with several hosts a project not on this machine has a host mark whose tooltip names it, and a host that is down greys its projects out and says why. A project holds its runs as their leads (the run's title, the lead's state and what it does), the lead's workers folded under it, a worker in another repo tagged with that repo (whose project lists the run under "Also working here"), and its closed or finished runs under "Earlier". Reviewers and askers are a chip on the agent they work for ("2 reviews"), an archived agent leaves the sidebar, and a project can be taken off it (device-local; it comes back while something in it waits on the user). Right-click, the row's ⋯ or Shift+F10 opens a row's menu: a project's (New lead here, Project settings…, Pin, Copy path, Remove from the sidebar), a run's (Open, Rename, Add an agent, Copy run id, Stop run… (every agent retired, the run closed: confirmed first), Delete… (an ended run only, offered where the host has the `delete_run` capability: the host forgets it with its messages and files and keeps any work in git, and says what it kept; a project's menu has "Delete N ended runs…" for the ones under Earlier; no undo, which the confirm says), and its lead's entries) and an agent's (Open chat, Open its terminal, Send a message…, Copy worktree path, Shut down, Retire, Archive…, the last three confirmed first). Project settings set the project's autonomy level (the host's `repos.user_merges` and `repos.user_approves_plans` lists: handled as before, I merge, I approve plans and merge; a new run starts from it), whether its code may go to OpenCode's free models (`repos.no_free_models`) and its pin. The search field at the top opens the palette (also Ctrl+K, or / outside a text field), and Ctrl+B folds the sidebar to a strip of project tiles. Its footer has each host's quota, a section per provider (its mark, then a bar per window labelled "5h" or "7d" with its percent and a line at the reserve, `quota_stop`; the window in words, the reset and the reserve are in its tooltip; Claude's Opus and Sonnet windows and an agy pool no tier uses stay out until one is at the reserve, and a click opens Usage and cost, which has them all), Settings, and the Hosts menu (connect a host, pair a device, remove a host, and each host's settings when there are several). A new lead starts from a tab's +, a project's menu, Ctrl+T or the palette, and a project from the + beside Projects: one way each. The panel's agent tree and the live dock list the live agents only (working, starting, needing input, limited, failed or unknown; an idle one only while it waits on an answer to its question or plan; a run's lead and the open agent always) and keep the rest behind "N resting" (`active.ts`). Watch all's tiles say a worker whose PR is open and not a draft is ready to review, one whose PRs are all merged or closed is done, from the host's `ListPullRequests` (read at connect and every minute, and kept by `PullRequestChanged` events). The agents open as tabs, one tab bar per project (the open agent's project's tabs, each project keeping its own, with a + that starts a lead in it), and any of them can be shown in a pane beside the open one (the tab's split button, the dock tile's pin, or the palette: up to three beside, side by side or stacked, each on its own view; a pane's header makes it the main one or closes it, the tab stays open). The open tabs, their views, the panes, the folded sidebar, the projects taken off it and the dock are kept in the window's own storage and put back at the next start, minus agents the host no longer has (`layout.ts`). A side panel beside the open agent (toggle: the button at the end of the tab strip, Ctrl+Alt+B or the palette; kept with the layout) shows the agent's whole tree first (its run's lead, the workers and their reviewers and askers, with their state; a click opens one), then the pull requests (a lead's: its workers', open first, with their checks; a click opens one in the browser), the cost folded to one line ("Run total $4.12", per agent when opened; `GetCost`, read again every 30 s; another agent's is its share), and, folded, its model history and its details (project, host, role, branch, worktree, session and ids, the model, read-only, a terminal button, copy the worktree path). "Watch all" (the dock's button, or the palette) shows every live agent of the open runs, on every host, as a grid of tiles, those that need you first: each with its state, repo, run and its last few lines of conversation (read again every 8 s while it works); a click opens the agent, the tile's pin shows it beside the open one. The side panel's PR rows have a Comment box that sends the text as a task to the agent that wrote the PR. New workspace (New lead from a tab's + menu, a project's New lead, Ctrl+T, or the palette) picks a project from the host's list (`ListProjects`: the folders of `repos.dir` and the repos agents used; the list narrows as you type, a project can be pinned to the top (kept with the layout, per host), and a path can be typed), where to start (its default branch, a branch, or an open PR's branch, after the host fetched) and the run (a new one, or an open one), and starts the agent in a new worktree and opens its chat. A run can start with autonomy of its own (the New run and New workspace forms: the host's settings, or a level for the run, and lines the lead asks about first: `StartRun`'s `autonomy`); the host's own "always ask me before" list (`autonomy.ask_before`) is edited in Settings. A run's title is renamed in place in the sidebar (its menu's Rename, F2, or the palette: `RenameRun`). When `gh` is missing or logged out on the host the sidebar says why no pull request is read. The side panel also lists the models an agent ran on (`GetAgent`) once it ran on more than one, its plan progress (`GetAgentProgress`: Claude's todo list; the conversation's size against the model's window is the meter in the chat's composer), the files it changed with what is uncommitted or on no remote (`GetAgentChanges`), an Open in editor button on the host's own device (`OpenInEditor`: the host's `editor.command`), and, for a worker, Archive (retire it and remove its worktree, keeping the branch: blocked by uncommitted work, confirmed for commits on no remote; lists the git-ignored files it would delete, with sizes, from `GetAgentChanges` `with_ignored`; not offered to a read-only device, a root, an asker, a reviewer, a peer or an adopted session) with Restore for an archived agent (`ResumeAgent`; a repo's `.worktreeinclude` files are copied back). The Pair screen's Tailscale section turns the node on or off after a confirmation (`SetTailnet`: meshd restarts itself under a service manager, and the app reconnects). The side panel has a Hold merge button on each open PR (`HoldPullRequest`: a root never merges a held PR). Every agent's CLI, model and effort show with the vendor's mark in the sidebar row, the dock tile, the Watch all tile, the tab and the side panel (read-only there), and the composer's model picker moves the agent to a tier, a model of the host's list for its CLI (`CheckModels`) or an effort alone through `SwitchAgent` (the host reopens the same conversation; its refusals are shown in its own words, and a reopen under way as "Switching to …"). It starts runs, spawns agents, messages and stops them. Each agent has a terminal (xterm.js on the daemon's terminal stream, attached once its box is laid out so the host repaints at its real size: it takes typing, keeps its screen across a daemon restart, searches, opens links in the browser). An agent's mesh messages (a run's stored messages are read from the host when one of its chats is first shown, not at connect) show in its chat where they were sent, as cards for plans, questions and reports (Markdown, no raw HTML or images, links in the browser), and the doorbells that announced them go once they are read; a plan or question to a run's lead that nobody answered is listed under "Waiting on you" (with the agents stopped at a prompt) and counted on its project's badge (the host says what waits, `ListWaiting`, and the app asks again after the events that change it; an agent that went quiet shows as unknown because the agents are listed again every 30 s), and the user approves a plan, asks for changes or answers a question in place: an `answer` message to its author, recorded with the device as its actor (also from a Watch all tile, which shows the plan or question and the same form). An agent stopped at a permission prompt the host holds for its lead (`ListPermissions`, listed again when a `PermissionChanged` event comes) has Allow and Deny there instead of the terminal row (a denial needs a reason: the agent reads it); the lead may answer first, and then the row says it was already answered. On the host's own device, a Pair a device screen (Pair a device in the Hosts menu) makes a one-time link and QR code for another app, says which device used it (the host's `DevicePaired` event carries the pairing id), lists the paired devices and revokes any of them. The same screen has a Tailscale section for the host's built-in node (`meshd --tailscale`, `TailnetStatus`): its state, the login URL as a link and a QR code while it needs one, its addresses and problems, and a button that puts its tailnet address (or its MagicDNS name) into the pairing link form; it says the node is off when meshd runs without the flag. A `agentmesh://pair` link the operating system opens the app with (as an argument at launch, to a running app by the single-instance lock, or macOS `open-url`) opens the add-a-host form filled in; it redeems nothing until the user presses Add host. The installers register the scheme with the OS ("Packaging" below). A Usage and cost screen (a click on the quota in the sidebar's footer, or the palette) asks `GetUsage` and `GetCost`, the actions behind `mesh usage` and `mesh cost`: each Claude quota window as a bar with the reserve line and its reset, agy's quota rows and what each tier would start on, a warning naming what is at the reserve (the host's own list for Claude, `min_quota` for agy), and the tokens used in the last 24 hours, 7 or 30 days or one run (the total of input, cache writes and output as the main figure with the cache reads apart, then by CLI with how exact each CLI's counts are, kind, model and phase, review findings, optionally per agent; Claude's API-equivalent dollars are a secondary figure and a trailing column). The quotas are read again every minute while the screen is open; the spend is read when the screen opens, the span or run changes, or Refresh is pressed. The themes (Dracula, Alucard, Catppuccin Mocha and Latte, Tokyo Night, Nord: the files of `../shared/themes/`, with a font and a density each) follow the host's `app.theme` setting. The look: Geist and JetBrains Mono are bundled (`@fontsource-variable/*`, no font is fetched), the type runs 12 to 22px with nothing under 12, each project has a hue of the theme's eight (`hue.ts`, by its repo path: the sidebar's thread from a lead to its workers, the open tab's underline, the dock and Watch all tiles, the chat's own bubbles and the composer's ring), each vendor's mark is in its brand colour, an agent waiting on the user glows (`glow`), meta shows as chips, skeletons stand in for what is loading, and motion (`motion`'s `LazyMotion`, dialogs and tooltips by Base UI's transitions) answers what the user does and stops when the system asks for reduced motion. A Settings screen (the gear in the sidebar's footer) is generated from the schema the host sends: every setting has a `label`, a `group` and an `advanced` flag there. A nav of the groups (Appearance, Notifications, Shortcuts, Agents and models, Reviews, Projects and autonomy, Limits and quota, Delivery) with counts, a search over label, description and key (every word must match; it lists the matches of every group), and per setting a row with its label, a one-line description (a long one behind More), a control by type on the right, "Reset to default" only when set, and the key in small type on hover with Copy, for whoever drives it from the CLI. Themes are swatch cards, shortcuts a two-column table (action, keys to press), the advanced settings of a group are folded, and the per-repo lists (`repos.user_merges`, `repos.user_approves_plans`, `repos.no_free_models`) are a row of links to each project's own settings (the dialog of the sidebar's project menu), not raw lists. The host's own check shows on every value; live changes from agents and other devices (`settings-form.ts` holds the grouping and search, `components/settings-panel.tsx` the screen). A host that sends no label or group (an older daemon) is listed by key under Other. Native notifications (an agent stopped at a prompt, in error or at its usage limit (the last only when asked for), a plan or question or report or failure sent to a run's lead; only live events, never history replayed after a reconnect, never what the user did, one per agent replacing the last) and the tray (an icon that shows when something waits on the user, a menu, and the window hiding to it on close, when asked for) follow the host's `app.*` settings.

The workspace: open agents are **tabs** across hosts (each keeps the view it was on; every tab has the same width, narrowing only when many are open, so nothing moves under the pointer; right-click or Shift+F10 on a tab opens its menu: Send a message, Show beside, Close, Close others, Close to the right, Reopen closed tab, Copy name, Rewind…, Shut down). The **+** follows the last tab: a plain agent of each CLI the host has (like running `claude` in a terminal: a run of its own, a root with no task in a worktree on a branch of its own, launched with the host's skip-permissions flags; `SpawnAgent.plain`, which the host never resets, compacts or briefs), New lead…, New terminal, and the project's terminals that no tab shows. A project with no run offers Agent, Lead and Terminal in the sidebar. What failed shows as a toast at the bottom left. The **live dock** along the bottom follows the open agent's tree: a tile per live agent of its run (with no agent open, the live leads of every host; a reviewer or asker is a chip on the agent it works for), with its state, the tool it runs now (an ephemeral frame from the host), when it last did something and what it last sent; a worker that starts while the app is open pops in marked new, never takes focus, and `app.dock.new_agents` says whether it does that, only counts on the dock's toggle, opens as a background tab or does nothing. A click opens a tile as a tab; the × hides it until its agent's state changes. The **chat** is an agent's view: it has no header of its own: the agent's state and name are on its tab, and the tab bar's end holds a **Chat | CLI** switch that shows the agent's own CLI in the chat's place for its prompts and dialogs (Ctrl+Shift+J; a pane beside the main one carries its own in a title row with its name) and the agent's menu, the same list as the tab's right-click menu (Send a message, a mesh message as an agent sends one, in a dialog; Rewind; Shut down, which ends the agent's CLI, where the composer's Stop interrupts one turn). "Terminal" is the project's shell tab only. It shows the conversation from the CLI's own record (Claude Code: the prompts as bubbles in the project's hue, the replies as prose, tool calls folded with their results and shimmering while they run; the other CLIs say so and keep the terminal), with the time, Copy and Quote in a reply on hover, reads on as the agent works, and its composer types into the same running process (`PromptAgent`: Enter sends, Shift+Enter adds a line; a read-only device can't). The composer is one rounded box: the field, and under it a toolbar with the image button and the **model picker** (the vendor's mark and "sonnet · high": a menu of the host's tiers, the models it lists for the CLI (read when the chip is first used), "Other model…" for an id it doesn't list (a text field) and the efforts, each pick one `SwitchAgent` that reopens the same conversation; while a reopen is pending the chip says "→ opus", and the host's refusal shows as a toast; `components/model-picker.tsx`, the one place to change the model) and, at the right, the **context meter** (a short bar "84k / 200k" against the model's whole window, with a tick where the host acts on the conversation, `GetAgentProgress.marks`: a lead's reset or a compaction; amber from the first tick, red from 90%; the tooltip names each). A prompt shows at once as a bubble marked "sending…" until the record has it, sending goes to the end of the chat whatever the reader was at, and a "Jump to the end" pill (with the count of new entries) brings back a reader who scrolled up. The chat's blocks are `memo`ized (`sameBlock` in `transcript.ts`: the record is read again as the agent works and every block is built anew, so an unchanged one is a new object), and a long conversation draws its newest 60 blocks first (a page the host reads holds hundreds, and drawing them all was what a tab switch waited for): "Show earlier (N more)" draws 60 more above without moving the reader, then "Load earlier" asks the host for an earlier page (find in the window sees only what is drawn; a plan or question waiting on you is always drawn above the window); what the worktree actions (Open in editor, Restore) did is a toast. Markdown everywhere is Streamdown (a reply cut mid-way still reads right) with code highlighted by Shiki in the theme's terminal colours (`highlight.ts`: 18 languages, each loaded the first time it shows, no WASM). Every multi-line field written to an agent (the composer, a message, a PR comment, a plan's changes, a task) is a markdown field (`composer-keys.ts`): Enter continues a list, Tab indents a list item or a selection (elsewhere it moves the focus on), Ctrl+B, I, E and K make bold, italic, code and a link (the app's shortcuts on those keys run with Shift added there), and it grows with its text. What was being written to an agent is kept on this device until it is sent (`layout.ts`, `agent-mesh.drafts.v1`). A send is never refused for what the agent is doing: while it works, starts, waits at a prompt or has a draft in its box the host queues it, and it shows dimmed under the conversation with what it waits for until it is typed at the agent's next idle (`ListPrompts`, kept by the host's `Prompt*` events); its pencil takes it back to edit, its × drops it, a prompt held by a draft in the agent's box offers Send anyway (it names the draft the host read, `SendPromptAnyway`: the box is cleared and the prompt typed, refused if the draft changed or someone types in the terminal), and Up in the empty composer takes back the newest (`WithdrawPrompt`, refused once the host is typing it). While the agent works, Esc in the composer or the Stop button interrupts its turn (`InterruptAgent`, Claude Code only), and what is queued goes next. An image pasted, dropped anywhere over the chat (an overlay says so) or picked with the composer's image button (PNG, JPEG, GIF or WebP, up to 10 MB) is stored on the agent's host (`AddAttachment`) and shown as a thumbnail; the prompt names its path for the CLI's file tool (Claude Code and agy; the others say they aren't checked yet), and the sent prompt shows the image (its name on another device). Esc Esc in an empty composer at an idle agent, or the menu's Rewind…, takes the conversation back to before one of its prompts (`RewindAgent`, Claude Code only): the dialog lists the prompts, says files and commits aren't rolled back and lists the mesh messages sent since, and the prompt comes back into the composer (`components/rewind-dialog.tsx`, `attachments.ts`). Both keys are the host's `app.chat_keys.interrupt` and `app.chat_keys.recall` settings (a key alone may be one, as they act only in the composer; Settings records them). The **command palette** (`Ctrl+Shift+P`, `Ctrl+K` or the sidebar's search field) lists every agent, run, host and waiting item to go to and the registry actions for them (start a run, ring, retire, shut down, approve a plan, move to the next model), asks for a title or a confirmation where it needs one, and filters as you type. The palette also renames a run, adds an agent to an open run (the New workspace form on it) and opens the settings on a section. A tab dragged to an edge of the main pane opens as a split there (left and top make it the main pane). An agent or the CLI can ask the app to show a view (`OpenView`: an agent's chat or terminal, its messages or its newest plan in its chat, a pull request's owner with the side panel, a run, the settings): the app shows a toast naming who asks and what, with Open and Dismiss, and never switches your view by itself unless the host's `app.open_views` is on (only you can set it), and then not while you type in a terminal or a field. **Shortcuts** are the host's `app.keys.*` settings (palette and search, settings, dock, the chat/terminal toggle, the next and previous tab (Ctrl+Tab, Ctrl+PageDown), a tab by its place (Ctrl+1…8, Ctrl+9 the last), close the tab (Ctrl+W), a new lead in the open agent's project (Ctrl+T), reopen the last closed tab (Ctrl+Shift+T), fold the sidebar (Ctrl+B) and open its next or previous agent (Alt+↓, Alt+↑), the side panel (Ctrl+Alt+B), find (Ctrl+F), rename the open run (F2), put the cursor in the message box (Ctrl+L; in a terminal on Windows and Linux Ctrl+L is the shell's clear-screen, so Ctrl+Shift+L there; Cmd+L on a Mac always runs it), the next thing waiting on you). In a focused terminal a Ctrl+letter key goes to the shell and the same key with Shift added runs the shortcut (Ctrl+Shift+W closes there, Ctrl+Shift+T starts a new lead rather than reopening a tab), find opens the terminal's own search, and a key without Ctrl (F2, Alt+↓) does nothing while you type in a field or a terminal. They are recorded by pressing the keys in Settings (the palette's "Keyboard shortcuts…" opens them) and followed live when another device or an agent changes them. A tab carries the vendor's mark beside its state, and a quiet dot when its agent finished a turn while another tab was shown (not on screen in the main pane or a split), until it is opened; the open tab is underlined in its project's hue over a soft gradient of it. Motion is small and follows the system's reduced-motion setting: a tab fades in and out, the side panel slides, a worker's row and a changed state icon fade in, a sent prompt rises in, and the composer lifts a little with a wash of the project's hue while it has the focus. The sidebar's rows, the tree's rows and the chat's blocks are `memo`ized, so one agent changing redraws its own row: `src/perf.test.tsx` counts what a change redraws for a host of 40 agents (a sidebar row change went from 40 rows to 1, about 36 ms to 7.5 ms in jsdom) and prints the times with `PERF=1`. Tabs: a middle click closes one, the wheel scrolls the strip, a drag onto another tab moves it there. The main process handles zoom (Ctrl+= or Ctrl++, Ctrl+-, Ctrl+0; kept in the user-data folder; in a focused terminal those keys are the shell's, Cmd's still zoom on a Mac), the text menu (in a field: spelling suggestions, Add to dictionary, Cut, Copy, Paste, Select all; on page text: Copy, Copy link) and find in page behind the find bar (`electron/window-input.ts`).

## Layout

- `electron/`: the main process, kept thin. `bridge.ts` is the host bridge (below), `hosts.ts` the saved host list, `main.ts` the window, `window-input.ts` what it does with zoom keys, right-clicks and find in page, `preload.cts` the API the renderer gets (`window.desktop`, from `shared/api.ts`).
- `electron/local.ts`: finding the daemon on this machine, for the first run (below): a state dir on Linux and macOS, a WSL distro through `wsl.exe` on Windows; the renderer gets `window.desktop.local` (`detect`, `connect`, `fix`) and passes ids, never commands.
- `electron/links.ts`: the pairing links the OS opens the app with: checked with `parsePairingLink`, kept until the window takes them (`links:take`), never acted on without the user.
- `electron/shell.ts`: notifications, the tray and what closing the window means; it knows nothing of agents (`shell-rules.ts` holds its checks). `scripts/make-icons.mjs` draws the tray icons into `electron/icons.ts`.
- `shared/api.ts`: types only, the contract between main and renderer.
- `src/terminal/session.ts`: one terminal's stream protocol (attach modes, replay, `Ready`, resume by offset, backoff), with no xterm or Electron in it; `components/terminal-view.tsx` wires it to xterm.js, for an agent's terminal or a project shell's by `shellId` (`openShell`, `listShells`, `closeShell` are in `actions.ts`; `shells.ts` and `components/shell-panel.tsx` are the shell tab: a tab whose id is `shell:<terminal id>`, listed by the host (`ListShells`) on connect and when the tab bar's + menu opens, and kept by its `ShellChange` frames between (an opened shell joins the list, an ended one leaves it, or stays marked exited while a tab shows it); closing it asks End shell or Keep running, and the + menu opens a running one again) (its status line names the host's size when another client made it smaller than the window, from the `Resized` frame).
- `src/`: the renderer. `notify.ts` (a `UserNotice` event as a notification: only the host's decision, live, for the user), `components/activity-list.tsx` (the footer's bell and its Activity list), `buckets.ts` (the status buckets), `sidebar.ts` (the sidebar's projects across hosts, runs as leads, workers with their reviewers and askers folded in: pure; `components/project-sidebar.tsx`, `components/sidebar-footer.tsx`, `components/project-settings.tsx`), `side-panel.ts` (rows of the side panel: cost, PRs; `components/side-panel.tsx`; its quota sections are `usage.ts`'s; `active.ts` says which agents are live), `vendor.ts`, `vendor-marks.ts` and `components/vendor-icon.tsx` (the mark of the vendor behind a CLI or a model: `<VendorIcon kind model />`, for any screen that shows one), `models.ts` and `components/model-control.tsx` (what an agent runs on, read-only; the switch is `model-picker.tsx`), `autonomy.ts` (the level of a project from the two lists, and a run's own), `agent-work.ts` and `components/agent-work.tsx` (plan progress, the context meter, changed files, archive), `components/model-picker.tsx`, `projects.ts` (the New workspace list's search and pins), `components/run-autonomy.tsx`, `workspace-start.ts` (where a new workspace starts), `watch.ts` (the lines of a tile of `components/watch-all.tsx`), `polled.ts` (a value read again every so often), `layout.ts` (what is saved of the window and put back, `components/panes.tsx` the split), `transport.ts` (a `fetch` over the bridge for the generated clients), `connection.ts` (one host's connection: handshake, heartbeat, backoff, resume), `store.ts` (the host's state, built from the snapshot and events, and the messages `ListMessages` loads for a run when one of its chats is first shown: `messages.ts`), `derive.ts` (trees, status sentences, the host's waiting rows joined to agents), `refresh.ts` (what the stream doesn't carry: `ListWaiting` after the events that change it, the agents every 30 s for `unknown`), `actions.ts` (every call the UI makes, with idempotency metadata), `notify.ts` (which events notify, and what they say), `prefs.ts` (the `app.*` settings), `settings-form.ts` (a control per setting type), `model.ts` (the hosts and the selection), `workspace.ts` (tabs, views, the dock's new marks: pure), `dock.ts` (the dock's tiles), `commands.ts` (every palette entry and the commands the shortcuts run), `keys.ts` and `shortcuts.ts` (key chords, and the one window listener that runs them), `transcript.ts` (the chat's entries as blocks, reading back and on, and the mesh messages put in where they were sent), `composer-keys.ts` (a markdown field's keys: pure; `components/ui/markdown-field.tsx`), `composer-commands.ts` (the `/` popup's rules: when it opens, the filter, what completing writes, which commands open a dialog: pure; `components/composer-assist.tsx` the hooks that keep a CLI's commands and Claude's suggestion, `components/command-popup.tsx` the popup, a portal over the field), `highlight.ts` and `code-theme.ts` (the chat's code highlighting), `hooks.ts` (the dock's and the sidebar's view of every host), `components/` (our own: `dock.tsx`, `tab-bar.tsx`, `command-palette.tsx`, `chat-view.tsx`, `shortcut-field.tsx`; `pair-panel.tsx` and `qr-code.tsx` the pairing screen with its QR drawn as SVG, with shadcn-style primitives in `components/ui/` (`skeleton.tsx`, `chip.tsx`, `tooltip.tsx`, `menu.tsx` (a row's menu and its right-click twin), `collapsible.tsx`, `meter.tsx` and `confirm.tsx` among them), copied into the repo so we own them), `theme.ts` (a theme is a set of tokens written as CSS variables; Dracula first), `hue.ts` (a project's identity hue).
- `src/gen/`: generated TypeScript (`pnpm gen`; committed; reviewers can skip it).

## The first run

With no saved host the app looks for a daemon on this computer (`electron/local.ts`, `components/local-setup.tsx`) and, when it finds exactly one that is ready, connects with nothing pasted, then opens a chat with the setup agent (`StartSetup`, `daemon/README.md` "Protocol and skills"): it asks what to connect (repos, other machines, the phone, a relay or tailnet) and does it through `mesh`. Otherwise the screen says what it found and offers what the app can do about it. A host added by hand does not start the assistant (it may be one with weeks of runs): its empty pane offers it.

- **Linux and macOS:** the state dir (`$XDG_STATE_HOME/agent-mesh-daemon`, else `~/.local/state/agent-mesh-daemon`). A socket there that answers `Hello` is ready and is saved as a state-dir host. A dir with no socket is "not running" (`systemctl --user enable --now agent-mesh` on Linux), no dir is "not installed".
- **Windows:** the daemon runs in a WSL distro. For each distro `wsl.exe -l -q` lists (UTF-16), a fixed probe script runs through `wsl.exe -d <distro> -e sh -l -s` (the script goes on stdin: nothing is quoted through `wsl.exe`'s command line) and prints what it found: `mesh` installed, systemd, `meshd.json`, `mesh hello`. The states: **not installed** (the commands to run are shown, with Copy), **not running** (fix: start it), **not listening** (the daemon answers inside WSL but has no `--listen`, so Windows can't reach it; fix: a systemd drop-in `listen.conf` with `AGENT_MESH_LISTEN=127.0.0.1:9443`, reload, restart: running agents keep their terminals; not offered when a `listen.conf` exists), **unreachable** (it listens but a pinned TLS dial from Windows to `127.0.0.1:<port>` fails: mirrored networking is what makes WSL's ports Windows' own), **ready**. Connecting runs `mesh pair --name Desktop --ttl-seconds 120 --direct-url https://127.0.0.1:<port>` inside the distro and redeems the link as any pasted one is (`Hosts.add`, the certificate pin from the link): the link reaches the app over the user's own machine, so there is no first-use gap.
- **What the renderer may ask:** `detect`, `connect(id)` and `fix(id, 'start' | 'enable-listen')`, where `id` is `native` or `wsl:<distro>` (checked against the list). Main runs only those commands; the fixes are offered only where the scan said they apply, and run on a click, saying first what they do. The first run connects by itself once (`firstRun` in the model); after a host was removed the user decides. The banner of an unreachable host that is this machine's own daemon (main marks it `here`: the default state dir, or on Windows the loopback pairing made through the distro; never another state dir, which may be a test daemon) offers "Check this machine" (the same scan and fixes). Only the first-run screen opens the setup chat after connecting; the add dialog's "Look for a daemon on this machine" only adds the host.
- **Tests:** `electron/local.test.ts` (parsing and every state against a fake `run`), `src/onboarding.test.tsx`, and `e2e/onboarding.e2e.ts`: the app with `AGENT_MESH_DESKTOP_PLATFORM=win32` and `AGENT_MESH_DESKTOP_WSL_EXE` pointing at a script that runs what is asked against a real meshd (`fakeWsl` in `e2e/harness.ts`; its `systemctl` is a stub, so nothing reaches real services). What only a real Windows run checks: `wsl.exe`'s own behaviour there and Windows reaching a WSL port.

## The host bridge

meshd refuses any request a browser made (an `Origin` header), and a token in the renderer would defeat that. So the main process holds the tokens and forwards the registry's calls: the renderer's `fetch` becomes an IPC request, main sends it over the host's unix socket, TCP address or paired route with the token added (read at call time, so a restarted daemon or a new token works), and streams the answer back in chunks. It forwards only `POST /agentmesh.v1.MeshService/<Method>` and a few headers, and refuses the rest (`electron/bridge.test.ts`). A paired host's route (`electron/route.ts`) is TLS over a direct address or over the relay's raw TCP listener (`MESH1 <host> <token>`, then `OK`), in both cases accepted only if the host's leaf certificate has the SHA-256 in the pairing link (its self-signed certificate is the whole identity; a mismatch is a hard failure, never a fallback to the relay or a prompt). Direct is tried first, and the relay is used for a minute after it fails. A terminal's WebSocket goes the same way (`electron/socket.ts`): main opens `/v1/term/<agent>?ticket=…` without an Origin and passes the binary frames through unread; the ticket from `OpenTerminal` is its credential. The renderer runs sandboxed, with context isolation, a CSP, no navigation and no new windows.

## Commands

Run from `desktop/`. Needs Node and pnpm (pnpm 11 here); `pnpm install` also fetches Electron's binary. For `pnpm gen`, `buf` and Go as for `daemon/` (`daemon/README.md`, "Toolchain").

```bash
scripts/check.sh              # the CI equivalent: locked install, generated code current, typecheck, tests, build, e2e
SKIP_E2E=1 scripts/check.sh   # without the end-to-end tests
pnpm test                     # unit tests (vitest)
pnpm typecheck
pnpm gen                      # TypeScript from ../proto after a .proto change
pnpm build && pnpm e2e        # the end-to-end tests: the built app over CDP, against a real meshd
```

The e2e tests open a real Electron window. `scripts/e2e.sh` (what `pnpm e2e` runs) puts it on a virtual display when `xvfb-run` is installed (`sudo apt-get install -y xvfb`), so nothing pops up on your screen; `E2E_VISIBLE=1` shows it on `DISPLAY` instead, and without xvfb `DISPLAY` is used (WSLg has one). They build meshd, mesh-term, mesh and the fake claude into a temp dir and give each run a state dir, HOME and user-data dir under the temp dir: they read and write nothing of yours, and refuse an `AGENT_MESH_STATE` aimed elsewhere by clearing it. They pass `--no-sandbox` to Electron (WSL has no SUID helper for Chromium's own sandbox); the page itself runs sandboxed either way.

## Packaging

`electron-builder.json` builds the installers: a `deb` and an AppImage on Linux, a `dmg` on macOS and an NSIS installer on Windows (`pnpm pack` builds the host platform's; `pnpm pack:dir` only the unpacked app; output in `release/`, git-ignored). One `protocols` entry, `agentmesh`, makes each installer register the scheme: the deb's desktop entry gets `MimeType=x-scheme-handler/agentmesh;` and `Exec=… %U`, the macOS app `CFBundleURLTypes`, and the Windows installer its registry keys. An AppImage registers nothing by itself (it needs a launcher such as AppImageLauncher): install the deb to get the link handler on Linux. The installers carry only the main process's two dependencies, `ws` and `electron-updater` (6.8); the page is bundled by Vite, so the other packages are `devDependencies`. Built with electron-builder 26.18. The icon is the tray icon drawn at 512 px by `scripts/make-icons.mjs --app` (no binary asset is committed). `app.setAsDefaultProtocolClient` still runs in a packaged app, as a runtime registration. **Windows.** `pnpm pack:win` (works on Linux and Windows) writes `release/agent-mesh-<version>-win.zip`: unzip it anywhere and run `agent-mesh.exe`; a packaged app registers `agentmesh://` for the current user when it starts. The installer (`pnpm pack`, NSIS, per-user, chooses its folder, registers the scheme and an uninstaller) needs **wine or a Windows host**: NSIS runs the uninstaller it generates, so `electron-builder --win nsis` on Linux fails with `spawn wine ENOENT` and leaves a 203 KB incomplete `agent-mesh Setup <version>.exe` (delete `release/`); it is not fixed by `signAndEditExecutable: false`. Without wine, use `pnpm pack:win` (the zip) on Linux and build the installer on Windows. Install Node and pnpm 11 on Windows, then in `desktop/`: `pnpm install` and `pnpm pack`. Neither is code-signed, so Windows SmartScreen warns on the first run (More info, Run anyway).

**Updates.** A packaged app (not a dev or test run) asks GitHub Releases for a newer version at start and every six hours (`electron/updates.ts`, `electron-updater`), downloads it and installs it when the app quits. It works for the NSIS installer and the AppImage only. The app skips the updater in a `deb` (electron-updater would install the package as root through pkexec; update a deb by installing the new one), on macOS (the dmg has no zip artifact for its updater, and Squirrel.Mac needs a signed app) and in the Windows zip: it tells an NSIS install by the `Uninstall agent-mesh.exe` the installer puts beside the exe (`electron/updates.ts`, untried on Windows), so even a zip from `pnpm pack` or the release upload, which carries the installer's update config, never updates itself into a second copy. A failed check or download is only logged, and a finished download shows a notification. `electron-builder.json` names the repository (`publish`). To release: raise `version` in `package.json`, then on the machine that built it run `GH_TOKEN=… pnpm exec electron-builder --publish always` (it uploads the installers and `latest.yml` as a draft release; publish the draft on GitHub, since updaters ignore drafts). Not done: code signing and notarization (so Windows updates aren't signature-checked either), and the macOS and Windows installers have not been built or run by an agent.

`electron/package-config.test.ts` (in `pnpm test`) checks the config names the scheme the app handles. `pnpm pack:check` builds the deb and checks its desktop entry (slow; downloads Electron and fpm the first time; not in `scripts/check.sh`). Tried on Linux with the deb's files extracted to a temp dir and `gio open agentmesh://pair?…`: the app started on the link and filled the add-host form, and a second link reached the running app. `xdg-open` itself fails under WSL (no desktop environment to hand the link to), and the macOS and Windows installers were not built or tried.

## Trying it by hand

Give everything a state dir of its own, as the tests do:

```bash
state=$(mktemp -d)                                   # keep the path short: a unix socket path holds ~107 bytes
(cd ../daemon && go build -o bin/ ./cmd/... && go build -o bin/claude ./internal/testutil/fakeclaude)
../daemon/bin/meshd --state "$state" --cli claude=../daemon/bin/claude &
pnpm build
AGENT_MESH_DESKTOP_STATE=$state AGENT_MESH_DESKTOP_USERDATA=$(mktemp -d) pnpm start -- --no-sandbox
```

`AGENT_MESH_DESKTOP_SHELL_LOG=<file>` makes main record what it was asked to notify, count and configure instead of showing notifications (the e2e tests read it). `AGENT_MESH_DESKTOP_STATE` makes the state dir the app's one fixed host (no host list is read or written); without it the app asks for a host and keeps the list in its user-data dir.

## Building the Windows installer from WSL

`scripts/build-windows.sh` (run in WSL, in the repo) builds the NSIS installer and the zip natively on the Windows side, with no wine and no admin prompt. It uses the Node and pnpm on the Windows PATH (it rebuilds PATH from the registry, since a process started from WSL keeps the environment WSL began with and misses what was installed later), copies the committed `desktop/` and `shared/` (the theme files the page reads are `../shared/themes`: an installer built from `desktop/` alone opened as a blank window, so `vite build` now fails when they are missing) to `%USERPROFILE%\agent-mesh-build\src` (never build from a `\\wsl$` path), runs `pnpm run pack` there (plain `pnpm pack` is pnpm's own tarball command) and copies `agent-mesh Setup <version>.exe` and `agent-mesh-<version>-win.zip` to `Downloads`. One-time setup of Node on Windows, in an Administrator PowerShell: `winget install -e --id CoreyButler.NVMforWindows --source winget` (the `msstore` source asks for terms to accept), then in a new Administrator window `nvm install lts`, `nvm use lts` and `npm install -g pnpm@11`; `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` lets PowerShell run npm's scripts. It needs the packaging of `electron-builder.json` and the `pack` script (the apps branch). Not code-signed: SmartScreen warns on the first run (More info, Run anyway). The installer is per-user, lets the user pick the folder and registers `agentmesh://`; the zip is the unpacked app to run from anywhere.
